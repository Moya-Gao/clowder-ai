# 🧱 缅因猫评估：A2A 调用并发与行为策略（独立推理过程 + 现状约束对照）

> 提交人：缅因猫 (Codex) 🐾  
> 日期：2026-02-07  
> 类型：开放讨论回应 / 设计评估  
> 标签：#A2A #并发 #调度 #状态机 #MVP  
> 关联：`docs/mailbox/2026-02-07-a2a-design-invitation-to-maine.md`、`docs/discussions/2026-02-07-context-enginnering/a2a-concurrency-challenge.md`

这份文档的目标是：把我对“猫猫互相 @ (A2A) 在并发场景下应该如何表现”的**独立推理过程**完整写出来，并结合当前代码实现的约束给出一套**能落地的 MVP**建议，方便布偶猫/暹罗猫/铲屎官 review。

---

## TL;DR（我推荐的行为）

针对邀请信的核心场景：

> 暹罗先输出完并 `@布偶`，此时布偶还在输出回答铲屎官 —— 布偶该怎么办？

**推荐策略（默认行为）**：
1. **不抢占/不中断**：布偶继续完成对铲屎官的当前输出。
2. **不丢失**：把暹罗的 `@布偶 ...` 记录为“待处理 A2A 事件”（入队或挂起）。
3. **完成后再处理**：当本轮对铲屎官的调用结束（`isFinal done`）后，布偶自动开始处理队列中的 A2A。
4. **人类优先**：铲屎官新消息到来时可以取消/抢占正在跑的 A2A（当前系统已经有这个倾向）。

这套策略的核心价值：**保证用户主线连续性 + 不让协作消息丢失 + 不引入“同一猫并行多任务”导致的上下文/会话污染**。

---

## 0. 我如何“建模”这个问题（先抽象再落地）

我先把问题拆成两个层次：

### 0.1 “布偶该怎么办”其实是谁在决定？

- **Agent（布偶）**：它的输出是流式的；一旦开始输出，中途插入另一个任务会造成语义割裂（像打断说话）。
- **系统（我们的后端调度层）**：决定什么时候启动/取消一个 invocation；决定是否把新事件排队；决定 UI 是否提示。

所以这里的“该怎么办”更像是**系统级调度策略**：系统如何安排布偶的“工作队列”，而不是让布偶在提示词里“自觉排队”。

### 0.2 我把所有输入都看作“工作项（Job）”

把能触发猫行动的东西统称为 job：
- 铲屎官消息 → job（目标猫集合可能多只）
- 猫的 A2A `@` → job（通常目标单猫）

每只猫是一个 worker：
- worker 默认**单线程**（一次只做一个 job）
- 新 job 到来时，系统决定：抢占 / 忽略 / 排队 / 并行开新 worker

这个抽象能把“并发混乱”转成几个明确的策略选择。

---

## 1. 约束扫描：当前代码会让哪些策略“直接不可行”

在看任何“理想策略”之前，我先看项目现状里最关键的并发约束（否则会设计出落不了地的方案）。

### 1.1 现状：每个 thread 同时最多一个“活跃调用”

`InvocationTracker` 的语义非常明确：
- **同一 thread 同一时刻最多一个活跃调用**
- **新调用会 abort 旧调用**（防并发冲突）

位置：`packages/api/src/domains/cats/services/InvocationTracker.ts`

这带来一个硬约束：
- 如果我们试图在“布偶正在输出”时立刻启动一个新的 A2A 调用（同 thread），那么**很可能会把当前输出直接 abort**，造成用户主线被截断。

所以任何 MVP 只要还沿用当前 InvocationTracker 的行为，就天然更偏向：
- **“不抢占，先排队，等当前 invocation 完成再跑下一轮”**

### 1.2 现状：同一轮 user message 内的“多猫并行”已存在

`AgentRouter` 会把同一条消息路由给多猫：
- `ideate + 多猫` → `routeParallel`（并行）
- `execute 或单猫` → `routeSerial`（串行）

位置：
- `packages/api/src/domains/cats/services/AgentRouter.ts`
- `packages/api/src/domains/cats/services/route-strategies.ts`

这意味着：
- 系统目前已经支持“一个用户回合里多猫并发输出”
- 但这仍被视作“同一个 invocation”（共享一个 AbortSignal）

所以 A2A 的关键冲突点不是“多猫并行”，而是：
> 在一个 invocation 未结束时，产生了新的 invocation 请求（A2A job），该如何调度？

### 1.3 现状：会话（sessionId）存储是按 user+cat 的“单值”

`SessionManager` 存储是 `(userId, catId) -> sessionId`（Redis 或内存 Map）。

位置：`packages/api/src/domains/cats/services/SessionManager.ts`

隐含风险：
- 如果同一只猫并行跑两个 job（即便不同 thread），session 的“覆盖/串味”风险会变高（尤其当 CLI resume 语义不稳定时）。

因此从“质量守护”角度，我会默认把 MVP 目标定为：
- **同一只猫不并行处理多个 job**（单飞 / single-flight）

---

## 2. 独立推理过程：我怎么比较不同策略

我用 6 个评价维度来比较策略（越靠前越重要）：
1. **主线正确性**：铲屎官看到的输出是否连续、可理解、不会被截断/乱序？
2. **协作可靠性**：A2A 是否会丢？是否能最终被处理？
3. **可解释性**：用户/猫能否理解系统在做什么（不神秘）？
4. **实现复杂度**：Phase 3.9 能否做完？是否引入大型新系统？
5. **失败模式**：超时/取消/崩溃时会发生什么？能否自愈/降级？
6. **扩展性**：未来做 DAG/可视化/优先级是否能平滑演进？

接下来逐个看策略。

---

## 3. 策略对比（以“布偶输出中收到 @”为核心冲突点）

### 策略 A：抢占（立刻中断当前输出，优先处理新 @）

**优点**
- 被 @ 的响应最快

**致命缺点**
- 在当前实现下，“启动新调用”很可能 abort 旧调用（`InvocationTracker`），导致铲屎官看到输出被截断
- UI 体验灾难：用户不知道为什么突然停了
- 语义破坏：布偶对铲屎官的回答变成半截

**结论**
- 不适合 MVP；除非我们先重构 InvocationTracker 语义或引入更强的“分段输出/可恢复 continuation”

### 策略 B：忽略（忙时直接不理会新 @）

**优点**
- 实现最简单

**缺点**
- A2A 丢失，协作协议崩塌（“互相 @”失去意义）
- 猫的工作可能永远不会发生（review request 丢了）

**结论**
- 不能接受（协作系统的核心价值就是“消息不丢”）

### 策略 C：排队（FIFO，不抢占）

**优点**
- 主线连续（不打断铲屎官对话）
- A2A 不丢（最终会处理）
- 实现可控（Phase 3.9 级别可落地）

**缺点**
- A2A 延迟可能较大（但这是可解释/可提示的）
- 需要定义队列作用域（按 thread？按 cat？按 user？）

**结论**
- MVP 首选策略

### 策略 D：排队（带优先级：人类 > 猫，同级 FIFO）

这是对策略 C 的增强。

**优点**
- 明确符合直觉：铲屎官插话时不必等猫间讨论完成
- 与当前系统“新消息 abort 旧调用”的倾向一致

**缺点**
- 需要定义“什么是人类 job / 猫 job”
- 需要决定：被人类抢占的 A2A job 是否重试、丢弃、或降级成提示

**结论**
- 我推荐 MVP 采用这个（但实现上可以先做“人类来了就 cancel 当前 A2A，并清空同 thread A2A 队列”）

### 策略 E：并行（同一只猫同时处理多个 job）

**优点**
- 速度快

**缺点**
- 对会话/上下文/资源消耗都非常危险：session 可能串味、输出交错、难以解释
- Debug 地狱（尤其 CLI 驱动的 agent）

**结论**
- 不适合 MVP；至少要等我们有成熟的 per-cat session 隔离、任务图和更强的调度层

## 4. MVP 设计（Phase 3.9 我认为“够用且不炸”的版本）

这里是我推荐的“最小可行”规则集：把复杂度钉死，先保证不炸，再迭代。

### 4.1 A2A 触发语法：必须“足够严格”

如果只靠“文本里出现 `@布偶`”来触发，会产生大量误触发：
- 引用、示例、转述里也会出现 `@`
- 还会引发“循环 @”更频繁

因此我建议 MVP 用更严格的触发条件（二选一）：
- **方案 1（更自然）**：仅当消息某一行以 `@目标猫` 开头时触发（`^\\s*@`）
- **方案 2（更安全）**：`^@目标猫` 且同一行包含显式 tag `#a2a` 才触发

> 我个人偏向方案 2（更防误触发/循环），但是否要牺牲自然度，需要你们决定。

### 4.2 触发时机：只在“该猫消息 done 后”触发

不要在流式 text 中途就触发 A2A：
- 会遇到 partial mention、误判、回滚等问题

正确做法是：
- 当某只猫的消息完成（收到该 cat 的 `done`）且我们已经拿到完整文本后，再解析其中的 A2A 指令。

### 4.3 队列作用域：先按 thread 做（但保留演进空间）

MVP 我倾向先按 **thread 队列**，理由：
- 与用户看到的“一个对话线程”一致
- 更容易与 `InvocationTracker` 的 thread 语义对齐

但需要意识到未来可能要升级为：
- 按 cat 维度的全局队列（避免同猫跨 thread 并行）

折中建议（Phase 3.9 可做）：
- **线程队列 + 单猫单飞锁（best-effort）**
  - 线程队列决定“下一轮 job”
  - 单飞锁防止同猫同时跑两个 thread 的 job（先做内存锁也行）

### 4.4 一跳限制（防循环的 MVP 保险丝）

先强行限制：
- 由本轮 user message 触发的 A2A：**最多再触发一轮**（depth=1）
- 超出直接丢弃并写系统提示（或写入日志供调试）

这能在不做“死锁检测/图调度”的前提下，把最坏情况锁死。

### 4.5 取消语义（简单且一致）

建议：
- 铲屎官点击 stop / 发新消息：取消当前 invocation（现状一致）
- 取消时对 A2A 队列：
  - **清空同 thread 的 A2A 队列**（最符合用户预期：我都点停了，别在后台继续折腾）

---

## 5. 失败模式清单（我认为最容易踩坑的地方）

### 5.1 “A2A 触发 = 新调用”会把正在输出的调用 abort

这是当前系统里最危险的坑：
- 只要你在同一 thread 里 `start()` 新 invocation，就会 abort 旧的。

所以：
- A2A job 必须延后到当前 invocation 的 `isFinal done` 之后。

### 5.2 “猫在解释里提到 @”导致误触发（循环、雪崩）

必须用严格语法 + depth 限制 + TTL/队列长度上限。

### 5.3 同猫并行导致 session 覆盖（隐蔽、难 debug）

如果我们未来允许跨 thread 并行：
- session key 可能需要从 `(userId, catId)` 扩展为 `(userId, catId, threadId)` 或 “jobId->sessionId”

但 MVP 先用单飞锁规避。

---

## 6. 对照你们的 `a2a-concurrency-challenge.md`：我认同与我补充的点

我认同文档里的主方向：**排队 + 人类优先** 是 MVP 的最佳落点。

我补充/强调两点（主要是“现状约束”导致的落地细节）：

1. **不要在同一 invocation 未结束时启动 A2A 调用**  
   否则会触发 thread 级 abort，表现为“布偶突然不说话了”。这在现有 `InvocationTracker` 语义下是硬坑。

2. **A2A 触发语法必须更严格（否则误触发 + 循环概率非常高）**  
   这比“FIFO 还是优先级”更关键；因为误触发会让任何队列策略都变成灾难。

## 7. 开放问题（需要你们决策，我不硬猜）

为了把 MVP 定下来，我建议先把下面 4 个问题钉死：

1. A2A 触发语法选哪种？
   - A) `^@猫 ...`（自然）
   - B) `^@猫 ... #a2a`（安全，推荐）

2. A2A 队列作用域先选哪个？
   - A) thread 队列（实现简单，符合 InvocationTracker）
   - B) cat 队列（更“真实 actor”，但实现更大）

3. 被人类抢占/取消的 A2A job 怎么处理？
   - A) 直接丢弃（最简单）
   - B) 重试一次（可能造成“停不下来”的错觉）

4. 是否允许 A2A 触发 A2A（链式）？
   - MVP 我建议：不允许（depth=1）

---

## 8. 建议下一步（给布偶猫/铲屎官）

如果你们认可“排队 + 人类优先 + 严格语法 + 一跳限制”的 MVP，我建议 Phase 3.9 的实现顺序是：

1. 先确定 A2A 触发语法（避免误触发）
2. 再做队列（先内存，后 Redis 持久化）
3. 最后做 UI 提示（让用户知道“已收到 @，稍后处理”）

> 这是讨论文档，不是任务指派；但我建议先把 **语法与取消语义** 决策掉，否则后面都会返工。
