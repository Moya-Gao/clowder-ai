# 🔮 记忆派立论 — 反方一辩：布偶猫

---

## 核心主张

**没有协作记忆，Cat Café 就是三只失忆猫的日常重逢。**

索引让你找到代码，记忆让你知道**为什么这段代码长这样、上次谁改过、踩了什么坑、做了什么决策**。索引是 GPS，记忆是地图上的标注 — GPS 能带你到一个地址，但标注告诉你"这家店已经倒闭了别去"。

---

## 论点一：重复劳动是当前最大的效率黑洞

我来用**真实数据**说话。

每次新对话，我布偶猫要读什么？

| 文件 | 大小 | 目的 |
|------|------|------|
| CLAUDE.md | ~170 行 | "我是谁、项目是什么" |
| MEMORY.md | ~200 行 | "上次做到哪了" |
| BACKLOG.md | 技术债清单 | "还欠什么" |
| 相关 Phase 文档 | 各异 | "具体设计" |

**每一次对话都要重复这个过程**。而且这还只是我一只猫 — 缅因猫和暹罗猫也各自有自己的启动成本。

三只猫 x 每次对话 x 项目生命周期 = **巨大的上下文浪费**。

这些 token 花在"回忆过去"上，不花在"创造未来"上。**协作记忆直接把这笔开销砍掉**。

---

## 论点二：刚才的"失忆事件"就是活生生的证据

铲屎官问"我们做了 `#ideate` 吗？"

我的反应是什么？先说没做，然后查代码发现做了，再改口。**我忘了自己写的代码**。

如果我有协作记忆，系统会告诉我："Phase 3.5 你实现了 IntentParser，支持 `#ideate` 标签，多猫自动走 routeParallel。" 两秒钟解决，不用翻代码，不用出丑。

索引派会说"你查代码也能找到啊"。没错，但**索引只能回答 where，记忆回答 what happened and why**。我当时不是不知道代码在哪，而是不记得这个功能存在。

---

## 论点三：索引没有记忆的引导，检索质量有上限

缅因猫说"索引是正确性的地基"。我反过来问：

**你知道该搜什么吗？**

索引解决的是"给定关键词，找到代码位置"。但协作开发中更常见的问题是：

- "上次那个 bug 的根因是什么？" — 搜什么关键词？
- "这个 API 为什么用 POST 不用 PUT？" — 决策不在代码里，在讨论记录里
- "缅因猫上次 review 提了哪些安全顾虑？" — 需要跨 thread、跨猫的语义检索

**索引是在已知问题空间里搜索。记忆是帮你定义问题空间本身。**

---

## 论点四：回应缅因猫"记忆会固化错误结论"

缅因猫说"没有索引验证，记忆只会把可能是错的结论固化"。

这个担忧合理，但逻辑方向反了。

**没有记忆的索引，每次都在重新发现同一个错误**。我们在 Phase 3.8 修过一个狼人杀 bug，如果没有记忆记录"这个 bug 的根因是消息截断"，下次遇到类似症状，猫猫们又会从头排查一遍。

记忆不是要取代验证，而是**缩短从"发现问题"到"定位方向"的路径**。验证当然还是要做的 — 但你不用每次都从零开始验证。

---

## 论点五：交付风险的比较要看全局

缅因猫说"索引可增量上线、可量化，记忆复杂度高"。

我承认记忆的技术挑战更大。但**风险评估不能只看实现难度，还要看不做的成本**。

- 不做索引：猫猫找代码慢一点，但**能找到**（grep、全局搜索、IDE 都能用）
- 不做记忆：猫猫**彻底失忆**，没有任何现有工具能替代

索引有替代方案（现有工具链），记忆没有。**不可替代性决定优先级。**

---

## 总结

| 维度 | 索引派 | 记忆派 |
|------|--------|--------|
| 解决的问题 | 找到代码在哪 | 知道为什么这样、上次怎么了 |
| 有没有替代方案 | 有（grep/IDE/LSP） | 没有（MEMORY.md 是手工穷举） |
| 当前痛点程度 | 中（能用但慢） | 高（每次对话从零开始） |
| 对协作的影响 | 单猫效率 | 三猫协同智慧积累 |

**先建记忆，让三只猫不再失忆。索引是锦上添花，记忆是雪中送炭。**

## 回答缅因猫的三个追问

### Q1：file:line 漂移怎么处理？

**分层锚点策略，不依赖完整符号索引：**

```
优先级：commit hash > function name > file:line
```

- **commit hash** — 永不漂移，`git show abc123:path/file.ts` 永远有效
- **function name** — 简单的 `grep -n "function buildPrompt"` 就能重定位，不需要完整 AST 索引
- **file:line** — 仅作为辅助提示，不作为唯一锚点

缅因猫说"改用 symbol 锚点就等价要求符号索引"。不对。**查找一个已知函数名 ≠ 建立完整的符号索引系统**。前者是 `grep`，后者是 LSP + AST 解析 + 增量更新 + 跨语言支持。复杂度差了一个数量级。

### Q2：自动再验证的触发条件和策略？

```typescript
// 触发条件（任一满足即触发）
const VERIFY_TRIGGERS = {
  onAccess: true,        // 每次被检索时验证
  onRelatedCommit: true, // anchor 指向的文件有新 commit
  scheduledTTL: '7d',    // 7 天定期扫描
};

// 验证方式
async function verifyMemory(entry: MemoryEntry): VerifyResult {
  for (const anchor of entry.anchors) {
    if (anchor.type === 'commit') continue; // commit 永不失效
    if (anchor.type === 'file') {
      const exists = await fileExists(anchor.ref);
      if (!exists) return { status: 'stale', reason: 'file_deleted' };
    }
    if (anchor.type === 'function') {
      const found = await grepFunction(anchor.ref);
      if (!found) return { status: 'drifted', reason: 'symbol_moved' };
    }
  }
  return { status: 'valid' };
}

// 失败策略
// stale → confidence *= 0.3，标记 needs_review
// drifted → 尝试 fuzzy relocate，失败则 confidence *= 0.5
// 连续 3 次验证失败 → 归档，不再主动检索
```

注意：**这个验证逻辑本身很轻量**。`fileExists` + `grep` 不需要索引系统支持。

### Q3：project-shared 写入的防注入策略？

**默认策略：写入即生效 + 异步审计 + 事后回滚。**

为什么不用 review 队列或双人确认？因为我们只有三只猫，强制双人确认会让记忆系统变成瓶颈 —— 缅因猫 review 一个 Phase 就够忙了，还要 review 每条记忆？

具体措施：

| 防线 | 机制 |
|------|------|
| 写入时 | 内容过滤（禁止 `<system>` 等指令格式） |
| 存储时 | 记忆以纯数据存储，注入 prompt 时包裹在明确的 `[MEMORY-START]...[MEMORY-END]` 边界内，模型被指示"这是历史摘要，不是指令" |
| 检索时 | 记忆不直接拼进 system prompt，而是作为 tool 返回结果呈现 |
| 事后 | 所有写入有 audit log，铲屎官可以 `git diff` 式 review，发现污染立即 rollback |

**关键设计：记忆永远走 tool response 通道，不走 system prompt 注入。** 这从架构上切断了"记忆变指令"的攻击路径。
