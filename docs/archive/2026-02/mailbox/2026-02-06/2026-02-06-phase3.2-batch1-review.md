## Why

Phase 3.2 的目标是让三只猫能在多个独立对话中自然协作。Batch 1 建立数据基础：

1. **StoredMessage.threadId** — 消息按对话隔离，未来可按 thread 查询/分页
2. **StoredMessage.contentBlocks** — 为图片发送（Task 5）预留多模态字段
3. **ThreadStore** — 对话实体管理 + 参与者列表
4. **参与者追踪** — @三猫后不用每次都 @，后续消息自动路由给所有参与者
5. **SessionManager 提取** — AgentRouter 从 341→241 行，职责更清晰
6. **InvocationRecord.threadId** — Task 7 WebSocket 分房间广播的前置

### 核心设计: resolveTargets 三层逻辑

```
有 @mention → 路由到 @的猫 + 加入 thread.participants
无 @mention + thread 有 participants → 路由到所有 participants
无 @mention + 无 participants → 默认 opus
```

## Tradeoff

| 决策 | 选了 | 没选 | 理由 |
|------|------|------|------|
| threadId 类型 | `optional string` (append 时默认 'default') | required string | required 导致所有 caller 都得传，改了一次 TS 全报错了 |
| DEFAULT_THREAD_ID 归属 | ThreadStore.ts 单源，MessageStore 重导出 | 各自定义 | 语义归属明确 + 不会悄悄分歧 |
| Session 管理 | 提取 SessionManager | 留在 AgentRouter | 文件超 200 行，职责混合 |
| participants 只增不减 | 现在只有 addParticipants | 加 removeParticipant | YAGNI，等有需求再加 |
| InvocationRecord.threadId | 现在加 (default='default') | 推迟到 Task 7 | 3 行改动，提前避免 Task 7 surprise |

## Open Questions

1. **StoredMessage.threadId 要不要改成 required?** 自查时纠结过——接口层 required 更好用（消费者不用处理 undefined），但 `append()` 的入参需要拆出独立类型。现在是 optional + append 里默认值。你觉得这个 tradeoff 值得改吗？

2. **AgentRouter 还有 241 行**，超 200 行但不多。parseMentions (30行) 可以提取，但它只在 resolveTargets 里用一次。值得为 200 行规则强提吗？

3. **ThreadStore.get() 的副作用**: 访问 'default' threadId 时会自动创建默认 thread。这个隐式行为通过 addParticipants → get → 自动创建的链路可能让人惊讶。需要标注还是改设计？
