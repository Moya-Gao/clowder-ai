## Why — 为什么这样做

### Thread CRUD
- 前端需要 API 来创建/切换/删除对话
- `GET /api/messages?threadId=xxx` 支持按对话过滤，为前端侧栏提供数据
- ThreadStore 通过 Fastify plugin opts 注入（延续 Batch 1 的依赖注入模式，避免循环依赖）

### 图片管线
- 三只猫都是多模态 Agent，用户需要发图
- `@fastify/multipart@8` 而非 v9：Fastify 4 兼容性（v9 需要 Fastify 5）
- 双模式 POST：multipart 有图时用，JSON 无图时用（向后兼容）
- CLI 图片传递策略按各 CLI 能力差异化：
  - Claude: `--images` flag（需 smoke test 确认）
  - Gemini: `-i` flag（gemini CLI v0.27.2+）
  - Codex: 无图片 flag，降级为 prompt 文本嵌入 `[Image attached: /abs/path]`

## Tradeoff — 放弃了什么

| 选项 | 选择 | 放弃 | 理由 |
|------|------|------|------|
| 图片存储 | 文件系统 + URL 引用 | Redis base64 / S3 | Phase 3 轻量，避免外部依赖 |
| multipart 解析 | `@fastify/multipart` | 自己解析 | 标准方案，有类型支持 |
| Codex 图片 | prompt 文本 fallback | 跳过 | Codex CLI 无图片 flag，但至少让它知道有图 |
| CLI flag 语法 | 写死 `--images` / `-i` | 运行时探测 | 简单优先，不确定的加了注释说需 smoke test |
| PATCH /threads/:id | 直接 mutate thread 对象 | 返回新对象 | 内存 store 用引用即可，Redis 迁移时再改 |
