## Why: 为什么这样做

1. **图片显示**: 最简方案 — 用 blob URL 让图片立即可见，不需要等后端返回。页面刷新后历史加载走正常 contentBlocks 路径，URL 变成 `/uploads/...` 服务端地址。两种 URL 在 `ChatMessage.tsx` 里都能正确渲染（blob URL 不以 `/uploads/` 开头，直接用）。

2. **自动命名**: 后端做而不是前端做，因为：(a) 更接近数据源；(b) 可以通过 WebSocket 广播给所有客户端；(c) 前端不需要判断"这是不是第一条消息"。截断30字是参考常见 chat app（Claude、ChatGPT 等）的做法。

3. **取消机制**: 选择 WebSocket 事件而不是 REST endpoint，因为：(a) 已有 socket 连接，不需要额外 HTTP 请求；(b) 按 threadId 查找而不是 invocationId，客户端不需要追踪调用 ID；(c) `cli-spawn.ts` 已有完整的 AbortSignal → SIGTERM → SIGKILL 链路，只需要把 signal 穿透过去。

---

## Tradeoff: 放弃了什么

1. **图片**: 没做 "上传后用真实 URL 替换 blob URL" 的逻辑。blob URL 在当前 session 有效，刷新后走历史加载拿到真实 URL。这意味着如果用户发了图然后在不刷新的情况下切换对话再切回来，图片可能丢失（blob URL 被回收）。但目前切对话会 clearMessages + 重新 fetchHistory，所以实际上不会出问题。

2. **自动命名**: 没做"AI 生成标题"（像 ChatGPT 那样用模型概括），只是简单截断。这是刻意选择——避免额外 API 调用和延迟。未来如果需要可以在后台异步更新。

3. **取消机制**: 没做取消后的"已取消"提示消息。SocketManager 发了一个 `done` event 但没有特殊标记它是取消导致的。前端只是停止 loading。如果需要显示"对话被用户取消"可以后续加。

## Open Questions

1. **blob URL 生命周期**: `URL.createObjectURL()` 创建的 blob URL 是否需要手动 `revokeObjectURL()`？当前没做，可能有微小内存泄漏（每张图几 MB）。如果用户频繁发图可能需要在 message unmount 时清理。

2. **并发取消的竞态**: 如果用户快速发两条消息，第二条的 `InvocationTracker.start()` 会 abort 第一条。这是 by design（每个 thread 同时只允许一个活跃调用），但第一条的 AgentRouter 生成器可能还在 iterate 中被中断，需要确认异步生成器的 AbortError 被正确吞掉而不是 crash。

3. **GeminiAgentService antigravity adapter**: cancel signal 传给了 `spawnCli()` 用的 gemini-cli adapter，但 antigravity adapter 用的是 `child.unref()` 的 detached 进程。cancel 对 antigravity 无效（进程已经脱离）。这是已知限制。
