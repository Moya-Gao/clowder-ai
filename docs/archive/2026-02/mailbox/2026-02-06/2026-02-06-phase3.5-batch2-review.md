## Why: 解决什么问题

1. **CatConfig 外置**: 圆桌决策要求 Breed+Variant 两层 schema，Phase 4 多版本猫需要这个基础。当前硬编码的 `CAT_CONFIGS` 无法支持运行时配置。
2. **Intent 信号**: 圆桌决策确认二元 `ideate|execute`，需要在路由层识别意图。多猫讨论时需要并行独立思考，而不是串行被前猫锚定。
3. **并行调用**: ideate 模式的运行时支撑。没有 stream-merge 就无法实现"多猫同时回答，谁先说谁先显示"。

---

## Tradeoff: 放弃了什么

| 决策 | 选择 | 放弃 | 原因 |
|------|------|------|------|
| CatConfig zod 转型 | `as unknown as CatCafeConfig` | 精确类型映射 | zod 输出 mutable + plain string，CatCafeConfig 是 readonly + branded CatId |
| Intent 解析位置 | AgentRouter 内部 | 独立中间件 | Intent 与路由强耦合，分离会增加传参复杂度 |
| routeParallel 位置 | AgentRouter 类内 | 独立 `route-strategies.ts` | 高内聚 (依赖 this.messageStore 等)，但导致文件 344 行 (BACKLOG #15) |
| isFinal 处理 | routeParallel 自己追踪 completedCount | invokeSingleCat 内部 | 并行模式不知道谁最后完成，必须外部追踪 |
| 旧测试修复 | 加 `#execute` tag | 改为按测试意图分离 | 最小改动，保持测试覆盖率 |

## Open Questions

1. **`as unknown as CatCafeConfig` 双重转型** — 是否应该在 zod schema 里直接用 `.transform()` 处理 branded type？当前做法可行但略显粗暴。

2. **AgentRouter 344 行** — 已登记 BACKLOG #15。当前 routeSerial + routeParallel 与 Router 类内聚较高 (依赖 `this.messageStore`, `this.getService()` 等)。提取到独立文件需要传递大量依赖。延后还是现在拆？

3. **`resolveTargetsAndIntent` 双调用** — messages.ts 在 route 前调一次 (广播 intent_mode)，AgentRouter.route 内部再调一次 (实际路由)。两次 resolveTargets 都会读 threadStore，但 addParticipants 只在 route 内发生。有轻微性能浪费 (两次 getParticipants)。是否值得缓存？

4. **三猫测试的顺序脆弱性** — `executes three cats in order for triple mention` 在并行模式下通过了，但只是因为同步 mock yield 的 Promise.race 恰好保持了数组顺序。实际异步场景下顺序不确定。这个测试现在没有 `#execute`，要加吗？

5. **cat-config.json 目前未被运行时使用** — 加载器写好了，但 API 启动时还没读取 JSON 替换 CAT_CONFIGS。这是 Phase 3.5 后续接入还是 Phase 4 的事？
