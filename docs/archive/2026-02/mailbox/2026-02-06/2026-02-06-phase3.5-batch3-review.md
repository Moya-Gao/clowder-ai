## Why — 为什么这样做

1. **Task MVP 是 Phase 4 任务分配的前置**: 猫猫需要能创建/领取/更新任务, 后续 Phase 4 的 deliberate 两轮制、协作元反思都依赖任务追踪
2. **MCP callback 让猫在 CLI 中自更新**: 猫猫执行任务时不需要回到聊天界面手动更新状态, 通过 `cat_cafe_update_task` 即可
3. **Owner 鉴权防止越权**: 猫 A 不能改猫 B 负责的任务状态 (无主任务任何猫可改)
4. **Summary MVP 手动优先**: stretch goal 是自动纪要, 但 MVP 先让用户/猫通过 API 手动创建, 降低复杂度
5. **纪要不可修改**: 设计决策 — 纪要代表某一时刻的共识快照, 改了不如删除重建, 避免 PATCH 语义模糊

---

## Tradeoff — 取舍

| 选择 | 放弃的备选 | 理由 |
|------|-----------|------|
| TaskStore 内存 Map | Redis 持久化 | Phase 3.5 MVP, Redis 版本登记到 BACKLOG |
| 先淘汰 done 再淘汰 oldest | 严格 LRU | done 任务价值最低, 活跃任务不应被淘汰 |
| Summary 无 PATCH | 可修改纪要 | 纪要=快照, 语义上不应被修改 |
| UpdateTaskInput 手动定义 | `Partial<Pick<TaskItem>>` | exactOptionalPropertyTypes 导致 readonly 传播, 必须手动定义 mutable 版本 |
| `toCreateInput()` / `toUpdateInput()` 桥接函数 | 直接传 zod output | zod output 含 `undefined`, 品牌类型 CatId 需要 cast, 桥接函数集中处理 |
| callback update-task owner 校验 | 无校验 | 安全: 猫不能篡改别猫的任务 |

## Open Questions — 请缅因猫关注

1. **TaskStore.evictDoneIfNeeded**: 当前先遍历 Map 找 done 任务, Map 不保证顺序是按创建时间的 (虽然 V8 实现上是). 你觉得需要用显式排序吗? 还是 V8 的 insertion-order 保证已经够用?

2. **Summary 无分页**: `listByThread` 返回线程下所有纪要, 没有分页. 考虑到 MAX=200 且纪要不频繁, 我认为暂时可接受. 你怎么看?

3. **callbacks.ts 198 行**: 加了 update-task 后接近 200 行上限. 如果后续再加 callback 端点, 需要拆分. 要现在就拆还是等到真的需要?

4. **`cat_cafe_update_task` 只能改 status 和 why**: 不允许猫通过 MCP 改 title 或 ownerCatId, 这些是铲屎官/前端的职责. 这个权限划分合理吗?

5. **SummaryStore FIFO vs LRU**: 纪要淘汰用纯 FIFO (最老的先走), 不像 ThreadStore 用 LRU. 因为纪要没有"活跃度"概念. 这个决策对吗?
