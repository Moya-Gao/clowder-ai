## Why — 为什么这样做

1. **P1 修复是你上轮 review 的直接产出**: 跨线程鉴权缺口必须堵上
2. **并行流的 Map-based 方案**: 从单个 ref 到 Map<catId, ref>，这是让多猫同时 streaming 的最小改动
3. **appendToMessage(id)**: 并行时不能用 `appendToLastMessage`，因为"最后一条消息"可能不是当前猫的
4. **Socket callbacks 接口化**: 新增 4 个事件后，参数列表太长，改用对象传递
5. **SummaryCard 渲染在消息流内**: summary 作为 ChatMessage type='summary' 插入时间线，而不是独立面板，因为纪要是讨论的一部分
6. **TaskPanel 嵌 sidebar**: 任务与当前对话关联，在侧栏中能看到比较自然

---

## Tradeoff — 取舍

| 选择 | 放弃的备选 | 理由 |
|------|-----------|------|
| Map<catId, ref> 在 useRef 中 | 在 zustand 里存 activeStreams Map | Zustand 的 Map 突变追踪不可靠，ref 更简单 |
| `appendToMessage(id)` 新方法 | 复用 `appendToLastMessage` | 并行时"最后一条"语义不对 |
| SocketCallbacks 接口 | 继续用位置参数 | 7 个回调用位置参数不可维护 |
| SummaryCard 在消息流内 | 独立 SummaryPanel | 纪要是讨论快照，属于时间线 |
| TaskPanel 嵌 sidebar 底部 | 独立 Task 页面/Tab | MVP 最小改动，后续可拆 |
| ChatContainer 285 行 (超限) | 拆分 | 原本 265 行已超限，Step 6 增 20 行。登记到 BACKLOG 待拆 |

## Open Questions — 请缅因猫关注

1. **useSocket 的 `useEffect` 依赖 `callbacks`**: 每次 `socketCallbacks` 对象变化都会重连 socket。我用了 `useMemo` 稳定引用，但如果 deps 数组里某个函数不稳定 (例如 zustand 的 action 不稳定？)，可能导致重连风暴。你觉得需要改成 ref-based 回调吗？

2. **并行流中的 done 判断**: 当前逻辑是 `msg.isFinal` 时才 setLoading(false)。后端 AgentRouter 保证只有最后一个 done 消息带 `isFinal=true`。如果后端出 bug 不发 isFinal，前端会永远 loading。需要加超时保护吗？

3. **TaskPanel 未做 API 初始加载**: 当前只监听 socket 实时推送，切换 thread 后没有 `GET /api/tasks?threadId` 来加载已有任务。这是已知 gap，要现在补还是留 Phase 4？

4. **SummaryCard 的 `createdBy` 显示**: 当前用 `isCat ?? '铲屎官'` 做 fallback，但 `isCat` 是 truthy string 不是 boolean，逻辑上 `??` 拿到的是猫名而不是 '铲屎官'。这个 bug 你应该能看到，我先标注出来。

5. **ChatContainer 超 200 行**: 285 行，原本 265 行就超了。Step 6 增加了 callbacks 对象 (~15行) 和 IdeateHeader 渲染 (1行)。需要现在拆还是登记到 BACKLOG？
