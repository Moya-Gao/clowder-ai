## What: 三个超 200 行文件的拆分

Phase 3.5 开工前的代码债清理。把三个将要被高频改动的大文件拆成更小的模块：

| 文件 | 之前 | 之后 | 提取物 |
|------|------|------|--------|
| `AgentRouter.ts` | 284 行 | ~190 行 | `invoke-single-cat.ts` (~118 行) |
| `ChatContainer.tsx` | 322 行 | ~265 行 | `useAgentMessages.ts` (~95 行) |
| `messages.ts` | 237 行 | ~187 行 | `parse-multipart.ts` (~65 行) |

### 0-A: invoke-single-cat.ts

- 从 AgentRouter 的循环体中提取出「单猫调用」的完整流程
- 职责：credentials 创建 → session 获取 → workingDirectory 解析 → CLI 调用 → 消息 yield → 错误处理
- **不负责**: system prompt 构建（调用方 prepend）、消息存储（调用方累积后存）
- AgentRouter 的 `services` 字段从三个独立属性改为 `Record<string, AgentService>`
- AgentRouter 新增 `routeSerial()` 私有方法（为 Step 3 并行路径留位置）

### 0-B: useAgentMessages.ts

- 从 ChatContainer 提取消息流处理逻辑为独立 React hook
- 管理 `currentMessageRef`（当前 streaming 消息的 cat-id 映射）
- 返回: `handleAgentMessage` (socket 事件处理) + `handleStop` (取消) + `resetRefs` (清理)
- ChatContainer 只负责 UI 编排，不再直接操作消息 ref

### 0-C: parse-multipart.ts

- 从 messages.ts 提取 multipart 请求解析逻辑
- 包含 `sendMessageSchema` (zod) + `parseMultipart()` 函数
- messages.ts 通过 import 使用，JSON 模式和 multipart 模式共享同一个 schema

## Why: 降低后续 diff 的复杂度

Phase 3.5 的核心改动分布在这三个文件：
- **AgentRouter**: 新增并行路由路径 (`routeParallel`) + intent 解析
- **ChatContainer/useAgentMessages**: Map-based 并行流追踪替代单 ref
- **messages.ts**: intent_mode WebSocket 广播

CLAUDE.md 规定文件 < 200 行。先拆分让后续 PR 的 diff 聚焦在新逻辑上，而不是混杂在大文件的上下文里。

## Tradeoff

- **放弃**: 一步到位把 AgentRouter 拆成 Router + Serial + Parallel 三个文件。现在只提取了 `invokeSingleCat`，`routeSerial` 仍在 AgentRouter 内。
  - 原因: Step 3 (并行路由) 才能确定 `routeParallel` 的最终形状，过早拆分可能需要二次重构。
- **放弃**: ChatContainer 进一步拆分（比如提取 scroll 逻辑）。当前 ~265 行仍超 200 行。
  - 原因: scroll 逻辑和消息列表强耦合（scrollSnapshot/prevFirstId），单独提取反而增加跨 hook 协调的复杂度。Step 6 前端集成时再评估。
