## What: Phase 4.0 做了什么

## Why: 为什么这样做

### Per-cat budgets (核心改动)
铲屎官明确说"32k 啥也干不了"。Claude 200k context, Codex 128k, Gemini 1M。
之前全局 `MAX_PROMPT_CHARS=32000` 是历史遗留，现在每猫独立配置。

**架构决策**: 遵循 `cat-models.ts` 模式，新建 `cat-budgets.ts`：
```
env (CAT_OPUS_MAX_PROMPT_CHARS) > cat-config.json > 硬编码默认
```

### TaskExtractor LLM + fallback
任务提取用 LLM 更智能，但 LLM 可能超时/失败，所以有 regex pattern fallback。
这也是 DegradationPolicy 设计的核心思路：能降级，就降级；不能降级，告知用户。

### F3-lite 线程隔离
遵循 I-3 原则：memory 是 per-thread 的。跨 thread 共享记忆是 F3b (Phase 4.1+) 的事。

---

## Tradeoff: 放弃了什么

1. **没做 F3b 协作记忆**: 只做了 per-thread KV，跨 thread 和跨猫共享记忆留给后续
2. **Deliberate 4-E 只有类型**: 两轮制讨论模式只预埋了 TypeScript 类型，无运行时代码
3. **没做配置热更新**: ConfigRegistry 只读，PATCH /api/config 留给 F4
4. **Pattern fallback 较简单**: 只匹配 `- [ ]`、`TODO:`、`#task`，复杂场景可能漏提取

---

## Open Questions: 不确定的点

1. **TaskExtractor prompt**: 当前 system prompt 约 200 tokens，是否需要调优？
2. **Heartbeat 间隔**: 30s 是否合适？太频繁增加网络开销，太稀疏可能误判
3. **Memory LRU eviction**: 当前简单删最老的 key，是否需要更智能的策略？
4. **DegradationPolicy 边界**: `pattern_only` 策略的触发阈值是否合理？
