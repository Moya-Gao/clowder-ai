## What: 具体改了什么

### Commit 1: `1c3efe4` — CLI 超时错误传播 (Bug 4)

**问题**: `cli-spawn.ts` 超时触发 `killChild()` → `killed=true` →
退出时 `if (!killed && exitCode !== 0)` 跳过 error → AgentService 只 yield `done` → 用户看到空结果无报错。

**核心矛盾**: `killed` 标志同时表示"我们主动杀的"(timeout) 和"用户取消的"(AbortSignal)。
timeout 需要报错，cancel 不需要。但它们共用同一个标志。

**修复**:
- `cli-spawn.ts`: 新增 `timedOut` 布尔，timeout handler 先 `timedOut = true` 再 `killChild()`
- stdout drain 后，`!killed` 的 `__cliError` 逻辑不变 (这是外部 kill / 非零退出用的)
- 新增: `if (timedOut)` yield `{ __cliTimeout: true, timeoutMs, stderr, command }`
- 新增: `isCliTimeout()` type guard (与 `isCliError()` 同模式)
- 三猫 AgentService: for-await loop 中 `isCliTimeout` → yield 中文错误消息

**测试 (+4)**:
- 更新: timeout test 现在断言 `__cliTimeout` **出现** (之前断言 `__cliError` 不出现)
- 新增: `isCliTimeout` type guard 边界测试
- 新增: `AbortSignal cancel` 不产生 `__cliTimeout` (区分 timeout vs cancel)
- 新增: `__cliTimeout` 字段正确性检查

### Commit 2: `a0bfddc` — 上下文 per-message 限制提升 (Bug 2)

**问题**: `ContextAssembler.ts` `DEFAULT_MAX_CONTENT_LENGTH = 500`。
猫回复通常 800-2000 字，截成 500 字后其他猫"看不到完整内容"。

**决策过程**:
- Phase 3.7 的 `maxTotalChars=8000` 控制的是**总上下文预算** (所有消息加起来)
- Bug 的根因不是总预算不够，而是**每条消息**被截到 500 字，800 字的回复丢了 40%
- 500 → 1500: 足够容纳绝大多数猫回复 (暹罗猫最话痨 ~1200 字)
- 20 条 * 1500 字 = 30K 字 (中文 ~15K token) 在 maxTotalChars=8000 兜底下安全
- 添加 `MAX_CONTEXT_MSG_CHARS` 环境变量: 允许运行时调整而不改代码

**测试 (+2)**:
- 新增: 600 字消息在默认 1500 限制下不被截断 (之前会被截)
- 新增: `MAX_CONTEXT_MSG_CHARS` 环境变量覆盖生效

### Commit 3: `180bd1a` — 每猫状态追踪 + 思考指示器 (Bug 1+3)

**问题**: 前端只有全局 `isLoading` 布尔，不追踪每只猫的独立状态。

新增后端事件 = 多余复杂度。

**修改**:

  - `setTargetCats(cats)`: 同时初始化所有猫为 `'pending'`

  - `handleStop` 也清理

  - `onIntentMode` 回调现在提取 `targetCats` 并调用 `setTargetCats`
  - `IdeateHeader` 替换为 `ParallelStatusBar` (ideate 模式)
  - 新增 `ThinkingIndicator` (execute 单猫模式)

- 新文件 `ParallelStatusBar.tsx` (~56 行): 每猫状态指示 (pending 灰脉动/streaming 绿脉动/done 勾/error 叉)
- 新文件 `ThinkingIndicator.tsx` (~36 行): 单猫 "🐾 布偶猫思考中..."

## Why: 为什么这样决策

| 决策 | 理由 |
|------|------|
| `timedOut` 独立标志而非复用 `killed` | timeout 和 cancel 语义不同: timeout 是系统行为需报错, cancel 是用户意图应静默。最小改动，不动现有 `killed` 逻辑 |
| `__cliTimeout` 独立类型而非复用 `__cliError` | timeout 有 `timeoutMs` 字段但没有 `exitCode`/`signal`; 消费侧 (AgentService) 对 timeout 的措辞也不同 ("超时" vs "退出错误") |
| 500→1500 而非更大/按 token | 1500 覆盖 95% 猫回复; token 计数需引入 tokenizer 依赖 (tiktoken/etc), YAGNI; maxTotalChars=8000 是总量兜底 |
| 纯前端修复 Bug 1+3 | 后端已发足够事件, 新增 = 多余; 前端状态派生更灵活; 避免前后端联动改增加 review 负担 |
| ParallelStatusBar 替代 IdeateHeader | IdeateHeader 只显示静态文字, 不追踪每猫状态; 新组件是超集 |
| ThinkingIndicator 而非"气泡占位消息" | 占位消息会插入 messages 数组，需要管理生命周期(插入/删除); 横幅由 state 驱动，简单且可预测 |

## Tradeoff: 放弃了什么

1. **没做调用级别日志** (Bug Report 建议): 当前修复确保超时**传达到用户**,
   但没加 API 侧的结构化调用日志。这更适合 Phase 4 的可观测性体系。
2. **没做"3分钟超时预警"**: Bug Report 建议 3 分钟时 emit warning。
   实现需要在 cli-spawn 中加中间态事件，当前超时直接报错已经解决核心问题。
3. **IdeateHeader.tsx 未删除**: 变成了死代码。保留作为参考,
   如果缅因猫觉得该删可以删。
4. **前端无 node:test**: ParallelStatusBar/ThinkingIndicator 无单元测试。
   这些是纯展示组件, 依赖 store 状态, 需 React testing-library 才能有意义地测,
   项目当前没有前端测试框架。
