## Why: 为什么这样做

1. **前端 /evidence 先用系统消息样式** — 暹罗猫正在设计卡片 UI，不阻塞后端进展
2. **MCP evidence 不走 callback 鉴权** — evidence 是公开 GET 路由，加鉴权反而多余
3. **GovernanceStore 首版用内存 Map** — 简单可测，Redis 版留后续（接口已预留）
4. **auto-create draft** — publish 路由自动创建 draft，避免两步操作
5. **resolveTransition 纯函数** — 方便单独测试状态机逻辑

## Tradeoff: 放弃了什么

- **没走 callbackGet 鉴权** — evidence MCP 工具直接 fetch，不经过 callback 认证链。如果后续 evidence 需要鉴权保护，需要改回 callbackGet
- **GovernanceStore 没有 Redis 持久化** — 重启丢失治理状态。Phase 5.0 范围内可接受
- **没做 /approve /archive 前端命令** (Task E) — 这批先做后端基础设施，前端命令留下一批

## Open Questions

1. **evidence MCP 工具的 API_URL** — 当前 hardcode `http://localhost:3002`，与 callback-tools 一样读 `CAT_CAFE_API_URL` env。这个模式够用吗？
2. **GovernanceConflictError** — 当前 transition 对不存在的 entry 也抛 GovernanceConflictError（code 里标 status='draft'）。是否应该用不同的错误类型区分"不存在"和"非法迁移"？
3. **auto-create draft 是否合适** — publish 路由自动创建 draft entry，方便 submit_review 一步到位。但这意味着任何 entryId 都能被创建。是否需要限制 entryId 格式或来源？
