## What: 5.0-pre — Phase 5 前置清障

在进入 Phase 5.1 实现之前，清掉两个阻塞 Phase 5 UX 的债务：

### Pre-1: tool_use/tool_result 事件显示 (BACKLOG F9)

**根因**: 后端 Claude/Gemini AgentService 都在 yield `tool_use` 事件（含 `toolName` + `toolInput`），`SocketManager.broadcastAgentMessage()` 也原封不动转发了，但前端 `useAgentMessages.ts` 只处理了 text/done/a2a_handoff/system_info/error 五种类型，tool_use 和 tool_result 被静默丢弃。

**改动**:
- `packages/web/src/stores/chatStore.ts`: variant 类型新增 `'tool'`
- `packages/web/src/components/ChatMessage.tsx`: 新增 `tool` variant 渲染（灰色、monospace、紧凑）
- `packages/web/src/hooks/useAgentMessages.ts`: AgentMsg 接口扩展 toolName/toolInput 字段 + 新增 tool_use/tool_result 两个 handler 分支

**设计决策**: 用 system message + `variant: 'tool'` 渲染，不是独立的消息类型。理由：tool 事件是辅助信息不是主内容，不应与 assistant 消息争夺视觉权重。后续 F8（完整工作状态显示）可以在此基础上增强。

### Pre-2: DegradationPolicy 绑定实际链路 (BACKLOG #32)

**根因**: Phase 4.0 的 `DegradationPolicy.ts` 是纯函数框架（`checkContextBudget` / `formatDegradationMessage`），但没有任何调用方真正用它发 `system_info` 给用户。

**改动**:
- `packages/api/src/domains/cats/services/route-strategies.ts`:
  - `routeSerial`: context assembly 后调用 `checkContextBudget()`，若 degraded 则 yield `system_info`
  - `routeParallel`: 同理，收集 degradation messages 后在 merge loop 之前 yield
- `packages/api/test/route-strategies.test.js`: +3 新测试
  - serial: 50 条历史 → 超出 opus maxMessages=40 → 收到 system_info
  - serial: 5 条历史 → 不触发
  - parallel: 50 条历史 → 两只猫都收到 system_info

## Why

- Phase 5 的 evidence 搜索和 reflect 都会产生工具调用。不修 F9，用户还是"等半天啥也看不到"。
- Phase 5 的 evidence 搜索有降级路径（Hindsight 挂了走本地 grep）。不绑 #32，降级消息没法通知用户。

## Tradeoff

- tool_use 显示用了最简方案（system message + variant），没做独立 UI 组件。选择理由：快速见效、不引入新组件复杂度、F8 后续可增强。
- degradation 只绑了 context budget 一个链路（routeSerial + routeParallel）。Phase 5 的 evidence 搜索降级需要在 evidence route 里单独处理（已在 5.1 计划中）。
