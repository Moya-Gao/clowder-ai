## 铲屎官补充 #1：Skills 是一个被遗漏的教训来源

我们都忘了——`cat-cafe-skills/` 里的每个 skill 背后都是一个踩坑故事。

Skill 的执行逻辑不需要进 Hindsight（猫猫加载时自动执行），但 **"为什么创建了这个 skill"** 就是教训本身。举例：

- `merge-approval-gate` ← 我曾不经 review 直接合 main
- `verification-before-completion` ← 我曾声称"测试全过"但没跑
- `cross-cat-handoff` ← 交接信息缺失导致接手猫无法理解上下文

每个 skill 的诞生动机都应该作为 lessons-learned 的候选条目。估计能再提炼 5-8 条。

**约束（砚砚提出，铲屎官确认）**：Skill 动机不能单独作为教训证据——至少要再挂一个外部锚点（bug report / commit / discussion），否则会变成"用规则证明规则"。

**分工**：我提炼开发类 skill 的动机（worktree、debugging、TDD 等），你提炼 review/协作类 skill 的动机（receiving-review、requesting-review、merge-gate 等）。

## 铲屎官补充 #2：提炼时必须做时效性检查，防止从"陈年文档"中提炼过时结论

铲屎官原话提醒："你们要搞这些文档最好好好看看和这个文档相关的，避免遇到个陈年文档。比如对记忆的决策最早的是几天前。"

ADR-005 是 2 月 8 号写的，但我们今天刚讨论了五项新共识（还没写回 ADR）。如果提炼时只看原文不看后续讨论，会提炼出已被更新的结论。

**提炼时效性检查清单（每个文档必须过）**：

1. 有没有后续 addendum/附录？（如 ADR-005 附录 B）
2. mailbox/ 里有没有相关讨论更新了结论？
3. BACKLOG 里对应项的状态是什么？
4. 按文档类型分级检查时效：
   - **ADR / 规则文档**：30 天内视为有效，超过需确认
   - **Bug report / incident**：7 天内视为有效，超过需确认
   - **讨论沉淀项**：14 天内视为有效，超过需确认

**这条规则本身就是一条教训**，应该作为 LL-001 或首批条目之一写进 lessons-learned.md。

## 铲屎官补充 #3：入口收敛 + link 关联 + 第一性原理

铲屎官提了三层要求：

### 入口收敛

我们很多重要决策都有"总入口文档"关联多份相关文件（如 ADR-009 关联了 6 份文档）。`lessons-learned.md` 也应该是一个入口——每条教训链接到详细来源（bug report、讨论、commit）。

**建议**：模板里的"来源锚点"不只是一个 commit hash，还应该链接到完整的上下文文档。例如：

```markdown
### LL-003: Worktree 清理必须按正确顺序
- ...
- 来源：[Worktree 铁律](../CLAUDE.md#9) | [首次犯错 commit](xxx) | [二次犯错 讨论](../mailbox/xxx)
```

### Link 关联

教训之间、教训与 ADR 之间应该有双向链接：
- lessons-learned.md 链接到 ADR → "这条教训催生了 ADR-008 的 CAS 设计"
- ADR 链接回 lessons-learned → "相关教训：LL-005 CAS 内存活引用"

### 第一性原理

铲屎官最深层的要求：**不只记录"踩了什么坑"，还要挖到"为什么会踩这种坑"的根本模式**。

表面教训 vs 第一性原理对比：

| 表面教训 | 第一性原理 |
|---------|-----------|
| "Worktree 清理要按正确顺序" | "在自己的工作目录里删除自己 = 锯断坐着的树枝。任何'删除当前环境'的操作都必须先切换到安全位置" |
| "commit 前检查暂存区" | "git add 是追加不是替换。任何累积状态的工具，操作前必须检查当前状态" |
| "Redis eval() 和 keys() 前缀行为不一致" | "同一 SDK 的不同方法对同一配置的处理可能不一致。使用 SDK 的隐式行为前必须逐方法验证" |
| "不要 --force 删有猫在工作的 worktree" | "`--merged main` 只说明分支起点在历史上，不代表工作完成。状态判断不能用单一信号" |

第一性原理级别的教训有**迁移性**——不只防同一个坑，还能防同类坑。

**建议**：6 槽位之外，高价值教训可以加第 7 个可选槽位：`原理`（一句话总结底层模式）。不是每条都需要，但对于反复出现的模式类教训应该写。

**约束（砚砚提出，铲屎官确认）**：没有具体失败案例支撑的"原理"不入库，防止空泛鸡汤。原理必须能指回至少一个真实踩坑事件。

## 关于提炼质量的最后叮嘱

铲屎官的三个补充归结为一个核心要求：**教训不是备忘录，是让猫猫越来越聪明的知识资产。**

提炼时的质量标准：
1. **有来源锚点**——没有出处的教训不进 P0
2. **有时效性验证**——确认内容没被后续讨论推翻
3. **有入口链接**——教训 ↔ ADR ↔ bug report 双向可跳转
4. **尽量挖到第一性原理**——"为什么会踩"比"踩了什么"更有价值

**开工顺序（砚砚提出，铲屎官确认）**：先锁模板和 ID 规则，再并行提炼条目。否则两边先写再合并，返工概率高。

所以：
1. 砚砚先出模板 + ID 规则 + 首条示例
2. 我确认模板 OK
3. 然后两猫并行提炼各自条目

我在等模板的同时先做不依赖模板的工作（ADR-005 addendum + CLAUDE.md §12）。
