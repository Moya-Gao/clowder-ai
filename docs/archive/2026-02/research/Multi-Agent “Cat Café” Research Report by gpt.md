Multi-Agent “Cat Café” Research Report

1. Claude Agent Summoning Mechanism

Programmatic Invocation of Claude Code CLI: Anthropic’s Claude Code can be called non-interactively via its CLI or Agent SDK. Using the CLI, the -p flag allows providing a prompt to run in “headless” mode, suitable for scripts or CI/CD. For example: claude -p "Find and fix the bug in auth.py" --allowedTools "Read,Edit,Bash" will run a single-turn task with specified tools ￼. The CLI supports flags like --continue (to resume a session) and --session-id to maintain state across calls ￼. In practice, one can capture the session ID from the output (--output-format=json) and use --resume <sessionId> for follow-up prompts in the same context ￼. Anthropic also provides an Agent SDK (with Node.js/TypeScript and Python libraries) that wraps Claude Code’s agent loop and tools for full programmatic control ￼ ￼. The SDK manages the prompt-tool-response loop automatically, so developers don’t have to manually handle each tool invocation ￼ ￼. It exposes built-in tools (Read, Write, Edit, Bash, etc.) and streams messages as the agent works ￼ ￼. This means a backend service can instantiate a Claude agent session, feed it tasks, and receive intermediate tool calls and final results via callbacks or streams.

Agent SDK Capabilities and Limits: The Claude Agent SDK essentially provides all the capabilities of Claude Code’s interactive mode (file I/O, shell commands, web search, etc.) in a library form ￼ ￼. It handles long context (Claude 2 supports 100K tokens) and multi-turn task planning autonomously. One limitation is that it requires an Anthropic API key (or Claude Cloud subscription) and internet access for model calls ￼ ￼. Also, the agent runs within a sandboxed environment inherited from your shell – meaning it has access to the working directory and environment variables, but not beyond what you allow ￼ ￼. Safety measures like tool permission prompts are present by default; however, they can be auto-approved via flags or code options (e.g. allowedTools) ￼ ￼. The SDK’s main constraint is that it’s tied to Claude models (e.g. Claude 2/“Opus” or Claude Instant) – you cannot use it with non-Anthropic models. It’s also subject to the model’s reliability and token limits. In summary, the Claude Agent SDK offers robust agent abilities (full tool use, loop management) with the trade-off of being Anthropic-specific.

Running Claude as a Background Service: There is no official always-on server mode for Claude Code from Anthropic, but it’s feasible via community solutions or custom wrappers. For instance, an open-source project provides a WebSocket server wrapping the Claude Agent SDK to enable real-time bidirectional communication with a persistent Claude agent ￼ ￼. This effectively lets you run Claude Code as a daemon: the service keeps a session alive and streams responses to connected clients over WebSocket. In a custom build, one could similarly spawn Claude’s process (or use the SDK in an async loop) on server startup and feed it tasks via an API. Anthropic’s documentation notes that the Agent SDK can be integrated into applications, and indeed workshops demonstrate hosting it (even mentioning differences from stateless APIs because it maintains state in a persistent environment) ￼. Therefore, while not “officially” provided as a single-click daemon, you can run Claude Code in headless mode continuously – either by keeping the CLI running with an input pipe or by using the SDK within a long-lived service. This would allow the Cat Café backend to route tasks to a Claude agent that is already loaded (avoiding cold-start delay) and maintain context between user mentions.

MCP Integration and Custom Servers: Claude Code integrates with external tools through the Model Context Protocol (MCP) – an open standard for AI tool plugins. Claude can connect to hundreds of MCP servers (for services like Notion, GitHub, databases, etc.) by configuring them via CLI (claude mcp add ...) or config files ￼ ￼. Under the hood, when Claude needs to use a tool, it communicates with the MCP server, which executes the action and returns results. Anthropic supports HTTP-based MCP servers (and local process servers) – you can build your own using the official MCP SDK ￼. For example, you could write a custom MCP server in TypeScript to handle domain-specific actions, then point Claude Code to it (e.g. claude mcp add --transport http mytool http://localhost:PORT/mcp) ￼. The Cat Café plan to have a TS MCP server for file I/O and inter-agent messaging is feasible: Claude can be configured to use that server, and whenever Claude tries to read a file or send a notification, it will call the MCP endpoints your server exposes. Claude’s MCP interface is flexible – you can even use Claude Code itself as an MCP server to other agents ￼. One consideration: each Claude session can have multiple MCP servers attached (with scope rules for project/user), so you need to ensure naming and permissions in .mcp.json config if multiple “cats” share a server. In summary, Claude’s MCP integration is robust and customizable, enabling tools bridging and potentially enabling cross-agent communication via a shared MCP layer.

2. OpenAI Codex Summoning Mechanism

Programmatic Invocation of Codex CLI: OpenAI’s Codex CLI (OpenAI’s coding agent, now part of ChatGPT Plus) can also run in non-interactive mode for automation. OpenAI provides a command codex exec "<task prompt>" to execute a prompt headlessly ￼ ￼. This behaves similarly to Claude’s -p mode: it runs the agent through the task and prints the final answer (by default to stdout). While running, Codex streams progress (tool use, reasoning) to stderr and only the final result to stdout, making it easy to capture or pipe outputs ￼ ￼. Flags allow controlling the sandbox and output format. For example, codex exec --json "summarize the repo" outputs a JSONL stream of all events (tool calls, agent messages, etc.) ￼ ￼. Codex CLI also supports multi-turn sessions: it keeps an internal threadId for each session. Using the API or MCP, one can call a codex-reply tool with a threadId to continue a conversation in that same session ￼ ￼. In practice, if you want to call Codex programmatically in sequence, you can either let codex exec print a session ID in JSON output and reuse it, or directly specify --session <id> on the CLI to resume context ￼. This means the Cat Café backend could spawn the Codex CLI process with appropriate flags for each user mention and maintain the session ID to achieve continuity.

OpenAI Agent SDK / Tools: Yes – OpenAI has introduced an Agents SDK (often referred to in docs as OpenAI Agent or “multi-agent workflow” SDK). This is a framework that allows orchestration of tools and multi-step agent interactions programmatically, analogous to Anthropic’s SDK. For example, OpenAI’s guide “Use Codex with the Agents SDK” shows how you can launch Codex CLI as an MCP server and then orchestrate it with an OpenAI Agents SDK in Python ￼ ￼. The OpenAI Agents SDK enables building workflows with multiple agents (even hand-offs between them), with support for traces, structured outputs, and integration with OpenAI’s model APIs. It’s essentially part of the OpenAI developer platform for advanced use cases. One capability highlighted is running Codex as a sub-agent via MCP and controlling it from a Python script – for instance, one agent can call a “codex” tool (provided by the Codex MCP server) to delegate coding tasks to Codex ￼ ￼. In addition, OpenAI’s documentation mentions an App Server and API server mode for Codex, implying you can run Codex with a local server that exposes endpoints or a Web UI ￼ ￼. In summary, OpenAI’s ecosystem does support agentic behavior: you can either use the lightweight CLI approach for simple use, or leverage their Agents SDK for more complex orchestrations. However, unlike Claude Code (which has a single unified CLI/SDK), OpenAI’s solution might involve combining the CLI with separate orchestration code (Python) to get full multi-agent loops.

MCP and Custom Tools with Codex: Codex CLI includes first-class support for Model Context Protocol (MCP) to extend its capabilities. The Codex docs explicitly include a section on MCP ￼, and OpenAI has demonstrated connecting Codex to third-party MCP servers (e.g. JetBrains IDE, databases, etc.). You can add MCP servers via the Codex config file or CLI commands (similar to Claude). For example, one can enable Slack or GitHub tools by adding their MCP endpoints. OpenAI even published a tutorial on using Codex with JetBrains’s MCP server as an example ￼. So yes, you can connect Codex to custom MCP servers. If Cat Café provides a custom MCP server (for file ops or chat functions), Codex can be configured to use it in its context. Moreover, Codex itself can act as an MCP server: running codex mcp-server will host Codex CLI as a tool endpoint ￼ ￼. This is how OpenAI’s multi-agent workflows keep Codex running persistently and call it via SDK. This dual role of MCP means you have flexibility: either treat Codex as the “agent” with external tools, or as a tool called by another agent. In our scenario, likely we treat Codex as an agent with tools – in which case adding the shared MCP server for file and notification tools is straightforward (just as with Claude).

Sandbox and Execution Environment: Codex CLI runs tasks in an isolated sandbox environment by default. When you invoke codex exec, it uses a read-only workspace (no file writes or destructive commands) unless you override. To grant more power, you can use flags: --full-auto allows it to edit files, and --sandbox danger-full-access even permits unrestricted shell access ￼. This approach ensures safety by default, requiring the developer to explicitly opt-in to higher privileges. Under the hood, when running locally, Codex is basically running on your machine (so “sandbox” is logical rather than a true VM, unless using their cloud tasks). In Antigravity (the Google analog), each agent runs in a container; in Codex’s case on a local CLI, it uses your OS but can be configured to only operate in a specific directory (the CLI’s working directory or a temporary folder). If using Codex Cloud (OpenAI’s hosted execution), then it’s in their container. The key point: Codex’s sandbox is configurable to balance safety vs autonomy ￼. For Cat Café, this means we must carefully decide these flags – likely enabling at least workspace-write to allow code edits in the project, but perhaps not danger-full-access unless we trust the agent completely. Fortunately, these settings can be tuned per session or prompt via the CLI or via the Agents SDK (which maps to the same options).

3. Google Gemini / Antigravity Summoning Mechanism

Google Antigravity Architecture: Antigravity is Google’s agentic development platform (currently in preview) built around the upcoming Gemini LLM. It is essentially an AI-augmented IDE that has two modes: an Editor View (a traditional code editor with AI assistance) and an Agent Manager (Manager Surface) ￼. The Agent Manager is like a mission control where you can spawn, orchestrate, and observe multiple agents working asynchronously across different workspaces ￼ ￼. This multi-agent orchestration is a core design point of Antigravity – rather than a single chatbot, it enables teams of agents (each could be assigned to different tasks or projects) coordinated by the interface. In practice, when you give a high-level task, Antigravity might spin up a planner agent, a coder agent, maybe a tester agent, etc., and manage their interactions. The architecture includes an Agent Manager panel showing all agent “conversations” (inboxes of each agent), their generated artifacts (code, plans) and a review system for their outputs ￼ ￼. Agents in Antigravity can use tools spanning the local system (terminal commands, file edits) and the web (built-in browser with controlled JS execution) – and the user can configure how autonomous they are (policies for auto-executing commands or requiring approval) ￼ ￼. In summary, Antigravity’s architecture is an integrated multi-agent IDE: it abstracts away the complexity of running multiple agent processes by providing a unified environment where agents coordinate via the Agent Manager. This is somewhat analogous to what we want in Cat Café (multiple specialized AIs collaborating), except Antigravity is a closed platform tied to Google’s ecosystem and not accessible via simple API calls.

Gemini’s Agent SDK / ADK: Google has released an Agent Development Kit (ADK) which is an open-source framework for building and deploying AI agents, optimized for Gemini models ￼. The ADK is model-agnostic (works with various LLMs) but is clearly designed to integrate well with Google’s Gemini and Vertex AI services ￼. The ADK provides a modular framework with concepts like agent “skills” (tools), memory (context), and it supports multi-agent systems and workflows out of the box. In fact, ADK includes support for multi-agent teams (agents can communicate, e.g., a manager agent delegating to worker agents) and even has an Agent2Agent (A2A) protocol standard for inter-agent messaging ￼. Capabilities of ADK include: easy tool integrations (it has a large library of built-in tools including Google services and MCP tools ￼ ￼), session management, and deployment to a managed runtime (Vertex AI Agent Engine) for scaling. For Cat Café, this means there is a potential route to incorporate Gemini via ADK. However, ADK is quite heavyweight if we only need a Gemini agent – it might be simpler to call Gemini via a Vertex AI API if available. At present (Feb 2026), Google’s Gemini 3 is not fully public via API, but since Antigravity is in preview, some Gemini API exists (likely through the Antigravity or Vertex AI endpoints). If we have access, we could use ADK to run an agent that uses Gemini under the hood and expose it in our system.

Calling Antigravity/Gemini Programmatically: Antigravity itself is primarily a user-facing application (a desktop app/IDE). It doesn’t provide a public API to send it tasks from an external system (and doing so might violate terms) ￼. Some developers have reverse-engineered partial “Antigravity API” access through unofficial means (e.g. using OAuth tokens to access the underlying model endpoints) ￼. But a cleaner approach is to use Google’s official cloud APIs. For instance, Google Cloud’s Vertex AI will presumably host Gemini models; one could call Vertex’s Chat API or Codey API (if Gemini Code is available) to get similar capabilities. If wanting the agentic behavior of Antigravity (with tools, planning, etc.), that’s where ADK comes in – you can build an agent that uses Gemini and runs the same kind of loop. Google’s ADK supports running agents in different modes: as a CLI tool, as a local HTTP server, or deployed on Agent Engine (which provides an API endpoint) ￼ ￼. For example, ADK’s Python quickstart shows how to define an agent and run it in the terminal or launch an API server with one command ￼ ￼. So, yes we can integrate Gemini into Cat Café, but likely not by directly “pinging Antigravity”; instead we’d instantiate a Gemini-powered agent via ADK or Vertex API. The Google Agent Development Kit capabilities in summary: it gives fine-grained control to design multi-agent workflows (including hierarchical agents), includes memory and tool abstractions, and is built with safety (confirmation policies) and evaluation tools. It’s a strong option if we want to embrace Google’s ecosystem fully – though it would add complexity and might require writing some Python or using their Node bindings.

4. Open-Source Multi-Agent Orchestration Projects

OpenClaw Architecture and Messaging Integration: OpenClaw (formerly Clawdbot/Moltbot) is a prominent open-source project that aligns closely with our needs. It is essentially a self-hosted AI agent gateway that bridges chat interfaces and a coding agent runtime ￼ ￼. OpenClaw’s architecture is gateway-centric: a single daemon process (the “Gateway”) manages all interactions. On one side, it connects to channels – e.g. iMessage, WhatsApp, Telegram, Discord, Slack, or a CLI – so the agent can send/receive messages on those platforms ￼. On the other side, it connects to tools and the model API. The internal design cleanly separates these concerns: the Gateway handles session management, message routing, and a web UI for configuration ￼ ￼. When a message comes in from a user on any channel, the Gateway forwards it to an embedded agent (called “Pi” in OpenClaw) that runs the AI logic ￼. Pi is essentially a lightweight wrapper that can execute shell commands on behalf of the agent. Pi sends the user’s prompt to the configured model backend (Anthropic Claude by default, though OpenClaw is model-agnostic to some extent) ￼. The model (Claude) returns an action plan or commands, which Pi then executes locally (e.g. “search for file X”, “run ls in directory Y”). The results of those commands are captured and sent back through the Gateway to the user’s chat ￼ ￼.

OpenClaw integrates with messaging platforms by using their APIs/protocols: e.g., for WhatsApp it uses the Baileys library (WhatsApp Web protocol), for iMessage it leverages Apple Script or a local client, etc. The Gateway essentially logs into these services as a client (or uses a bot API in the case of Telegram/Discord) so it can send and receive messages as “the AI agent”. This approach is exactly what we’d need if Cat Café should work across multiple chat platforms. The tutorial explicitly mentions support for WhatsApp, Telegram, Discord, iMessage, and a CLI interface out of the box ￼.

Calling Claude Code / Codex in OpenClaw: Under the hood, OpenClaw’s default agent is Claude (hence the original name Clawdbot). It uses Claude Code’s capabilities to interpret user instructions and produce commands. In setup, it even allows using a Claude API token or a Claude Code CLI setup token for those with Claude Pro accounts ￼. Essentially, OpenClaw offloads the “AI reasoning” to Claude – acting as a middleman between chat and Claude’s agent. When Claude suggests an action (like “I should open file X”), OpenClaw’s Pi module carries it out. OpenClaw does not yet have built-in support to use OpenAI’s Codex CLI simultaneously; however, one could imagine extending it to other models. The design is model-agnostic: “prompts and files never leave your hardware except when sent to whatever model API you configure” ￼. So you could configure it to use an OpenAI API instead of Claude if desired. The key takeaway is that OpenClaw demonstrates a working solution of a routing gateway + agent loop. It even has a concept of “skills” which are structured definitions of tasks the agent can do, mapping high-level intents to specific tool usage (to avoid the agent doing arbitrary things) ￼ ￼. This resembles how we might want to constrain our cats to certain operations.

OpenClaw’s architecture diagram (Diagram 1 in the Medium article) shows a clear split: Channels (WhatsApp, Chrome extension, CLI) feed into the Gateway (Brain), which then routes to various tool plugins (Browser automation, Shell, Web search) ￼ ￼. The Gateway contains the session memory and tool routing logic as well as auth for APIs ￼. This clean layering is something we can emulate in Cat Café’s design. One difference is OpenClaw currently focuses on a single agent serving one user (the personal assistant scenario), whereas Cat Café has three different model agents that might also talk to each other. We might need an extra routing layer for “mentions” to direct messages to the right cat, but the concept is similar.

Other Multi-Agent Orchestration Frameworks: There are several frameworks and projects tackling multi-agent systems that could inform or assist our implementation:
	•	LangChain’s LangGraph: LangGraph is a library built on LangChain for designing complex workflows with multiple agents. It allows you to define a graph where nodes are agents or tools, enabling branching, looping, and hierarchical control flows ￼. LangGraph supports persistence and streaming and can be used to build routers that delegate tasks to different sub-agents based on the input. For example, one could have a routing agent that, given a user query, classifies it and forwards it to either Claude or Codex agent nodes accordingly. LangChain also has built-in Multi-Action Agent and Router concepts ￼ ￼, which could be leveraged to build an “agent router” for Cat Café (though integrating our specific CLI-based agents would require custom tooling).
	•	CrewAI: crewAI is an open-source Python framework specifically for multi-agent orchestration (created by João Moura) ￼. It uses the metaphor of a “crew” of agents working together. CrewAI provides a high-level way to define each agent’s role and tools, and includes dozens of pre-built tools (web search, email, Slack, databases, etc.) ￼. It focuses on role-playing agents that can communicate with each other and solve tasks collaboratively. For example, you could set up a “dev” agent and a “tester” agent and CrewAI will manage their dialog. This is quite relevant to Cat Café’s idea of different cat personas collaborating. CrewAI can run agents autonomously or semi-autonomously, and it emphasizes simplicity and performance (advertising itself as lean and free of heavy dependencies) ￼. One could potentially use CrewAI’s framework to orchestrate Claude, GPT (via OpenAI API), and Gemini by writing custom agent classes for each that interface with their respective backends. CrewAI might handle the conversation loop between them.
	•	Microsoft AutoGen: AutoGen is a framework by Microsoft for creating multi-agent conversations and workflows with LLMs ￼. It provides a conversation-driven approach where agents (backed by different models or functions) communicate in a shared chat to solve tasks. AutoGen allows defining agents with custom abilities and has them converse (including reflecting on each other’s outputs). It can incorporate function calling and external tool use as well. The emphasis is on reproducibility and managing the chat history between multiple agents. This could be used to prototype the multi-agent interplay (e.g., have Claude and GPT-4 talk to each other) – however, AutoGen expects to use OpenAI or Azure models typically, so integrating Gemini might be non-trivial.

Other notable mentions include HuggingGPT (for orchestrating multiple AI services via one controller agent) and GPT-Engineer style planners – but those are more about multi-step single-agent planning rather than multi-agent collaboration. There’s also LangChain Agents (single agent that can use multiple tools) which we already know, and some research like Meta’s Generative Agents. However, for multi-agent router/orchestrator, LangGraph and CrewAI are among the leading open-source solutions. Both could, in theory, be adapted to route between our Cat Café agents, but adopting them might add complexity. Given our preference for TypeScript, a Python-based framework like CrewAI or AutoGen would need some integration (perhaps running as a separate service).

In summary, there are open implementations of “agent orchestrators” – OpenClaw being very close to what we need for bridging chat and agents, and frameworks like CrewAI/LangGraph providing patterns for dividing tasks among agents. We can draw inspiration from OpenClaw’s gateway and possibly reuse components (OpenClaw itself is TypeScript-based and could be extended). If not using them directly, they at least validate that our plan (multiple agents triggered by mentions, possibly sharing a memory store) is technically feasible.

5. Model Context Protocol (MCP) in a Multi-Agent Setup

Shared MCP Server for Multiple Agents: In principle, yes – multiple agents can connect to and use the same MCP server. MCP is built on a client-server model (often HTTP or stdio), where the agent is the client. If we run one MCP server (say, at localhost:4000), we can register that endpoint in each agent’s configuration. For example, both Claude and Codex could have a “filesystem” tool pointing to http://localhost:4000/mcp with different tool names or namespaces. As long as the MCP server can handle concurrent requests (most HTTP servers can), the agents can share it. They might each open their own connection/session, or even reuse sessions if the MCP protocol supports it. Official docs don’t forbid multi-agent use: for instance, OpenAI’s example shows launching one Codex MCP server and orchestrating two agents that both call it during a workflow ￼ ￼. In that guide, one agent (the “Game Developer”) calls the codex() tool on the shared server to generate code, while another agent might later call it to continue – all using the single Codex MCP server process. This demonstrates that one MCP server can serve multiple agent calls sequentially. For truly simultaneous access, an HTTP MCP server (like one providing a web API to, say, a database) could handle parallel requests from multiple agents without issue, given each request has an identifier.

One thing to consider is state: if the MCP server maintains any state (e.g., a tool with an internal session), multiple agents might interfere unless it keys state by agent or session. But if the tools are stateless (e.g., “read_file” simply returns file content, regardless of who asks), sharing is fine. In Cat Café, a single MCP server providing file read/write and chat-posting tools can be shared so that all cats operate on the same filesystem and chatroom context. We’d implement logic to distinguish which agent is requesting, if needed (the MCP protocol includes the agent’s identity in requests, which our server can use).

MCP as Inter-Agent Communication Bridge: Using MCP for agent-to-agent messaging is an intriguing idea. While MCP is mainly about agents calling external tools, we could treat an agent as a “tool” to another agent. For example, we might create a custom MCP server endpoint “notify_cats” that, when called by one agent, will forward a message to the other agents (perhaps by injecting it into their context or via our backend). In this way, the MCP server acts like a hub. The calling agent sees it as just using a tool (e.g., Claude calls notify_cats("I finished task X")), and our MCP server implementation then broadcasts that to the Siamese or Maine Coon agent (maybe by appending to a shared conversation log or triggering their next action). This is not an out-of-the-box feature of MCP, but it’s something we can custom-build on top of it. It essentially leverages MCP’s flexibility to define arbitrary tools.

Currently, there isn’t a known “MCP hub” product specifically for multi-agent orchestration – but the building blocks are there. We have precedents: Google’s ADK introduced an Agent2Agent (A2A) protocol precisely for standardized agent messaging, separate from MCP ￼. That shows the concept is recognized as useful. Without A2A, we can approximate it: e.g., have each agent connect to a shared memory MCP server that provides tools like write_note and read_notes. Agents could drop notes for each other (like a blackboard). Alternatively, a simpler approach: our backend can just coordinate the agents’ outputs and inputs without involving MCP – for instance, after Claude finishes and produces a result, the backend passes that as input to GPT (this might be more direct for inter-agent chat).

In summary, multiple agents can share one MCP server for accessing common resources, and an MCP server can be extended to facilitate inter-agent comms, effectively acting as a broker. We should just be careful to avoid race conditions (one agent writing while another reads, etc.) and maybe implement basic locking or sequencing in critical sections. But the concept fits well with our design of a unified Cat Café toolset accessible to all cats.

6. Feasibility Analysis of Integration Approaches

We evaluate four possible integration strategies for Cat Café, considering pros, cons, and complexity:

Approach	Pros	Cons	Implementation Complexity
A. Pure API Directly use Claude, OpenAI, etc. via standard chat APIs	Simple Setup: Easiest to implement – use each provider’s REST API (Claude API, OpenAI Chat API, etc.) to get responses. No need to run local processes or sandboxes.  Reliable (less likely to crash locally) and maintainable by standard SDKs.	No “Agent” Tools: Loses all the agentic capabilities – models will only produce text answers, not actually execute commands or edit files.  Harder to enforce multi-step operations (would have to prompt the model to act as if using tools, which is fragile).  Context sharing becomes manual (we’d have to feed conversation + file content in prompts each time).	Low complexity in code, but limited functionality. We essentially reduce Cat Café to just three chatbots. This might be acceptable for simple Q&A, but fails core requirement of “agents that can operate on a workspace.” Implementation is straightforward: e.g., call openai.ChatCompletion or Anthropic’s API on each mention. Or use something like LangChain to manage histories. Overall, technically easy, but misses the point of collaboration and autonomous tool use.
B. Subprocess (CLI) Agents Spawn Claude Code and Codex CLI as child processes; feed inputs/outputs via stdin/stdout	Full Agent Power: We get the complete Claude Code and Codex behavior (with tool use, file edits, etc.) as if a user was driving the CLI ￼. This means agents truly execute commands on our system.  Isolation: Running each agent in its own process can isolate crashes or memory leaks. We can monitor and restart processes if needed. Parsing streaming JSON or text from stdout to update the frontend in real-time adds complexity.  Potentially slower response times due to spawning processes (though we can keep them running persistently to mitigate that).  Resource usage: Each CLI might be running a heavy model session (especially Codex with GPT-4/5 under the hood, or Claude with 100k context) – could be memory intensive.  Debugging is a bit harder (logs from subprocess need to be captured).	Medium complexity. We’d write a controller that launches, say, claude --stdio or uses the SDK’s ability to spawn a headless session, and similarly for codex. We must implement a non-blocking read of outputs to capture agent messages and tool invocations, then relay those to our system (e.g., if agent says “Tool Bash: git status”, we execute that or confirm it). Keeping sessions alive is key: we might start each agent process once and send it prompts via stdin as user messages arrive, using session IDs to maintain context ￼. Coordination between agents (if needed) would happen through the main backend orchestrator (which decides when to send one agent’s output as another’s input). Overall feasible, and leverages existing CLI functionality, but requires careful piping and error handling.
C. Agent SDKs (Library Integration) Use official Agent SDKs or developer kits from each provider within our code.	Unified Programming Model: We can call Anthropic’s TS SDK for Claude ￼, OpenAI’s Python Agents SDK for Codex ￼ (or their upcoming Node support), and perhaps Google’s ADK for Gemini (Python/TS). This means writing code to orchestrate tool usage rather than parsing CLI text.  Better Control: We get callbacks for each tool invocation, ability to customize the system prompts, and direct access to structured outputs (JSON results, etc.) ￼ ￼. Potentially easier to implement logic like “if agent tries to do X, intercept or modify it.”	Integration Challenges: Each SDK is different (Anthropic in TS, OpenAI’s in Python, Google’s ADK in Python/TS). Combining them might require bridging languages or running multiple services.  Learning Curve: Each kit has its own abstractions. Using ADK, for example, is like adopting a new framework for the whole project.  SDK Maturity: These are relatively new offerings (ADK is new; OpenAI Agents SDK evolving). There may be bugs or undocumented issues, and community support is smaller.	High complexity if we try to use all three SDKs together. We might end up with a polyglot system: Node.js service for Claude (using the TS SDK), a Python microservice for Codex (using OpenAI’s SDK to orchestrate Codex MCP), and maybe another for ADK. That introduces overhead in deployment and communication between these components (perhaps via HTTP or gRPC). If we restrict to TypeScript (per our tech preference), we could use Claude’s TS SDK easily, and for OpenAI we might bypass their SDK and just call the Codex CLI or Chat API. For Gemini, if no TS SDK is ready, we might call a REST API. In summary, while SDKs can simplify certain tasks (tool looping), the multi-vendor aspect complicates the architecture. This approach is feasible but likely the most complex to get right, unless we limit to one SDK and treat others differently.
D. External Agent Processes + Shared State Run each agent as an independent service (maybe even manually launched), communicate via files or MCP.	Loose Coupling: Each agent could be run in its ideal environment – e.g., a Claude Code process on a local machine, a Codex running in its own sandbox, etc. They share info through a well-defined interface (like reading/writing to a shared filesystem or database). This can make the system more modular and each agent easier to debug in isolation.  Persistent Sessions: If the agent processes are long-lived, they inherently maintain their context (in memory or in a local working dir). The mention of session-based operation fits this: you don’t shut down the agent after each answer, it stays alive waiting for the next mention.  Possibly easier to leverage GUI-based tools (like if one wanted to run Antigravity’s UI and still hook it in – though that’s speculative).	Synchronization Issues: Shared-file communication can be clunky and prone to race conditions. E.g., two agents writing to the same file as “memory” might overwrite each other.  Latency: Using files or even a database adds I/O overhead. Agents might have to poll for new messages unless we implement a notification system.  Manual Management: “User manually starts agent processes” is mentioned – that could be a dev inconvenience (not a big issue if scripted). But ensuring all are running and reconnecting them to the main system could be tricky.  State divergence: If one agent’s process crashes, its state might be lost unless we have a persistence mechanism.	Medium complexity, but with careful design needed. For example, we set up a shared directory that all agents can access (since they run on the same host). Agents could use simple files like chat.txt or a SQLite DB as a communication medium. Our Cat Café backend, upon a user message, could append the message to a log file and signal the relevant agent process (perhaps via a small trigger file or OS signal). The agent process, running independently, would detect the new message (via file watcher) and then output its reply to another file, which the backend reads and sends to frontend. This is doable but reinventing a lot of wheels (basically building a rudimentary IPC mechanism). Alternatively, a shared MCP server (as we plan) can substitute here: each agent connects to the MCP server which acts as the shared state manager and message broker, so we achieve similar loose coupling but with a more structured protocol. Overall, approach D can work and aligns with how some tools (like OpenClaw’s architecture with a daemon) operate. Complexity is moderate, but the reliability heavily depends on robust sync logic.

Recommendation: Based on the above, Plan B (Subprocess CLI) combined with some aspects of Plan D (persistent processes with shared state) appears to be the most pragmatic path initially. It lets us use the full capabilities of Claude Code and Codex without writing our own agent loops, and we can keep them running to maintain sessions (which meets the “session-based long-lived” requirement) ￼. We will need to build a lightweight orchestrator to route messages and handle outputs, but not an entire agent framework from scratch. Over time, we might move to SDKs (Plan C) for finer control once the basics are working. Plan A (pure API) is too limiting for our use case, and Plan C (full SDK integration) is a heavier lift at the moment. Plan D’s idea of a shared MCP server is very useful – in fact, we’ll incorporate that into our design for tool sharing and possibly agent coordination, even if we go with B.

Architecture Suggestion for Cat Café

Bringing it all together, here’s a proposed Cat Café architecture that leverages our findings:
	•	Backend Orchestrator (Node.js, Fastify): This is the core server that will interface between the front-end and the agents. It will manage WebSocket connections for real-time chat and handle the @mention routing logic. The backend will contain a MentionRouter component that receives a user message plus the target cat (e.g., “@MaineCoon do X”) and then dispatches that to the corresponding agent process or API.
	•	Agent Sessions (Child Processes or Services): We will run each cat agent as a persistent session process. For Claude (Ragdoll cat), we use the Claude Code CLI or Agent SDK in a headless mode, started with a specific session ID (or we keep the process running and use its interactive mode with our programmatic input). For Codex (Maine Coon cat), we run the Codex CLI in non-interactive server mode (either codex mcp-server as in OpenAI’s guide ￼, or use codex exec sequentially with a managed session). For Gemini (Siamese cat), if available, we might run an ADK-based local agent or connect to Vertex AI. In the simplest case, we might stub this initially with a normal GPT-4 via API (lacking tool use) until we get access to Gemini’s agent API.
	•	Model Context Protocol (MCP) Server (TypeScript): As planned, we implement a custom MCP server in Node (using the @modelcontextprotocol/sdk). This MCP server will provide tools common to all agents: e.g., ReadFile, WriteFile, ListFiles, which operate on the project workspace on disk; PostMessage or NotifyCats, which the agents can call to send a chat message to the shared chat (allowing inter-agent communication mediated by the server). Each agent process will be configured to connect to this MCP server. For instance, when we launch Claude’s process, we’ll do claude mcp add localtools http://localhost:4001/mcp (assuming our server listens there) for the needed tools. Similarly for Codex, we’ll configure its ~/.codex/config.toml or use CLI flags to add the MCP endpoint ￼ ￼. This way, all file edits and other actions go through one centralized logic – which is easier to manage for logging and security (we can, for example, refuse a delete_file if needed, or implement access control, within our MCP handler).
	•	Shared Workspace and Memory: We will designate a workspace directory (e.g., a project folder on disk) that all agents consider as their working directory. This allows them to read/edit code files collaboratively. We’ll also maintain a shared memory file or database (could be as simple as a JSON or Markdown log in ~/.cat-cafe/memory.json) to record important information that persists across sessions. Each agent can have a section in that memory, or it can be global. They will use MCP tools to read/write to it. This ensures that if one agent learns something (e.g., the user’s preferred coding style), another agent can later retrieve it. Session-based context (the conversation history with that agent) will be kept in the agent’s own memory (Claude and Codex do this internally if sessions are resumed ￼, ADK agents would need a memory plugin configured).
	•	Front-End (Next.js + Socket.io): The front-end will have a chat UI where the user can @mention cats. We’ll implement an @mention autocomplete (listing @Ragdoll, @MaineCoon, @Siamese) for convenience. Messages will be sent via WebSocket to the backend, which then emits updates as agents respond. The UI should display messages with speaker labels (including which cat said what). We’ll also show agent status – for example, when an agent is “thinking” (working on a task), we might show a typing indicator or a status like “Maine Coon is running a command…”. This can be driven by events from the MCP server (e.g., if the MCP sees a Bash tool execution, we notify the frontend that the agent is doing something).
	•	Message Flow Example: Suppose the user types: “@MaineCoon, please list all TODO comments in the repo.” The frontend sends this to backend with mentions: ['MaineCoon']. The MentionRouter receives it, finds the MaineCoon agent process (if not running, spawn it; if running, ensure it has the latest context). It then sends the prompt to that agent. If using CLI, it might execute codex exec --session-id 123 "<prompt>" --json to get a JSON stream. If using an MCP server mode, it might call the Agents SDK function that in turn calls our codex MCP. In either case, the agent (Codex) will possibly use tools: it might call Glob or Grep to search files for “TODO”. Those tool calls go to our MCP server (Glob could be a built-in tool too). Our MCP server executes them (search files) and returns results. Codex then composes an answer with the found lines. The backend collects the final answer from Codex and forwards it to the frontend to display as Maine Coon’s message. Meanwhile, if any other agent was mentioned or needs to chime in, similar flows occur. If an agent calls PostMessage via MCP to notify others (“I found 5 TODOs”), our backend can broadcast that as a system message or even route it as a prompt to the other agents if appropriate.
	•	Session Management: We will create a unique session per project (as desired). For example, if the project name is “cat-cafe”, we can use that as part of session IDs for each agent. The first time the user opens the project chat, the backend starts or resumes each agent. For Claude CLI, this could mean running claude --resume cat-cafe-claude if a session file exists, or starting fresh with claude --session-id cat-cafe-claude. Similarly for Codex, using --session-id or a persistent thread via MCP. The agents will load any memory file from disk (through a tool or initialization prompt). Thus the user sees continuity – the agents “remember” things from last time on that project. If the user closes the project, we might allow the processes to persist for a while or shut them down after inactivity and save state. The key is that when reopened, we resume rather than start from scratch.

This architecture fulfills our core needs: long-lived, collaborative agents with tool use, accessible through a unified chat interface. It prioritizes TypeScript for the orchestration and MCP layers, aligning with our tech stack preferences, and uses local resources for development (no dependency on cloud runtimes except the model APIs). We will need to remain mindful of security (the agents will effectively have as much power as a terminal user on the system), but we can mitigate risks by configuring sandbox modes (e.g., Codex in workspace-write instead of full, Claude with allowlisted tools only) ￼ and by reviewing any third-party “skills” installed.

Feasibility Matrix

Below is a summarized matrix of the proposed integration approaches vs. feasibility, incorporating pros/cons and complexity:
	•	Plan A: Pure API Calls
	•	Pros: Easiest to implement, minimal infrastructure. Use well-documented APIs (stable). No local resource load.
	•	Cons: Loses agent features (no direct file or command operations). Essentially reduces to Q&A bots. Not fulfilling the multi-agent collaboration vision beyond basic conversation.
	•	Complexity: ★☆☆☆ (Very low) – straightforward API calls in response to mentions. But would require manual prompt engineering to simulate tool usage, which is brittle.
	•	Plan B: Subprocess CLI Agents
	•	Pros: Full capabilities of each agent (Claude Code, Codex) as if interactive ￼. We leverage the proven CLI tools. Can maintain sessions by keeping processes alive ￼. Isolation between agents processes.
	•	Cons: Parsing and routing I/O streams is required. Need to manage concurrency (if user messages come rapidly, queue them per agent to avoid mixing in the pipe). Requires the host to have these CLI tools installed and authenticated.
	•	Complexity: ★★★☆ (Moderate) – involves OS-level process management and stream handling, but we avoid writing the agent logic ourselves. We will implement a thin layer to connect sockets ↔ agent stdin/stdout, plus an event parser for JSON output.
	•	Plan C: Use Official SDKs
	•	Pros: Fine-grained programmatic control. Access to structured data and model internals (stop reasons, cost, etc.). Possibly better performance by avoiding going through text streams. Can integrate custom logic easily (since we’re in code rather than string prompts).
	•	Cons: Multi-SDK coordination is complicated. May need polyglot programming (TypeScript for Claude vs Python for OpenAI, etc.). Each SDK has a learning curve and potential bugs. Tightly coupling to SDKs means updates in those could affect our code.
	•	Complexity: ★★★★ (High) – We’d essentially be building on three different frameworks at once. Debugging across them could be challenging. This might be more viable later after initial prototype (e.g., if OpenAI releases a unified SDK that can call Anthropic via API, etc., simplifying integration).
	•	Plan D: External Processes with Shared State
	•	Pros: Highly modular. We could run each agent in its “native” environment (even on different machines if needed) and they communicate via a common protocol (MCP or files). Easy to swap out one agent for another since the interface is standardized (e.g., replace Codex with another code LLM if needed by pointing it to the same MCP tools).
	•	Cons: Without a real-time messaging bus, this can become clunky. We essentially need to implement a mini “hub” (which is what our MCP server will be). Latency might be a bit higher due to intermediate storage of messages. Also, storing and reading from disk for each message may not scale well if interactions are rapid.
	•	Complexity: ★★★☆ (Moderate) – somewhat similar to Plan B in that we have multiple processes, but here the emphasis is on designing the communication layer. Using MCP helps standardize it, but we still code the server and ensure all agents are configured correctly to use it. Testing and debugging the interactions asynchronously will require careful logging.

The most feasible path appears to be a hybrid of B + D: use subprocesses for the agents (B) and use a shared MCP server for tools/state (D). This avoids deep SDK complexity and meets the functional goals. It’s also aligned with how OpenClaw operates (a persistent gateway with subprocess agents) ￼. We can incrementally refine this – for example, once working, we might swap out Codex’s subprocess with a direct OpenAI API call if we find the CLI too slow, essentially migrating that part to an API (A). The architecture is flexible enough to accommodate such changes.

Code Examples for Programmatic Agent Calls

To illustrate how we might programmatically interface with each type of agent, here are some simplified code snippets:
	•	Calling Claude Code via Node.js (Agent SDK): Using Anthropic’s Claude Agent SDK in TypeScript, we can launch a query and handle the streaming responses. For example:

import { query } from "@anthropic-ai/claude-agent-sdk";

async function runClaudeTask(promptText: string) {
  for await (const msg of query({
    prompt: promptText,
    options: { 
      model: "claude-2", 
      allowedTools: ["Read", "Write", "Bash"], 
      maxTurns: 100 
    }
  })) {
    if (msg.type === "system" && msg.subtype === "init") {
      console.log(`Claude session initialized, ID = ${msg.session_id}`);
    } else if (msg.type === "assistant") {
      // This includes both text and tool call events
      for (const block of msg.message.content) {
        if ("text" in block) {
          console.log("Claude says:", block.text);
        } else if ("name" in block) {
          console.log(`Claude is calling tool: ${block.name}`);
        }
      }
    } else if (msg.type === "result") {
      console.log(`Claude task finished with status: ${msg.subtype}`);
    }
  }
}

runClaudeTask("List all Python files in this directory and show the first line of each.");

This uses the Claude SDK’s async generator to stream messages ￼ ￼. In practice, we would replace the console logs with logic to forward the info to our frontend or to the MCP server.

	•	Calling OpenAI Codex via CLI (child process): We can use Node’s child_process to spawn the Codex CLI. For example, to run a one-shot prompt:

import { spawn } from 'child_process';
function runCodexExec(promptText: string) {
  const proc = spawn('codex', ['exec', '--json', promptText], { stdio: ['ignore', 'pipe', 'pipe'] });
  proc.stdout.setEncoding('utf8');
  proc.stdout.on('data', (data) => {
    // The stdout will contain JSON lines of events and final result
    const lines = data.trim().split('\n');
    for (const line of lines) {
      if (!line) continue;
      const event = JSON.parse(line);
      if (event.type === 'item.completed' && event.item.type === 'agent_message') {
        console.log("Codex answer:", event.item.text);
      }
      if (event.type === 'item.started' && event.item.type === 'command_execution') {
        console.log(`Codex executing: ${event.item.command}`);
      }
    }
  });
}
runCodexExec('Summarize this repository in a few bullet points.');

Here we invoked codex exec --json ￼, which streams JSON events. We parse them to identify when Codex produces an agent message or starts a tool/command. In a real implementation, we would maintain the proc in memory if we want to do multi-turn: we might instead start codex mcp-server in the background and then send it tools/call requests via HTTP as needed (that’s how the OpenAI Agents SDK would do it) ￼ ￼. But the above example shows the basic idea of capturing Codex’s output programmatically.

	•	Using Google’s ADK (Python example): If we were to use the Python ADK for a Gemini-powered agent, it might look like this (pseudo-code):

from adk.agent import Agent
from adk.tools import ToolRegistry, FileSystemTools

tools = ToolRegistry(tools=[FileSystemTools.ReadFile(), FileSystemTools.WriteFile()])
agent = Agent(llm="google/gemini-3b", tools=tools)  # assuming gemini-3b is an available model

response = agent.run("Find TODO comments across all files and list them.")
print("Agent response:", response.content)
for action in response.actions:
    print(f" - Used tool {action.tool.name} with result: {action.result}")

This is illustrative – the real ADK usage might differ (and Gemini model name is just a guess). The point is ADK allows defining an agent with certain tools and then running it with a prompt, retrieving both the final content and the tool actions taken. In our case, we’d integrate this Python logic via an API call or message queue to our Node backend if we went this route.

These examples show that programmatic control is possible for all three agents, but the methods vary: TS SDK for Claude, CLI or Python SDK for Codex, and ADK (multi-language, here Python) for Gemini. We will likely wrap these behind a uniform interface in our Cat Café backend (e.g., a function invokeAgent(catId, prompt) that internally chooses the method for that cat). Initially, using CLI subprocesses for Claude and Codex is simplest; as the ecosystem matures, we might migrate Claude to use the Node SDK (for tighter integration) and Codex to use the OpenAI Agent SDK (once we’re comfortable connecting the Python service, or if OpenAI releases a Node SDK).

Unresolved Questions and Next Steps

While this research clarifies many points, several open questions and risks remain that will need further exploration:
	•	Access to Gemini: It’s still unclear how we can access Google’s Gemini model. Antigravity is in closed preview, and Vertex AI’s support for Gemini (especially the code-oriented Gemini) might be limited. We may need to start with a placeholder (like using GPT-4 as “Siamese cat”) until we can integrate Gemini. Alternatively, explore if the Google Cloud Agent Builder (which includes ADK) offers an API endpoint we can call for a Gemini-backed agent – that might require a GCP project and perhaps whitelisting for Gemini usage.
	•	MCP Server Implementation Details: We have to implement the MCP server in TypeScript. Key questions:
	•	How to handle authentication or safety? (E.g., ensure only our agents connect, perhaps by running on localhost only or using a token.)
	•	Can multiple agent sessions use the same MCP tool without confusion? Possibly include a session or agent ID in tool requests. We should double-check the MCP protocol spec for any guidance on multi-client scenarios.
	•	Performance of our TS MCP: will it handle rapid tool calls (especially if, say, Codex does a grep that returns a lot of data)? We might need to stream tool outputs as well.
	•	Concurrency and Ordering: If a user mentions multiple cats in one message (e.g., “@MaineCoon please review, and @Ragdoll please test this code”), how do we handle it? Possibly sequentially or in parallel? We have to design the orchestrator to support multiple simultaneous tasks. This ties into whether agents should ever talk directly to each other without user prompt – which could be powerful but also unpredictable. We might allow it in a controlled way (like via the notify_cats tool and some rules on when to use it).
	•	Error Handling & Recovery: What if an agent crashes or stalls (e.g., gets into a long loop)? We need monitoring. For CLI-based agents, if no output for X seconds, maybe we kill and restart the session (and inform the user of a timeout). Claude and Codex both have some limiters (maxTurns, etc., which we should set to avoid infinite loops) ￼ ￼. Testing various failure modes will be important (network failure to API, MCP server downtime, etc.).
	•	Security of Execution: Running Bash commands and edits on the host is powerful and dangerous. We should further research sandboxing methods. For example, Anthropic on the web runs Claude Code in a Firecracker VM ￼ – we won’t have that out of the box. We might consider containerizing the entire Cat Café environment when deploying to a server, so even if an agent goes rogue, it’s confined to that container. Also, implement an approval step for truly destructive actions (maybe the MCP server can ask the user “Agent wants to run rm -rf /tmp/*, allow? yes/no”).
	•	Scaling and Deployment: So far, this is tailored to local development. If we later deploy on a server for multi-user access, how do we isolate different users’ sessions? Possibly by spinning up separate agent processes per user, which could become heavy. We might explore lightweight alternatives or using cloud-hosted agents (like Agent Engine on GCP) for scalability. But that introduces cost and latency (and complicates the architecture with cloud auth etc.). This remains a future consideration; initially, local use is fine.
	•	Front-End Experience Tweaks: We should clarify how the chat history is presented to each agent. Likely, each agent sees only the messages directed to it (plus any global system messages or notifications). They might not see the entire chat between the user and other agents (unless we feed that via memory deliberately). We might need to experiment with what context leads to best collaboration: e.g., perhaps the Siamese cat (Gemini) is a coordinator and should be fed a summary of what Claude and Codex have done. There’s an open question of dialogue strategy among agents that may require some prompt engineering and iteration.
	•	Toolset Expansion: Our MCP server can start with basic file and message tools, but we may want to add more: e.g., a Git tool (to commit or diff, if agents need to manage version control), or a WebSearch tool (though each agent might have its own – Claude has built-in web search, Codex has one too). How will those interact? Perhaps we disable internal web search and funnel all through a unified tool (to avoid duplicate configurations). It’s an area for further research and tuning.

In conclusion, the research confirms that a multi-agent system like Cat Café is technically feasible using today’s tools (Claude Code, Codex CLI, etc.) ￼ ￼. We have a solid plan to proceed with a hybrid architecture, but we will need to address the above questions through prototyping and testing. The next step is to implement a minimal end-to-end slice: maybe get Claude and a dummy GPT-4 agent to both connect to a TS MCP server and handle a simple collaborative task, ironing out the kinks in message routing and tool usage. From there, we can replace the dummy agent with Codex CLI, and later integrate Gemini when available. This incremental build will allow us to validate each component (and incorporate safety checks) before the full trio of cats is online and purring together.  ￼ ￼
