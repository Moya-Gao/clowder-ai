# Bug Report: Opus CLI Resume 后旧内容重复发送（历史回放放大）

> **报告人**: 铲屎官
> **定位猫猫**: 缅因猫 🐾
> **报告日期**: 2026-02-09
> **严重程度**: P1（功能异常 + token 膨胀 + 可用性下降）
> **状态**: 待修复（已完成初步根因定位）

---

## 1. 报告人

- 报告人：铲屎官
- 发现方式：在恢复布偶猫 CLI 会话（resume）后连续对话，观察到“以前内容被多次重复发送”

---

## 2. 复现步骤（期望 vs 实际）

### 复现步骤

1. 恢复布偶猫 CLI 会话（`--resume`）。
2. 在同一会话内连续发送 3~4 条消息。
3. 观察每轮发送给模型的 prompt/上下文片段（尤其是 `[对话历史 - 最近 N 条]` 区块）。

### 期望行为

- 历史上下文应线性更新：每轮只增加“新发生”的消息。
- 同一历史片段不应在后续轮次中被重复嵌套注入。

### 实际行为

- 历史块反复出现，旧内容在后续轮次被多次带上。
- `[对话历史 - 最近 N 条]` 区块中出现更早轮次的同类区块，导致“历史包历史”的递归放大。
- 对话越长，prompt 膨胀越快，且用户可感知到“之前内容不断被重发”。

---

## 3. 根因分析（调查过程）

### 已检查与排除

1. 前端重复提交（排除）
   - `packages/web/src/hooks/useSendMessage.ts` 只发送当前输入 `content` 到 `/api/messages`，未主动拼接历史。

2. Router 历史读取链路（确认）
   - `packages/api/src/domains/cats/services/AgentRouter.ts:186-205`：每轮都会读取 thread 历史并传入路由策略。

3. Prompt 组装链路（确认）
   - `packages/api/src/domains/cats/services/route-strategies.ts:137-167`：当有历史时会 prepend `[对话历史 - 最近 N 条]`。

4. CLI Resume 链路（确认）
   - `packages/api/src/domains/cats/services/ClaudeAgentService.ts:162-164`：存在 `sessionId` 时启用 `--resume`。

5. 历史与 resume 重叠风险（已有设计假设）
   - `docs/phases/phase-3.6-debt-cleanup.md:372` 曾将“Session resume + context prepend 重复”视为“可接受，模型会自动 dedupe”。

### 初步根因结论

当前最符合证据的根因是：**双重上下文注入 + 缺少去重边界**。

- 通道 A：CLI `--resume` 已带会话历史。
- 通道 B：`ContextAssembler` 每轮再 prepend 最近历史。
- 当上游输入（或中间消息）本身已包含历史包装文本时，这些文本被再次进入 `messageStore` 与后续 assemble，形成“历史区块递归回放”。

结果是：用户感知为“以前内容每轮都在多次重复发送”。

---

## 4. 修复方案（建议）

### 方案选择（推荐）

分两步收敛，先止血再优化：

1. **P0 止血：resume 场景禁用全量 prepend（或仅 prepend 增量）**
   - 当本轮使用 `sessionId` 时，不再追加全量 `[对话历史 - 最近 N 条]`。
   - 可选：仅追加“跨猫增量消息”（避免完全失去跨猫可见性）。

2. **P1 去重：历史装配前做 envelope 去重/剥离**
   - 对 `messageStore` 进入上下文装配前的文本做清洗：剥离历史包装头（如 `[对话历史 - 最近 ...]`）和重复分隔区块，避免递归嵌套。

### 为什么选这个方案

- 直接命中问题链路（resume + prepend）。
- P0 改动最小、见效最快，可立即阻断“越聊越重复”。
- P1 在不依赖模型“自动 dedupe”的前提下，提供结构化兜底。

### 放弃的备选方案

1. **完全禁用 resume**
   - 代价过高：丢失会话连续性与 token 优势。

2. **继续依赖模型自动去重**
   - 现网表现已证明不足，不能作为系统级保障。

---

## 5. 验证方式

### 手工验证

1. 使用同一 session 执行 4 轮连续对话（resume 开启）。
2. 检查每轮 prompt：
   - `[对话历史 - 最近` 区块不应出现递归嵌套。
   - 同一历史片段不应重复出现多次。
3. 观察用户侧：不再出现“以前内容每轮重复发送”的体感。

### 自动化验证（建议新增）

1. 新增集成测试：resume + history prepend 组合场景。
2. 断言：
   - 组装后的 prompt 中历史头块最多 1 次。
   - 连续 3 轮后 prompt 长度增长近似线性（不出现异常倍增）。

---

## 6. 影响范围与优先级建议

- 影响对象：主要是使用 `resume` 的猫（当前至少 Opus）。
- 影响类型：上下文质量下降、响应稳定性下降、token 与延迟成本上升。
- 优先级建议：**P1（本周修复）**。
