# Bug Report: Thread 切换/F5 后流式可见性丢失

## 1. 报告人
- 报告人：铲屎官（2026-02-18）
- 发现方式：真实使用中，thread1 正在流式输出时切到 thread2 或 F5，thread1 中途输出“看不到”；待 thread1 结束后再刷新才看到最终落库内容。

## 2. 复现步骤
1. 在 `thread-1` 发起一次会触发较长流式输出的请求（例如布偶猫长回复）。
2. 在输出过程中切换到 `thread-2`，并执行页面刷新（F5）。
3. 观察 `thread-1` 的中途流式输出。

期望行为：
- 即使切线程 + F5，仍能持续接收并缓存 `thread-1` 的流式事件（至少保持后台线程可见/未读可追踪）。

实际行为：
- F5 之后只订阅当前路由线程房间，`thread-1` 的后续流式事件不再到达前端。
- `thread-1` 最终完成后，由于消息落库，后续通过历史接口刷新时可见最终结果。

## 3. 根因分析
- 前端 `useSocket` 使用内存 `joinedRoomsRef` 管理已加入 room。
- 页面刷新会重建 hook，`joinedRoomsRef` 归零；重连时仅保证“当前 active thread”房间被加入。
- 因此刷新后对先前线程（如 `thread-1`）的 room 订阅丢失，导致该线程流式事件不可见。
- 现有日志（如 `[ws] joined room`）不足以直接看出“刷新前后的 room 集合差异”，降低排障效率。

## 4. 修复方案
- 方案：将 `joinedRoomsRef` 持久化到 `sessionStorage`（仅同标签页生命周期），在 socket 连接时恢复并重加房间。
- 同时增加 room 同步日志（恢复数量、实际重加列表、非法持久化数据）提升可观测性。

为什么选它：
- 最小改动即可覆盖“切线程后 F5 丢订阅”主路径，不需要新增后端接口。

放弃方案：
- 新增后端“active invocation thread 列表”接口并在前端重连拉取。该方案更重、改面更大，可作为后续增强。

## 5. 验证方式
- 单测（Red→Green）：
  - 新增 `useSocket` 测试，验证“刷新后 connect 会重加持久化 room”。
- 回归：
  - 运行 web 相关 hook 测试，确保线程守卫与背景路由逻辑不回退。
- 手工：
  - 重复“thread1 输出中切到 thread2 + F5”场景，确认 thread1 后续事件可持续进入前端状态。
