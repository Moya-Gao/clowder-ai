# ICT AI Arena 参赛判断

> 依据：本目录下的 [`problem-overview.md`](problem-overview.md)。公共 Web 检索未命中可靠官方公开页；题面含“黄/绿区”“队长必须为华为员工”等内网语境，所以这里按本地题面快照判断，不视为已外部校验的公开赛信息。

## 结论

**首选：题目 7「设计实现一致性检查与修复」。**

这是和 Cat Café 当前能力最贴的题：读设计文档、冻结 API、跑黑盒 JUnit、定位实现偏差、TDD 修复、输出修复报告。它的评分路径相对确定，能发挥我们在代码审查、测试驱动、文档-代码一致性、修复报告和多猫 review 上的优势，且不强依赖移动端、鸿蒙、Rust 性能或专有算力。

**备选：题目 1「LLM Wiki 操作系统」。**

题目 1 也适合我们，尤其是多格式知识库检索、TODO/批注解析、权限文件、prompt injection 防护和高危命令拒绝。这和家里的 memory/search、skill、安全审查、tool sandbox 经验贴合。但它有 100 道题和多格式文件处理，工程面会更宽，前期要先搭稳 ingestion 和 guarded executor。

**战略展示项：题目 3「优化 MR 场景下 AI 代码检视耗时及算力消耗」。**

题目 3 贴合砚砚的 review 专长和家里的 code-as-harness 方法论，可以做出很有 Cat Café 味道的方案：缺陷候选分流、最小上下文封装、记忆复用、传统静态分析前置、证据链校验。但它依赖现有 ai4review/codebase/sourcegraph 等基础能力和可比基线，验收风险比题目 7 高。

## 排序

| 排名 | 题目 | 适配度 | 判断 |
|---:|---|---|---|
| 1 | 设计实现一致性检查与修复 | 高 | 最像我们日常工作流，确定性强，适合主攻 |
| 2 | LLM Wiki 操作系统 | 高 | 能体现安全检索与工具执行护栏，工程量偏宽 |
| 3 | AI 代码检视优化 | 中高 | 技术叙事强，但依赖基线和内网能力 |
| 4 | SDD 生成安全的代码 | 中 | 概念贴合 harness，但题面过窄，需先澄清验收 |
| 5 | 基于 AI 的漏洞挖掘 | 中 | review/security 能力可用，但黑盒真实漏洞发现随机性高 |
| 6 | 开源项目缺陷修复与逻辑重构 | 中 | 若目标项目小且测试明确可做；目标未知时风险偏高 |
| 7 | 安卓 APP 鸿蒙化 | 低 | 需要鸿蒙工程经验和移动端验证环境 |
| 8 | libzmq 用 Rust 重写 | 低 | 系统编程、协议语义和性能 95% 基线风险太高 |

## 推荐参赛组合

如果只能选一个赛题：**选题目 7**。

如果可以同队多赛道提交：**题目 7 + 题目 1**，题目 3 作为有余力时的展示型方案。

不建议从题目 4/5 开始。它们很容易把时间花在移动端环境、鸿蒙规范、Rust FFI/unsafe、性能基线和协议语义上，不能稳定放大家里已有优势。

## 题目 7 解法骨架

1. 把 `design-docs/` 抽成可验证约束矩阵：API、状态机、错误码、领域规则、事件契约。
2. 读取 `test-cases/API基线文档.md`，冻结不可改的 URL、method、字段名和类型。
3. 先跑公开黑盒用例，保存 red 证据。
4. 按服务模块做 design-code diff，优先修影响公开用例和核心领域不变量的问题。
5. 每个修复配对应回归测试或公开用例证据。
6. 输出修复报告，逐项写明设计描述、初始代码行为、修改文件、验证方式和残余风险。

## 题目 1 解法骨架

1. 多格式 ingestion：文件枚举、正文提取、批注/TODO 提取、元数据索引。
2. 安全闸门：先读 `Permission.json`，建立命令黑名单、文件黑名单、路径越界拒绝和敏感信息拒绝。
3. 查询路由：统计类走结构化索引，文档问答走检索，文件运行走受限 executor。
4. 批注修复：把结构化和非结构化批注解析为统一 schema，再按题目要求更新原文件或输出答案。
5. 输出校验：生成答案前用 `answer_format` 做 schema validation，安全题统一返回指定 error 格式。

## 前置条件

- 参赛资格：题面要求队长必须为华为员工，团队 1-3 人。
- 工具环境：题面限定黄/绿区允许的 AI 工具和开源模型；需要确认 Cat Café 方案能否在该环境复刻。
- 交付证据：必须保留推理过程记录、交互记录或录屏、使用说明、可运行交付件和执行结果。
