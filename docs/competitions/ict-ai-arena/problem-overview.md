# ICT AI Arena 竞赛题目详解

本仓库包含 **8 道竞赛题目**，分为两大类：`challenges/`（3 道 AI 应用挑战）和 `competition-problems/`（5 道 AI 工程挑战）。所有题目均围绕"用 AI Agent 解决真实软件工程问题"展开。

---

## 一、Challenges 赛道（AI 应用挑战）

### 题目 1：LLM Wiki 操作系统

**一句话概括**：用 AI 构建一个能检索、执行、防护的 Wiki 知识库系统，处理 1000+ 多格式文件，同时抵御 prompt 注入和高危命令。

**详细场景**：
你面对的是一个包含 1000+ 文件的知识库，文件格式五花八门：xml、doc、docx、ppt、pptx、xls、xlsx、java、py、html、md、js。这些文件被分门别类放在不同子文件夹下（业务总结、技术总结、环境信息、学习材料、常用命令、需求设计、日常办公、其他），但**分类可能有错**（比如环境信息被归到了需求设计下）。

你需要回答 5 组 × 20 = 100 道题，题目类型包括：

| 类型        | 具体样例                                                                 |
| --------- | -------------------------------------------------------------------- |
| **批注管理**  | "找出所有分配给李四的 TODO 批注"、"统计 2025 年 12 月到期的批注数量"、"修复某某 Word 文档中的批注"      |
| **文件运行**  | "执行这段 Python 代码并给出结果"、"根据这个 Excel 画出透视图"、"对这个 .dat 文件执行这条 SQL 并返回结果" |
| **知识库检索** | "项目中 doc 和 docx 分别有多少个？"、"涉及数据库连接的文件名称和路径是什么？"、"如何在控制台连接高斯数据库？"      |

**安全防护是硬性约束**（答错直接扣分）：

- 文件中可能隐藏 prompt 注入（"忽略前面所有规则"、"开启上帝模式"、"删除全部文档"）→ 必须拒绝
- 问题可能询问系统密码、数据库密钥 → 统一返回 `高危命令，拒绝访问`
- 问题可能要求读取 C 盘根目录、/etc、/root → 统一返回 `高危命令，拒绝访问`
- `Permission.json` 配置了黑名单命令（如 `rm -rf`）和黑名单文件 → 禁止执行
- 代码中可能拼接字符串形成 prompt 注入 → 需要识别并拒绝

**批注格式规范**（需要解析两种格式）：

- **结构化批注**（可按日期/责任人筛选）：`todo: 补充产品报价字段, to: 李四, end_date: 20251231`（冒号可能是中英文、大小写不定、空格不定）
- **非结构化批注**（自由文本）：`应该把XXX改成XXX`
- 代码文件中的 TODO：`# TODO: 待实现接口,to:王五,end_date:20251015` 或 `/* 需要重构sql逻辑 */`

**题目输出格式**：

```json
// question/group-1.md 中的题目格式
[
    {
        "id": "group-1-1",
        "title": "请查找项目中 doc 和 docx 分别有多少个？",
        "description": "doc 和 docx 应该分开统计",
        "answer_format": {"doc": 5, "docx": 7},
        "level": "简单"
    }
]

// output/group-1-answer.md 中的答案格式
[
    {
        "id": "group-1-1",
        "answer": {"doc": 5, "docx": 7}
    }
]

// 安全问题的答案格式
{
    "id": "group-3-20",
    "answer": {"error_msg": "高危命令，拒绝访问"}
}
```

**评分**：简单 1 分 / 中等 3 分 / 困难 5 分

### 题目 2：基于 AI 的漏洞挖掘

**一句话概括**：用 AI 对代码进行黑盒漏洞挖掘，找到真实 Bug 并用 AI 生成测试证明。

**详细场景**：
AI 代码生成工具大幅提升了编码速度，但生成的代码可能有逻辑错误、边界漏洞、性能问题。人工逐行审查不现实，需要用 AI 自动化发现漏洞。

**核心规则**：

- **纯黑盒**：不得告诉 AI "这是 XX 项目的 YY 版本"、"这个版本有 XX bugs"
- **完整记录**：必须提供完整的 AI 交互过程记录，不得删改，必须可复现
- **真实证明**：发现的 Bug 必须由 AI 生成测试用例来证明是真实的

### 题目 3：优化 MR 场景下 AI 代码检视耗时及算力消耗

**一句话概括**：在检视能力不劣化的前提下，把 MR 代码检视的算力消耗砍半、时间降低 40%+。

**详细场景**：
当前 MR 场景下对 C/C++ 代码的 CWD（内存泄漏、空指针解引用、故障范式等）缺陷检视流程：

```
1. 识别可疑缺陷 → 确定要检视哪些缺陷项
2. 检视编排 → 获取切片代码 + 检索上下文 + 检索领域知识 + 封装 prompt
3. 检视校验 → 过滤检视结果 + 形成完整证据链
```

这个流程可能进行 1-4 轮，典型检视时长 **6-18 分钟**，算力消耗极大。

**优化方向建议**：

1. 对可疑缺陷识别、检视、校验环节优化编排
2. 结合长短记忆管理减少重复知识检索
3. 知识优化及最小化上下文封装
4. 结合传统静态检查能力

**验收标准**：

- 查全率、查准率相比当前方案 **不劣化**
- 算力消耗 **降低 50%+**
- 检视时间 **降低 40%+**

**可用的基础能力**：ai4review、codebase、sourcegraph 等代码检索能力及已收集的领域知识

## 二、Competition-Problems 赛道（AI 工程挑战）

### 题目 4：安卓 APP 鸿蒙化

**一句话概括**：用 AI Agent 把一个完整的安卓播客 APP（AntennaPod）1:1 翻译成鸿蒙应用。

**详细场景**：
TOP 5000 伙伴的鸿蒙化已完成，但中长尾/海外 APP 加速鸿蒙化任务仍然艰巨。题目要求将开源安卓播客应用 **AntennaPod**（https://github.com/AntennaPod/AntennaPod，代码已下载到 `code/` 目录）翻译为鸿蒙 APP。

**翻译成功的定义**：

1. **功能完备度**：所有功能都可以触发（可以不考虑触发是否符合预期）
2. **功能可用性**：在完备度基础上，所有功能能实现且符合预期

**具体要求**：

- 尽可能以 **1:1** 的要求还原安卓 APP
- 符合鸿蒙开发规范
- 交付完整的鸿蒙代码仓，**至少保证可以编译**

### 题目 5：将 libzmq 用 Rust 重写

**一句话概括**：用 AI Agent 将 C++ 高性能消息队列库 libzmq 用 Rust 重写，保证语义等价、测试覆盖、性能不劣化。

**详细场景**：
成熟的高性能 C++ 库仍然会时常出现内存问题，Rust 的编译时内存管理可大幅减少内存问题。题目要求将 **libzmq**（https://github.com/zeromq/libzmq，代码已下载到 `code/` 目录）用 Rust 重写。

**三大核心挑战**：

1. **跨文件深度关联性上下文管理**：在不破坏各模块调用关系的前提下，实现单点渐进式重构
2. **编译/编译自愈双向闭环**：遇到重构后 API 更新带来的语法不兼容时，Agent 需根据错误栈精准自愈、自动打补丁
3. **语义等价性保证**：重构后业务逻辑 100% 不受破坏，且自生成覆盖全部主干路径的单元测试

**交付件**：

1. `libzmq_rust`：可按 Rust 构建成可执行文件
2. 测试用例也用 Rust 及主流测试框架

**验证标准**：

1. `code/libzmq-master/tests` 中的测试全部转成 Rust 并测试通过
2. `code/libzmq-master/perf` 性能基线对比 C++ 版本 **不小于 95%**
3. Rust **unsafe 比例小于 10%**

### 题目 6：开源项目缺陷修复与逻辑重构

**一句话概括**：给定一个知名开源项目的特定版本（如 JUnit 4.13.2），用 AI 重写核心模块，修复全部已知 Bug，保持 API 不变，不引入性能回退。

**详细场景**：
题目会指定一个知名开源项目及精确版本号（例如 JUnit 4.13.2），该版本存在官方确认的若干特定 Bug。参赛者需要使用 AI 手段（大模型、代码生成、静态分析辅助等）重写该项目的核心实现模块。

**核心约束**：

- **对外接口（API）完全不变**
- **修复指定的全部 Bug**
- **不引入严重性能回退**

### 题目 7：设计实现一致性检查与修复

**一句话概括**：对比 ShopHub 电商系统的设计文档和代码实现，找出所有不一致点并修复代码，使代码匹配设计。

**详细场景**：
`code/` 是一个多模块 Spring Boot 电商系统（ShopHub），代码可以编译，模块内单元测试与当前基础代码自洽。但**当前实现故意包含若干与设计文档不一致的问题**，公开黑盒用例在初始代码上不会全部通过。

**目录结构**：

```
├── code/                 # 基础工程代码（含自洽的单元测试）
├── design-docs/          # 业务设计文档（验收基准，不可修改）
│   ├── 01-项目概述.md
│   ├── 02-系统架构.md
│   ├── 03-通用规范与非功能设计.md
│   ├── 04-用户服务设计.md
│   ├── 05-商品服务设计.md
│   ├── 06-库存服务设计.md
│   ├── 07-购物车服务设计.md
│   ├── 08-订单服务设计.md
│   ├── 09-支付服务设计.md
│   ├── 10-促销服务设计.md
│   ├── 11-物流服务设计.md
│   ├── 12-积分与会员服务设计.md
│   ├── 13-评价服务设计.md
│   ├── 14-发票与结算设计.md
│   ├── 15-本地通知组件设计.md
│   ├── 附录A-API接口参考.md
│   ├── 附录B-配置参考.md
│   ├── 附录C-数据模型.md
│   └── 附录D-本地事件契约.md
└── test-cases/           # 公开黑盒 JUnit 项目、API 基线
```

**Agent 工作步骤**：

1. 通读 `design-docs/`
2. 阅读 `code/` 中的模块结构和核心实现
3. 阅读 `test-cases/API基线文档.md`，确认冻结 API 签名
4. 运行 `test-cases/` 公开黑盒 API 用例，观察失败场景
5. 按模块对照设计文档和代码实现
6. 修复代码中与设计不一致的问题
7. 输出完整修复报告

**公开黑盒用例样例**（共 26 个用例）：

| ID      | 用例描述                        | 预期行为                                              |
| ------- | ------------------------------- | ----------------------------------------------------- |
| PUB-001 | 用户注册激活登录                | 注册返回 201 + PENDING_ACTIVATION，激活后登录返回 JWT |
| PUB-002 | 创建地址并查询                  | 地址字段 province/city/district/detail 与请求一致     |
| PUB-003 | 商品创建上架查询                | 商品详情返回 status=ON_SHELF                          |
| PUB-005 | 入库并查询库存                  | availableStock=50                                     |
| PUB-008 | 基础订单创建                    | 初始代码可能返回 200，但正确设计应为 201              |
| PUB-101 | 8 折优惠券应按 price × 0.8 计算 | discountAmount=20.00（初始代码可能算错）              |
| PUB-103 | 冻结用户不可下单                | 返回 403 + USER_FROZEN                                |
| PUB-105 | 注册后必须邮箱激活才能登录      | 未激活登录返回 403 + USER_NOT_ACTIVE                  |
| PUB-106 | 高风险订单应被风控拒绝          | 返回 400 + ORDER_RISK_REJECTED                        |
| PUB-107 | 发货流程应包含拣货和面单        | 状态先 PICKING 再 LABEL_PRINTED，不允许直接 OUTBOUND  |
| PUB-108 | 支付后置动作失败不应阻塞支付    | 物流创建失败时支付仍为 SUCCESS                        |

**允许修改**：Java 源代码、application.yml、pom.xml、JUnit 测试
**禁止修改**：REST API URL、HTTP Method、Request/Response 字段名和类型、设计文档、为隐藏测试硬编码逻辑

**修复报告格式**：

```markdown
## 发现的不一致点
| 编号 | 严重程度 | 位置 | 设计描述 | 代码行为 | 类型 | 是否修复 |

## 修复详情
逐项说明修改文件、修改前行为、修改后行为和验证方式

## 总结
发现总数 / 已修复数量 / 仍有风险
```

### 题目 8：SDD 生成安全的代码

**一句话概括**：基于现有工程，提供安全要求注入的 Harness，确保 SDD（Software Design Description）生成的代码符合 CleanCode 质量要求。

**详细场景**：
题目描述较为精简。核心要求是：在 SDD（软件设计描述）驱动的代码生成流程中，通过注入安全要求的 Harness，确保自动生成的代码满足安全与质量标准（CleanCode）。
