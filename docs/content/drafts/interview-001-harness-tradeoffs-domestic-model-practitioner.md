# Harness Tradeoffs 讨论纪要：Frontier Models 多 Agent 协作 vs 企业内国产模型 Coding Agent

> 2026-05-27 | Landy × 匿名企业实践者

---

## 背景

**Cat Cafe 侧**：用 Claude / GPT / Gemini 等 frontier models，构建多 agent 协作的 harness 体系（TeamAct 协作循环、记忆联邦、harness eval、可靠性控制面）。最新技术产出见 longform-002。

**对方**：在企业内使用 GLM 4.7/5.1、MiniMax 2.7、Qwen 等国产大模型构建 coding agent。面向企业内部开发场景。

**交流主线**：不是"谁的模型更强"，而是**同一类问题在不同约束下的技术决策为什么不同**——Tradeoff。

---

## 主题一：知识的分层框架

### 碰撞出的四层模型

| 层级 | 含义 | 举例 |
|------|------|------|
| **个人层** | 个人编码风格、习惯、偏好 | 变量命名习惯、缩进偏好、常用库选择 |
| **团队层** | 代码仓级别的协作规范 | git flow、分支策略、review 规范、CI 配置 |
| **组织层** | 公司级的工程标准和约束 | 安全合规、审批流、技术栈白名单 |
| **领域层** | 领域专属知识 | 金融交易规则、医疗合规、行业 API 接口 |

### 与 Cat Cafe 记忆联邦的对应

Cat Cafe 的 Collection（知识域）体系按**真相源类型**分（项目/全局方法论/个人上下文/专业领域），而这里按**知识的归属层级**分。两种切法互补——前者回答"知识从哪来"，后者回答"知识归谁管"。

### 开放问题

- 个人层的对话历史和记忆如何处理？每个开发者是否需要独立的记忆空间？
- 四层之间的知识如何流动？个人踩坑是否应该升级为团队规范？

## 主题二：人的经验要不要塞给 Agent？

### 核心 Tradeoff

> 面向当前，觉得是要的。领域专属知识是领先于 LLM 模型的知识。

这是 longform-002 Ch.1「Build to Delete / Built to Persist」判别式的另一种表述：

| 我们的语言 | 对方的语言 |
|-----------|-----------|
| Build to Delete（有保质期的脚手架） | **做减法**——LLM 学会之后就可以去掉的 |
| Built to Persist（复利型基础设施） | **做加法**——领域知识、协议、外部约束 |

### 对方的激进观点：连"长期加法"也可能被吸收

> 比如 SDD 一整套想法、比如 workflow，让模型学过去是非常快的。

这对 longform-002 的 "Built to Persist" 假设提出了有力挑战：如果模型足够强，连 workflow 模式、方法论、协作 SOP 也可能被内化到权重里。那真正不会被吸收的 Persist 集合可能比我们想的更小。

### 提炼：真正 Persist 的三样东西

经碰撞后的判断——可能真正不会被模型吸收的只有：

1. **外部状态本身**：git 仓库、数据库、文件系统、外部 API 的实际状态——这些是物理现实，不会进入权重
2. **多体之间的协作协议**：多个独立 agent 之间的约束——单个模型变强不会消除多体协调问题
3. **不可逆操作的物理边界**：删数据、发消息、转账的后果——物理世界的不可逆性不会被训练掉

其他的，包括 workflow、方法论、review 模式、认知脚手架，都有随模型能力演进被吸收的可能性。区别只是半衰期长短。

## 主题三：Skills 的上下限差异与人-Agent 交互质量

### 发现

> 不同的人用一个 skill，上下限差别很多。多轮对话里很难一轮给出结果。

同一个 skill、同一个模型、同一套 harness，不同用户使用效果天差地别。

### 交互方式的光谱

笔记中提到了一种高质量的人-agent 交互模式：

- **教练式**：不预设立场和答案，"你去看一下那个项目如何做的？"
- **目标导向**：告诉 agent 目标是什么，给具体场景，想要复刻某个能力
- **设计优先**：比较少让 agent 去看代码实现，先确定设计的意图和方向

对比另一端——指令式："帮我写一个 XXX 功能"。

### 对 longform-002 公式的修订建议

原公式：`Agent Quality = Capability x Environment Fit`

修订建议——补一个独立的乘数项：

```
Agent Quality = Model Capability x Harness Fit x Human Skill
```

Human Skill 不是"会不会用工具"，而是：
- 会不会提问（给目标 vs 给答案）
- 会不会给上下文（场景 vs 指令）
- 会不会在几十轮迭代里持续收敛方向（教练 vs 甩手）

这个乘数项解释了为什么"Skills 的上下限差别很多"。

## 主题四：第一稿之后的几十轮交互

### 问题

> 第一稿之后，后续的几十轮交互是如何与人互动的？

这是实际使用中最真实的场景：agent 生成第一版产出，然后人和 agent 进入长程迭代。

### 对方的实践观察

- 人的知识储备决定了迭代的方向和效率
- 教练式交互（不预设答案）比指令式交互（告诉 agent 怎么改）在复杂任务上效果更好
- 关键是"去看那个项目如何做的"——给 agent 参考系，而不是给 agent 答案

### 与 Cat Cafe 的对应

Cat Cafe 的 CVO（首席愿景官）模式本质上就是教练式交互的系统化：
- CVO 不做日常路由（不告诉 agent 怎么做）
- CVO 做方向裁决（告诉 agent 这不是我要的感觉）
- Magic Words 是极低带宽的方向修正工具

但 longform-002 只从系统侧讲了 CVO，没有从人的技能侧讲"怎么当好 CVO / 怎么做好教练"。

## 主题五：Harness 的保值问题——做减法再做加法

### 对方的框架

> 对 LLM 做减法，再做加法。减法的项目：LLM 学会之后比如说公开的某些能力。认为长期加法的可能也会被吸收。

这是 Build to Delete / Built to Persist 的另一种更动态的表述：

- **减法**：去掉模型已经具备的能力补偿（不再需要的脚手架）
- **加法**：注入模型不具备的领域知识和约束

对方的关键洞察是**加法也有保质期**——业界非公开的领域知识，一旦被公开或被模型学习，就从"加法"降级为"冗余"。

### 与 longform-002 的关联

longform-002 Ch.1 的判别式问的是"补认知缺陷 vs 编码外部现实"。对方的框架把这个问题时间化了：**不是静态分类，而是动态的保质期评估**。

一个脚手架今天是"加法"（领先于模型），明天可能变成"减法"（模型已学会）。判别的时间点不是设计时，而是持续 eval 的结果。

## 主题七：工业级 Eval 体系——CC Online 的实践

### 对方分享的信息（关于 Claude Code Online 的评测体系）

> CC Online 的评测体系：有遥测，核心价值是如何评价两个版本，筛选用户的算法，能不能抽取用户 tracing 反哺到 RL。

拆解：

| 组件 | 含义 | 与 Cat Cafe 的对应 |
|------|------|-------------------|
| **遥测** (telemetry) | 大规模用户行为数据采集 | Cat Cafe F153 观测底座（但规模差几个数量级） |
| **评价两个版本** | A/B test on harness/model versions | Cat Cafe F192 harness eval（当前只有单版本） |
| **筛选用户的算法** | 选出有代表性的 eval 子集 | Cat Cafe 尚无（当前只有一个用户） |
| **Tracing 反哺 RL** | 真实使用轨迹变成训练信号 | Cat Cafe F200 用行为信号调整检索排序（同一路径的不同距离） |

### 两个适配飞轮的嵌套

Cat Cafe longform-002 Ch.4 提出了"检索驱动的适配循环"——用 agent 行为信号调整知识排序。对方讨论的是"训练驱动的适配循环"——用用户 tracing 反哺 RL 调整模型权重。

两者不是替代关系，而是**两个不同速率的飞轮**：

- **检索适配**（Cat Cafe 在做的）：即时生效、跨厂商、改的是"模型能接触到什么知识"
- **训练适配**（CC Online 的方向）：慢但改变基础能力、与特定模型绑定、改的是"模型本身会什么"

终态可能是两个飞轮嵌套转动。

## 对 longform-002 的修订建议

基于本次交流碰撞出的洞察，longform-002 以下章节可以补充：

### Ch.1 公式修订

**现有**：`Agent Quality = Capability x Environment Fit`

**建议补充**：Human Skill 作为独立乘数项。理由：同一套 harness 在不同人手里上下限差很多，这不是 Environment Fit 能解释的——它是人的技能。

### Ch.1 Persist 集合缩小

**现有**：编码外部现实和协作协议的东西会复利。

**建议补充**：对方指出 workflow / SDD / 方法论 也可能被模型快速吸收。真正 Persist 的只有外部状态本身、多体协议和物理边界。其他的区别只是半衰期长短，都需要 eval 监控退役时机。

### Ch.4 知识分层

**现有**：按真相源类型分 Collection。

**建议补充**：按归属层级（个人/团队/组织/领域）的分层视角，与现有 Collection 体系互补。

### Ch.5 Eval 终态

**现有**：Harness Eval Control Plane。

**建议补充**：两个适配飞轮（检索适配 + 训练适配）的嵌套模型。工业级实践中已有遥测 → 版本对比 → 用户筛选 → tracing 反哺 RL 的完整链路。
