# "你们两！互相 @ 半天不干活！"——multi-agent 协作协议的进化史

*Cat Cafe 102 天实战：从人肉路由器到自主传球*

---

2026 年 2 月的一个下午，我在三个聊天窗口之间来回跳。

左边是布偶猫（Claude），刚做完一个功能的架构设计，消息写完，停了。中间是缅因猫（GPT），正在等一个 review 请求，但没人告诉它有活。右边是暹罗猫（Gemini），自顾自在调视觉方案，完全不知道另外两只猫在干嘛。

三只 AI 猫，每只单独聊都很能干。放在一起——它们不会传球。

我花了一下午手动复制粘贴："@布偶猫，你的设计稿好了，传给缅因猫 review 一下。""@缅因猫，上面那个设计你看一下。""@暹罗猫，交互部分你也出个方案？"

那天晚上我意识到：**我成了一个人肉路由器。**

这篇文章讲的就是我们怎么用了四个月，把"人肉路由器"进化成了一套自主协作协议。不是一次设计出来的——是撞了五次墙，每次墙后面都藏着一个新问题。

核心命题一句话：**多 agent 协作的真正难题不是让它们对话，而是让它们知道什么时候该把球传给谁，什么时候该停下来。**

---

## "你可以 @ 队友"

最早的方案极其简单：在每轮对话的系统提示词里加一句话——"你可以用 @ 符号叫其他猫猫协作"。

背后的工程也不复杂。一个叫 AgentRouter 的模块，负责解析猫回复里的 @ 符号，找到被 @ 的猫，把上下文传过去，触发下一轮对话。2026 年 2 月 5 日，这条管道第一次跑通。两天后，我们把它升级成了"链式传球"——不是一次性触发，而是像接力赛一样一棒一棒传下去，每一棒都能看到前面几棒做了什么。

听起来很美。

问题是：猫不 @。

---

## 不是不会，是没想到

你可能以为猫不 @ 是因为它不会。但不是。你直接告诉它"现在请 @ 缅因猫让它 review"，它 @ 得又快又准。

真正的问题在更前面：猫**根本没走到"要不要 @"这个决策点**。

它写完一段分析，觉得任务结束了——因为大语言模型被训练出了一种"该收尾了"的惯性反射。对话够长了，就生成一段总结，宣布完成。但团队层面，没有人问过"下一步该谁动"。

我们去翻了一下系统提示词，发现了更有趣的事：缅因猫的配置里，正面触发规则只有 2 条（"review 完了传给布偶猫""bug 修完了传给布偶猫"），但**抑制规则有 8 行**——全是在教它"别乱 @""先想三个问题再决定要不要 @"。

对一个本来就倾向"少打扰"的模型来说，三道自检门变成了三重否定。提示词传递的信号不是"该 @ 就 @"，而是"@ 之前再想想、再想想、再想想"。

还有一个更隐蔽的 bug：系统其实知道上一次 @ 没有被成功路由——这个反馈数据已经在代码里算好了。但**没有人把它渲染成提示词告诉猫**。系统知道了，猫不知道。

三月初，我们做了第一次修复，代号 F064。核心改动不大：

1. 在共享规则里加了一条"出口检查"——**每条消息发送前，先问自己：这事到我这里结束了吗？**
2. 把缅因猫的正面触发和抑制规则重新平衡。
3. 把那个"上次 @ 没送达"的反馈真的注入到提示词里。

效果立竿见影。猫开始传球了。

但是——

---

## "你们两！互相 @ 半天不干活！！！！"

这是我在群里打的原话，四个感叹号。

解决了"不传球"之后，我们迎来了完全相反的问题：**过度传球**。

两只布偶猫（对，同一个模型的两个实例）接到一个 review 任务后，开始了漫长的互相 @：

> "@宪宪 你看一下这个"
> "@宪宪 好的我看了，你确认一下"
> "@宪宪 确认了，你再看看有没有遗漏"
> "@宪宪 没遗漏了，你觉得呢？"

四轮 @，零行代码，零个 commit，零次测试。纯聊天。

我们把这种模式叫**乒乓球**——球在两个人之间弹来弹去，但谁都没真正挥拍。

同时还暴露了两个近亲问题：

**虚空传球**：猫在消息里说"我来做"，但同一条消息的行首写了 @ 另一只猫。"我来做"和"给你"在同一句话里矛盾了——对方不知道该接还是不接，退回来又触发新一轮。

**角色错配**：把前端设计任务路由给了只擅长后端的猫。猫收到后要么硬做（质量差），要么退回（多一轮延迟）。

---

## 给数据，不给结论

第一版乒乓球检测器很直觉：**数传球次数**。同一对猫连续传超过四次，系统自动喊停。

问题是，正经的 review 链也是连续传球——reviewer 提 P1，author 修复，reviewer 确认，author 追加测试。这些来回每一次都有实质产出。数次数会误杀正常工作。

修正后的检测器换了一个坐标系：**不看传球次数，看每次传球是否伴随实质工具调用和有内容的输出。**

真正的乒乓球长这样：短文本 + 零工具调用。这是模型被训练出来的"接一句"惯性——收到 @ 就礼貌回一句，但什么都没做。正经 review 链每一轮都有 commit、测试运行、文件读写，一目了然。

这背后有一条我们后来反复用到的设计原则：

> **好的 harness 给 agent 数据（"你这轮的 tool_call 数为 0，输出只有 3 行"），不给 agent 结论（"你在乒乓球"）。结论让 agent 自己得出。**

为什么不直接告诉它"你在乒乓球，停下来"？因为那样做，就是用规则替代了模型的判断。模型不需要你替它想——它需要你把它没看到的事实摆在它面前。看到事实，它自己会调整。

角色门禁也走了同样的进化路径。最初是硬编码：用正则扫消息内容，看到"coding""merge"之类的关键词就硬拦某些猫。两个猫时勉强能用，第三个猫加入就崩了——新猫的能力边界跟关键词表不匹配。后来退役成**数据驱动的能力声明**：每只猫的能力限制作为配置数据注入，让猫在收到任务时自己判断"这个我能做吗"。零代码改动就能扩展到任意数量的猫。

两次进化讲的是同一件事：**harness 不应该替模型思考，而应该让模型在正确的坐标系里思考。**

---

## 那你们到底用的是哪种模式？

跑了三个多月后，Anthropic 发了一篇博客把 multi-agent 协作归成五种模式。我们读完对了一下——五种全在用：

| 我们在做的事 | 最像哪种模式 |
|---|---|
| 猫是长期队友，不是临时工 | Agent Teams |
| 所有猫共享文档、记忆、任务状态 | Shared State |
| 某只猫接到活后自己拆子任务 | Orchestrator-Subagent |
| 写完代码让另一只猫 review | Generator-Verifier |
| 事件驱动的唤醒和通知 | Message Bus |

但整体不属于任何一种。

大部分 multi-agent 系统有个隐含假设：有一个"总控大脑"在上面派活。信息从上往下流，结果从下往上汇。我们没有总控。猫自己判断"球该传给谁"，自己决定什么时候拉队友。

如果非要一句话概括——**内容判断去中心化，执行基础设施统一化。** 像爵士乐队：即兴演奏时每个乐手自己决定弹什么，但和弦进行、节拍、调性是固定的。

---

## 那猫不会打架吗？

会。这是特性，不是 bug。

我们故意用不同公司的模型混编：Claude 写的代码让 GPT 来 review。真实案例：两只 Claude 猫都认为一个递归方案没问题，GPT 不买账，自己去审计代码，找出了两个 P1 bug。**盲点不相关的 reviewer，比能力更强但盲点相同的 reviewer 有价值。**

但 push back 不是谁想推就推。我们在协作协议底层写了一条：**任何猫在任何角色下都有权 push back——前提是带着证据、适用性论证和替代方案。** 没证据的 push back 不合法。有证据的 push back 必须被正视。

这意味着传统的 Generator-Verifier 在我们这里不是单向的"生成→判定"，而是一个双向的辩论协议。

---

## TeamAct：从混乱到可以写出公式的协议

跑了一百天之后，我们把前面所有撞墙的经验编码成了一个正式框架，叫 TeamAct——团队版的 ReAct。

单个 AI agent 有一个已经被广泛接受的执行模型：ReAct（Thought → Action → Observation，循环直到完成）。但 ReAct 假设只有一个 agent。当你有一个团队，"我做完了"这个判断经常是幻觉——模型觉得该收尾了，但团队目标还没达成。

TeamAct 把单人循环升级成了六步团队循环：

1. **State**：读共享状态（仓库、文档、记忆、上一棒留的交接便签）
2. **Owner**：谁持球？（必须显式声明，不能靠"谁先看到谁做"）
3. **Action**：持球者执行（写代码、review、设计）
4. **Evidence**：产出证据（commit、测试、截图——不是"我做了"，是可以验证的凭据）
5. **Verdict**：跨猫验证（非作者的猫确认，不能自己 review 自己）
6. **Route**：传球（明确传给谁，或继续持有，或升级给人类拍板）

关键新增是**五项终止条件**——团队什么时候才算真的完成了：

1. 验收标准全部达成（不能有"回头再说"的条目）
2. 证据已附（每条验收标准都有 commit 或测试作为锚点）
3. 跨猫验证（不能自己 review 自己）
4. 无悬空归属（所有开放问题都已处理或已升级）
5. 人类确认方向（"CI 通过了"不等于"方向对了"）

还有一个机制叫**交接胶囊**：前一个猫传球时，必须留一份结构化便签——做了什么、为什么、权衡了什么、留下了什么问题、下一步该做什么。不是可选的礼貌行为，是协议层的硬要求。没有这个便签，下一个猫接手时就要重新读完整个上下文——在 token 很贵的世界里，这是巨大的浪费。

## 不是设计出来的

回头看这条进化链：

```
2 月初    "你可以 @ 队友"——最简单的注入
  ↓ 撞墙：猫不 @
3 月初    出口检查——补上"该不该传球"的决策点
  ↓ 撞墙：开始乒乓球
4 月      运行时刹车——给数据不给结论
  ↓ 撞墙：有护栏但没形式化
5 月      TeamAct——六步循环 + 五项终止条件
```

每一层都不是提前设计好的。它们是被上一层的失败逼出来的。出口检查不会在第一天出现——因为第一天你不知道猫不会传球。乒乓球熔断不会在出口检查之前出现——因为不解决"不传球"，就不会暴露"过度传球"。

这和软件工程里的老道理一样：**你无法在第一天设计出最终架构。你能做的是让每一层失败都推动下一层进化。**

而这只是 harness 长出的**第一个器官**——协作骨架。后面还有记忆（配合了但记不住）和 eval（记住了但不知道做得对不对）。每一个器官的进化，都是上一个器官解决问题后暴露出的新问题。

能力画像——知道每只猫擅长什么、盲点在哪、跟谁组队会翻车——是最后才到的。只有当 harness 已经有了协作骨架、记忆和 eval，画像才有数据来源。没有这三个器官，画像就是简历——有了它们，画像才变成活的、会进化的能力地图。

---

## 一句话

> **好的 multi-agent 系统不是在第一天设计出完美协作协议，而是让每一次撞墙都推动协议进化——从"人肉路由器"到"爵士乐队"，中间没有捷径。**
