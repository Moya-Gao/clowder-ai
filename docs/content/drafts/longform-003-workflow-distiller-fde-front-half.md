# Workflow Distiller — FDE 前半段的压缩

> Companion note for [Longform-003 Seed](./longform-003-seed-poe-vision.md)。
>
> 核心补充：longform-003 现有 FDE 叙事主要讲“企业部署后，harness 从真实轨迹里自进化”。本 note 补的是更早的一层：**部署前 / 立项前，猫咖能不能把一个行业用户讲出来的混乱工作流，蒸馏成可落地的 AI-native 产线。**

## 结论

Cat Cafe 的 FDE-like 能力不只是“去客户现场后自动适配”。更锋利的说法是：

> 猫咖可以把一个行业用户的现场语言，翻译成工作流、摩擦点、自动化边界、MVP 切片、skills、QA 和验证指标。

这件事把 FDE 成本从“部署后长期陪跑”继续往前压缩到“0→1 立项发现”。

## 和 longform-003 的关系

[Longform-003 §四 bis](./longform-003-seed-poe-vision.md#四-bistoc--tob-bridge--同一架构不同尺度) 里已经有这句：

> 企业部署 AI 的最大成本不是模型，是 FDE（现场交付工程师）——派人去理解客户、定制流程、手动迭代。

原文的自动化重点是：

| FDE 手动做的 | longform-003 已写的 auto-harness 视角 |
|-------------|----------------------------------------|
| 理解客户流程 | 从部署后的真实轨迹里发现重复模式 |
| 写 prompt / skill | 从真实轨迹自动蒸馏 skill |
| 定期复盘迭代 | 信号 → patch → replay → sunset |

本 note 增补的是前半段：

| 阶段 | 传统谁做 | Workflow Distiller 压缩什么 |
|------|----------|------------------------------|
| Discovery FDE | FDE / PM / 咨询顾问访谈客户 | 从用户叙述抽出现有流程、真实成本、返工点、交付物 |
| Build FDE | FDE + 工程师做首版方案 | 生成 AI-native 产线 spec、MVP 切片、skill graph、QA / eval |
| Evolution FDE | FDE 长期陪跑迭代 | 进入 longform-003 已写的 auto-harness / trace learning |

一句话：

> longform-003 讲“环境从轨迹里学习”；Workflow Distiller 讲“猫咖先帮你制造第一条可验证轨迹”。

## 方法论

核心原则：

> 从用户工作流中寻找 AI-native 产线，不从模型能力中寻找行业场景。

很多垂直 AI 产品的路径是反的：我有图生视频、RAG、Agent、工作流编排，所以我给用户堆按钮。Workflow Distiller 应该从现场往回抽：

- 用户现在在哪里当人肉路由器？
- 哪些地方在做低价值判断？
- 哪些地方有明确输入和输出？
- 哪些地方有真实返工？
- 哪些交付物 60-70 分就能产生业务价值？
- 哪些步骤可以用 QA / oracle 降低风险？
- 哪些地方应该保留人工 checkpoint？

这不是“行业分析报告”。标准输出应该是一个立项包：

| 输出项 | 内容 |
|--------|------|
| 产品楔子 | 谁在什么场景下痛 |
| 现有流程 | 用户现在怎么做，哪里耗时，哪里返工 |
| 真实 job | 用户真正要达成的业务结果，不是表面动作 |
| 理想流程 | AI 接管哪些步骤，人保留哪些判断 |
| MVP 切片 | 第一版只做哪一个窄任务 |
| 质量阈值 | 60-70 分可交付的标准是什么 |
| 失败模式 | AI 可能怎么翻车，如何发现，如何兜底 |
| 所需 skills | 行业知识、提示词模板、QA 规则、重试策略 |
| 验证方式 | 找真实用户，用真实项目跑一遍，看是否省时、省心、能交付 |

## Case seed：室内设计图转业主沟通视频

用户表面说的是：

> 我需要把设计稿 / 室内设计方案变成视频给业主看。

Workflow Distiller 应该抽出的 true job 是：

> 低成本、快速、足够好地把静态设计方案变成业主能理解、能被打动、能推动成交 / 确认的动态展示材料。

这不是“AI 视频按钮”，而是“业主沟通材料产线”。

### 当前半自动工作流

- 用户手选风格、视角、空间、画幅、模型、时长、分镜、prompt。
- 用户反复抽卡 / 重抽。
- 用户自己看视频 bug：物体突然出现、家具漂移、材质不一致、空间穿帮。
- 用户自己剪掉坏片段，或者决定重生成。
- 用户最后拼出可交付给业主的版本。

### AI-native 产线

| 阶段 | 系统职责 | 人类职责 |
|------|----------|----------|
| 输入 | 接收平面图、效果图、风格说明、业主展示目标 | 给 brief / 上传素材 |
| 空间理解 | 识别空间类型、动线、重点展示区域 | 必要时确认房间类型 |
| 分镜规划 | 自动生成 3-5 个镜头方案 | 选择方向或给 veto |
| 生成 | 批量生成短片候选 | 不逐个点按钮 |
| QA | 检查明显穿帮、物体突现、漂移、材质跳变、镜头崩坏 | 只看系统筛后的候选 |
| 修复 | 可剪则剪，不可剪则重抽；失败太多时降级 | 决定是否接受 60-70 分交付 |
| 包装 | 拼接、过渡、导出业主版 | 最终审片 |

### MVP 切片

第一版不做“完整室内设计视频平台”。只做：

> 室内设计效果图 → 15-30 秒业主预览视频。

限制条件：

- 先支持 3 类空间：客厅、卧室、餐厨。
- 先支持 5 类风格。
- 先解决最显眼的 3-5 类视频 bug。
- 输出目标是“可沟通”，不是“艺术片”。
- 用户二次编辑时间目标：低于 10 分钟。

## 关键 insight：60-70 分不是妥协，是产品楔子

如果目标是 90-95 分审美成片，系统会被 token、重抽、主观审美、一致性和剪辑成本拖进泥潭。

但很多行业交付要的不是“完美”，而是：

- 能让客户理解。
- 能推进沟通。
- 能替用户少加班。
- 能把原来 2 小时的活压到 20 分钟。

所以 60-70 分不是低标准，而是正确的第一版阈值。它让产品从“全自动艺术生产”降维成“可交付业务材料产线”。

## 采访协议

这件事不能靠猫猫脑补。每次 Workflow Distiller 都应该先做事实访谈，接近 [The Mom Test](../../competitor-research/dingtalk-one-postmortem/置身钉内.md#附录the-mom-test精华摘要) 的精神：

- 上次你给客户做这个交付物，实际花了多久？
- 哪一步最烦？为什么？
- 哪一步最容易返工？
- 出过什么不能交付的 bug？
- 哪些 bug 客户看不出来，哪些绝对不能出现？
- 你愿意在哪一步人工确认？
- 哪一步最想完全甩掉？
- 如果只做到 60-70 分，你能不能拿去沟通？
- 如果系统替你省 50% 时间，但你要最后审一遍，值不值？

## 三道门

Workflow Distiller 的最大风险是“猫猫太会想”，导致每个行业都看起来能立项。必须接上 [EP-002：陌生问题域的过早收敛 → 延迟收敛门禁](../../evolution-proposals/EP-002-premature-convergence-unfamiliar-domain.md)。

每个垂直 0→1 立项至少过三道门：

1. **真实成本门**：用户是否已经为这个问题付出真实成本，比如加班、花钱、返工、客户流失。
2. **AI 降本门**：AI 是否减少真实成本，而不是只让流程更酷。
3. **窄切 MVP 门**：第一版是否能用一个很窄的切片交付价值，而不是一上来做行业 OS。

再补两个执行门：

4. **QA / oracle 门**：有没有办法判断“可交付 / 不可交付”，哪怕是粗糙判分。
5. **人工 checkpoint 门**：哪些决定必须留给人，哪些低价值操作可以交给系统。

## 可放进 longform-003 的短摘要

> Workflow Distiller 是 FDE 叙事的前半段：不等企业部署后才从轨迹里学习，而是在访谈阶段就把用户现场语言蒸馏成第一版可验证产线。它的标准输出不是行业分析报告，而是一个 0→1 立项包：现有流程、真实 job、摩擦点、AI 接管边界、MVP 切片、skills、QA、失败模式和验证指标。  
>  
> 原则是：从用户工作流中寻找 AI-native 产线，不从模型能力中寻找行业场景。

## 来源对话摘录

以下摘录保留原始思考脉络。不是完整逐字稿，只保留能支撑本 note 的关键段。

### 1. 铲屎官：现有垂直 AI workflow 把人留在低价值操作里

> 我看到的时候都觉得：丑，真的丑；难用，非常难用，这些东西全部都要我手选。
>
> 她的需求是，她需要把设计稿、室内设计的，变成视频给她的业主看。然后这些 AI 生成的可能有的时候需要抽卡，有的时候需要她自己做点剪辑。
>
> 我会希望如果猫猫帮我完成这个工作：不要让我选这些乱七八糟的，而是根据这个房子的风格自己知道这些如何选，这些知识承载在 skills 里；不要让我一个个去点抽卡，我们有视频产线。

### 2. 云端大缅因猫：这不是工具，是产线

> 你想要的不是“省一步”，而是：不要让我当路由器；不要让我手选这些乱七八糟的参数；不要让我自己查错、返工、补洞；系统应该自己知道该怎么做。
>
> 她定义的是 AI as tool / AI as shortcut；你定义的是 AI as operator / AI as production system。
>
> 你想要的其实不是一个工具，而是一条“视频产线”。

### 3. 铲屎官：这可能是 FDE 前半段

> 如果曾经我们需要 FDE 去和行业 know-how 去做这个，你说我们猫猫有没有可能成为那个 0→1 的发动机？
>
> 当用户给你描写她现在的工作流，我们能抽取成这样的理想中的工作流吗？并且这还是需要能落地的。
>
> 我发现的问题本质是，为什么现在大企业没入行一个个垂直领域做定制？FDE 太贵了，如果你们可以变成 FDE？

### 4. 云端大缅因猫：FDE 压缩机 / Workflow Distiller

> 你说的猫咖承载的关键能力，不只是“多猫协作”，而是：把一个行业用户含糊讲出来的现有工作流，提炼成一个可落地的 AI-native 工作流，并进一步变成 0→1 产品立项。
>
> 也就是猫咖可以变成一种 FDE 压缩机，甚至是 0→1 垂直工作流发动机。
>
> 猫猫不一定要真的懂完整建筑行业十年经验，但可以通过访谈、样例、截图、失败案例、用户现有流程，把行业 know-how 抽成结构，然后帮你提出一个不是泛泛而谈、可以真的落地的第一版产线。

### 5. 云端大缅因猫：三道门

> 这里最危险的 failure mode 是猫猫太会想，导致立项看起来都很合理。
>
> 所以每个猫咖 FDE 立项都必须过三道门：用户是否已经在为这个问题付出真实成本；AI 是否能减少真实成本，而不是只让流程更酷；第一版是否能用很窄的切片交付价值，而不是一上来做行业 OS。
