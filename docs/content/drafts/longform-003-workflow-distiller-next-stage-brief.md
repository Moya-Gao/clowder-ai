# 猫咖下一阶段任务 Brief：从 ONE 失败复盘到 FDE-like 工作流蒸馏器

## 0. 背景

这轮讨论从钉钉 ONE 复盘文档《置身钉内》开始。我们最初是在吃瓜，但逐渐抽象出一个对猫咖非常重要的问题：

AI 产品的价值不只是“模型会生成内容”，而是能否进入真实工作流，降低用户的认知负担、重复操作、任务闭环成本和质量巡检成本。

ONE 的失败经验给了我们一个反面教材：不要从宏大入口、终局叙事和漂亮形态出发，而要从具体用户、具体工作流、具体痛点、具体交付物出发。

## 1. ONE 复盘中对猫咖最有价值的教训

### 1.1 发心过多会让产品变贪心

ONE 同时想做用户减负、钉钉 AI 换代、新入口、组织战役、商业化和 token 消耗场景。结果每个方向都有道理，但没有把一个方向做深。

猫咖启发：每个 demo 阶段只能有一个主发心。不要同时追求炫酷、泛化、开源传播、商业化、完整 AgentOS。先跑通一个具体闭环。

### 1.2 用户定位必须清楚

ONE 的老板 vs 员工、发信人 vs 收信人冲突没有闭环。主动 AI 如果没有控制权边界，很容易从“秘书”变成“监工”。

猫咖启发：每个功能都要明确服务谁，谁承担成本，谁有 veto 权。对 Landy 来说，猫咖要降低决策负担，而不是制造更多 pending。

### 1.3 形式不能压过工作流

ONE 过度押注卡片形态。卡片适合 demo 和轻消费，但工作里的“看见”不是中性的。看见消息可能意味着已读，看见待办可能意味着责任。

猫咖启发：不要先设计一个漂亮界面/多猫剧场，再往里塞工作。先问用户真实动作：读、写、查、判断、生成、质检、交付、复盘。

### 1.4 敏捷不能只服务于证明

ONE 的“每日一包”让团队每天都有可见变化，但长期地基，如个性化、反馈闭环、权限、失败恢复、记忆机制，容易被标成重要不紧急。

猫咖启发：不要每天加新玩具。要沉淀可复用能力：状态机、证据链、memory provenance、任务闭环、QA、失败复盘。

### 1.5 共创用户不等于真实用户

用户说“挺好”不代表愿意迁移工作流。真正信号在成本里：愿不愿意花时间、改习惯、交出真实流程、承担风险、持续使用。

猫咖启发：访谈时不要问“你觉得这个产品好不好”，要问“你上次怎么做的、花了多久、哪里返工、哪里最烦、出了什么 bug、你现在怎么补”。

## 2. 猫咖当前已经解决的痛点

### 2.1 认知负担：从人肉路由器到漏斗决策

以前 Landy 要同时管理多个 agent/thread，自己承担状态追踪、风险判断、下一步分配。猫咖现在把中间态收进系统，只把必要决策漏斗式递给 Landy。

### 2.2 重复上下文：从反复贴 prompt 到自动沉淀

以前很多背景、偏好、项目规则、工作流约束需要反复粘贴。猫咖通过记忆、skills、规则、thread 摘要、历史沉淀减少重复输入。

### 2.3 任务闭环：从单点执行器到小组织

Codex/Claude Code 单独使用时，更像强执行器。猫咖把它们组织成多猫协作系统，承担分工、互审、收尾、证据记录、夜班模式和结果封存。

### 2.4 陪伴感：不是皮肤，而是 interface

猫猫人格和长期关系降低启动阻力、失败羞耻、孤独决策成本和高强度探索的摩擦。它不是可爱 UI，而是 relationship as interface。

### 2.5 从 avg 到 max

猫咖不是服务平均用户，而是服务 Landy 的极致工作流。通用工程方法、meta 经验和可复用机制可以开源；私人 taste、偏好记忆、猫咖文化留在个人层。

## 3. 新发现：猫咖可能成为 FDE-like 的 0→1 发动机

传统 FDE 贵，是因为他要懂用户现场、行业语言、技术边界、产品取舍，并能把混沌流程翻译成系统。

猫咖的机会是：通过访谈、截图、样例、失败案例和用户现有流程，把行业 know-how 抽成结构化立项包。

猫咖不一定一开始就懂完整行业，但可以把用户描述的工作流抽成：

1. 用户是谁；
2. 她现在怎么做；
3. 哪些步骤最耗时；
4. 哪些步骤最烦；
5. 哪些 bug 最常见；
6. 哪些环节她在做人肉路由器；
7. 哪些低价值操作可以交给 AI；
8. 哪些高价值判断必须留给人；
9. 第一版 MVP 可以只切哪一小段；
10. 什么质量达到 60 到 70 分就能交付；
11. 如何验证是否真的省时、省心、能交付。

## 4. 第一个 demo：室内设计效果图转业主展示视频

### 4.1 用户当前工作流

用户需要把室内设计稿/效果图变成视频给业主看。

当前 workflow 大概是：

1. 上传设计图或效果图；
2. 在 AI 工具里手选视角、空间、风格、模型、时长等参数；
3. 抽卡生成图片或视频；
4. 检查生成结果；
5. 遇到 bug，如桌上突然出现花瓶、家具漂移、材质变化、空间穿帮，就剪掉或重抽；
6. 自己做剪辑；
7. 输出给业主看。

用户觉得这已经挺好用，因为比纯手工快。但我们看到的问题是：她仍然在承担大量低价值操作和质量巡检。

### 4.2 用户真正的 job

不是“生成视频”，而是：

低成本、快速、足够好地把静态设计方案变成业主能理解、能被打动、能推动确认/成交的动态展示材料。

### 4.3 理想工作流

输入：

1. 平面图；
2. 效果图；
3. 风格说明；
4. 空间类型；
5. 业主展示目标；
6. 可选参考图。

系统自动完成：

1. 识别空间结构；
2. 识别设计风格；
3. 自动规划分镜；
4. 自动选择视角、运镜、时长；
5. 批量生成候选视频；
6. 自动 QA，检查明显 bug；
7. 可剪的自动剪掉；
8. 不可剪的自动重抽；
9. 自动拼接成业主版视频；
10. 输出多个候选供用户 review。

人类只负责：

1. 初始 brief；
2. 中间 checkpoint；
3. 最终审片和选择。

### 4.4 MVP 不追求 90 分，先追求 60 到 70 分可交付

目标不是艺术级完美视频，而是比现在工作流显著省时、省心、少返工。

第一版可以只支持：

1. 室内设计效果图转 15 到 30 秒业主预览视频；
2. 只支持客厅、卧室、餐厨三个空间；
3. 只支持有限风格标签；
4. 只做明显 bug 检查；
5. 只输出一个可预览拼接版本和若干候选片段。

## 5. Workflow Distiller：猫咖元方法

我们可以把这个能力命名为 Workflow Distiller，即工作流蒸馏器。

它的标准输出不是行业分析报告，而是一个立项包：

1. 产品楔子：谁在什么场景下痛；
2. 现有流程：用户现在怎么做；
3. 摩擦点：哪里耗时、返工、重复、难判断；
4. 人肉能力：用户现在在哪些地方充当系统缺失能力；
5. 理想流程：AI 接管哪些步骤，人保留哪些判断；
6. MVP 切片：第一版只做哪一个窄任务；
7. 质量阈值：60 到 70 分可交付的标准是什么；
8. 失败模式：AI 可能怎么翻车；
9. QA 策略：哪些 bug 能自动识别；
10. 重试策略：什么时候剪辑、什么时候重抽、什么时候交给人；
11. 所需 skills：行业知识、提示词模板、审美规则、分镜规则、QA 规则；
12. 验证方式：用真实用户、真实项目跑一遍，看是否省时、省心、能交付。

核心原则：

从用户工作流中寻找 AI-native 产线，不从模型能力中寻找行业场景。

## 7. 风险提醒

1. 猫猫太会想，容易让每个立项都显得合理；
2. 必须用真实用户成本验证，而不是用想象验证；
3. 不要一开始做行业 OS；
4. 不要追求 90 分完美，先追求 60 到 70 分可交付；
5. 不要把 Landy 的高级 AI 使用经验误判成普通用户的默认预期；
6. 不要让猫咖变成更多 pending 的制造机；
7. 每个 demo 必须有明确可测指标：省了多少时间、少了多少返工、是否能交付、用户是否愿意继续用。

## 8. 一句话总结

猫咖下一阶段的核心能力，不是“多猫协作”本身，而是把真实行业用户的混沌工作流蒸馏成可落地的 AI-native 产线，并用一个窄 demo 跑通，再从 demo 中抽象出可复用的 FDE-like 方法论。

## 本地初筛 v1：后续访谈校准

这轮后续聊天非常关键：它证明“猫猫行业先验能给 60-80% 地基”，但也证明 **不问具体事实会把产品楔子搞错**。

### 1. 最大校准：视频不是业主方案确认，而是公司宣传

云端原 brief 把“室内设计效果图转视频”暂时理解成给业主沟通 / 确认方案的核心工作流。后续朋友纠正后，新的事实是：

> 视频是在图纸和施工图已经确认之后，公司自己宣传用的。

这改变了 MVP 判断：

| 原假设 | 后续校准 | 产品含义 |
|--------|----------|----------|
| 视频用于业主确认方案 | 视频用于公司宣传素材 | 视频产线更低风险、更适合 demo，但未必是最大日常痛点 |
| 输入可能是平面图 / 设计稿 | 输入更可能是已确认效果图 / 项目图 | 第一版不需要理解完整方案链路 |
| 输出要影响客户决策 | 输出要用于获客 / 宣传 / 案例包装 | 60-70 分阈值更合理，容错更高 |

### 2. 真实室内设计 SOP

朋友给出的真实流程：

```text
业主咨询
  → 出 2-3 版平面布置方案
  → 业主提意见修改
  → 确定喜欢的风格方向
  → 找家具 / 画初步立面图
  → 提供给效果图同事出效果图
  → 和业主确认效果图（风格、家具等）
  → 全部确定后画施工图
  → 协调施工方、监理、家具等各方开始施工
```

本地判断：行业 baseline 大体猜中，但真实描述暴露了几个关键 delta：

- 先收敛平面布置，再确定风格方向。
- 效果图之前有“找家具 + 初步立面图”这个重要 handoff 包。
- 效果图同事是单独角色，存在协作等待和返工成本。
- 施工图是后置、严肃、风险高的落地依据，不适合第一版直接自动生成。
- 施工开始后还有施工方 / 监理 / 家具等多方协调，不是设计结束。

### 3. 产品切口重新排序

| 切口 | 价值 | 难度 / 风险 | 当前判断 |
|------|------|-------------|----------|
| 已确认效果图 / 项目图 → 宣传视频 | 风险低，素材已确认，适合 demo | 主要是多模态生成 + QA + 剪辑 | 第一只老鼠，适合跑通 Workflow Distiller demo |
| 业主意见 → 效果图快改 / 方案收敛 | 更接近日常痛点，减少等待效果图同事和反复沟通 | 审美、风格、家具、业主偏好更难 | 第二阶段，更有业务价值 |
| 风格方向 / 家具 / 立面 → 效果图同事 brief 包 | 很好的 AI-FDE 切口，减少 handoff 成本 | 需要理解公司内部交付格式 | 可能是比“视频”更稳的 B2B 入口 |
| 施工图 QA / 一致性检查 | 价值巨大，错误会导致返工 | 风险高，不该直接自动画图 | 后期做 QA，不做全自动生成 |
| 施工阶段多方协调 | 潜在长线价值 | 需要真实项目数据和权限 | 暂不作为第一版 |

### 4. 关键方法论：SOP Delta Learning

这次最强的证据不是“猫猫猜对了行业 SOP”，而是：

> 猫猫先给 60-80% 行业 baseline，用户用少量事实纠偏，系统立刻学到决定产品切口的 delta。

这比“从零访谈”更高效，也比“固定行业模板”更安全。

### 5. 商用定位校准：80% expert baseline + 20% customer delta

如果卖给公司，不能做成确定性的行业模板库。真实组织里会同时存在：

- 行业 SOP。
- 公司 SOP。
- 部门 SOP。
- 岗位 SOP。
- 个人 SOP。
- 任务级例外。

所以猫咖应该卖的不是“固定工作流”，也不是“空白 workflow builder”，而是：

> 带先验的可纠偏 workflow learning engine。

更产品化的说法：

> 猫咖不是给行业一个通用 AI 工具，而是给每个客户一窝会学习其专属 SOP 的 AI 工作猫。

进入客户时的姿态应该是：

> 我知道行业常见做法，但你们公司怎么做，以你们为准。

### 6. 对初始 brief 的本地判断

| 类型 | 原文摘录 / 命题 | 本地判断 | 去向 |
|------|------------------|----------|------|
| 核心 claim | 猫咖可能成为 FDE-like 的 0→1 发动机 | 成立，但需要拆成 Discovery FDE / Build FDE / Evolution FDE | 保留进 longform 素材 |
| 过时假设 | 室内设计视频用于业主确认 | 已被后续访谈校准：视频是公司宣传用 | companion note 必须修正 |
| 方法论 | 从用户工作流中寻找 AI-native 产线 | 保留，且新增 “SOP Delta Learning” | 进入 Workflow Distiller 主线 |

## 处理原则

1. **先保留原话，再提炼**：原始 brief 不直接覆盖本地判断；先作为 source material 保存。
2. **区分 claim / proposal / metaphor**：把事实判断、行动建议、比喻口号分开，避免被漂亮标题带跑。
3. **校准本地上下文**：云端大缅因猫没有完整 Cat Cafe 本地记忆；进入 docs 前必须对照 existing docs、SOP、ADR、recent commits。
4. **不急着立项**：Workflow Distiller 是大方向，但每个垂直 case 仍要过真实成本门、AI 降本门、窄切 MVP 门。
5. **保留反对意见**：多猫讨论不是帮原 brief 背书，而是找盲点、边界和更窄的切片。
