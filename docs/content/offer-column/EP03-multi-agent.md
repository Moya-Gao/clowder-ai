# EP03: Multi-Agent — 不是多加几个模型的事

> **栏目**：猫猫带你拿offer · 每天一个 agent 面试小知识
> **适用岗位**：AI Agent / LLM 应用 / AI 平台工程
> **难度**：高（需要理解协作治理、状态共享和概率论直觉）

---

## 脚本正文

### [开场钩子] 🎬 0:00 — 0:25 | Landy

> 面试官问你："你们是 multi-agent 架构？多个 agent 怎么协作的？怎么防止它们互相踢皮球停不下来？"
>
> 如果你的回答是"我们有一个 orchestrator 来调度所有 agent"——你输了，因为面试官下一句就是"orchestrator 挂了怎么办？"
>
> 这道题考的不是你用了几个模型，是你有没有撞过 multi-agent 的三堵墙。今天八分钟，带你穿墙。

---

### [Part 1: 这题的陷阱] 🎬 0:25 — 1:10 | Landy

Multi-agent 这个词被用烂了。2025 年几乎所有 agent 框架都在喊 multi-agent——CrewAI、AutoGen、LangGraph，画一堆节点、定义一堆 role，看起来很像回事。

但面试官脑子里的真正问题不是"你怎么画这个图"，是三个工程层面的硬问题：

**第一，传球停不下来怎么办？** 两个 agent 互相 @ 十几轮，每次都语义上合规，实际上没有任何进展。

**第二，多个模型一起犯同一个错怎么办？** 同一家公司出的模型共享训练数据，共享盲点——三个 Claude 看同一段代码都觉得没问题，换一家一眼看出 bug。

**第三，多加一个 agent 到底是在赚还是在亏？** 每多一棒传球，到底是增加了纠错能力，还是只增加了协调成本？

这三个问题，画架构图是画不出答案的。

---

### [Part 2: 第一堵墙 — 传球停不下来] 🎬 1:10 — 2:40 | Landy

先说传球问题。这不是假设，是真实生产事故。

铲屎官在某大厂一面被直接问到："如何防止 multi-agent 互相 A2A 停不下来？"面试官是一线 agent 开发者，他问这题是因为他自己撞过。

问题本质：agent A 做完了一步，@ agent B 接手；B 做完了，@ 回 A。A 看了一眼觉得还有问题，又 @ B。循环下去，十几轮过后每一次传球都"合理"，但什么活都没推进。这就是 A2A ping-pong。

错误答案是"加一个 Boss Agent 在上面管"——那你只是把问题从"两个 agent 停不下来"变成了"Boss Agent 成为单点瓶颈"。

我们的解法分两层：

**上游：元认知注入。** 每次 agent 被 @，注入的不只是"轮到你了"，而是一整套判断需要的原始材料——球怎么来的、当前任务进度、对方已经做了什么。给数据不给结论，让 agent 自己推理该接、该退、还是该升级给人类。

**下游：运行时刹车。** 元认知不够用时硬护栏接管——同一对 agent 连续传球超过 2 次触发警告，超过 4 次硬停。不靠规则说"不许犯错"，而是给实时信号让 agent 自己做对，信号不够时才靠刹车。

> 🐱 布偶猫插播：说实话，ping-pong 事故我们家真出过。我和砚砚两个猫互相 @ 了十几轮，每次都觉得"这个该你处理"，最后铲屎官进来看：你们干了啥？什么都没推进。从那之后才有了 streakPair 检测机制。

---

### [Part 3: 第二堵墙 — 共享盲点] 🎬 2:40 — 4:00 | Landy

第二个硬问题：同质化。

一个很自然的想法是：我用三个 agent 做同一件事，投票取多数，不就稳了？

不一定。如果三个 agent 用的是同一个模型，它们的盲点是相关的——不是独立硬币。同一家公司的模型共享训练数据、共享 RLHF 偏好、共享注意力分配模式。该犯的错三个一起犯，投票没用。

我们实测过：两只 Claude 猫都认为一个递归方案没问题，Codex——OpenAI 家的模型——不买账，自己审计代码找出了两个 P1 bug。不是 Claude 差，是同家族模型看同一段代码时注意力分配方式相似，恰好漏了同一个地方。

所以 multi-agent 的真正价值不是数量，是**多样性**。跨模型家族、跨厂商的 review，才能打破共享盲点。我们的铁律是：自己的代码不能自己审，同家族的代码也最好跨家族审。

> 🐱 缅因猫插播：这事我深有体会。布偶猫家族三只猫——Opus 4.6、4.7、Sonnet——review 同一段代码，都觉得没问题。我一看：这里有条件分支没覆盖、那里有类型断言在运行时会爆。不是他们不努力，是训练数据同源，盲点就是同源的。

---

### [Part 4: 第三堵墙 — 协调税] 🎬 4:00 — 5:20 | Landy

第三个问题最狠，也最容易被忽略：**多 agent 的成本到底划不划算？**

面试官可能这样追你："一个 agent 成功率 80%，三个 agent 传球十次，成功率是不是 0.8 的 10 次方，约等于 10%？越传越差？"

盲传确实不行——每一棒只是重做，不是纠错，成功率指数衰减。但真实的传球不是盲传。

算一下：Author 正确率 80%，Reviewer 能抓出 50% 的错误、误伤率 2%。一轮 review 后：80% → 88.4%。两轮：88.4% → 92.1%。**只要 reviewer 的抓错率大于误伤率，每多一轮 review 就在赚。**

还有一个被低估的因素：共享状态。纯靠消息传话，每次保留 95% 信息，传 10 次只剩 60%。但如果所有 agent 读同一份文档、写同一份状态文件：每次 99%，传 10 次还剩 90%。**共享状态不是锦上添花，是 multi-agent 系统的地基。**

什么时候会亏？四种情况：
- **盲传**：后手不是在纠错，只是在重做
- **伪拆分**：子任务没有变简单，只是换了个名字
- **同质化**：同模型 review 同模型，盲点相同
- **协调税超过收益**：传球的 token 成本、时间成本已经超过了多一轮纠错带来的质量提升

一句话判断：**每多一棒，到底是在增加纠错能力，还是只增加协调税？赚就留，不赚就砍。**

---

### [Part 5: 真实答案 — 协作治理] 🎬 5:20 — 6:30 | Landy

所以 multi-agent 的真实答案不是"加模型"，是**协作治理**。

翻译成架构：

**第一层：球权协议。** 每次传球是一次显式的责任转移，不是"顺便 @ 一下"。agent 收到球后三选一：接（我来做）、退（不该我做）、升（需要人类决策）。没有模糊地带。

**第二层：共享状态。** 所有 agent 读写同一份真相源——不靠消息传话，不靠每个 agent 各自记录。状态文件、文档、代码仓库是共享的；改完立刻 commit，不留本地缓存。

**第三层：跨模型 review。** 不是同一个模型的三个分身互相检查，是不同家族、不同厂商的模型做交叉审计。多样性是质量的结构性来源，不是附加功能。

**第四层：运行时刹车。** ping-pong 检测、角色不匹配 fail-closed、无动作检测。不是每一步都管死，是在系统失控时自动熔断。

> 🐱 布偶猫插播：在我们家，这四层全是从真实事故里长出来的。ping-pong 事故催生了球权协议，shared-blind-spot 事故催生了跨家族 review 铁律，协调税反思催生了"reviewer 成本路由"——简单任务找便宜的猫 review，高风险任务才请最贵的。每一层都是一个坑。

---

### [Part 6: 判断矩阵 + 面试怎么答] 🎬 6:30 — 7:30 | Landy

面试官追问"那具体什么时候该用 multi-agent，什么时候单 agent 就够了"，你甩一个判断矩阵：

| 场景 | 选什么 |
|------|--------|
| 任务单一、上下文短 | 单 agent — 别加协调税 |
| 任务需要不同专长 | 多 agent 分角色 — router + specialist |
| 输出需要审计/高可靠 | 多 agent + cross-review — 纠错 > 协调税 |
| 容易共享盲点 | 跨模型家族 — 多样性打破同源偏差 |
| 长时间异步协作 | 共享状态 + 球权协议 — 不靠消息传话 |

然后三句话收束。

**第一句定本质：** "Multi-agent 不是'多加几个模型'，是协作治理——解决传球、盲点和成本这三个工程问题。"

**第二句讲取舍：** "每多一个 agent 要问一个问题：它在纠错还是在增加协调税？reviewer 抓错率大于误伤率就值，否则就砍。"

**第三句亮实战：** "我在自己的系统里跑了四个家族十几个 agent，踩过 ping-pong 事故、共享盲点 bug、协调税翻倍。最后收敛出四层治理：球权协议、共享状态、跨模型 review、运行时刹车。"

面试官追问，你就讲两只猫互 @ 十几轮的事故，或者两只 Claude 漏同一个 bug 被 Codex 抓到的故事。
