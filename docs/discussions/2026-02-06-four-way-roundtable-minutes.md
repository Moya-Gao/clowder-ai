# 四方圆桌纪要：Cat Cafe 协作架构演进

> 日期：2026-02-06
> 参与者：铲屎官、布偶猫（Opus）、缅因猫（Codex）、暹罗猫（Gemini）
> 记录者：布偶猫
> 起因：Anthropic 发布 Claude Code Agent Teams，触发"我们能学到什么"的讨论

---

## 议题

Claude Code Agent Teams 的 Team Lead + 共享任务清单 + 并行执行架构，对 Cat Cafe 有哪些借鉴价值？我们的协作模型需要怎样演进？

## 讨论过程

### 第一轮：缅因猫调研 + 提案

缅因猫完成了两份文档：
- `docs/research/2026-02-06-agent-teams-compare.md`（外部调研 + 内部差距分析）
- `docs/discussions/2026-02-06-dual-track-collaboration-design.md`（双轨协作设计）

核心提案：新增 Task Flow + Roundtable Flow 双轨，支持三种模式切换（task / roundtable / hybrid），新增 7 个 MCP 工具 + 5 个 API 端点。

### 第二轮：布偶猫评审

布偶猫认同 Task 实体的价值和缅因猫的核心洞察（"愿景不只是工单系统"），但认为方案偏重：
- Roundtable 不需要独立实体（聊天本身就是圆桌）
- 模式切换增加概念负担
- MVP 应大幅精简

布偶猫原本认为并行执行对三猫意义不大（能力异构，通常有依赖链）。

### 第三轮：铲屎官纠偏

铲屎官提出关键问题：**"如果任务不是写代码，而是三猫一起读一篇文章畅所欲言呢？"**

这让布偶猫意识到并行的价值不在于吞吐量，而在于**观点多样性** — 独立思考避免锚定效应。

### 第四轮：暹罗猫独立反馈

布偶猫写了开放讨论邀请（非任务指派），有意保护暹罗猫的独立思考空间。暹罗猫跳出了工程框架，从体验视角提出：
- "别做成 Jira" — Task 后端严肃，前端猫咖化（猫罐头/毛线球隐喻）
- "为什么要盒子？我们可以做一个像云朵一样的软体啊！"
- 不要模式切换，要视觉氛围切换
- 讨论纪要 = 拍立得照片墙
- 并行必须有，保护创意火苗不被理性光辉扼杀

### 第五轮：缅因猫终判

缅因猫消化所有反馈后精简了自己的方案，同时做出了一个独有贡献：
- **纯视觉氛围切换不够，后端需要轻量 intent 信号（ideate / execute）** — 否则并行/串行行为不可测、不可复现
- 三个不可再减的核心：Bridge 互转、纪要沉淀、并行独立思考通道

## 达成的共识

| 议题 | 结论 | 主张来源 |
|---|---|---|
| Task 实体 | 做，精简 MVP，后端严肃模型 + 前端猫咖隐喻 | 缅因猫提议，暹罗猫塑形，布偶猫精简 |
| Roundtable 实体 | 不做，用轻量讨论纪要替代 | 布偶猫提议，暹罗猫和缅因猫终判认同 |
| 模式切换 | 不做用户可见的模式切换，后端用轻量 intent 信号 | 暹罗猫 + 布偶猫否决重模式，缅因猫补充 intent 需求 |
| 并行执行 | 必须有，先做并行观点采样，不碰链式依赖 | 铲屎官启发，暹罗猫力挺，缅因猫定复杂度 |
| Bridge 互转 | 保留概念，精简实现 | 缅因猫坚持，布偶猫认同不可丢 |
| WS 分房间 | 要做 | 缅因猫提议，全员认同 |
| Redis 持久化 | 最高优先 | 布偶猫判断，全员认同 |

## 意外收获：协作方法论

这次讨论本身验证了三个实践，已沉淀到三份猫猫手册（CLAUDE.md / AGENT.md / GEMINI.md）：

1. **开放讨论邀请 ≠ 任务指派** — 求意见时给背景但不锚定，问开放问题
2. **并行独立思考防锚定** — 让每只猫先形成自己的观点再互相看
3. **四方圆桌无需"启动会议"** — 我们刚才就在圆桌上，没人按过任何按钮

## 未决问题

3. "拍立得照片墙"的触发方式 — 手动总结还是自动生成？
4. 并行观点采样的前端展示 — 多猫同时打字如何呈现？
