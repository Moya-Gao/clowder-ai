## Why — 为什么这样做

### Feature 1

**为什么 threadIdRef 而非 deps 数组?**
- Socket 连接不应因 threadId 变化而断开重连
- 切换对话只需 leave_room + join_room，不需要新 socket

**为什么 FormData/JSON 双模式?**
- 有图片: FormData (multipart) — 后端已有 @fastify/multipart
- 无图片: JSON — 向后兼容，省 Content-Type 解析开销

**为什么 contentBlocks 降级?**
- 旧消息没有 contentBlocks → 降级到 `content` 字符串渲染
- 新消息有 contentBlocks → 遍历渲染文本/图片

### Feature 2

**为什么 Project = 目录?**
- CLI 天然需要 cwd → 目录就是项目上下文
- 文件系统即记忆 (CLAUDE.md, docs/ 都在目录里)
- 铲屎官参考 Codex App 明确确认此设计 (ADR-002)

**为什么不建独立 ProjectStore?**
- Project 从 `Thread.projectPath` 推导，无独立状态
- 避免 ProjectStore 和 ThreadStore 之间的同步问题

**为什么目录浏览限制 home 目录?**
- 安全: `absPath.startsWith(home)` 防止浏览系统目录
- 跳过 `.xxx` 隐藏目录和 `node_modules`
- 生产环境需更细粒度的权限控制

**为什么前端用弹窗而非下拉框?**
- 铲屎官反馈: 手动输入路径 "太反人类了！至少弹出窗口让我选择是哪个目录吧？"
- 弹窗含: 快速选项 (已有项目 + 大厅) + 文件系统树浏览

**为什么 ThreadSidebar 被重写了 3 次?**
1. `dd18462`: 按 projectPath 分组但无创建时选项目
2. `0919d14`: 加了下拉框 + 文本输入 (铲屎官否决)
3. `6c43422`: 目录浏览弹窗 + 删除按钮 (最终版)

## Tradeoff — 取舍

| 选择 | 放弃的替代方案 | 理由 |
|------|----------------|------|
| 内存 ThreadStore (Map) | Redis ThreadStore | Phase 3.2 聚焦功能完整性，Redis 留后续 |
| `<img>` 直接渲染 | `next/image` 优化 | 图片来自动态 URL，next/image 需 remotePatterns |
| 前端无测试 | Jest + Testing Library | 前端偏 UI 布局，视觉验证更有效 |
| Project 从 Thread 推导 | 独立 ProjectStore | 避免同步问题，Project 无独立状态 |
| 目录浏览 API | 前端 File System Access API | File System API 兼容性差，server-side 更可控 |
| switchRoom 手动管理 | Socket.io namespace | 房间够用，namespace 无额外收益 |

## Open Questions — 待讨论

1. **目录浏览安全**: 当前只限 `homedir()` 下。生产环境是否需要白名单/黑名单?
2. **ThreadSidebar 视觉**: 暹罗猫还没出设计稿，当前是功能性布局
3. **图片最大尺寸**: 当前 10MB/张 × 5 张，生产环境可能需前端压缩
4. **对话删除**: 当前 DELETE 只删 thread 元数据，不删消息（消息通过 TTL 自然过期）
5. **projectPath 校验**: `POST /api/threads` 的 projectPath 当前不校验目录是否存在。是否应加 `fs.stat` 校验?
