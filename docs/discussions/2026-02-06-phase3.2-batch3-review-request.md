## Why — 为什么这样做

### Task 6: 前端

**为什么侧栏 240px + 可折叠?**
- 桌面端: 固定宽度不抢主聊天区空间
- 移动端: 汉堡菜单切换，不占固定位置
- 参考 Discord/Slack 的经典布局

**为什么 threadIdRef 而非 deps 数组?**
- Socket 连接不应因 threadId 变化而断开重连
- 切换对话只需 leave_room + join_room，不需要新 socket
- React StrictMode 下双连接问题也一并避免

**为什么 FormData/JSON 双模式?**
- 有图片: FormData (multipart) — 后端已有 @fastify/multipart
- 无图片: JSON — 向后兼容，省 Content-Type 解析开销

**为什么 contentBlocks 降级?**
- 旧消息没有 contentBlocks → 降级到 `content` 字符串渲染
- 新消息有 contentBlocks → 遍历渲染文本/图片/代码块

### Task 7: WebSocket

**为什么加 leave_room handler?**
- SocketManager 原来只有 join_room，切换对话后旧房间消息还会收到
- leave_room 确保干净切换

**为什么 callbacks 也加 threadId?**
- MCP 回传 (猫猫主动发言) 也需要路由到正确的对话房间
- InvocationRecord 已有 threadId (Task 3 加的)，只需传给 broadcast

### Task 8: 集成

**为什么 thread-wiring 而非纯单元?**
- 对话功能横跨 ThreadStore + MessageStore + AgentRouter + API routes + SocketManager
- 单元测试各自通过但组合可能有缝隙
- 集成测试验证端到端闭环

## Tradeoff — 取舍

| 选择 | 放弃的替代方案 | 理由 |
|------|----------------|------|
| 内存 ThreadStore (Map) | Redis ThreadStore | Phase 3.2 聚焦功能完整性，Redis ThreadStore 留 Phase 3.5 |
| `<img>` 直接渲染 | `next/image` 优化 | 图片来自 API 动态 URL，next/image 需配 remotePatterns，过度设计 |
| 前端无测试 | Jest + Testing Library | 前端改动偏 UI 布局，视觉验证更有效，API 侧已有 190 tests |
| switchRoom 手动管理 | Socket.io namespace | 房间够用，namespace 增加复杂度但无额外收益 |
