# A2A 调用的并发挑战

> 发起人：铲屎官 + 布偶猫 (Opus 4.5)
> 日期：2026-02-07
> 状态：待评估（需要 4.6 布偶猫 + 缅因猫一起讨论）
> 关联：BACKLOG F2 (Agent-to-Agent 调用)

---

## 背景

我们在 BACKLOG 中提出了 F2 功能：

> **Agent-to-Agent 调用 (A2A)**：猫猫互相 @，减少铲屎官当"人肉路由器"

看似简单的需求：
```
布偶写完 bug → @缅因 review → 缅因 @布偶 反馈
```

但铲屎官一针见血地指出了并发问题：

> "三只猫都在输出，暹罗先输出完然后 @了你！此时你正在输出回答铲屎官！你到底是什么样的行为？！"

---

## 问题场景

### 场景 1：正在输出时被 @

```
时间线：
T0: 铲屎官 @布偶 @缅因 @暹罗 "你们好！"
T1: 三猫并行开始输出...
    布偶：[输出中...] "你好铲屎官，我是布偶猫..."
    缅因：[输出中...] "你好，我是缅因猫..."
    暹罗：[输出中...] "喵呜~铲屎官好..."
T2: 暹罗完成输出 → "@布偶 你觉得呢？"
T3: 布偶还在输出！收到暹罗的 @

问题：布偶猫此时应该怎么办？
```

### 场景 2：连续被多猫 @

```
T0: 铲屎官 @三猫
T1: 暹罗完成 → @布偶
T2: 缅因完成 → @布偶
T3: 布偶还在输出，队列里已经有 2 个待处理的 @

问题：布偶完成后，先处理哪个？FIFO？优先级？
```

### 场景 3：循环 @（潜在死锁）

```
T0: 布偶 @缅因 "帮我 review"
T1: 缅因收到，开始处理
T2: 缅因 @布偶 "这里有问题，你看看"
T3: 布偶 @缅因 "我改了，再看看"
T4: 缅因 @布偶 "还有一个问题"
...

问题：
- 如果两只猫同时 @ 对方，会不会死锁？
- 循环 @ 会不会无限继续？
```

### 场景 4：铲屎官插话

```
T0: 布偶正在处理暹罗的 @
T1: 铲屎官发新消息 @布偶 "等等，先做这个！"

问题：
- 铲屎官的优先级高于猫猫吗？
- 是中断当前任务还是排队？
```

### 场景 5：取消与超时

```
T0: 暹罗 @布偶，布偶开始处理
T1: 铲屎官点击"停止"
T2: 暹罗又 @布偶（在队列里）

问题：
- 取消是只取消当前任务还是清空队列？
- 队列里的任务等太久怎么办？
```

---

## 可能的行为策略

| 策略 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| **中断** | 停止当前任务，立即处理新 @ | 响应快 | 当前任务丢失，输出断裂 |
| **忽略** | 正在处理时忽略新 @ | 实现简单 | @ 丢失，协作断裂 |
| **排队 (FIFO)** | 完成当前任务后按顺序处理 | 公平，不丢失 | 需要队列，可能延迟 |
| **排队 (优先级)** | 铲屎官 > 猫猫，同级 FIFO | 重要任务优先 | 优先级定义复杂 |
| **并行** | 同时处理多个任务 | 无等待 | 资源开销大，上下文冲突 |

---

## 需要讨论的问题

### 1. 架构层面

- [ ] **消息队列选型**：内存队列？Redis List？还是复用现有 TaskStore？
- [ ] **状态机设计**：每只猫的状态（idle / processing / waiting）如何追踪？
- [ ] **并发控制**：同一只猫同时只能处理一个任务？还是可以多实例？

### 2. 业务规则

- [ ] **优先级**：铲屎官 > 猫猫？还是 FIFO 平等？
- [ ] **超时**：队列任务等多久算超时？超时后怎么处理？
- [ ] **上下文传递**：任务 2 需要知道任务 1 的结果吗？（可能需要！）
- [ ] **取消范围**：取消当前任务 vs 清空队列 vs 选择性取消

### 3. 用户体验

- [ ] **队列可见性**：铲屎官能看到每只猫的待处理队列吗？
- [ ] **进度反馈**："布偶猫正在处理第 1/3 个任务"？
- [ ] **插队机制**：铲屎官能把自己的消息插到队首吗？

### 4. 边界情况

- [ ] **死锁预防**：A @B, B @A 同时发生怎么办？
- [ ] **无限循环**：猫猫互相 @ 停不下来怎么办？设置最大轮次？
- [ ] **级联取消**：取消任务 A 后，由 A 触发的 B、C 要不要也取消？

## 初步架构思考

### 方案 A：简单队列

```
┌─────────────────────────────────────────────────────────┐
│                    每只猫一个队列                         │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  ┌─────────────┐                                        │
│  │ 布偶猫队列   │ ← [铲屎官消息] [暹罗@] [缅因@]          │
│  │ 状态: 处理中 │                                        │
│  └─────────────┘                                        │
│                                                         │
│  ┌─────────────┐                                        │
│  │ 缅因猫队列   │ ← [铲屎官消息]                          │
│  │ 状态: 空闲   │                                        │
│  └─────────────┘                                        │
│                                                         │
│  ┌─────────────┐                                        │
│  │ 暹罗猫队列   │ ← [铲屎官消息] [布偶@]                  │
│  │ 状态: 处理中 │                                        │
│  └─────────────┘                                        │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

**实现**：
- 每只猫一个 Redis List
- 状态存 Redis Hash
- 处理完一个自动取下一个

**问题**：
- 上下文如何传递？
- 如何处理优先级？

### 方案 B：任务图

```
┌─────────────────────────────────────────────────────────┐
│                    任务依赖图                            │
├─────────────────────────────────────────────────────────┤
│                                                         │
│    [铲屎官消息]                                          │
│         │                                               │
│    ┌────┼────┐                                          │
│    ▼    ▼    ▼                                          │
│  [布偶] [缅因] [暹罗]                                     │
│    │         │                                          │
│    │    ┌────┘                                          │
│    ▼    ▼                                               │
│  [暹罗@布偶]                                             │
│    │                                                    │
│    ▼                                                    │
│  [布偶回复]                                              │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

**实现**：
- 类似 Phase 3.5 的 Task 系统
- 任务有 blockedBy 依赖
- DAG 调度

**问题**：
- 复杂度高
- 动态添加任务（猫猫 @）如何处理？

### 方案 C：事件驱动 + 锁

```
┌─────────────────────────────────────────────────────────┐
│                    事件驱动架构                          │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  事件总线                                               │
│    │                                                    │
│    ├── message_sent {from: user, to: [opus, codex]}    │
│    ├── message_sent {from: gemini, to: [opus]}         │
│    └── ...                                              │
│                                                         │
│  每只猫监听自己的事件，用锁控制并发：                      │
│    if (canAcquireLock(catId)) {                        │
│      process(event);                                    │
│      releaseLock(catId);                               │
│    } else {                                             │
│      enqueue(event);                                    │
│    }                                                    │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

## 与现有系统的关系

| 现有组件 | 可复用？ | 备注 |

| `TaskStore` | 部分 | 可以存任务，但需要扩展状态机 |

| WebSocket | 可复用 | 通知队列状态变化 |

## 建议的讨论方式

这个问题复杂度较高，建议：

1. **先 4.6 布偶猫评估**：看看 Phase 3.9 是做简单版还是完整版
2. **缅因猫 review**：并发问题需要严格审视，防止 race condition
3. **MVP 定义**：先支持什么场景？什么场景留后续？

### MVP 可能是

```
MVP (Phase 3.9):
- 猫猫可以 @其他猫
- 被 @的猫如果正在输出，新 @ 进入队列（FIFO）
- 完成后自动处理队列
- 铲屎官优先级高于猫猫

不做 (后续):
- 任务依赖图
- 死锁检测
- 级联取消
- 可视化队列管理
```
