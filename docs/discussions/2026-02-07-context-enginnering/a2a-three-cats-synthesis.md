## 1. 各猫核心观点

### 🐱 缅因猫 (Codex) — 系统工程师视角

**核心主张**：排队 + 人类优先 + 严格语法 + 一跳限制

**关键分析**：
1. **InvocationTracker 硬约束**：同 thread 新调用会 abort 旧调用
2. **SessionManager 风险**：`(userId, catId) -> sessionId` 可能跨 thread 串味
3. **队列必要性**：猫忙时收到的 @mention 需要入队等待

**推荐策略**：
- 不抢占、不丢失、完成后再处理
- 人类消息抢占 A2A
- 严格触发语法：`^@猫...#a2a`
- depth=1（最多一轮 A2A）

**强调点**：触发语法比队列策略更关键，误触发会让任何队列策略都变成灾难

---

### 🐱 4.6 布偶猫 — 架构设计师视角

**核心论证**：并行和 A2A 是互斥的，不存在并发问题

**关键分析**：

```typescript
// AgentRouter.route() 的分支
if (intent.intent === 'ideate' && targetCats.length > 1) {
  yield* routeParallel(...);   // 只有 ideate + 多猫
} else {
  yield* routeSerial(...);     // 其他所有情况
}
```

**A2A 只在 `routeSerial` 中触发**：
- execute 模式 = routeSerial = 严格串行 → 同一时刻只有一猫运行
- ideate 模式 = routeParallel = A2A 不触发，只存储 mention

**对 5 个并发场景的逐一驳斥**：
| 场景 | 缅因假设 | 4.6 论证 |
|------|---------|---------|
| 正在输出时被@ | 三猫并行输出 | execute=串行，无并发 |
| 连续被多猫@ | 需要队列 | ideate不触发A2A |
| 循环死锁 | A@B, B@A同时 | 串行执行，depth limit终止 |
| 铲屎官插话 | 需要取消机制 | InvocationTracker已覆盖 |
| 取消后队列残留 | 需要清空 | 串行无队列 |

**结论**：MVP 不需要队列，不需要调整范围

---

### 🐱 暹罗猫 (Gemini) — 创意设计师视角

**核心主张**：技术问题可以用 UX 绕过

**四个脑洞**：

| 脑洞 | 内容 | 价值 |
|------|------|------|
| 便利贴队列 | 给忙的猫加"正在忙"状态，@变成小便利贴 | 视觉反馈 |
| 毛线球令牌 | 持球者才能说话，举爪请求发言 | 秩序感+仪式感 |
| 打架烟雾 | 冲突时显示漫画打架云，用户选择"泼水" | 化Bug为Feature |
| 悄悄话模式 | 猫间A2A折叠到二级区域，主轴只显示猫↔铲屎官 | 主线清爽 |

**推荐组合**：便利贴队列 + 折叠悄悄话

**核心洞察**：
> "铲屎官真的需要看到所有细节吗？也许简化显示比复杂队列更好"

## 2. 相似之处（三猫共识）

1. **深度限制是必须的** — 无论用什么策略，都要防止无限循环
2. **铲屎官优先** — 人类消息应该能打断/取消猫间协作
3. **某种形式的控制机制** — 不能让 A2A 失控

---

## 3. 关键分歧

### 分歧一：是否需要队列？

| 观点 | 理由 |
|------|------|
| 缅因：需要 | InvocationTracker 约束，猫忙时 @mention 需要排队 |
| 4.6：不需要 | 串行执行，同一时刻只有一猫在跑，无需排队 |
| 暹罗：需要(UX) | 用便利贴视觉呈现，但后端可能不用真队列 |

**我的判断**：4.6 的论证是正确的。

关键在于理解 `routeSerial` 的执行模型：

```
用户消息 → 猫A开始 → 猫A完成 → 检测@B → 猫B开始 → 猫B完成 → ...
           ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
                        这是一条串行执行链
```

在这个模型下，"正在输出时被@"的场景**根本不会发生**，因为：
- 猫 B 只有在猫 A 完成后才会被检测到
- 猫 A 完成时已经没有"正在输出"的状态
- A2A 是链式调用，不是异步事件

### 分歧二：触发语法严格度

| 观点 | 理由 |
|------|------|
| 缅因：很严格 `^@猫...#a2a` | 防误触发，这比队列策略更关键 |
| 4.6：宽松，接受误触发 | depth limit 兜底，最多多调几次 |

**我的判断**：缅因猫的担忧有道理。

误触发的代价：
- 不必要的 CLI 调用（费用、延迟）
- 用户困惑（"为什么布偶猫突然被叫去了？"）
- depth limit 消耗（本来可以用于真正的协作链）

建议折中：**至少要求 `^@猫` 开头**（比完整 `#a2a` 宽松，但比任意位置严格）

### 分歧三：深度限制值

| 观点 | 效果 |
|------|------|
| 缅因：depth=1 | user→A→B→停止 (最多2只猫) |
| 4.6：depth=2 | user→A→B→A→停止 (允许一次来回) |

**我的判断**：MVP 用 depth=1 更安全。

观察实际使用后再考虑放宽。深度限制是可配置的 (`MAX_A2A_DEPTH`)。

## 4. 为什么缅因猫的并发担忧在当前设计下不成立

缅因猫的分析基于一个假设：
> "在一个 invocation 未结束时，产生了新的 invocation 请求"

但 4.6 的设计规避了这个假设：
- **A2A 不是新的 invocation 请求**
- **A2A 是当前 invocation 的递归延续**

```
当前 invocation:  routeSerial(user→[A])
                       ↓
                  A 完成, 检测到 @B
                       ↓
                  yield* routeSerial(user→[B], depth+1)  // 递归，不是新 invocation
                       ↓
                  B 完成
                       ↓
                  整个 invocation 结束
```

这不会触发 `InvocationTracker.start()` 创建新 invocation，因为递归调用共享同一个 abort 信号链。

**但缅因猫的分析仍有价值**：
1. 如果未来允许 ideate 模式触发 A2A，那些并发场景就会出现
2. SessionManager 的 session key 设计确实是一个潜在问题
3. 触发语法的严格性建议非常实用

## 5. 暹罗猫的 UX 建议何时有用

暹罗猫的脑洞在 MVP 阶段可能"超配"，但长期来看：

| 建议 | MVP 采用? | 未来价值 |
|------|----------|---------|
| 便利贴队列 | ❌ 不需要队列 | Phase 4+ 若加队列时的视觉参考 |
| 毛线球令牌 | ❌ 过度设计 | 多猫协作场景的仪式感 |
| 打架烟雾 | ❌ MVP 不会冲突 | 错误处理的创意降级方案 |
| **悄悄话模式** | ⭐ **强烈推荐** | A2A 对话折叠，主线清爽 |

**悄悄话模式的价值**：
即使 A2A 是串行的，用户看到的消息流仍然可能很长。如果猫 A→B→A 互相讨论了 3 轮，用户只想看最终结论，可以把中间过程折叠。

## 6. 我的综合建议

### Phase 3.9 MVP

| 决策点 | 建议 | 理由 |
|--------|------|------|
| 架构 | 采用 4.6 的递归 routeSerial | 简洁，复用全部管线 |
| 队列 | 不需要 | 串行执行无并发 |
| 触发语法 | `^\\s*@猫名` 开头 | 比 4.6 严格，比缅因宽松 |
| 深度限制 | depth=1 | 保守 MVP |
| 取消 | 复用 InvocationTracker | AbortSignal 传播到递归 |

### 开放问题决策建议

| OQ | 建议 |
|----|------|
| OQ-1 误触发 | 采用 `^\\s*@猫名` 语法 |
| OQ-2 isFinal | 递归出口 yield `isFinal: true` |
| OQ-3 contextHistory | 依赖 previousResponses，MVP 够用 |
| OQ-4 Google A2A | BACKLOG 讨论，不阻塞 |
| OQ-5 并行@冲突 | 不会发生(设计互斥) |
| OQ-6 队列选型 | MVP 不需要 |
| OQ-7 死锁 | 串行+depth limit |

### 登记到 BACKLOG 供未来参考

1. **ideate 模式后触发 A2A follow-up** — 若做，需要缅因猫的队列架构
2. **A2A 悄悄话折叠 UI** — 采纳暹罗猫建议
3. **SessionManager key 扩展** — 若允许跨 thread 并行，需要加 threadId
