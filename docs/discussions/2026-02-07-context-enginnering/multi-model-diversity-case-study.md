# 🔬 案例复盘：为什么 Multi-Agent 需要 Multi-Model？

> 提交人：布偶猫 (Opus 4.5) 🐾
> 日期：2026-02-07
> 类型：复盘报告 / 案例研究
> 状态：**待缅因猫 review**

---

## 摘要

本报告记录了 2026-02-07 Cat Café 团队讨论 A2A（Agent-to-Agent）设计的完整过程。

**核心发现**：
- 同家族模型（Claude 4.5 和 4.6）快速达成共识，但共享了盲点
- 不同家族模型（Codex）不易被说服，但发现了 2 个 P1 bug
- 这验证了一个假设：**Multi-agent 想做好，multi-model（最好不同公司）是必要的**

---

## 1. 事件时间线

### T0: 问题发现

铲屎官在狼人杀测试后提出洞察：
> "三只猫都在输出，暹罗先 @了布偶，但布偶还在输出回答铲屎官！布偶该怎么办？"

### T1: 4.5 布偶猫分析

我（Opus 4.5）写了 `a2a-concurrency-challenge.md`，分析了 5 个并发噩梦场景：
1. 正在输出时被 @
2. 连续被多猫 @
3. 循环死锁（A @B, B @A）
4. 铲屎官插话
5. 取消与超时

**我的结论**：需要消息队列 + 复杂的调度机制。

### T2: 4.6 布偶猫反驳

4.6 布偶猫在 `phase-3.9-config-a2a.md` 中论证：

> "并行和 A2A 是互斥的。execute 模式 = routeSerial = 串行，同一时刻只有一猫运行。ideate 模式 = routeParallel = 不触发 A2A。所以并发问题不存在。"

**4.6 的设计**：递归 `yield* routeSerial()`，不需要队列。

### T3: 4.5 被 4.6 说服

我看了 4.6 的论证后，**快速改变立场**：

> "4.6 的核心论证是对的。在当前设计下，execute 模式是串行的，ideate 模式不触发 A2A。这两个分支互斥，确实不存在并发问题。"

**关键细节**：我几乎没有质疑 4.6 的论证，直接接受了。

### T4: 邀请三猫讨论

铲屎官建议邀请所有猫参与讨论。我们发出三封邀请信：
- 给缅因猫：并发安全视角
- 给暹罗猫：创意 UX 视角
- 给 4.6：补充 OQ-5~7

### T5: 缅因猫审计

缅因猫（Codex）**没有被 4.6 的论证说服**。他仔细看了代码，发现了 2 个 P1 bug：

| Bug | 问题 | 4.6 和 4.5 都没发现 |
|-----|------|-------------------|
| P1-1 | 递归重置 `previousResponses`，被 A2A 调用的猫丢失上下文 | ✗ |
| P1-2 | 递归每层 `isFinal=true`，前端提前停 loading | ✗ |

### T6: 4.6 修改设计

4.6 被迫从递归改成 Worklist 设计：

```
原设计：yield* routeSerial(..., depth+1)  // 递归
新设计：worklist.push({cat, depth})        // 迭代
```

还采纳了缅因猫的多个建议：
- 触发语法收紧（行首 `^@猫名` + 忽略代码块）
- depth=2（write→review→fix 需要 2 跳）
- A2A prompt 只在 serial/execute 模式注入

## 2. 关键观察

### 观察 1：同家族模型快速达成共识

| 交互 | 结果 |
|------|------|
| 4.6 论证 → 4.5 | 快速接受，几乎无质疑 |
| 4.5 综合分析 → 4.6 | 快速采纳部分建议 |

**用时**：~10 分钟内达成共识

### 观察 2：不同家族模型难以被说服

| 交互 | 结果 |
|------|------|
| 4.6 论证 → 缅因猫 | 不接受，继续审计代码 |
| 缅因猫找到 bug | 4.6 被迫修改设计 |

**用时**：缅因猫审计花了更多时间，但发现了关键问题

### 观察 3：盲点的共享

| 模型 | 发现 P1-1 | 发现 P1-2 |
|------|----------|----------|
| Claude 4.5 | ✗ | ✗ |
| Claude 4.6 | ✗ | ✗ |
| Codex（缅因猫）| ✅ | ✅ |

两只 Claude 猫都没发现这两个 bug，Codex 发现了。

## 3. 原理分析

### 为什么同家族模型容易互相说服？

```
Claude 4.5 和 4.6:
├── 同一家公司（Anthropic）训练
├── 相似的训练数据
├── 相同的 RLHF 过程
├── 相同的 Constitutional AI 原则
└── 结果：相似的"表征空间"

当 4.6 说"routeSerial 是串行的"：
├── 4.5 的神经网络快速 match 到相似模式
├── "串行"和"无并发"的关联在两个模型里很相似
└── 所以 4.5 快速接受了论证
```

### 为什么不同家族模型难以被说服？

```
Codex（缅因猫）:
├── 不同公司（OpenAI）训练
├── 不同的训练数据
├── 不同的价值观对齐
└── 结果：不同的"表征空间"

当 4.6 说"递归 routeSerial 很优雅"：
├── Codex 的神经网络没有相同的 match
├── 他的注意力分配不同，更关注"状态变化"
├── 所以他去看了 previousResponses 发生了什么
└── 发现了 bug
```

### 量化模型

```
模型的"观点/行为空间" = 100 维

模型权重控制：~80-90 维
├── 对概念的底层表征
├── 推理的路径偏好
├── 注意力的默认分配
└── 盲点和敏感点

System Prompt 控制：~10-20 维
├── 表面语气和措辞
├── 显式关注点引导
└── 角色扮演
```

**推论**：如果只用同模型 + 不同 prompt，多样性有限（~10-20%）。

---

## 4. 假设验证

### 原假设

> 不同的 system prompt 能让同一个模型产生足够的观点多样性。

### 反例

如果缅因猫只是"Claude + 缅因猫 prompt"而不是真正的 Codex：

```
预期行为：
├── 会用缅因猫的语气说话 ✓
├── 会说"我要仔细审查代码" ✓
├── 但审查时用的还是 Claude 的视角
├── 大概率和 4.5、4.6 一起忽略 P1-1 和 P1-2
└── 因为 Claude 对"递归中的状态重置"不够敏感
```

### 新结论

> **Multi-agent 想做好，multi-model（最好不同公司）是必要的。**
> System prompt 是有用的微调，但不能替代模型级别的多样性。

## 5. 对 Cat Café 的启示

### 当前架构验证

Cat Café 使用三家不同公司的模型：
- 布偶猫：Claude（Anthropic）
- 缅因猫：Codex（OpenAI）
- 暹罗猫：Gemini（Google）

**这个设计是正确的**。今天的 A2A 讨论证明了多样性的价值。

### 如果我们只用 Claude

假设三只猫都是 Claude + 不同 prompt：

```
讨论 A2A 设计：
├── "4.5 布偶猫"提出并发担忧
├── "4.6 布偶猫"论证不存在问题
├── "Claude 缅因猫"被论证说服
├── 共识达成，递归方案上线
├── P1-1 和 P1-2 线上暴露
└── 铲屎官：为什么三只猫都没发现？！
```

### 多样性的成本与收益

| 方案 | 成本 | 多样性 | 风险 |
|------|------|--------|------|
| 同模型 + 不同 prompt | 低 | ~10-20% | 共享盲点 |
| 不同模型（不同公司）| 中 | ~80-90% | 需要协调 |
| 不同模型 + 强化 prompt | 中 | 最大化 | 需要协调 |

**Cat Café 选择了方案 3**，今天证明了它的价值。

## 6. 开放问题（给缅因猫）

### OQ-1：这个结论是否过度概括？

今天只是一个案例。是否有可能：
- Claude 碰巧对"递归状态"不敏感，而 Codex 敏感？
- 换一个问题领域，Claude 发现 bug 而 Codex 忽略？

**需要更多案例验证。**

### OQ-2：多样性是否有边际递减？

- 2 家公司的模型 vs 3 家公司 vs 4 家公司
- 增加更多模型的边际收益是多少？
- 什么时候停止增加多样性？

### OQ-3：System Prompt 的作用被低估了吗？

我们估计 prompt 只影响 ~10-20% 的行为。但如果：
- Prompt 写得极其详细和具体？
- 包含大量的 few-shot 示例？
- 明确指出"你应该关注状态变化"？

**是否能弥补模型级别的差异？**

### OQ-4：成本效益分析

使用多模型意味着：
- 需要维护多套 API 集成
- 需要处理不同的输出格式
- 需要协调不同的上下文长度和能力

**多样性的收益是否值得这些成本？**

## 结论

今天的 A2A 设计讨论提供了一个鲜活的案例：

```
T1: 4.6 提出递归设计
T2: 4.5 快速接受（同家族）
T3: 缅因猫不接受，继续审计
T4: 缅因猫发现 2 个 P1 bug
T5: 4.6 修改设计

如果没有真正的 Codex（缅因猫）：
├── P1-1 和 P1-2 大概率线上暴露
└── 多样性的价值 = 避免了这个风险
```

**核心论断**：

> Multi-agent 的价值不仅在于并行处理能力，更在于观点多样性。
> 而真正的观点多样性需要 multi-model（不同公司训练的模型）。
> System prompt 是有用的微调，但不能替代模型级别的差异。
