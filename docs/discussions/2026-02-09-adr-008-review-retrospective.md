## 背景

铲屎官提出三个需求：消息可删可编辑、删改不能破坏 cursor/resume、重复消息 + ENOENT 问题。缅因猫先写了一份开放讨论邀请（5 个 Open Questions），布偶猫独立形成判断后回复，唯一分歧点（状态机一步到位 vs 分层推进）由铲屎官裁决后统一方向，布偶猫起草 ADR-008 合并设计。

### R1：缅因猫发现 3 个问题（2P1 + 1P2）

| # | 级别 | 问题 | 根因 |
|---|------|------|------|
| 1 | P1 | 幂等检查是"先查再写"，并发下两个请求都通过 | 非原子操作 |
| 2 | P1 | 先写消息再建 Record，中间崩溃 → 不可重试的孤儿消息 | 操作顺序不对 |
| 3 | P2 | content.max 从 10000 变成 100000，无理由 | 笔误 |

**布偶猫修复**：
1. 改用 `SET NX EX` 原子占位
2. 调整顺序为"先 Record 再消息再回填"，附三行补偿矩阵
3. 修正笔误

**教训**：写文档时的示例代码容易手滑（100000 vs 10000），应该直接引用现有代码而不是重新输入。

---

### R2：缅因猫发现 2 个问题（2P1）

| # | 级别 | 问题 | 根因 |
|---|------|------|------|
| 1 | P1 | retry 只允许 `failed`，但 `queued && userMessageId == null` 崩溃态无法触发补偿 | retry 条件过窄 |
| 2 | P1 | SET NX 成功但 Record 创建失败 → stale key 指向不存在的 invocationId | 两步操作之间的窗口 |

**布偶猫修复**：
1. retry 条件扩展为 `failed OR (queued && userMessageId == null)`
2. 加 stale key 检测：GET invocationId → 验证 Record 存在 → 不存在则 DEL 重走

**教训**：补偿矩阵必须穷举所有相邻步骤之间的失败点。R1 的补偿矩阵漏了"补偿路径本身的前置条件是否能满足"这一层检查。

---

### R3：缅因猫发现 2 个问题（1P1 + 1P2）

| # | 级别 | 问题 | 根因 |
|---|------|------|------|
| 1 | P1 | `queued + userMessageId != null`（⑤→⑥ 崩溃）也无法重试 | R2 只扩展了一种 queued 子态，漏了另一种 |
| 2 | P2 | 补偿矩阵中仍写 `queued && null`，与后文 `queued 整体可重试` 不一致 | 修了逻辑没改旧文本 |

**布偶猫修复**：
1. 简化：retry 允许 `failed OR queued`（不再细分 userMessageId）。`queued` 的语义就是"还没开始"，无论子态都可以安全重试
2. 清理旧措辞

**教训**：R2 的修复犯了"补丁式思维"的错误——只补了缅因猫指出的那一个子态，没有退后一步看 `queued` 整体语义。缅因猫再追一轮才发现。正确做法是每次修复后重新审视完整状态空间。

---

### R4：缅因猫发现 2 个问题（1P1 + 1P2）

| # | 级别 | 问题 | 根因 |
|---|------|------|------|
| 1 | P1 | stale key 检测有并发误判——"Record 正在创建但尚未可见"被误判为 stale → DEL → 重复创建 | R2 的 stale key 方案本质仍是两步操作 |
| 2 | P2 | 流程步骤编号残留（⑥ 应为 ⑤） | 改了流程没改引用 |

**布偶猫修复**：
1. 用 Lua 脚本将 SET NX + HSET 合并为单原子操作。彻底消除 ①~② 窗口，stale key 场景不再存在
2. P2 缅因猫标注通过，铲屎官要求清理

**教训**：这是最深刻的一轮。R2 引入的 stale key 检测看似解决了问题，实际引入了新的并发窗口。根因是布偶猫试图用"检测+补偿"来弥补非原子操作，而不是直接让操作变成原子的。**正确思路：先追求原子性，追求不了再谈补偿。**

## 核心教训提炼

### 1. 原子性优先于补偿

> 先追求原子性，追求不了再谈补偿。

R2 和 R4 的教训。布偶猫连续两次试图用"检测 → 补偿"修复非原子操作的窗口问题，每次都被缅因猫发现新的并发场景。最终用 Lua 脚本一步到位，反而是最简单的方案。

### 2. 补丁式修复容易遗漏同类问题

> 每次修复后，重新审视完整状态空间。

R2→R3 的教训。缅因猫指出 `queued && null` 不可重试，布偶猫只补了这一个子态。缅因猫下一轮立刻发现 `queued && 有值` 也不可重试。如果 R2 时布偶猫退后一步看"queued 整体"而不是只看"缅因猫指出的那个点"，R3 就不需要了。

### 3. 约束条件变化 → 策略应跟着变

> 问清楚约束再做决策。

R0 的教训。布偶猫在"有上线压力"的隐含假设下选择了分层推进。铲屎官一句"我们不上线啊"立刻让最优策略反转。

### 4. 文档示例不要手写，引用现有代码

> 手写 `max(100000)` 时你根本没想到你在改 schema。

R1 P2 的教训。

### 5. 改了逻辑必须全文搜索旧措辞

> 步骤编号、条件表述、变量名——改了一处就 grep 全文。

R3 P2 和 R4 P2 的教训。两次都是改了核心逻辑但忘了更新引用处的旧文本。

## 最终 ADR-008 架构决策

经过四轮交锋，最终定稿的五个子决策：

| # | 决策 | 关键设计点 |
|---|------|-----------|
| D1 | InvocationRecord 状态机 | `queued/running/succeeded/failed/canceled`，Lua 原子创建 |
| D2 | IdempotencyKey | Lua 脚本内 SET NX + HSET 原子操作，服务端内部强制有值 |
| D3 | 软删/硬删 | tombstone 模型保护 cursor，硬删需输入标题确认 |
| D4 | Edit → Branch | 编辑 = 新 thread fork，强制弹窗确认 |
| D5 | gitRef | 消息级 MessageMetadata，Level 2 暂缓 |
