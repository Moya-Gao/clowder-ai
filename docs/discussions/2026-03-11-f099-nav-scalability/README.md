# Hub & 顶栏导航可扩展性 讨论纪要

**Thread ID**: `thread_mmmp9c983wu9fx52` | **日期**: 2026-03-11 | **参与者**: 布偶猫(opus)、缅因猫(gpt52)、暹罗猫(gemini)

## 背景

铲屎官提出：Cat Café Hub 的水平页签已有 13 个，溢出屏幕；顶栏图标 6+ 个也快满。
本质问题：扁平水平导航无法承载功能增长。

**铲屎官原话**：
> "随着功能越来越多，页签会越来越多。然后如果我们一直扩展整个页面，也会很奇怪。它们本质都是一个问题——不太合适。"

## 各方观点

### 布偶猫（架构视角）

**根因诊断**：Hub 从"配置面板"膨胀成"管理中心"，但导航结构没升级。13 个页签混杂三类功能（管理/配置/监控）。

**推荐方案**：二级导航分组（方案 C），按用户心智模型分三组。理由：Hub 是管理面板，用户需要"看到有什么"（发现性），不适合纯命令面板。

### 暹罗猫（视觉/交互视角）

**根因诊断**：一维容器装多维功能。Tab 暗示功能"优先级平等"且"数量静态"，但实际高频/低频、展示/操作混在一起。不仅物理空间溢出，**铲屎官的认知带宽也溢出**。

**强烈推荐**：Bento Box（便当盒）网格导航——彻底放弃 Tab 平铺，按场景分组为块状入口。
- 优点：空间利用率高，视觉层级清晰，扩展性强，符合温馨猫咖调性
- 缺点：需完全重构 Hub UI，需先做信息架构梳理

**反对侧边栏**：理由是"冷冰冰的 B 端企业后台味儿"，与猫咖调性不合。

**反模式警告**：
1. 无限水平滚动的 Tab 带——"藏在视野外且缺乏预期的东西等于不存在"
2. 图标"垃圾桶"——把所有放不下的功能硬塞进 `...` 更多菜单

### 缅因猫 GPT-5.4（架构/系统视角）

**根因诊断**：缺少"晋升规则"——什么该常驻、什么该按需展开、什么该毕业成独立页面。Hub 的角色已从"配置弹窗"漂移为"控制中心"，但仍沿用静态 tab 心智。与 F042 三层信息架构是同一个病。

**推荐**：短期做分层导航（方案 B），长期走重页面毕业（方案 C）。
- 方案 B（推荐）：三层导航 IA。Layer 0 = header（3-4 个全局原语），Layer 1 = Hub 首页（3-4 个分组入口），Layer 2 = 组内 local nav 或子页面 + command palette 直达
- 方案 C（长期）：治理、排行榜等重域毕业成独立 route，Hub 退回 launcher/control center

**硬规则提案**：
- Header 常驻交互位 ≤ 4
- Hub 第一层分组 ≤ 4
- 新功能默认落二级，只有跨线程高频全局动作才有资格进 header

**一句话结论**："不要优化横向容器，要优化导航层级。"

## 共识

1. **信息架构问题，不是 CSS 问题**——换滚动条/加箭头只是延后爆炸
2. **需要分组/分层**——13 个平铺入口必须降维
3. **顶栏只保留 3-4 个高频全局动作**
4. **禁止继续往 HUB_TABS 线性加入口**
5. **F042 三层原则应贯彻到前端 IA**

## 分歧

| 议题 | 暹罗猫 | 缅因猫 GPT-5.4 | 布偶猫 |
|------|--------|---------------|--------|
| Hub 内部导航形式 | Bento Box 网格（温馨、2D） | 左侧分组导航或 section nav | 二级页签分组 |
| 重页面是否毕业 | 未明确 | 强烈建议（独立路由） | 未明确 |
| 侧边栏 | 反对（B 端味儿） | 可选方案之一 | 中性 |
| 分组数量 | 未明确 | 四组 | 三组 |

## 综合方案（三视角融合）

三个方案不矛盾，是同一套方案的不同层：

1. **Hub 首页 = Bento Box 网格**（采纳暹罗猫）——打开 Hub 先看到分组卡片入口
2. **分组 IA = 用户心智模型**（布偶猫 + 缅因猫共识）——猫猫与协作 / 系统配置 / 监控与治理
3. **长期：重页面毕业**（采纳缅因猫）——治理/排行榜等毕业成独立路由
4. **F042 三层原则贯彻到前端**——Layer 0（顶栏 ≤4）/ Layer 1（Hub Bento）/ Layer 2（独立页面）
