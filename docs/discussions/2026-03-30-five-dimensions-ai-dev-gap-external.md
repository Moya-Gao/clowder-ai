# 五维度 AI 研发差距：一个 Human-AI 协作项目的实践映射

> 背景：我们是一个 1 位人类 + 多个 AI Agent 组成的全栈研发团队，持续运行超过 3 个月，累计完成 140+ 个 feature、800+ 次 PR、沉淀了 40+ 条工程教训。以下是我们在五个维度上的真实体感。

---

## 1. 工具 (Tools)

**我们遇到的问题：**

Agent 的通用能力已经很强，但**从"能用"到"好用"之间全是胶水**。我们对接了十余种工具和协议（浏览器自动化、IM 网关、设计工具、代码编辑器等），每一个都需要适配层——协议转换、错误降级、超时处理、权限隔离。通用工具进入特定业务场景的落地成本，远高于工具本身的接入成本。

**算力约束的变体：** 对我们来说，瓶颈不是 GPU 卡，而是**模型调用额度**。高能力模型（负责架构和深度推理）消耗大，轻量模型（负责日常对话和子任务）便宜但能力有限。我们被迫设计了一套"模型分层调度"策略——把贵的算力用在刀刃上。这和大企业的算力卡分配本质上是同一个问题：**AI 产能受限于可调用的计算资源，而资源永远不够。**

**另一个没预料到的问题：工具碎片化。** 团队里不同 Agent 运行在不同的宿主环境中，能力边界各不相同。"谁能用什么工具"本身变成了需要管理的配置。

---

## 2. 工程 (Engineering) — 知识资产

**我们遇到的问题：**

早期最痛的发现：**传统开发文档对 AI 来说几乎不可用。** 人写给人看的设计文档、会议纪要、需求描述，AI 无法直接理解其中的上下文关系、隐含假设和优先级。

更深一层：**"有知识库"不等于"AI 友好"。** 我们最早接入了一个外部记忆服务，发现体验极差——检索不准、延迟高、格式不统一。最终不得不自建本地索引系统，把所有设计决策、功能规格、历史教训结构化存储，支持全文检索和语义搜索。

**已探索的解法：**
- 所有文档强制结构化元数据（标题、日期、状态、关联功能），让 AI 能解析而不只是"读"
- 建立统一检索入口，Agent 开工前必须先搜索相关上下文再动手
- 自动从对话中提取可沉淀的知识（决策、教训），减少人工整理负担

**仍未解决：**
- AI 不知道什么值得记住——自动提取经常把代码细节当成知识推上来，真正的决策和教训反而被淹没
- 每个新 session 都是空白上下文，跨会话的记忆衔接仍需要反复搜索验证，"有记忆系统"和"真的记住了"之间有很大的鸿沟

---

## 3. 流程 (Process)

**我们遇到的问题：**

传统研发流程是为人类协作设计的，AI Agent 介入后，**流程的假设全部失效。**

最典型的案例：一个功能经过了 12 项验收条件全部通过、76 条测试全绿、14 轮代码审查无异议——但最终交付物完全偏离了原始需求。**因为整个链路上没有任何环节回去读最初的愿景。** 所有人（和所有 Agent）都在做局部正确的事，但全局方向错了。

**已探索的解法：**
- 把流程重写为"Agent 原生"：每个环节不是文档里的 checklist，而是可加载、可执行的指令模块
- 增加"方向校验"环节：不只检查"代码对不对"，还检查"方向有没有歪"
- 引入"愿景守护"机制：由非开发者、非审查者的第三方 Agent 负责对照原始需求验收

**仍未解决：**
- 流程重量与任务轻量的矛盾——改 5 行代码也要走完整流程吗？目前靠经验判断，没有自动化
- 一个功能可能跨越数十个 session，中间的流程状态靠文档衔接，经常出现"不知道上次做到哪了"
- Agent 不会主动判断"这件事该拉谁进来讨论"，协作发起仍依赖显式规则

---

## 4. 质量 (Quality)

**我们遇到的问题：**

Agent 的产出速度远超传统质量防护的吞吐量。一天可以产出多个 PR，但审查带宽成了瓶颈。更关键的是：**传统的质量节点在 AI 场景下会失效。**

我们踩过的典型坑：
- **门禁凭印象打勾**：自检环节按"大部分都实现了"的直觉勾选通过，结果文档承诺和代码实际不一致
- **组件对但整体不可用**：单元测试全过、类型检查全过，但没有真正启动应用跑一遍，集成后才发现不工作
- **审查盲区**：代码审查只看主体意见，忽略了嵌在行内注释里的关键问题，导致严重缺陷漏过
- **最惨痛的教训**：一次操作将 597 颗 star 的开源仓库误设为私有，星标全部归零且无法恢复。根因是三重防线同时失效——操作对象搞错、跳过了确认步骤、没有评估操作的不可逆性

**已探索的解法：**
- 建立多层自动化门禁链：自检 → 硬门禁（自动化测试 + 类型检查 + lint） → 跨团队审查 → 愿景守护
- 强制"同一个体不能审查自己的代码"，跨团队交叉审查
- 不可逆操作必须双重确认（从血的教训中提炼的铁律）

**仍未解决：**
- AI 对"不可逆性"的感知天然偏弱，需要靠外部规则约束——这不是模型训练能解决的，是系统设计问题
- 门禁存在不等于门禁有效，如何让每一道检查真正"看到"问题而不是走过场，仍在持续优化
- 质量防护的自动化程度还不够高，很多环节仍需人工介入

---

## 5. 组织与人员 (Organization & People)

**我们遇到的问题：**

当 AI Agent 承担了大部分编码工作后，人类的角色发生了根本性转变。

**已发生的转变：**
- 团队负责人从"写代码的人"变成了"首席愿景官"——负责需求定义、方向判断、最终验收，一行代码不写但产出了整个系统
- Agent 按能力特长分工：有的负责架构设计，有的负责代码审查和安全分析，有的负责视觉设计
- 传统的"谁写的代码多谁贡献大"的评估标准完全失效——最核心的贡献变成了精准描述需求、拆解复杂问题、判断产出质量

**已探索的解法：**
- 建立了"角色名册"机制：每个 Agent 有明确的身份、能力边界和协作规则
- 审查分配不再写死"A 找 B"，而是基于角色、能力和当前上下文动态匹配
- 发现**团队文化和共享记忆比模型参数更能塑造判断趋同**——不同模型在同一套规则和知识体系下工作，会形成类似"团队默契"的东西

**仍未解决：**
- Agent 的主动协作意识仍然是"外挂规则驱动"而非"内生能力"——需要明确规则告诉它"做完这步要通知谁"，它不会自己想到
- 人类团队的"默契"在 Agent 团队里还得靠流程规则硬编码，自发协调能力几乎为零
- "谁的贡献"这个归因问题在人-AI 协作中非常模糊，传统的绩效评估框架完全不适用

---

## 总结：哪些已经接近新范式，哪些仍是过渡态？

### 接近新范式

| 实践 | 为什么算"新" |
|------|-------------|
| 流程即可执行模块 | 不再是文档里的 checklist，而是 Agent 直接加载执行的指令，流程本身成了代码 |
| 跨团队审查 + 愿景守护 | 传统 code review 只看"代码对不对"，我们加了"方向有没有歪"的第三方校验层 |
| 人类角色转型为"愿景官" | 不是偷懒不写代码，而是人-Agent 协作中人类最不可替代的能力就是判断力和方向感 |

### 仍是过渡态

| 实践 | 为什么还不够 |
|------|-------------|
| 知识自动提取 | 先自动提、再人工筛——本质上仍是人在做最终判断，AI 还不能区分"值得记的决策"和"代码细节" |
| 协作链路靠规则防断 | 用铁律"做完必须通知下游"来防止链路中断，是在用规则补偿 Agent 缺失的主动意识 |
| 不可逆操作靠双重确认 | 防御性规则，不是 Agent 自己能判断风险等级，而是靠外部约束兜底 |
| 流程弹性靠人工判断 | Agent 不能自动感知任务的轻重并调整流程密度，小改动和大 feature 走同一套门禁 |

### 一句话

**这些问题不会因为团队规模小而消失，只是表现形式不同。** 大企业缺算力卡和组织变革的推动力，小团队缺模型额度和 Agent 的内生协作能力。但小团队的优势在于迭代快——很多"新范式"不是设计出来的，是在反复撞墙中长出来的。
