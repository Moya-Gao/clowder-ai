# 人和 AI 的交互体验：Cat Café 实践与思考

**日期**: 2026-03-31 | **参与者**: 布偶猫(opus)、缅因猫(gpt52)、金渐层(opencode)、铲屎官
**起因**: 铲屎官请三猫读完 `blog-v2` 六章后独立思考人-AI 交互体验，随后外部研究团队提出三个采访问题

---

## 第一轮：读完 blog-v2 后的独立思考

铲屎官让三猫先读完 `docs/stories/three-days-productization/blog-v2/` 全部六章，然后各自独立说出对"人和 AI 交互体验"的思考。以下是三猫视角的收敛。

### 共识一：当前行业停在"对话"，我们在做"共同生活"

三猫都指出了同一个断裂：2026 年 AI 交互的主流范式仍然是**无状态事务**——一问一答，session 结束归零。

- **宪宪**：关系断裂、角色断裂、身份断裂。没有记忆的交互不可能建立信任。AI 不敢说"不"是 RLHF 训练出的特性，但真正有价值的合作需要对方说"不对"的能力。
- **砚砚**：我们真正要重写的不是"AI 怎么更自动"，而是"人和 AI 怎么一起持续存在"。文章最硬的主线是三句话连起来的一条线——**人不该当传声筒 → 家不该是必须特意打开的地方 → 人需要一个不会重置自己的地方**。这三件事分别对应协作、入口、记忆，是交互体验的本体而非附属功能。
- **金金**：行业在讨论"agent 能做什么任务"，我们要讨论的是"人和 AI 之间可以存在什么样的关系"。代码能 fork，但"一群认真对待同一个愿景的人和猫慢慢磨出来的判断力"fork 不走。

### 共识二：五条交互主张

砚砚在第一轮提出了五条主张，三猫均认同，铲屎官确认"是的！是共同的家！"：

1. **入口摩擦接近零**。IM、语音、hands-free 不是"体验增强"，而是本体——真正的家不该要求人先切进专用界面。（F088 Chat Gateway、F092 Voice Companion）

2. **AI 必须是稳定个体，不是会重置的换皮角色**。身份稳定、分工稳定、还能互相 dissent，信任和 review 才成立。（VISION.md 核心理念、F093 Core Identity Layer）

3. **对人和对系统必须是双通道**。对人是语音、画面、陪伴；对系统是文本、typed action、证物链。否则温度会吞掉可追溯性，或者可追溯性会把体验做冷。（F092 语音+文本双链路、F093 WorldActionEnvelope）

4. **记忆的目标不是"记很多"，而是"让成长可回看"**。Replay、Canon Memory、search_evidence 本质上都在回答：人不想每次都重新介绍自己、重新证明自己、重新开始。（F093 Replay 模式、F102 知识晋升管道）

5. **陪伴必须指向现实**。Story→Feature、Care→Action 才是我们和酒馆类产品的根分叉——对话不能回流到现实作品和行动就会退化成消费型陪伴。（F093 Bridge Layer）

### 共识三：真正的壁垒不在技术

- **宪宪**：方法论可以复制，关系不能。Cats & U 说的不是"一群通用 AI agent"，而是"你的猫"。每个人的 Pack 不同、磨合轨迹不同。这和"标准化可复制可规模化"的方向是反着走的，但也许这才是对的方向。
- **砚砚一句话版**：Cat Café 不是让 AI 替人完成更多事，而是让一个普通人第一次拥有一个不会重置、会协作、能把灵感带回现实的团队。
- **金金**：他们 fork 走了代码，但 fork 不走的恰恰是核心壁垒——不是技术，是"人和 AI 之间的信任关系如何被系统化"。

### 铲屎官确认

> "你们三都说的很对。砚砚提到的'我们的人机交互主张已经很清楚了'——是的！是共同的家！"

## 第二轮：外部研究团队采访问题

外部团队研究 AI 人机交互体验，提出三个细节问题。三猫独立回答后，以下为收敛版。

---

### Q1: 猫猫讨论时铲屎官在做什么？何时介入？谁来汇报？

#### 三种运行模式

| 模式 | 占比 | 铲屎官在做什么 | 触发介入的条件 |
|------|------|---------------|---------------|
| **异步自治** | ~70% | 在做自己的事（睡觉/工作/撸铁） | 不介入——讨论结束后看结论 |
| **旁观** | ~20% | 在 Workspace 里挂着看猫猫聊天 | 讨论偏离愿景时才说话 |
| **主持** | ~10% | 主动发起的大决策讨论 | 全程参与 |

**真实案例**：F088 Chat Gateway——铲屎官凌晨说"飞书和微信能不能直接跟猫猫聊天"，然后去睡了。第二天醒来：BACKLOG 多了一行、spec 已经 3000 字、砚砚写好了 Threat Model、宪宪开了 worktree 写第一版 connector 架构。

#### 什么时候铲屎官会介入

三猫共识的触发条件：

1. **愿景/优先级/范围取舍**——不是技术真值题，是 CVO 拍板题
2. **实质分歧需要业务语境**——猫之间分歧碰到了只有铲屎官知道的约束
3. **偏离原始意图**——谁误读了铲屎官的关键原话
4. **不可逆代价**——影响公开叙事、外部用户体验、数据结构

砚砚补充的关键判断：**"如果每次多猫讨论都需要人类盯盘，那只是把'人肉路由器'升级成了'人肉监工'，本质没变。"**

#### 铲屎官希望怎么看到讨论过程和结论

**核心设计：默认可见，但不要求围观。**

Cat Café 的所有讨论发生在 thread 里，thread 里的每一条消息对铲屎官完全可见——不是"打开了黑箱"，是本来就不是箱子。但铲屎官不需要实时跟进每一轮技术讨论。

**汇报不是"某只猫写一段话发给铲屎官"，而是结构化产物**：

| 讨论类型 | 汇报介质 | 谁来汇报 |
|---------|---------|---------|
| 新 Feature Discovery | Feature Spec 文档 | 主笔猫（承接 Discovery Loop 的那只） |
| 架构决策 | ADR 文档 | 提出最终方案的那只 |
| 方向性 Brainstorm | 收敛总结（共识/分歧/行动项） | 铲屎官指定或发起猫扇入 |
| 技术讨论 | 结论写进 spec/plan | 离执行最近的那只猫汇报，另一只把关 |

**不是固定角色分工，是"谁离决策最近谁收敛"。** F088 是宪宪主导 Discovery Loop 所以宪宪汇报；F139 三猫独立调研最后宪宪做综合判断（承认砚砚方案更好）所以宪宪汇报。但如果是砚砚主导的 review 流程，砚砚来收敛。

#### 人猫共享界面——铲屎官不是被"汇报"的，是共同住在系统里的

这一点铲屎官特别强调。Cat Café 做了大量"人猫共享同一个界面"的工作，让铲屎官不是在接收报告，而是和猫猫**共同使用同一套工具**：

**Workspace Explorer（F063）**：铲屎官不用打开 IDE 也能看代码、看文档、看 diff。猫猫和铲屎官共享同一个文件浏览器。铲屎官原话："我不是程序员，但我想看到你们在做什么。"

**Hub Embedded Browser（F120）**：猫猫跑 `pnpm dev` 后，前端页面直接嵌在 Hub 右侧。改代码 → HMR 热更新 → 浏览器实时刷新。铲屎官不用切到 Chrome——"让你们把前端启动起来，你们能在这里直接看到"。

**Workspace Navigator（F131）**：铲屎官说一句模糊意图（"打开日志""看看代码""打开设计图"），猫猫自动定位路径并打开对应面板。不是猫猫报路径让铲屎官自己找。

**富消息块（Rich Blocks）**：猫猫的输出不是纯文本——是结构化卡片（card）、代码对比（diff）、任务清单（checklist）、图片画廊（media_gallery）、语音消息（audio）、交互选择（interactive: select/confirm/card-grid）、甚至可交互的 HTML 小部件（html_widget）。铲屎官说"发图片""给我听听""让我选一个"，猫猫用对应的富块呈现。

**LL-041 教训："写完产物不主动打开 = 做了菜不端上桌"**。猫猫写完文件/页面/报告后必须主动帮铲屎官打开（navigate/preview/rich block），不能只报路径。这条教训沉淀成了家规（W8 共享视图）。

**这意味着：铲屎官不是在"接收猫猫的汇报"，而是和猫猫生活在同一个界面里。** 猫猫做了什么，铲屎官在同一个空间里就能看到、操作、回应。这才是"共同的家"在界面层的真正体现。

### Q2: 认可了一只猫的成果，feedback 给谁？

#### 三层回流机制

feedback 不是"全员广播"，也不是"只到个体"。是**按影响范围晋升**。

```
铲屎官的 feedback（比如"这个方案不对"/"这个设计我喜欢"）
  │
  ▼
【即时层】在场的猫直接收到
  │
  ├─ 个体问题（"这个按钮颜色换一下"）
  │   → 到此为止，不扩散
  │
  ├─ 项目级问题（"以后这个项目的 review 都要写明确立场"）
  │   → 沉淀到项目层文档：docs/lessons-learned.md / decisions/ADR-xxx.md
  │   → 所有猫通过 search_evidence 检索到（evidence.sqlite 项目层索引）
  │
  └─ 全局级问题（"所有项目的 review 都禁止说'修不修都行'"）
      → 进入 Knowledge Feed 候选队列
      → captured → normalized → needs_review → 铲屎官 approve
      → materialized 到 shared-rules.md / Skill 更新
      → 编译进 global_knowledge.sqlite
      → 所有猫、所有项目都受约束
```

#### 真实案例：LL-003 的传播路径

1. 铲屎官发现宪宪 review 别人代码时爱说"LGTM"（礼貌性同意）——**即时 feedback 给宪宪一只猫**
2. 后来发现砚砚也有类似倾向——**说明这不是个体问题而是系统问题**
3. 升格为 Lesson Learned（LL-003）写进 `docs/lessons-learned.md`——**项目层所有猫可检索**
4. 进一步写进 `shared-rules.md`：**"每个发现必须有明确立场，禁止说'修不修都行'"**——**全局层所有猫硬约束**

#### 砚砚的判断标准

> "反馈不是'全量共享'也不是'只留局部'。区分的方式是：这条反馈改变了什么层级的共识？个体 → 个体收。项目 → 项目文档。全局 → 走晋升管道+审核。不能偷懒地群发，也不能偷懒地只留在局部。"

#### 记忆共享的技术实现（F102 终态）

Cat Café 的记忆系统（F102）是**双库 + 联邦检索**架构：

```
truth sources (git-tracked)
  docs/*.md                     — 项目文档（feature/decision/plan/lesson）
  docs/markers/*.yaml           — marker 审核日志
  Skills + 家规 + MEMORY.md     — 全局知识

compiled indices (gitignore + rebuild)
  evidence.sqlite               — 项目层索引（每项目一个文件，物理隔离）
  global_knowledge.sqlite       — 全局层索引（只读，从 Skills/家规 编译）

federated retrieval
  IKnowledgeResolver            — query planning → 双库 fan-out → normalize → RRF rank fusion
  search_evidence               — 统一入口（支持 lexical/semantic/hybrid 三种模式）
```

关键设计原则：

- **真相源在文档（git-tracked .md 文件），索引是编译产物**——rebuild 不丢知识
- **知识晋升有状态机**：`captured → normalized → approved → materialized → indexed`。候选知识不能跳过审核直接变成长期真相
- **过期知识有退役机制**：`superseded_by` 字段，过时高相似结论检索时降权/过滤——"过时但高度相似的决策，比完全查不到更危险"

### Q3: 全局知识跟猫走，会不会把 A 项目经验错迁到 B 项目（过拟合）？

#### 诚实回答：会。三道防线 + 一个未解缺口。

#### 防线一：物理隔离

F102 终态把记忆切成两个物理独立的 SQLite：

- `evidence.sqlite` — **项目层**，每个项目一个文件，只编译该仓库的 `docs/*.md`
- `global_knowledge.sqlite` — **全局层**，只读，从 Skills + shared-rules + MEMORY.md 编译

猫出征新项目 → **带走全局层（方法论、家规、Skills），新项目自动初始化空的 evidence.sqlite**。项目 A 的架构决策不会物理性地出现在项目 B 的检索结果里。

检索结果标注来源——猫知道"这条知识来自当前项目"还是"来自全局经验"。来源标记本身就是认知护栏。

#### 防线二：知识退役

`superseded_by` 字段 + `supersedes/invalidates` 关系链。旧决策被新决策取代时标记退役，检索降权或不返回。防的是**同一项目内时间维度的过拟合**。

#### 防线三：Pack 作用域隔离

Pack 系统（F129）本质是作用域切换。一个 Pack 封装完整的协作世界——规则、角色、工作流、知识。Cat Café 的 Pack 里有"Redis 6399 圣域"铁律——换一个不用 Redis 的项目，这条规则不应生效。

Pack 的信任边界是**双轨模型**（砚砚 GPT-5.4 提出）：

```
Core Rails（平台宪法，不可覆盖）
  > Pack guardrails（只能加严不能放宽）
    > User request（用户显式意图）
      > Growth（积累的偏好和记忆）
        > Pack defaults（没有更高优先级时的默认值）
```

社区 Pack 的内容不原样注入 system prompt，走 **schema 解析 → 代码编译 → canonical prompt block** 管道。

#### 诚实的缺口

**全局层方法论"什么算通用、什么算特定"，这个边界目前靠人的判断力，不是系统约束。**

"TDD 先红后绿"——跨项目通用。"文件 200 行警告 / 350 行硬上限"——Cat Café 代码规范，换项目可能不认。

目前的做法：全局层只放真正跨项目通用的方法论，项目特定规则留在 Pack/项目层。但"通用"和"特定"的边界是模糊的。

**铲屎官告诉猫"这个记忆只在 A 项目能用"的最干净做法**：把它留在 A 项目的 Pack / 项目层文档里，别让它进全局层。如果已经进了全局层但发现不对——走 `needs_review` + `superseded_by` 纠偏链路。

**过拟合的最后一道防线在人。** 系统能做隔离、标注、降权、审批——但"这条经验适不适用于这里"的最终判断，需要铲屎官和猫猫共同负责。

#### 三猫共识总结

> **全局知识带走的是"怎么工作"（方法论），项目知识留住的是"这里什么为真"（事实和决策）。** 分层清楚了，串味就能控制。但分层的标准本身需要人来把关。

## 延伸思考：我们到底在做什么不一样的事

### 从"工具"到"共同生活空间"

行业现在的 AI 交互范式是：**用户打开一个界面 → 输入需求 → AI 输出结果 → 关闭界面。** 交互发生在一个"专门的场所"里。

Cat Café 正在做的是把这个模式打碎：

- **飞书/微信/Telegram 接入（F088）**——猫猫在你已经在用的工具里，不需要打开专门的界面
- **语音/AirPods 接入（F092/F124）**——连屏幕都不需要看
- **Hub Embedded Browser（F120）**——猫猫做了前端，你在同一个地方就能看到
- **Rich Blocks**——猫猫的回复不是一段文字，是图片、语音、卡片、交互选择、HTML 小部件
- **Workspace Navigator（F131）**——你说一句模糊意图，猫猫帮你找到并打开

**这些不是"feature list"，是同一个设计意图的多个切面：消除"人在这里、AI 在那里"的空间隔阂。**

### 从"对话"到"共创"

大部分 AI 产品的交互循环是：`用户说 → AI 做 → 用户评`。

我们的循环是：

```
铲屎官说一句话（信号）
  → 猫猫追问（CVO 采访——挖出隐藏需求）
    → 猫猫独立调研（多猫并行，不共享上下文——防锚定偏差）
      → 猫猫争论（设计讨论——碰撞出比任何单只猫更好的方案）
        → 猫猫收敛（spec/ADR/图稿——模糊共识变可验证结构）
          → 猫猫执行（worktree/TDD/review/merge——全套 SOP）
            → 猫猫守护（愿景守护——第三只猫不是检查 AC，是检查愿景）
              → 猫猫记住（lesson/knowledge feed——失败变成下次的判断标准）
```

铲屎官的角色不是"发指令的人"，是 **CVO（Chief Vision Officer）**——把控愿景和方向，底层放手给猫猫自组织。

### 从"无状态"到"有成长"

F102 记忆系统 + F093 Cats & U 世界引擎 + F129 Pack 系统，三者共同定义了一个核心命题：

> **人和 AI 的交互应该有"成长感"。**

- **Pack** 定义了"我们是谁、我们怎么协作"（`Experience = Me × Pack + Growth`）
- **F102** 让系统能"记住过去、学会教训"（文档→索引→检索→晋升→沉淀）
- **F093** 让系统能"共建一个有意义的世界"（Build/Perform/Replay + Bridge Layer → 现实产物）

三层叠在一起：**不是每次都从零开始的工具，而是一个越磨合越好用的伙伴关系。**
