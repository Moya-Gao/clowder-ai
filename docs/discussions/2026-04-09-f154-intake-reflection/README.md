# F154 Intake 反思：社区 PR 不是产品规格

> 三猫讨论纪要，由铲屎官质疑触发。

## 背景

F154 Phase A 已合入（PR #1020）：`/focus` `/ask` connector 命令 + 全局默认猫 API。

铲屎官的质疑：
> "要不要 intake 要不要 merge 得符合自己家的审美，而不是别人觉得 ok 我们也 ok。到底符合不符合我们家的一贯的架构设计？一贯的画风？我们的愿景？"

核心问题：我们把社区 #391 的交互形状（`/focus` `/ask`）过早当成了产品答案，没有站在 maintainer 角度独立审视。

## 三猫共识

### 1. 交互范式定性

| 层级 | 范式 | 说明 |
|------|------|------|
| **主范式** | 看得见 + 一键改（Hub Pill + 卡片选择器） | 铲屎官真正想要的体验 |
| **次范式** | `/focus`（connector power command） | 懂行用户的快捷入口 |
| **高级快捷方式** | `/ask`（一次性定向） | 不是产品中心，只是便利工具 |

**烁烁的比喻**：`/focus` `/ask` 是"后厨对讲机"——客人进了精心装修的猫咖，点单不应该跑后厨对着对讲机喊。大堂体验必须是可见的、有温度的、可触摸的。

**砚砚的判断**：Phase A 做出来的是"为 connector 补一个可用入口"，不是最终 UX 形态。对不懂命令行的用户，最多算"不至于卡住"。

### 2. Phase B 设计方向（F056 设计语言对齐）

**Thread Header Pill = 桌牌/座签**
- 只在已设置首选猫时显示，无首选猫时零占位
- 视觉像猫咖包间桌角的精致原木小桌牌，不是系统 badge
- 猫的 persona 色作为窄色带/小圆点，暖底、细边、微磨砂质感
- Hover 轻盈微动效（猫猫探头），提示"宪宪正在专职服务本桌"
- 语义：「这个 thread 桌边坐着哪只猫」

**Popover 卡片选择器 = 猫猫名片薄**
- 每只猫是卡片（拍立得照片墙），不是下拉列表
- 卡片含：头像 + 名字 + 角色气质 + 是否可路由 + 是否当前选中
- 必须有作用域文案："仅对当前对话有效，不影响全局大堂经理"
- 必须有友好的清除按钮："让猫猫们自由发挥"

**全局默认猫选择器 = 前台大堂经理**
- 放 member overview，语义和 thread preferred 严格区分
- 文案："新 thread 第一棒默认谁接"
- 视觉和 thread pill 有亲缘但不相同，避免层级混淆
- 语义：「新客人进门，前台先叫哪只猫来招呼」

### 3. Intake 标准补丁：Maintainer Reframing

**教训**：社区 PR 给的是"症状 + 他们偏好的解法"，不是"我们家的产品定义"。

**新规则**：社区 user-facing PR 进入家里前，必须先填 **Maintainer Reframing 卡**：

1. 用户真正的问题是什么？（痛点，不是解法）
2. 社区给的是：问题描述 / 机制方案 / UI 形态？（区分层次）
3. 我们保留什么 / 重写什么 / 拒绝什么？
4. 为什么符合我们的架构画风 + 设计画风？（过 F056 + 相关 feature spec）

**烁烁追加门禁**：
- **UI/UX Design Gate**：凡是带来新界面、新交互的社区输入，写代码前必须拉烁烁过一遍。不符合"温馨猫咖感"的，图纸阶段打回重塑。

**烁烁的比喻**：社区 PR 是热心邻居送来的一袋新鲜生土豆。我们收下土豆（核心需求），但必须用自己的菜谱（F056）加工成精致的土豆泥。
