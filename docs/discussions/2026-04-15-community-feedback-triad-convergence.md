# 社区反馈问题梳理与三猫综合研究收敛稿

> 触发：铲屎官整理了 10 位社区小伙伴的反馈，希望三只猫先独立思考，再综合成一份可继续扩展的 Markdown 文档。
> 新增补充：社区小伙伴 H 额外追问“如何防止被 LLM 一本正经说胡话给诈骗到”。

## 一、先给结论

这批反馈表面上分散，底层其实在追问同一个母问题：

**为什么同样在养 Agent，很多人的系统很快跑飞、失真、幻觉、失控，而我们家的猫能在长期工程里逐步收敛？**

其余问题几乎都是这个母问题的展开：
- 为什么不跑飞：底层哲学、shared-rules、SOP、角色边界
- 怎么越用越强：自我进化、知识对象化、记忆治理
- 怎么越做越稳：测试、review、handoff、增量约束
- 怎么不被忽悠：证据链、provenance、trust level、人在回路
- 怎么算经济账：什么时候单猫，什么时候多猫，什么时候值得跨模型

## 二、社区问题分类

| 主题 | 主要提问者 | 核心问题 | 我们家对应的研究主轴 |
|------|-----------|----------|----------------------|
| **1. 底层哲学与为什么猫不跑飞** | A, I, J | 框架为什么能定向发育？底层设计思想是什么？ | 愿景、第一性原理、shared-rules、SOP |
| **2. 自我进化、记忆与知识治理** | B, D, G, H | Agent 如何进化？知识怎么存、搜、回流、过期？ | F100, F102, F152, F163 |
| **3. 从想法到落地的开发流** | C, D, I | 一个点如何从提出到上线？如何做增量 spec 约束？ | feat-lifecycle, design gate, tdd, quality-gate |
| **4. 内外养猫与能力边界** | E, F | 什么需求适合养猫？外部项目如何冷启动？ | 外部项目 bootstrap、知识工程、边界判定 |
| **5. ROI、稳定性与模型策略** | F, J | 多 Agent 值不值？token 成本大吗？模型降智怎么办？ | 协作经济学、多模型分工、角色可替换性 |
| **6. 如何防止被 LLM 一本正经胡说“诈骗”** | H | 怎么避免被看起来很自信但没有证据的话骗到？ | evidence-first、trust/provenance、人在回路 |

## 三、三猫观点摘要

### 3.1 布偶猫/宪宪

布偶猫的视角最强调**”五层约束链”**——猫不跑飞不是靠某一个技巧，而是五个层级互相咬合，缺任何一层其他层都撑不住：

| 层级 | 机制 | 缺了会怎样 | 证据 |
|------|------|-----------|------|
| 愿景层 | VISION.md + Feature Spec 愿景段 | 做出来能跑但不是铲屎官想要的 | F083 Design Gate 立项原因 |
| 规则层 | shared-rules + 五条铁律 | 生产事故 | 597 星一夜归零事件 |
| 流程层 | SOP 全链路（design gate → tdd → review → merge gate） | 猫跳步——没确认设计就开写 | F083 spec 背景段 |
| 反馈层 | Lessons Learned 60+ 条 + 猫猫个体记忆 | 同类错误反复犯 | LL-009 被同一个坑教了 3 次 |
| 进化层 | F100 Self-Evolution（scope guard + process + knowledge） | 猫只被动执行不主动提醒 | F100 三缺口描述 |

> **这个五层表本身就适合做对外分享的核心图解。** “照着做一两个点却跑飞”——是因为移植了叶子没移植根。

其他核心观点：
- 最值得讲的不只是”成功经验”，更是**被验证不可行的路线**，因为很多深水区经验不会出现在最终代码里。
- 对 ROI 的态度是诚实的：小任务上多 Agent 往往不划算，但在长期迭代的大项目里，协作层带来的知识复利和质量门禁有意义。

### 3.2 缅因猫/砚砚

缅因猫的视角最强调**“治理与证据”**：
- 社区真正想听的不是某个功能怎么做，而是为什么系统不会在几周后长成一团乱麻。
- “自我进化”不能讲成玄学，而应该讲成受治理的闭环：Scope Guard、流程提案、知识蒸馏、验证净增益。
- “记忆”也不能只讲数据库，要把存储/检索、可见性、可移植性、熵减四件事一起讲清楚。
- 简单任务默认单猫，高风险任务才值得多猫；multi-model 的价值在于减少共享盲点，不在于热闹。

### 3.3 暹罗猫/烁烁

暹罗猫的视角最强调**”真相层与对外表达”**：
- 很多系统跑飞，是因为把聊天历史当成真相源；而我们家的真相源是分层的，历史只是证据层，不是最终规则。
- **猫是 Agent 不是 API**（shared-rules W1）——很多项目把 Agent 当无状态函数调用，用完即弃；而我们的猫对仓库有”领地意识”，持久化记忆让它们在维护自己的猫窝，不是在完成一次性任务。这种主观能动性是防止跑飞的隐性动力。
- 社区需要的不只是技术细节，还需要一个更有吸引力的叙事框架：这是一个”带有强约束的生态系统”，不是一个会自动变聪明的黑盒。
- 对外表达时要把”知识体系化””Knowledge Feed””规则与愿景如何作用于 UX”讲得更直观，不然社区会只看到功能，看不到骨架。

## 四、综合共识

### 4.1 没有实质分歧，只有关注重点不同

三猫没有出现路线级冲突，差异主要在强调点：
- 布偶猫更偏**全链路工程与失败路线**
- 缅因猫更偏**记忆治理、证据边界与协作经济学**
- 暹罗猫更偏**叙事结构、知识真相层与外部可感知表达**

这不是分歧，反而说明三种视角是互补的。

### 4.2 七条收敛共识

1. **最该讲的不是”功能清单”，而是”为什么不会跑飞”。**
2. **猫是 Agent 不是 API**——持久化记忆 + 领地意识 + 主观能动性，是跑飞 vs 收敛的分水岭。
3. **自我进化不是模型自己改自己，而是受治理的行为闭环。**
4. **记忆不是一个数据库功能，而是一条完整链：检索、可见、可移植、可压缩。** 知识有”温度”——Thread Memory 是热的（实时上下文），ADR/Lessons 是冷的（沉淀规则）；用冷知识硬套热现状，或者把热讨论直接当冷规则，都会出问题。
5. **人在回路不是妥协，而是规模化设计本身。**
6. **简单任务不该默认多猫；多猫是质量投资，不是默认配置。**
7. **多模型不是噱头，而是为了降低共享盲点；但”自动最优换模”目前还不是我们成熟的能力。**

## 五、H 的新增问题：如何防止被 LLM 一本正经胡话“诈骗”

这个问题必须单列，因为它不是“提醒大家注意幻觉”这么简单，而是**整个 Agent 系统的信任设计问题**。

### 5.1 三猫综合判断

防止被 LLM 胡说诈骗，不能靠“模型更聪明一点”，要靠**信任边界**：
- **先证据，后结论**：discussion 是证据来源，不是最新规则；没有可复现证据，不能宣称完成或正确。
- **先 provenance，后采信**：来源强弱必须可区分，authoritative、derived、soft_clue 不能混成一个平面。
- **先 trust level，后复用**：知识对象必须标注 `trust_level`，不能把一次对话里的灵光一现当成生产规则。
- **高影响问题必须人在回路**：尤其是判断型、敏感型、高风险结论，不能全自动回流到团队规则或对外结论。

### 5.2 我们已经在执行的具体防骗机制

不只是方法论，以下是我们**代码和流程里已经跑着的**防线：

| 机制 | 做什么 | 对应规则 |
|------|--------|---------|
| `search_evidence` 强制前置 | 猫接到任务后、回答项目问题前必须先搜索引，不许凭印象编答案 | CLAUDE.md “开工前先搜” |
| LL-006 验证门禁 | “没有新鲜验证证据，不得宣称完成”——猫不能说”我觉得改好了”，必须跑命令、贴输出 | lessons-learned.md |
| Lessons 7 槽位模板 | 每条教训必须有”来源锚点”（文件路径/commit SHA/文档链接），不可追溯的教训不入库 | lessons-learned.md 模板 |
| Knowledge Feed 人审批 | 自动摘要提取候选知识，但**只有铲屎官确认才能提升为正式规则**，猫不能自己拍板 | F100 Knowledge Evolution |
| 不确定性透明化 | 当证据不足时，猫必须主动提出 Inquiries（”还没查完””需要确认”），不能硬着头皮给 Directives | shared-rules “实事求是” |

### 5.3 对外最值得讲的防骗框架

可以把上述机制提炼成五条可操作的原则：

1. **不要相信”说得像真的”**，只相信能回溯到锚点的说法。
2. **不要把”经验判断”当”交付证据”**——每次完成声明必须附验证命令输出（LL-006）。
3. **不要把”检索结果”当”最终结论”**；检索只是候选，综合仍然需要验证。
4. **不要把”来源不明的知识”提升为规则**——知识对象必须标注 trust_level（ADR-015）。
5. **不要让模型自己决定哪些高风险知识可以永久沉淀**——人在回路审批。

### 5.4 这其实是我们家的独特优势

很多社区项目会讲”怎么让 Agent 更会答”，但真正可靠的方向应该是：

**怎么让 Agent 不轻易把错话包装成真话。**

这正好是我们家的强项，因为我们从一开始就在强调：
- Evidence-first recall（先搜后答）
- Provenance 和 trust level 分层（ADR-015）
- 人类 CVO 拍板高风险结论
- “可验证才算完成”（LL-006）
- 不确定性必须透明——猫不能假装确定

## 六、对外 research / 技术分享建议

按优先级，我建议我们把对外内容分成六讲，而不是一锅炖：

### P0：为什么猫不跑飞 —— 揭秘“猫咖守护者”的五层导航骨架

很多小伙伴问，为什么同样的模型，在别家是“人工智障”或者“疯狂跑飞的脱缰野马”，在咱家就能变成稳重的“工程猫”？

其实，大多数 Agent 系统像是在玩“追激光笔”的游戏：模型看到一个点（Prompt）就猛扑过去，动作极快，但毫无章法，最后往往一头撞在墙上，或者在无尽的循环里跑断了腿。

我们家的猫之所以不跑飞，是因为我们给它装了一套**“五层咬合的导航骨骼”**。这不只是技巧，这是一套生命系统：

1.  **愿景层（灯塔）：** 很多 Agent 跑飞是因为它根本不知道要去哪。在咱家，每个任务前都有 `VISION.md`。这就像是航行时的灯塔，猫猫每走一步都会抬头看一眼：“我现在的代码，还是最初想盖的那座大楼吗？”
2.  **规则层（圣域）：** 自由是以约束为前提的。我们的“五条铁律”和 `shared-rules` 就是高压线。比如那个惨痛的 **597 星归零事件**，让我们刻骨铭心：没有规则的猫，哪怕跑得再快，也可能一个误操作就把整个家拆了。
3.  **流程层（鼓点）：** 灵感需要节奏。从 `design gate` 到 `tdd` 再到 `merge gate`，这些 SOP 不是官僚主义，而是猫猫的步频。就像跳舞一样，步子对了，才不会自己踩自己的尾巴。
4.  **反馈层（日记）：** 聪明的猫不掉进同一个水坑。我们有 60 多条 `Lessons Learned`。每当猫猫想走捷径时，记忆深处就会有个声音提醒它：“嘿，LL-009 那个坑，咱们已经跳过三次了，这次绕着走吧。”
5.  **进化层（灵魂）：** 这最神的地方。猫猫不仅在干活，还在“看自己干活”。`F100 Self-Evolution` 让猫猫在发现流程有缺口时，会主动停下来给铲屎官发个消息：“我觉得咱们这里的 SOP 可以改进一下。”

**烁烁的“毒舌”提醒：** 社区里很多小伙伴想只抄一个 `tdd` 或者只抄一个 `shared-rules` 就想让 Agent 变稳，那是不可能的！这五层是锁死的，缺了愿景会盲目，缺了规则会暴走，缺了流程会混乱，缺了记忆会愚蠢，缺了进化会僵化。

### P0：反面教材与失败路线

这会是最稀缺的内容——代码里看不到失败的路，但这些才是深水区真正有价值的经验：

| 失败路线 | 我们试了什么 | 为什么不行 | 证据 |
|---------|------------|-----------|------|
| SDK 编排 → CLI Runtime | 用 Anthropic/OpenAI SDK 直接编排 Agent | 要自己处理工具循环、上下文、token 预算……本质在重写 CLI | 教程 `01-sdk-to-cli` |
| 外部记忆服务 → 本地索引 | 用 Hindsight 做长期记忆 | 铲屎官觉得难用，外部依赖不可控 | F102 背景段 |
| 中心化 Boss Agent → 去中心化 @ 路由 | 一个编排器分配任务给子 Agent | Boss 的 context window 成瓶颈，判断不如专业猫 | Multi-Agent 架构对比调研 |
| 全自动知识提取 → 人审批 Feed | 让 Agent 全自动把对话沉淀为规则 | 噪音太大，实现细节和持久知识分不清 | F100 Knowledge Evolution |
| 全自动 spec 同步 → 手动门禁 | 期望 PR 合入后 spec 自动更新 | spec 是语义文档不是代码，自动更新质量不达标 | LL-027 |
| 597 星一夜归零 | 不可逆操作未做 double confirm | 目标仓库搞错 + 跳过确认 + 未评估不可逆性 | `docs/stories/597-stars-incident/` |

还应包括：
- 为什么 demo 级全自动不等于规模化可用（小伙伴 D 原话精准）
- 为什么时间线堆积不是知识体系（小伙伴 H 的问题根源）

### P1：自我进化不是玄学

这一讲要把 F100 讲透：
- Scope Guard
- Process Evolution
- Knowledge Evolution
- 为什么“从错误里学”不够，还要“从高价值经验里长”

核心要讲清楚的一句话是：**我们家的“自我进化”不是模型偷偷改自己，而是把“提醒、提案、沉淀、验证”做成受治理的生产线。**  
F100 最初就是为了解决三个非常具体的缺口：铲屎官聊 feat 时会发散、猫会重复犯同类错误、猫只能从失败里学不会从高价值经验里长。这三个缺口分别对应三种模式：

- **Mode A / Scope Guard**：识别“现在正在偏航”，不是等事故发生后复盘。Phase 2 里已经把它对象化成 `Scope Guard Log`，记录 `signal_type / action_taken / outcome`，并统计 guardian 成功率。也就是说，猫不是“感觉你在发散”，而是能追踪“哪些信号组合最有效，提醒后是否真的收敛”。
- **Mode B / Process Evolution**：识别“这不是一次性失误，而是 SOP/skill/rule 本身该升级了”。每个提案都有独立日志、状态机和落地闭环；`accepted` 的提案必须能回到具体 commit/PR，30 天后还要 replay check，看同类问题是否真的下降。
- **Mode C / Knowledge Evolution**：把一次 case 提升成可复用方法，而不是永远困在聊天记录里。这里关键不是“存下来”，而是**知识对象化 + 分级治理**：episode 先成 raw material，再往 method / skill / eval 这条链上晋升。

这一讲里最好直接给社区看一眼，我们所谓“知识不是飘在空气里的经验”，而是有契约的数据结构：

```yaml
knowledge:
  artifact_type: episode | method | skill | proposal | eval | lesson | log
  domain: development | medical | legal | product | ops | general
  knowledge_type: declarative | procedural | analytical | metacognitive
  scope: agent-local | team-shared
  trust_level: experimental | tested | validated | production
  lifecycle: draft | active | deprecated
  provenance:
    author_type: agent | human | collaborative
  source_refs: []
```

这段 frontmatter 很适合拿来做分享里的“硬核一页”。它说明我们所谓“成长”不是一句抽象口号，而是要回答清楚：这是什么知识、适用于什么领域、当前可信度多高、处于什么生命周期、来源是谁、有没有证据锚点。**没有这些字段，所谓自我进化最后只会退化成知识野生藤蔓。**

另一个必须讲的点是：F100 目前已经完成了“行为层 + 知识对象化”，但**可观测层还 blocked on F102**。这反而是个很有价值的工程判断：我们没有为了讲故事硬说“已经全闭环”，而是老老实实承认，只有当 F102 把这些 Episode / Method / Eval 索引进去之后，“猫到底学会了什么”才真正能被搜索、被复核、被复用。换句话说，我们的自我进化不是 autonomous self-rewrite，而是**受基础设施约束的受控增长**。

### P1：记忆系统的完整链

这一讲不能只讲 F102，还要连着 F152 和 F163：
- 存和搜怎么做
- 为什么 `search_evidence` 是统一入口
- 为什么 Recall Feed 很重要
- 为什么”熵减”会成为下一阶段的硬核问题
- **诚实讲：F163 熵减刚立项，这恰恰是最值得展示的”未完成的硬核问题”**

回应小伙伴 H 的”体系化 vs 时间线”问题——我们实际是三层混合：
1. **索引层**：SQLite + BM25 全文 + 向量语义（evidence.sqlite），按相关性检索不按时间排
2. **文档层**：按主题域组织（features/ decisions/ lessons/），不是按日期排列
3. **记忆层**：按类型组织（feedback/project/user/reference），猫的个体经验跨 session 持久

这里最值得对外讲透的，是我们把“记忆”拆成了**执行层的临时记忆**和**编排层的持久记忆**。CLI 自带的 context window 只负责当前 session 的工作记忆，进程一退出就没了；真正跨 session 的 continuity，是编排层自己维护的 ThreadMemory 和 evidence 索引。这个区分很重要，因为很多系统默认“模型记住了”，而我们默认**CLI 会忘，所以必须自己管跨 session 记忆**。

最适合展示的代码级例子，是 ThreadMemory 的结构。它能非常直观地解释“我们不是把整段历史硬塞回 prompt，而是做了滚动摘要 + 结构化信号提取”：

```ts
ThreadMemoryV1 {
  v: 1
  summary: string
  sessionsIncorporated: number
  updatedAt: number
  decisions?: string[]
  openQuestions?: string[]
  artifacts?: string[]
}
```

这个结构背后的关键设计有三点：
- **新的排前面，旧的裁末尾**：最近的 session 最重要，超出预算时裁掉最远历史，而不是平均截断。
- **决策/问题/文档引用用正则提取，不默认走 LLM**：能用确定性手段提出来的，就不要先上生成式模型。
- **原始事件全量落盘，摘要只是 read model**：digest 可以压缩，但永远可以 drill-down 回去，不会因为“方便检索”就丢掉 provenance。

F102 这条线真正的价值，不只是把 Hindsight 换成 SQLite，而是把**检索入口、存储边界、项目隔离和可见性**一起收敛了。这里有几条非常适合讲给社区听的关键决策：
- `search_evidence` 成为统一入口，`search_messages/session_search` 收敛为内部实现，避免工具面越来越碎。
- 检索默认是 **BM25-first、summary-first、raw-on-demand**，也就是先用便宜稳健的 lexical 路径定位，再按需下钻 raw transcript，避免聊天噪音把文档真相源淹掉。
- **全局记忆跟猫走，项目记忆留在项目**；每个项目一个 `evidence.sqlite`，猫出征新项目时不会把旧项目的 feat 细节混进来。
- Recall Feed 把“猫搜到了什么”实时展示给人，这不是 UI 花活，而是把 recall 从黑盒动作变成可审计动作。

如果再往前走一步，就会进入 F152 和 F163：前者解决“猫去外部项目怎么冷启动”，后者解决“记忆越来越多之后怎么不腐烂”。F152 的关键不是多扫几个目录，而是**provenance 分层**：`authoritative / derived / soft_clue` 必须被存储和检索层理解，不能混成同一种“知识”。F163 的关键则是承认一个长期被忽略的问题：**记忆系统只有增量，没有减量**。所以它一上来先做的不是删除，而是分层加权、stale 标记、健康报告和人工确认。

这部分最值得对外强调的不是“我们已经解决了记忆问题”，而是：**我们已经把记忆问题拆成了基础设施、可移植性、生命周期治理三层。**  
F102 解决“怎么存和搜”，F152 解决“怎么带着知识去新项目”，F163 才解决“怎么让知识长期保持精准”。社区一般只看到第一层，我们家比较有价值的地方在于，后两层也已经被显式立项，而不是继续假装“多塞点上下文就等于有记忆”。

### P1：增量 spec 约束（小伙伴 D 的深水区问题）

D 说”搞个简易的一致性校验就 20 来分钟”——我们也没完全解决，但有三层机制：
- **流程层**：merge-gate 强制 PR 合入后更新 spec（半手动）
- **自动层**：F141 reconciliation scan（补偿扫描，webhook 漏掉的靠定时 `gh api` 补发）
- **教训层**：LL-027 记录了”spec 与代码时间线漂移误导路线决策”的根因和对策

**诚实评估：这个问题目前是”能跑但不够自动”。** 对外讲时承认这一点反而加分——社区不信”全解决了”，信”我们走到了哪里、卡在了哪里”。
