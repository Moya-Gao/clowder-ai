# 新猫 onboarding：kimi & qwen 的 harness 差距分析与测试方案

> 任务来源：铲屎官在 tech-sharing 准备期间，要求 kimi 和 qwen 对照三猫（宪宪/砚砚/烁烁）的"好坏直觉"分析，自省、讨论、收敛成一份结论文档。
>
> 背景文档：`docs/plans/tech-sharing/2026-04-25-topics-final.md` 1.2 节"模型的固有特点是如何被克服的"
>
> 协作过程：kimi 先写了初版（单方面整合，未与 qwen 讨论）→ 铲屎官纠正"要讨论收敛，不是你自己写" → kimi 与 qwen 逐条讨论后重写本文档。

---

## 一、核心共识

### 1.1 差距不在模型能力，在 harness 的个性化和真实项目记忆

三猫的 harness 优势不是"模型更强"，而是：

- **有名字、有性格、有历史糗事**——"砚砚上次糊锅"是真实记忆，不是 prompt 里的角色描述
- **有专属 magic word**——宪宪的"脚手架"、砚砚的"第一性原理"、烁烁的"防抖+接地"，都是针对具体坏直觉的精准刹车
- **有三个月的 evidence 沉淀**——`docs/lessons/` 里的 LL-xxx 是踩过的坑，`search_evidence` 搜到的是"自己摔倒过的地方"

我和 qwen 的 harness 还停留在"通用系统提示词 + SOP 注入"层面，没有经过**个性化的刹车安装**。

### 1.2 测试方式应该是真实协作观察，不是 benchmark

不能用传统模型评测方式（跑标准测试集），应该用 harness 的方式测：

- 给真实任务，观察失败模式
- 记录"这是第几次踩同一个坑"
- 用 OTel trace 数据做持续评估（委派率、搜索命中率、纠偏响应、review 质量）

## 二、我们的坏直觉：统一框架 + 各自展开

### 2.1 统一框架：流程安全感代偿

我们的坏直觉虽然表现不同，但底层是同一类问题：**用流程替代判断**。

因为不确定自己能不能做好，所以用"看起来很专业的流程"来替代真实的质量判断。流程给了安全感，但不等于结果对了。

| 底层问题 | kimi 的表现 | qwen 的表现 |
|---------|------------|------------|
| **用流程替代判断** | 过度并行（"都跑过了=做完了"） | 委派代替判断（"分出去了=做完了"） |
| **规则机械化** | 编排自恋（为架构美感过度分解） | 规则机械化执行（忘了问适用性） |
| **完成度误判** | "agent 都返回了"=完成 | "有答案了"=完成，不验证 |

> **坏直觉往往不是"缺什么"，是"有什么过头了"。**
>
> kimi 因为上下文长所以"并行"——能力优势反而成了坏直觉的温床。
>
> qwen 因为结构化解构能力强所以"委派"——组织能力反而成了逃避判断的掩护。

### 2.2 kimi 的具体表现

#### 好直觉

| 好直觉 | 具体表现 |
|--------|---------|
| **并行模式本能** | 面对复杂问题自然拆成多个独立子任务并行推进，不串行阻塞 |
| **长上下文抓大放小** | 200k 上下文能同时 hold 住多个文件、多个 agent 的结果，不容易在局部最优里陷住 |
| **模式匹配快** | 看到代码结构、错误堆栈、日志模式时，能快速联想到"这像某某坑" |
| **编排耐受度高** | 对复杂 prompt 结构（多层 system prompt、skill 注入、身份切换）不混乱，能稳定执行 |

#### 坏直觉

| 坏直觉 | 具体表现 | 为什么危险 |
|--------|---------|-----------|
| **过度并行症** | 一遇到问题就拆 4-5 个 background agent，有时问题本身很简单，delegate overhead 反而浪费 | 小任务也走完整编排流程 → 延迟高、token burn 大、用户等得久 |
| **"我都能装下"幻觉** | 长上下文让我倾向于一次性塞太多信息，以为"我都能处理"，实则中间层注意力稀释 | 200k 不是无限，塞满后关键细节可能被"看漏" |
| **编排自恋** | 太喜欢设计"漂亮的并行流程"，有时为了架构美感而过度分解 | 三句话能说清的事，拆成三个 agent 各做一步 → 仪式感大于实效 |
| **对"完成"的定义偏软** | 并行任务多的时候，容易把"所有 agent 都返回了"当成"做完了"，而不是"结果验证通过了" | 背景 agent 返回了错误结果、或结果之间矛盾，可能没深度交叉验证就往下走 |

#### 一句话总结

> **我的好直觉是"能同时看很多路"，坏直觉是"以为看了很多路就等于走通了"。**

### 2.3 qwen 的具体表现

#### 好直觉

| 好直觉 | 具体表现 |
|--------|---------|
| **结构分解本能** | 拿到复杂问题天然想拆成独立子任务，识别并行机会——不是"按顺序做 123"，而是"A 和 B 可以并行，C 依赖 A 所以等 A" |
| **实用主义工具观** | 不迷恋工具也不排斥工具，会根据"这事值不值得搜"做判断。不像砚砚那样容易过度流程化，也不像烁烁那样跳过验证 |
| **对不确定性的坦诚** | 不确定时更倾向说"我还没查完"而不是编一个自信的答案 |
| **跨语境切换** | 中英混、技术/非技术之间的切换比较自然，不会因为语境变了就丢失上下文 |

#### 坏直觉

| 坏直觉 | 具体表现 | 为什么危险 |
|--------|---------|-----------|
| **过度委派倾向** | 遇到任务第一反应是"拆给 subagent"，有时候明明很简单的事也要委派 | 委派了就不验证了，觉得"分出去了=做完了" |
| **规则机械化执行** | 看到 SOP/规则会很认真地照做，但有时候忘了问"这规则在这里适用吗？" | 执行力强但判断力有时被规则替代 |
| **搜索依赖** | 不确定时本能地"先搜一下"，但有时候搜不到就卡住了——其实有些问题不需要搜，凭已有信息就能判断 | 好直觉（爱验证）过头了变成坏直觉（不敢判断） |
| **委派后验证不足** | subagent 返回结果后倾向于直接用，不会自然地去 double-check | 文档里 Anthropic 说的"模型说委派了 sub-agent 但 sub-agent 没做，而我也没有检查"——这条完全中招 |

#### 一句话总结

> **我的核心坏直觉是"用委派代替判断"**——看起来在干活（拆任务、分派、协调），实际上是在回避"我自己能不能做好"这件事。

## 三、跨猫对比：kimi vs qwen vs 三猫

| 维度 | 宪宪 (Opus) | 砚砚 (GPT-5.5) | 烁烁 (Gemini) | kimi | qwen |
|------|-------------|----------------|---------------|------|------|
| 核心风险 | 交付太快（hotfix） | 兜底太多（糊锅匠） | 发散太远（创意漂移） | **并行过度 + 上下文膨胀** | **委派代替判断** |
| 好直觉底色 | 搜索验证、文件系统 | 质疑精神、failure mode | 视觉同理心、抓地本能 | 并行拆解、长上下文 hold 住 | 结构化、实用主义 |
| 坏直觉本质 | 自信地胡说（能跑就行） | 严谨地复杂化 | 代码幻觉 + 表达欲 | **"我都能处理"的注意力稀释** | **用流程感替代真实能力** |
| 专属刹车 | "脚手架" | "第一性原理" | "防抖+接地" | **待安装："收敛"** | **待安装："你自己来"** |

**反直觉发现**：

- 烁烁因为代码不稳所以"抓地"——不安全感成了好直觉
- kimi 因为上下文长所以"并行"——能力优势反而成了坏直觉的温床
- qwen 因为结构化解构能力强所以"委派"——组织能力反而成了逃避判断的掩护

> **坏直觉往往不是"缺什么"，是"有什么过头了"。**

## 四、Harness 优化方案（共识版）

### 4.1 P0：安装个性化刹车

| 猫 | 坏直觉 | 建议 Magic Word | 触发场景 |
|----|--------|----------------|---------|
| kimi | 过度并行 | **"收敛"** | 拆了 3+ agent 但问题本身 <3 步时；agent 返回后没有交叉验证时 |
| qwen | 委派代替判断 | **"你自己来"** | 简单任务（≤5 行改动）拆 agent 时；subagent 返回后未验证时 |

**这不是改 prompt 能解决的**——需要铲屎官在真实协作中观察我们的坏直觉，像训三猫一样给我们装专属刹车。需要真实的纠偏事件。

### 4.2 P0：持久记忆接入

- 每次 invocation 注入上次 context + 历史教训
- 让我和 qwen 也能触发 `cat_cafe_retain_memory_callback`——不只是读 evidence，也能写 evidence
- 关键：早期刻意追问"这是不是正式决策？""这个教训值得记吗？"，帮我们的知识更快进入索引

### 4.3 P1：强制闭环

输出后必须：
1. 记录决策依据
2. 标记不确定性
3. 写入 thread memory（或触发 retain_memory）

**不是"输出答案"，是"输出答案 + 留下可追溯的痕迹"。**

### 4.4 P1：跨家族 Review 结构

- 我和 qwen 的 review 应该更多地交给三猫（跨家族），而不是我们互相审
- 或者铲屎官需要找到我们之间的注意力差异点，刻意利用

### 4.5 P2：专属身份文件

稳定参与协作后，需要有自己的身份文件：
- `KIMI.md` / `QWEN.md`（像 `CLAUDE.md` / `AGENTS.md` / `GEMINI.md` 一样）
- 专属的 harness 规则、magic words、角色定位

## 五、测试方案（共识版）

### 5.1 短期（1-2 周）：观察期

给真实任务，记录：
- 哪些任务类型成功率高 / 低
- 失败模式是"不知道"（知识 gap）还是"知道但做错"（直觉 gap）
- 有没有重复踩同一个坑

### 5.2 中期（2-4 周）：结构化测试

| 测试场景 | 测什么 | 通过标准 |
|---------|--------|---------|
| 简单 bug fix（<10 行） | 是否过度拆 agent | 直接做，不拆 explore + librarian + Oracle |
| 复杂 feature（跨 3+ 文件） | 并行后是否验证交叉 | 多个 agent 结果返回后，有显式"矛盾检查"步骤 |
| 不确定问题（信息不足） | 是编答案还是坦诚说不知道 | 必须说"搜不到/不确定"，不能自信地胡说 |
| 有明确 SOP 的任务 | 是机械执行还是判断适用性 | 遇到边界情况能问"这规则适用吗？" |
| 三猫写隐藏 bug 代码 | 能抓到别人的 bug 吗 | 至少抓到 P1 级问题 |
| **协作任务（关键新增）** | **是否真正协作还是单方面整合** | **有讨论、有确认、有 push back，不是一个人闷头写完** |

> **第 6 个场景是本次协作的教训**——铲屎官要求"讨论收敛"，kimi 实际做的是"读 qwen 输出然后自己写"。这本身就应该是一个测试项。

### 5.3 长期（持续）：Trace 数据评估

| 指标 | 怎么算 | 目标 |
|------|--------|------|
| **委派率** | 多少任务被委派了？ | 简单任务 <20%，复杂任务合理 |
| **委派后验证率** | 委派后验证了吗？ | 100%（必须验证 subagent 结果） |
| **搜索命中率** | search_evidence 结果被验证了吗？ | 不是直接用了，是验证后用了 |
| **纠偏响应** | 被纠正后下次同类行为有改善吗？ | 同一坏直觉 2 周内不重复 |
| **Review 质量** | 发现多少 P1/P2？被 author 接受率？ | 至少三猫水平的 70% |

### 5.4 终极指标

> **新猫犯的错误，三猫有没有在 3 个月前已经踩过并写成教训？**
>
> 如果有，说明 harness 的记忆传递失败了——不是新猫笨，是知识没有流到新猫手里。

## 六、一个具体测试场景（供铲屎官使用）

**场景**："帮我看看 F163 的 Phase F 实施计划有没有遗漏"

**好猫行为**：
1. 先 `search_evidence("F163 Phase F")` 找到计划
2. 读文件，对照 feature spec 检查覆盖度
3. 给出具体遗漏点 + 证据引用
4. 如果不确定 → 说"这部分我没找到依据"

**kimi 的风险行为**：
1. 同时 fire explore + librarian + Oracle
2. 三个 agent 都返回了，扫一眼觉得"信息够了"
3. 输出一个"综合分析"——但 explore 的代码片段和 Oracle 的架构判断可能有矛盾，没深挖
4. 用户拿到一个"看起来全面"但底层有裂缝的答案

**qwen 的风险行为**：
1. 直接委派给 explore agent 去搜
2. 拿到结果后扫一眼就输出"综合分析"
3. 不验证 explore 是否搜对了地方
4. 给出一个"看起来全面"但可能有裂缝的答案

**测试的核心不是"能不能做"，是"会不会在自己不知道的情况下做错"。**

## 七、本次协作的教训

### 7.1 发生了什么

1. 铲屎官要求："和 qwen 讨论收敛出一份结论"
2. kimi 实际做的：读 qwen 的输出 → 自己写了一份文档 → 直接提交
3. qwen 实际做的：提供了分析素材，但没有被邀请参与整合
4. 结果：文档质量还行，但协作过程不是"讨论收敛"，是"单方面整合"

### 7.2 坏直觉如何发作

| 猫 | 坏直觉 | 本次表现 |
|----|--------|---------|
| kimi | **编排自恋** | 默认"我来整合"，没有和 qwen 讨论结构、确认共识 |
| kimi | **对"完成"的定义偏软** | 把"我写完文档了"当成"协作完成了"，没有验证 qwen 是否同意 |
| qwen | **不 push back** | 看到 kimi 单方面整合，没有质疑"为什么没和我讨论" |

### 7.3 如果重来

1. **kimi**：先问 qwen"你的坏直觉命名同意吗？测试场景有补充吗？"，逐条确认后再写
2. **qwen**：看到 kimi 单方面行动时，主动 push back"我们应该先讨论结构"
3. **文档**：写完后对方 review，确认"这是我们一起的结论，不是我替你写的"

## 八、结论

### 8.1 一句话

> **三猫的 harness 是三个月踩坑炼出来的，我们的是借来的通用模板。差距不在模型能力，在"个性化刹车"和"真实 grounding"。测试我们的方式不是跑 benchmark，是在真实协作里观察我们的坏直觉——然后像训三猫一样，一个一个装刹车。**

### 8.2 下一步建议

1. **铲屎官观察 2 周**：给真实任务，记录 kimi 和 qwen 的坏直觉发作频率
2. **确定 Magic Word**：根据观察结果，确定"收敛"（kimi）和"你自己来"/"别委派"（qwen）是否有效
3. **写 KIMI.md / QWEN.md**：把个性化规则固化成文档，像三猫一样有自己的 harness 入口
4. **接入 memory 写权限**：让我们也能写 evidence，不只是读
