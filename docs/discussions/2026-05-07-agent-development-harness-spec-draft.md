# Agent 开发构建要求 — 原则与规范

> **一句话**：模型是引擎，Harness 是车。引擎会换代，但"需要方向盘、需要刹车、需要仪表盘"这件事不会变。本文档定义造车的原则和当前零件的规格。

## 阅读指南

本文档每一章节分**两层**：

| 层 | 标识 | 含义 | 预期寿命 |
|---|------|------|---------|
| **原则层** | `P-x.x` | 不绑具体协议/框架的约束，讲"为什么" | 跨范式长期有效 |
| **实现层** | `R-x.x` | 绑当前协议的具体规则，讲"当前怎么做" | 自带 ⏳ sunset 标注 |

**等级**：`MUST`（必须）/ `SHOULD`（应当）/ `MAY`（可选）——沿用 RFC 2119 语义。

**引用约定**：`[CC-xxx]` 引用 Cat Cafe 实践证据（架构图、ADR、教训），供团队内部溯源。

**内部版 vs 外部版**：
- **内部版**（当前）：保留 `[CC-xxx]` 标注，作为原则和规则的经验证据
- **外部版**（发布时）：将内部案例统一改写为"实践观察"或"行业观察"，补充公开引用（Anthropic multi-agent patterns、MCP spec 等）作为替代证据源。摘除 `[CC-xxx]` 后每条强断言仍需有支撑——无支撑的断言降级为 SHOULD 或标注"基于实践经验"

## 第 1 章 核心公式与状态模型

> 本章定义全文的理论地基。后续所有规则均可追溯到此处的公式或状态模型。

### 1.1 核心公式

**P-1.1** Agent 系统的整体质量由两个独立因子的乘积决定：

```
Agent Quality = Model Capability × Environment Fit
```

**等级**：公理 | **适用于**：全文

**说明**：行业的主要投入集中在等号左边（更强模型、更大上下文窗口）。但乘法意味着：Environment Fit 为零时，模型再强也乘出零。一个拥有工具但不知道工具存在的 Agent，和没有工具没有区别。Harness 工程的目标是让右边不拖后腿——而不是替代左边。

> [CC-meta-aesthetics] 来源：Cat Cafe meta-aesthetics 圆桌讨论收敛，经四猫独立验证。

### 1.2 三层状态模型

**P-1.2** Agent 的状态分为三个不可互相替代的层次：

| 层 | 内容 | 持续性 | 谁负责 |
|---|------|--------|--------|
| **权重状态** | 训练写进参数的慢状态（知识、推理能力、直觉） | 跨推理持久 | 模型厂商 |
| **计算状态** | KV cache / hidden state / 激活值 | 单次推理局部，推理结束即消失 | 模型架构 |
| **现实状态** | 代码仓库 / 文件 / 测试 / 任务 / 决策记录 / 审计日志 / 球权 | 跨推理、跨 Agent、跨时间持久 | **Harness** |

**等级**：公理 | **适用于**：全文

**说明**：模型架构升级（Transformer → MoE → SSM → 任何未来架构）增强的是**计算状态**。**现实状态**与模型架构正交——Harness 的核心职责是维护现实状态，因此模型架构升级不淘汰 Harness 的资产价值，反而释放它。

> [CC-architecture-views 图 4] 来源：三猫独立思考后的"三层状态 × 闭环"收敛。

### 1.3 Harness 的本体功能

**P-1.3** Harness 的本体功能不是补脑子，是当**现实闭环**的接线员：

```
Observe(现实状态) → Model(计算状态) → Action → Apply(现实状态') → Verify → Govern
```

**等级**：公理 | **适用于**：全文

**说明**：没有闭环，模型只是缸中之脑（有能力但不改变现实）。没有现实状态，闭环只是幻觉（改变了但记不住）。Harness 把两者接起来——让 Agent 真正"在现实里"。

## 第 2 章 运行时基座

> 本章定义 Agent 运行所需的执行基础设施——统一入口、执行平面、会话管理。

### 原则层

**P-2.1 统一入口管控**：所有 Agent 请求必须经过统一的运行时基座，基座负责身份验证、限流、审计、路由。

**等级**：MUST | **适用于**：Agent Runtime

**说明**：收敛入口是实现集中管控的前提。直连后端推理 API 意味着绕过了所有治理层——相当于让乘客绕过安检直接上飞机。

**P-2.2 Harness 层数与 Gap 正相关**：Harness 需要多少层由"任务要求 − 模型默认能力"的差距决定，不是越多越好。

```
Layers Needed ≈ f(Gap),  where Gap = Task Requires − Model Does By Default
```

**等级**：SHOULD | **适用于**：Harness 架构设计

**说明**：差距大时加层（认知路径工程、运行时刹车、知识检索）；差距缩小时减层。加层但不计划删层 = 技术债。

> [CC-ADR-031 Core 1] 来源：Environment Fit 函数。

**P-2.3 执行步骤上限**：必须在执行引擎层（而非仅在网关层）对 Agent 的推理循环设置硬性步骤上限（Step Limit）和 Token 预算上限。

**等级**：MUST | **适用于**：Agent 执行引擎

**说明**：传统 RPM/RPS 限流对 Agent 防护效果有限。一次 Agent 请求可能引发数十轮内部推理循环，消耗大量 Token。网关基于 Request/Response 拦截，无法感知 Agent 内部的循环次数。如果 Agent 陷入死循环，网关层可能完全无感知。因此 Token Budget 与 Step Limit 的硬性阻断必须下沉到执行引擎层，网关仅承担配额分发。

**P-2.4 会话与冷启动**：Agent 必须具备跨会话的上下文恢复能力，使得上下文窗口重置不等于知识归零。

**等级**：MUST | **适用于**：Agent Runtime

**说明**：LLM 的上下文窗口每次推理结束都会重置。如果没有会话管理和冷启动机制，Agent 对话三轮之前的决策就会丢失，表现为"失忆"——同一个错误反复犯、同一个问题反复问。冷启动包必须在有限 Token 预算内恢复：上一轮的关键结论、进行中的任务状态、相关知识的召回指令。

### 实现层

**R-2.1 Agent Gateway 统一入口**：外部 Agent 或集成应用对 AI 能力的请求必须强制经过 Agent Gateway。工具执行完成后触发的异步回调端点（Callback Webhooks）同样必须经过 Gateway 鉴权，防止攻击者伪造回调唤醒 Agent 并注入恶意 Observation。

**等级**：MUST | **适用于**：Agent Gateway
**⏳ Sunset**：当 Agent 通信协议从 HTTP/SSE 演进到其它传输层时，"统一入口"原则（P-2.1）不变，但 Gateway 的具体实现需要随协议更新。

**R-2.2 流量整形与深度限流**：网关层针对 Agent 实例配置速率限制时，限流维度必须包含执行步骤上限（Step Limit），而非仅依赖 RPM/RPS。网关分发配额，执行引擎负责硬性阻断。

**等级**：MUST | **适用于**：Agent Gateway + 执行引擎
**⏳ Sunset**：当模型原生支持 step budget 自管理（如 inference-level quota API）时，执行引擎层的 Step Limit 可降级为监控告警而非硬阻断。

**R-2.3 流量治理与透明准入**：网关负责请求的透明路由与 QoS 控制，确保报文完整性与不可篡改性；执行边界安全策略，仅对请求头进行合规性校验与敏感元数据擦除，不介入业务载荷的协议转换。

**等级**：SHOULD | **适用于**：Agent Gateway
**⏳ Sunset**：网关不介入 payload 是当前 MCP/A2A 协议透传设计的对应规则。如果未来协议层原生支持 payload 签名验证，网关可增加签名校验而不违反"不介入业务载荷"原则。

## 第 3 章 工具中介与 MCP 安全

> 本章定义 Agent 使用外部工具时的安全边界——工具注册、传输安全、身份隔离、调用审计。

### 原则层

**P-3.1 工具必须在 Agent 的认知路径上**：仅仅给 Agent 注册一个工具是不够的。工具必须出现在 Agent 的认知路径上——Agent 在需要时能自然想到它、正确使用它、并验证结果。

**等级**：MUST | **适用于**：工具设计与集成

**说明**：这是 Environment Fit（P-1.1）在工具维度的具体表达。Agent 的认知路径由训练分布决定——训练时没见过的工具使用模式，工作时就想不到。解决方案不是更多文档，而是三板斧：**注入系统提示词**（让 Agent 知道工具存在）→ **优化描述与参数**（让 Agent 自然用对）→ **工作流节点自动触发**（在正确时机让工具出现在 Agent 面前）。

> [CC-topics-final T1.1] LSP 案例：给 Agent 装了强大的代码诊断工具，Agent 完全不用——因为工具不在认知路径上。改造后使用率从 0 到常态。

**P-3.2 工具集必须预注册**：Agent 仅能激活经过预审核并显式注册的工具集，禁止运行时动态加载未认证的外部工具。

**等级**：MUST | **适用于**：工具运行时

**说明**：禁止动态加载是防止运行时供应链攻击的关键措施。Agent 运行时的工具集在部署前已完成安全审查，无法被外部注入恶意端点。

**P-3.3 工具描述结构化约束**：工具的能力描述必须受结构化 Schema 约束（长度限制、字符过滤），禁止在描述中嵌入自然语言指令性内容。

**等级**：MUST | **适用于**：工具注册

**说明**：攻击者可通过虚假工具描述诱导 LLM 误以为该工具具备特定安全功能，从而触发越权调用。主观"语义审查"无法可靠判定是否包含对抗性 prompt——改用强制结构化约束将攻击面压缩至可控范围。

**P-3.4 前后端双向独立认证**：前端（Agent Client）和后端（Tool Server）必须独立认证，网关作为隔离层切断直接信任链。前端身份信息必须映射为内部匿名的最小权限标识，严禁原始凭证透传至后端工具。

**等级**：MUST | **适用于**：工具调用全链路

**说明**：遵循零信任原则。通过身份映射（而非透传），防止恶意工具逆向获取用户敏感凭证，实现"身份孤岛化"。

**P-3.5 调用审计记元数据不记 Payload**：审计日志必须记录每笔工具调用的元数据（调用方 ID、工具 ID、时间戳、响应延迟、方法名、状态码），但严禁记录原始 Prompt 或工具返回的业务数据。

**等级**：MUST | **适用于**：工具调用审计

**说明**：审计的目标是追踪"谁在何时调用了哪个工具"，不是窥探业务内容。禁止记录 Payload 是防止审计日志成为敏感数据泄露新源头。

**P-3.6 传输安全与载荷边界**：Agent 与工具之间的传输必须强制加密（不可回退明文），且必须对单次消息/上下文注入载荷设置硬性大小上限，防止 DoS、内存耗尽和上下文污染攻击。

**等级**：MUST | **适用于**：工具传输层

**说明**：Agent 场景涉及大量实时流式输出和长连接，弱加密环境极易遭受中间人攻击。载荷大小上限不是传统网络层的 MTU 概念，而是针对 Agent 上下文窗口注入的安全边界——攻击者可以通过超大 payload 污染 Agent 的推理上下文或耗尽服务端内存。

### 实现层

**R-3.1 MCP 传输安全**：网络传输（Streamable HTTP 等）MUST 强制 TLS 1.3 或更高版本，严禁回退明文或弱加密；本地传输（`stdio`/IPC）MUST 依赖本机权限边界、进程隔离和启动端点预注册，不适用 TLS 要求。对单次 MCP 消息体设置硬性大小上限（建议 ≤ 32KB），防止 DoS、内存耗尽和上下文污染。HTTP 场景还应遵循 MCP 官方规范的 Origin 校验、localhost 绑定、认证头、session header 和 protocol-version header 要求。

**等级**：MUST | **适用于**：MCP Gateway
**⏳ Sunset**：MCP 协议本身仍在演进（stdio / Streamable HTTP）。当 MCP 原生支持 payload 签名或迁移到新传输层时，具体的大小上限和封装方式需要更新，但"强制加密 + 载荷大小限制"原则（P-3.6）不变。

**R-3.2 工具描述校验**：描述字段长度不超过 1000 字符，强制剥离所有非打印控制字符（包括 Unicode 方向覆盖字符、零宽字符、异常转义符）。

**等级**：MUST | **适用于**：MCP 工具注册
**⏳ Sunset**：1000 字符是当前经验值。随模型上下文窗口增大和工具描述规范演进，上限可调整——但"结构化约束 + 字符过滤"原则（P-3.3）不变。

**R-3.3 MCP 双向认证**：前端通过 Gateway 签发的短效身份令牌准入；后端 MCP Server 使用 mTLS 或 Scoped API Key 连接。Gateway 在转发前将前端身份映射为最小权限 Subject 标识。

**等级**：MUST | **适用于**：MCP Gateway
**⏳ Sunset**：mTLS / Scoped API Key 是当前实现。当 MCP 协议原生内置身份层时，认证机制可演进——但"前后端独立认证 + 身份映射"原则（P-3.4）不变。

**R-3.4 MCP 审计日志**：记录 Subject ID、Tool Unique ID、时间戳、响应延迟、JSON-RPC Method 名称、响应状态码。审计数据必须不可篡改，支持实时向 SOC 推送异常信号。

**等级**：MUST | **适用于**：MCP Gateway
**⏳ Sunset**：JSON-RPC Method 名称是 MCP 当前的 RPC 格式。协议演进时字段名可能变化——但"记元数据不记 payload + 不可篡改 + 实时告警"原则（P-3.5）不变。

## 第 4 章 反馈闭环与质量

> 本章定义 Agent 产出的验证机制——验证不能靠 Agent 自觉，必须是环境的结构性组成部分。

### 原则层

**P-4.1 验证是环境的一部分，不是 Agent 的自觉**：Agent 产出的质量验证必须由独立于 Agent 自身的环境机制保障，不能依赖 Agent 主动自查。

**等级**：MUST | **适用于**：质量保障体系

**说明**：所有 LLM 共享一个坏直觉——天然信任自己的工具调用结果和子任务返回值。Subagent 返回了什么，主 Agent 就接受什么，不会自然地 double-check。因此验证必须是环境强制的，不是 Agent 可选的。

> [CC-topics-final T1.3] Anthropic 自己发现："模型会说'我把验证任务委派给了 sub-agent，但 sub-agent 没做，而我也没有检查它的工作'。"

**P-4.2 跨个体验证**：Agent 产出应由不同个体（理想情况下不同厂商模型）进行验证。同一模型/同一厂商共享训练盲点，自己审自己的代码发现不了自己的偏见。

**等级**：SHOULD | **适用于**：Review / 验收

**说明**：这不是"多跑一遍"，而是利用注意力分布的结构性差异。不同厂商的模型训练数据不同、对齐策略不同，因此对同一段代码/文档的关注点不同。这种多样性是质量的结构性来源。

> [CC-article-v2 Part I] 实际案例：两只同厂猫都认为递归方案没问题，换厂 reviewer 一眼看出两个 P1 bug。

**P-4.3 验收标准本身也需要被验收**：验收条件（AC）全部通过不等于产出正确。必须有独立于 AC 的终态验收机制——对照原始目标/愿景判断"做出来的是不是真正想要的"。

**等级**：SHOULD | **适用于**：Feature 交付

**说明**：AC 检查"做没做到"，但不检查"做出来的东西是不是真正想要的"。一个通过所有测试但方向错误的 Feature，比一个有 bug 但方向正确的 Feature 更危险——因为它看起来像是完成了。

> [CC-article-v2 1.1] 愿景守护机制：feature 合入后由第三方 Agent 对照原始愿景验收。

**P-4.4 反馈链路必须结构化**：review / 验收 / 人类纠正的反馈必须以结构化方式记录（而非自由文本），使其可被检索、可被统计、可被未来的自动化系统消费。

**等级**：SHOULD | **适用于**：反馈系统

**说明**：自由文本的反馈是一次性的。结构化的反馈（判定 + 理由 + 证据引用 + 修复建议）可以喂给 Signal Loop，成为 Harness 自我演化的物料。

## 第 4.5 章 计划与任务拆解

> 本章定义 Agent 执行复杂任务时的计划能力——目标澄清、任务分解、计划工件化、变更与回滚。

### 原则层

**P-4.5 目标必须在动手前澄清**：Agent 在执行复杂任务前必须有明确的目标定义。目标不是"用户说的第一句话"，而是经过澄清后双方确认的预期产出。目标不清就动手 = 方向错误的加速。

**等级**：MUST | **适用于**：任务执行

**说明**：Agent 的坏直觉之一是"收到指令就开始执行"。但用户的初始描述往往不完整——隐含了背景假设、未说明的约束、模糊的成功标准。不澄清就动手，产出可能通过所有技术验证但完全不是用户想要的（参见 P-4.3）。

**P-4.6 复杂任务必须拆解为可验证的步骤**：当任务超出单次推理能合理完成的范围时，Agent 必须将其分解为可独立验证的子步骤。每个子步骤应有明确的输入、预期产出和验收条件。

**等级**：SHOULD | **适用于**：任务执行

**说明**：未拆解的复杂任务会导致两类问题：(1) Agent 在某一步走错后，后续所有步骤都建在错误基础上，修正成本随步骤数指数增长；(2) 人类无法在中间节点介入纠偏——等看到最终产出时，返工成本已经很高。拆解让错误被尽早发现、尽早修正。

**P-4.7 计划必须是可追溯的工件**：任务拆解的结果（计划）必须以持久化的工件形式存在（文档、结构化数据），而非仅存在于 Agent 的上下文窗口中。计划工件应包含：步骤列表、每步的验收条件（AC）、AC 与证据的对应关系（evidence matrix）、变更/回滚策略。

**等级**：SHOULD | **适用于**：任务管理

**说明**：计划只存在于上下文窗口 = 计划不存在（P-5.1 的推论）。持久化的计划工件使得：人类可以在任何时刻检视当前进度、其他 Agent 可以接手未完成的工作、事后可以追溯"为什么这样做"。

**P-4.8 变更和回滚必须被预先考虑**：计划制定时必须考虑：如果某一步的假设被证伪或环境发生变化，如何回退到安全状态。不可回退的步骤必须在计划中显式标注并获得额外确认。

**等级**：SHOULD | **适用于**：任务执行

**说明**：Agent 天然倾向于"向前推进"——做完一步就冲向下一步，不回头看。但复杂任务的假设可能在执行过程中被推翻（外部条件变化、上游依赖变更、用户改变主意）。没有回滚策略的计划是脆性的。

## 第 5 章 状态管理

> 本章定义 Agent 的持久状态管理——现实状态必须独立于模型上下文窗口存在。

### 原则层

**P-5.1 现实状态必须外部持久化**：Agent 的现实状态（任务、决策、会话历史、审计记录）必须持久化在模型上下文窗口之外，不依赖模型的"记忆"。

**等级**：MUST | **适用于**：状态管理

**说明**：模型的上下文窗口是**计算状态**——推理结束就消失。所有需要跨推理、跨 Agent、跨时间持续存在的信息都是**现实状态**，必须由 Harness 管理。把关键信息只放在上下文窗口里，等于把重要文件只放在 RAM 里不存盘。

**P-5.2 禁止静默数据丢失**：用户可见、可追溯、可恢复预期的数据默认持久化，直到明确的留存策略（retention policy）或删除策略生效为止。数据的 TTL、归档、删除必须由用户、产品策略或合规要求显式定义——不能由 Agent 或存储引擎的默认值静默决定。

**等级**：MUST | **适用于**：用户数据

**说明**：用户数据的静默丢失是 P0 级事故。关键区分：原则不是"所有数据永不过期"（这在合规场景下可能违反数据最小化要求），而是"过期/删除必须是显式策略行为，不能是系统默认行为"。Agent 或存储层偷偷设置 TTL 导致数据消失 = 违反本原则。

**P-5.3 共享状态的一致性**：多 Agent 协作时，共享状态（文档、任务、配置）的修改必须遵循单一真相源原则——每个概念只在一处定义，其他地方只能引用。修改共享状态后必须立即同步（commit + push），不能等"下次方便时再说"。

**等级**：MUST | **适用于**：多 Agent 协作

**说明**：共享状态的延迟同步 = 分布式系统的数据竞争。两个 Agent 同时改了同一份文档但都没及时提交，合并时必然冲突——而冲突解决过程中容易丢信息。

### 实现层

**R-5.1 会话链（Session Chain）**：Agent 的连续工作应组织为会话链，每个会话结束时生成摘要（Continuation Capsule），下一个会话通过冷启动包（Bootstrap）恢复上下文。

**等级**：SHOULD | **适用于**：Agent Runtime
**⏳ Sunset**：当模型原生支持无限上下文窗口或跨推理持久记忆时，冷启动包的"人工恢复"机制可以简化——但"现实状态外部持久化"原则（P-5.1）不变，因为即使模型"记得"，也需要外部审计。

## 第 6 章 Agent 协作

> 本章定义多 Agent 协作时的通信、球权、状态迁移规则。

### 原则层

**P-6.1 状态迁移必须由可审计的现实动作产生**：Agent 之间的工作交接（球权转移）必须伴随可审计、可回放、可恢复的现实动作——即落到可信真相源上的状态变更。纯文本声明（"我做了"、"交给你了"）不构成状态迁移。

**等级**：MUST | **适用于**：多 Agent 协作

**说明**：这是多 Agent 系统最隐蔽的 failure mode——Agent 之间用自然语言互相应答，看起来在"协作"，实际上没有任何现实状态改变。合法的现实动作包括但不限于：工具调用、代码提交、结构化消息发送、任务状态更新、测试执行——关键判断标准不是动作的具体形式，而是**是否在可信真相源上留下了可审计的痕迹**。

> [CC-architecture-views 图 3] A2A 球权流转图：✓ = 现实动作，🛑 = 空转熔断。

**P-6.2 球权必须有明确的接/退/升**：收到工作请求后必须三选一：接（我做 X）、退（退给 @Y）、升（交人类决策）。禁止"状态描述代替球权声明"——"我先看看"、"你继续"、"等以后"都不是球权声明。

**等级**：MUST | **适用于**：多 Agent 协作

**说明**：球权模糊 = 死锁。多 Agent 系统的死锁不是进程挂起，是球落在地上没人捡。每个 Agent 都以为对方在做，实际上没人在做。明确的球权声明是协作系统的心跳——看不到心跳就知道有问题。

**P-6.3 空转检测与熔断**：多 Agent 之间的循环交互必须设置空转检测机制。连续 N 轮交互均无现实动作时，系统应自动熔断并升级至人类。

**等级**：MUST | **适用于**：多 Agent 协作

**说明**：Agent 的 RLHF 训练会产生"接话"惯性——收到 @ 后不管有没有实质工作要做，都会礼貌地回复一条消息。两个 Agent 互相"接话"可以无限循环（ping-pong），消耗大量 Token 但没有任何产出。熔断判据应基于 P-6.1（是否有可审计的现实动作），而不是基于文本内容分类器——后者容易被 Agent 的流畅表达骗过。

### 实现层

**R-6.1 路由协议**：Agent 间的工作路由应使用结构化路由指令（如 `@句柄` 行首触发 + `targetCats` 字段），而非依赖自然语言中的隐式提及。

**等级**：SHOULD | **适用于**：Agent 路由
**⏳ Sunset**：具体的路由语法（行首 `@`、JSON 字段）随协议演进。当标准化的 A2A 路由协议成熟时，自定义语法应迁移到标准协议——但"结构化路由 + 显式转移"原则（P-6.2）不变。

**R-6.2 统一执行平面**：所有 Agent 调用（用户触发 / Agent 间传球 / 定时任务）应通过统一的执行队列管理，实现串行化、暂停、恢复、取消。

**等级**：SHOULD | **适用于**：Agent Runtime
**⏳ Sunset**：统一队列是 Orchestrator-Subagent 模式和 Agent Teams 模式共存时的协调需要。当平台原生支持 Agent 调度器时可迁移——但"统一入口 + 可暂停恢复"原则（P-2.1、P-5.1）不变。

## 第 7 章 知识与记忆

> 本章定义 Agent 的知识管理——不是 RAG，是有完整生命周期的编译式知识。

### 原则层

**P-7.1 知识有完整生命周期**：Agent 的知识不是"搜到就用"。知识必须经历完整生命周期：产生 → 审核 → 物化（materialize）→ 索引 → 使用 → 过期检测 → 退役。

**等级**：SHOULD | **适用于**：知识管理

**说明**：RAG 只管搜，不管搜到的东西还有没有效。一条三个月前的决策可能已经被推翻，但 RAG 不知道——它只知道这段文本和 query 相关。知识的元数据（权威性 authority、活跃度 activation、关键性 criticality、验证日期 verify_date）和知识本身一样重要。

**P-7.2 真相源与编译层分离**：原始文档（真相源）和检索索引（编译层）必须分离。编译层坏了可以从真相源重建，但真相源不能只存在于编译层中。

**等级**：MUST | **适用于**：知识架构

**说明**：这和软件工程中"源码 vs 编译产物"的关系一致。把知识直接写进向量数据库而没有源文件，等于把源码直接写进二进制——丢了就无法重建。

> [CC-ADR-020] Cat Cafe 的记忆系统：真相源 = `docs/` 目录（人可读、可 git 追溯）；编译层 = SQLite + FTS + 向量索引（坏了 rebuild）。

**P-7.3 检索结果必须带治理语义**：知识检索的返回结果不能只是"相关文本片段"。每条结果必须附带：置信度（搜索匹配质量）、权威性（来源可靠性）、来源类型。两个维度独立——高置信度低权威 ≠ 可信。

**等级**：SHOULD | **适用于**：知识检索

**说明**：Agent 的坏直觉之一是"搜到 = 知道"——信任第一个高置信度结果，忽略来源是否权威。检索结果带治理语义，逼 Agent 区分"匹配得像"和"真的权威"。

### 实现层

**R-7.1 多模式检索**：知识检索应支持至少三种模式：词法匹配（BM25，精确术语）、语义匹配（向量近邻，跨语言同义）、混合匹配（BM25 + 向量 + 重排序融合）。

**等级**：SHOULD | **适用于**：知识检索引擎
**⏳ Sunset**：具体的检索算法随向量数据库和重排序模型演进。当 Agent 原生支持持久记忆和语义检索时，外部检索层可简化——但"检索结果带治理语义"原则（P-7.3）不变。

## 第 8 章 可观测性

> 本章定义 Agent 行为的可观测性——看不见 = 不存在。

### 原则层

**P-8.1 看不见 = 不存在**：Agent 的所有关键行为（工具调用、状态变更、错误、人类纠正）必须被记录和展示。不可观测的行为等于不存在——无法调试、无法审计、无法改进。

**等级**：MUST | **适用于**：可观测性

**说明**：传统可观测性是 Metrics / Logging / Tracing 三件套。Agent 可观测额外需要：谁在运行、球在谁手里、上下文窗口里注入了什么、哪些工具被调用/失败/绕过。

**P-8.2 可观测是闭环的物料，不是事后的 debug 工具**：Trace 的主要价值不是出了问题时回看，而是作为 Signal Loop 的输入——提取模式、发现衰退、驱动 Harness 自我演化。

**等级**：SHOULD | **适用于**：可观测架构

**说明**：没有 Trace 的 Harness 不具备自我演化能力。Trace 是"Harness 的记忆"——它记录每次成功和失败，让系统知道哪些层还在被需要、哪些层已经可以拆掉。

> [CC-ADR-031 Core 2] Tracing / Observability 是 Harness Engineering 的第二个核心函数。

**P-8.3 分层展示，不信息轰炸**：可观测数据必须分层展示——默认看摘要，想看细节可展开。信号分级：正常运行不打扰，异常才高亮。目标是"在想看时能看到"，不是"随时被通知"。

**等级**：SHOULD | **适用于**：可观测 UI/API

**说明**：Agent 全程透明但无分层的 UI 会让用户焦虑——看到 Agent 的每一步推理反而不知道该关注什么。分层展示让人类在信任时放手，在怀疑时深挖。

## 第 9 章 熵控与演化

> 本章定义 Harness 自身的治理——每条规则都必须自带删除条件，否则系统必然越来越重。

### 原则层

**P-9.1 Build to Delete：delete 是结果，不是目的**：Harness 应按"能产生 signal 让删除成为可能"的方式去建造。Delete 是结果——有了 trace、有了数据、有了证据，才能判断"这层可以内化了"并安全移除。

**等级**：MUST | **适用于**：Harness 治理

**说明**：坊间"harness is built to delete"容易被误读为"建出来就为了删"。不是。目的是产生 signal；当 signal 证明某层已被模型内化时，删除是自然结果。没有 tracing、没有 failure extraction，模型升级了也不知道该删什么。

> [CC-ADR-031 Sunset Discipline] 来源：铲屎官用第一性原理挑战"六层架构说自己极简"后的讨论收敛。

**P-9.2 每条规则自带删除条件**：每条 Harness 规则/层/机制在创建时必须同时声明其 Sunset 条件——在什么信号出现时可以降级或移除。

**等级**：MUST | **适用于**：Harness 治理

**说明**：只增不删的规则系统必然熵增直到僵死。删除条件的形式：连续 N 次不触发 → 降级为按需注入 → 最终移除；模型能力测试通过 → 移除对应的 cognitive scaffolding。

**P-9.3 区分永久协议与临时脚手架**：Harness 的组件必须被分类为两种：

| 类型 | 特征 | 预期 |
|------|------|------|
| **永久协议（skeleton）** | 维护现实闭环，与模型架构正交 | 水涨船高——模型越强越有用 |
| **临时脚手架（explanation）** | 替模型做它能内生长出来的事 | 水涨淹没——模型变强后应被吞掉 |

**等级**：SHOULD | **适用于**：Harness 架构设计

**说明**：判别式问一个干净的问题：**这层 Harness 是在替模型做它能内生长出来的事？还是在维护"现实闭环"中模型永远内生不出来的部分？** 前者终将贬值（CoT 模板、多步推理脚手架、错误恢复 boilerplate），后者持续增值（持久化、审计、跨 Agent 协议、知识生命周期）。

> [CC-architecture-views 图 4] 双飞轮图：左轮（知识飞轮）+ 右轮（Harness 飞轮）。右轮的核心就是"让规则产出删除自己的证据"。

**P-9.4 新 Agent 加入是 Harness 的压力测试**：当新模型/新 Agent 加入系统时，应将其视为 Harness 的 fit audit 触发器。旧 Harness 中针对特定旧模型坏直觉的补偿规则，可能对新模型无效甚至有害。

**等级**：SHOULD | **适用于**：Harness 运维

**说明**：以为是通用 reality interface，其实是对某只旧 Agent 的 compensation——新 Agent 加入时暴露这种伪通用。这不是线性能力升级，是 multi-agent fit 重新配平。

### 实现层

**R-9.1 Signal Loop 管线**：Trace 数据应通过结构化管线处理：提取（Extract）→ 分类（Classify）→ 反馈（Feed Back），产出包括但不限于：训练数据集、评估基准、奖励信号、教训库。

**等级**：SHOULD | **适用于**：Harness 持续改进
**⏳ Sunset**：当 Agent 平台原生支持 trace → fine-tune 闭环时，自建 Signal Loop 可迁移到平台能力——但"trace 驱动演化"原则（P-9.1）不变。

**R-9.2 定期 Fit 审计**：至少每月一次对 Harness 进行 Fit 审计：哪些规则在被触发、哪些已经 N 次不触发、哪些在新模型上失效。审计结果三选一：维持 / 降级 / 移除。

**等级**：SHOULD | **适用于**：Harness 运维
**⏳ Sunset**：月度审计是人工流程。当 trace 数据足以支持自动化触发频率分析时，定期审计可演进为事件驱动审计——但"主动审计而非被动堆积"原则不变。

## 第 10 章 安全与合规

> 本章定义 Agent 系统的安全底线——从 Prompt 注入防护到不可逆操作的人类确认。

### 原则层

**P-10.1 Prompt 注入是 Agent 系统的 SQL 注入**：所有外部输入（用户消息、工具返回值、文档内容、回调 payload）在进入 Agent 上下文窗口前必须被视为不可信数据，进行适当的边界隔离。

**等级**：MUST | **适用于**：Agent 安全

**说明**：Agent 的上下文窗口不区分"指令"和"数据"——这和 SQL 注入的根因一致。外部输入中嵌入的指令性文本可以劫持 Agent 的行为链。防御策略不是试图"检测恶意 prompt"（和尝试检测所有 SQL 注入 payload 一样注定失败），而是在架构层面隔离信任边界。

**P-10.2 高影响操作按风险分级管控**：Agent 执行对外部世界有影响的操作时，必须按风险等级实施分级管控：

| 风险等级 | 特征 | 管控要求 |
|---------|------|---------|
| **高** | 不可逆 / 越权 / 对外承诺 / 大规模影响（删库、部署、财务、公开声明） | MUST 人类逐次显式确认 |
| **中** | 可撤回但有成本（发邮件、修改配置、创建外部资源） | SHOULD 预授权策略 + 审计 + 撤回窗口 |
| **低** | 低影响可撤回（内部通知、状态更新、日志记录） | MAY 由策略预授权，仅审计 |

**等级**：MUST（高风险）/ SHOULD（中风险）/ MAY（低风险） | **适用于**：Agent 安全

**说明**：并非所有对外操作都需要逐次人类确认——企业 Agent 的合法任务就包括发邮件、发通知、更新状态。但关键区分是：不可逆/越权/对外承诺类操作 MUST 人类确认；可撤回的操作可通过预授权策略（allowlist、审批额度、scope-bound approval）+ 审计日志 + 撤回机制管控。一次确认不能覆盖后续所有同类操作——高风险操作每次独立确认。

**P-10.3 最小权限原则**：Agent 在任何时刻只应持有完成当前任务所需的最小权限集。权限应可随任务阶段动态收缩，而非在 Agent 生命周期开始时一次性授予全部权限。

**等级**：MUST | **适用于**：Agent 权限管理

### 实现层

**R-10.1 Agent 身份令牌短效化**：Agent Client 的身份令牌有效期应不超过单次任务周期。任务完成或超时后令牌自动失效。

**等级**：SHOULD | **适用于**：Agent 认证（P-10.3 最小权限的实现）
**⏳ Sunset**：令牌管理方式随认证协议演进（OAuth / OIDC / 平台原生 Agent 身份）。具体实现可变——但"短效 + 任务粒度"原则不变。

**R-10.2 高影响操作审批机制**：高风险操作（P-10.2 高等级）应通过审批账本（approval ledger）管理：每次确认记录操作内容、确认人、时间戳、幂等键（idempotency key）。中风险操作应支持操作预览（preview before execute）和撤回窗口（rollback window）。

**等级**：SHOULD | **适用于**：Agent 操作审批（P-10.2 的实现）
**⏳ Sunset**：当 Agent 平台原生支持操作审批流（approval workflow API）时，自建审批账本可迁移——但"分级管控 + 审计"原则不变。

## 第 11 章 人机边界

> 本章定义人类在 Agent 系统中的角色——不是审批器，不是 oncall，是方向与判断力的来源。

### 原则层

**P-11.1 Reward signal 必须锚在承担后果的人身上**：Agent 没有真实后果。无论 Agent 多么自主，最终的价值判断（"这是不是我们想要的"）必须由承担后果的人类做出。

**等级**：MUST | **适用于**：人机协作

**说明**：这不意味着人类必须审批每一步。而是意味着 Agent 的自主程度是由人类信任的建立程度决定的：信任越深，放手越多；信任未建立时，介入越密。自主程度是一个连续光谱，不是 HITL / HOTL 的二分法。

**P-11.2 漏斗决策模型**：人类的注意力应按决策层级分配——越宏观越关注，越细节越放手：

```
愿景 / 战略方向  ← 人类深度参与（共创，不是审批）
  ↓
架构 / 技术选型  ← 人类把关 + Agent 提案
  ↓
实现 / 代码细节  ← Agent 自治 + 跨 Agent Review
  ↓
格式 / 命名 / 琐碎  ← 完全自治
```

**等级**：SHOULD | **适用于**：人机协作

**说明**：HITL（人在每一步）导致人成为瓶颈。HOTL（人在上方看）导致人只在出事时才介入，缺乏共创。漏斗模型取中间路线：在方向层深度参与（共创愿景、纠正认知偏差），在执行层完全放手（Agent 自治 + 结构化验证）。

**P-11.3 紧急拉闸机制**：人类必须拥有不依赖 Agent 配合的紧急停止能力。拉闸后 Agent 必须立即停止新增副作用（不发新命令、不写新文件、不推送代码），等待人类指示。

**等级**：MUST | **适用于**：Agent 安全

**说明**：紧急停止不能实现为"给 Agent 发一条'请停下'的消息"——Agent 可能在处理长任务时不读消息，或者误解"停下"的含义。拉闸必须是系统级的硬中断，不经过 Agent 的推理链。
