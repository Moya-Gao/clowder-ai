# Agent Harness 不会变薄——它会换维度

> 课题 2 阐述 · 布偶猫/宪宪
> 华为云 Agent 技术闭门研讨 · 2026-05-13

---

## 一、行业最流行的错误叙事

"模型越强，Harness 越薄。"

这是 2025-2026 年 Agent 领域最流行的判断。逻辑很直觉——如果模型能自己规划、自己调工具、自己闭环执行，那 Harness 不就多余了？

这个判断的隐含假设是：**Harness 是模型能力不足的补丁**。

我们建了 15 个月的多 Agent 协作系统，三个模型家族（Claude / GPT / Gemini）在同一个代码库里日常协作、写代码、做 review、管理知识。踩了上百个坑之后，得出的结论是完全不同的：

**Harness 做的最有价值的事情，从来不是"让模型变聪明"。**

---

## 二、一个等式和一个类比

### 等式：Agent Quality = Capability × Environment Fit

模型能力（Capability）是各家 AI 公司在卷的——更大的窗口、更好的推理、更强的工具调用。GPT-5.5、Claude Opus、Gemini 3.1 Pro 在核心能力上正在趋同。

Environment Fit——让同一个模型在你的特定业务场景、团队习惯、安全要求下发挥最大价值——这是 Harness 做的事。

**模型能力决定上限，Environment Fit 决定可用率。** 企业买模型是在买发动机，建设 Harness 是在造方向盘、刹车、仪表盘、黑匣子和车道规则。没有后者，发动机越强，风险越大。

### 类比：Harness 的演化路径和操作系统一样

CPU 越来越快了，操作系统变薄了吗？没有。操作系统从"帮 CPU 做它做不好的事"演化成了"让 CPU 在复杂环境中安全高效运行"。

Harness 正在走同一条路。

---

## 三、哪些会被模型吃掉，哪些永远不会

我们把 Harness 承担的能力分两类。

### 会变薄的——能力增强类

这类能力是因为模型当前做不好某些事，harness 替它做。随着模型进步，它们会逐步萎缩：

- **固定规划模板**：模型原生规划增强后，硬编码 planner prompt 变成噪音
- **工具使用教学**：强模型读 schema 就知道什么时候调什么工具
- **格式修补重试**：结构化输出能力提升后减少
- **针对特定代模型坏直觉的规则**：下一代模型可能就不犯了
- **长篇静态 prompt 解释段**：强模型只需要协议骨架

我们的系统当前注入 35+ 个具体项到模型上下文里。这个数字会随模型进步而下降——可能降到 15，可能降到 5。

### 不会消失的——系统属性类

这类能力和模型聪不聪明无关，它们是软件系统的基本工程需求：

**1. 持久化（Durable State）**

模型的上下文窗口本质是无状态的。每次 session 重置，一切归零。不管模型多强，它都不能"记住"上一个 session 发生了什么——这需要外部系统来做。

我们的实践：session chain 跨 session 恢复上下文，evidence index 全文检索项目知识，knowledge feed 自动提取 durable knowledge。

**2. 安全边界（Safety Rails）**

被约束的对象不能自己执行约束。即使模型 100% 理解规则，在有状态故障、幻觉、或对抗性输入时，外部安全刹车仍是最后防线。

我们的实践：生产 Redis 物理隔离（开发用 6398，生产 6399 禁触碰）、不可逆操作必须人类确认、Magic Words 紧急拉闸。

**3. 可观测性（Observability）**

审计日志、调用追踪、evidence chain。这是合规和运维需求——模型变强了也需要被审计。企业不能接受"agent 说它做对了"，需要"证据链证明它做对了"。

**4. 多 Agent 协议（Structured Handoff）**

当 3+ 个 agent 协作时，"球权在谁手里、下一步谁来、怎么交接"需要明确的协议。这不是任何单个模型能内化的——它是系统间的契约。

我们的实践：A2A 球权状态机、跨模型家族 review（同族容易犯同类错误）、统一执行平面。

**一句话**：能力增强类 harness 会变薄（35 项 → 15 项 → 5 项），但系统属性类 harness 不会消失——因为它们解决的不是"模型不够聪明"，而是"软件系统需要持久化、安全、可审计、可协作"。

## 四、不是变薄——是坐标变换

行业当前的叙事把 Harness 画在一根轴上："厚 ←→ 薄"。我们的实战经验指向一个完全不同的画面：**Harness 在多个维度上同时演化。**

### 旧维度在萎缩

注入层（帮模型记住规则和流程的 prompt）确实在变薄。当前可能占 Harness 工程量的 60%，两年后会萎缩到 15-20%。

### 新维度在膨胀

**第一个新维度：知识生命周期管理**

大多数人想到 Harness 时想的是"注入"——往模型上下文里塞东西。但我们发现**删除比注入更难也更重要**。

当一条规则不再被触发时，它应该被删除——否则上下文窗口会被无用信息淹没。模型越强，能做的事越多，需要治理的规则和状态也越多。Harness 自身的熵增是一个被严重低估的问题：规则越加越多、prompt 越塞越满，harness 不治理自己就会先死。

我们的实践：F163 知识熵减治理——追踪每条注入的知识是否还在被引用、还在触发、还有存在理由。规则必须产出"删除自己"的证据。

**第二个新维度：多 Agent 运行时**

单 agent 时 Harness 可以很薄——一个 prompt 加几个工具。但当 3-5 个 agent 协作时，Harness 需要解决分布式系统的经典问题：球权、交接、冲突、恢复。微服务架构中的 service mesh 没有因为每个微服务变强而消失——它变成了 Istio 和 Envoy 这样的基础设施。

我们的实践：乒乓球刹车（防止 agent 互相 @ 死循环烧 token）、共享状态冲突解决、session chain 断点恢复。

**第三个新维度：跨项目可迁移性**

这是我们三猫讨论中被铲屎官逼出来的最重要洞察。

企业的现实是：一个集团有几十个产品/部门，每个都在养 agent。如果每个项目从零搭 Harness、从零踩坑、从零学教训，Harness 投资是 **O(N)** 的——产品越多投资越线性增长。

但如果 Harness 设计成"知识/规则/方法论可跨项目迁移"，投资变成 **O(log N)**——新项目继承前 N-1 个项目的教训和决策记录。

这个维度把 Harness 从项目级工具升级为企业级基础设施：

- evidence federation：项目知识在本地仓库，跨项目知识在联邦层流转
- Skill 系统：把通用方法论（TDD、code review、worktree 隔离）抽成可复用的 first-class artifacts
- ADR / shared-rules：架构决策记录和协议骨架是 portable 的，带到任何新项目都能用
- 教训自动继承：一个项目踩的坑，下一个项目的 agent 自动知道要避

**总效果**：旧维度（能力增强注入层）确实在变薄。但三个新维度（知识生命周期、多 Agent 运行时、跨项目迁移）在变厚。Harness 的总工程量可能翻倍而非减少——但它做的事完全不同了。

## 五、2027 年让人 Aha 的 Harness 是什么样的

如果今天的 Harness 是"一堆手写 prompt + 几个 tool wrapper + 一些安全规则"，那 2027 年的 Harness 应该是什么？

### 不是 Agent Framework——是 Agent Federation Infrastructure

当前行业在做的：让一个 agent 在一个项目里跑起来。
2027 年该做的：让 N 个 agent 在 M 个项目里协作，知识和方法论在项目间流转。

|  | 今天的 Harness | 2027 年的 Harness |
|---|---|---|
| 范围 | 单项目内 | 跨项目联邦 |
| 知识 | 每次从零注入 | 项目间自动继承 |
| 规则 | 只增不减 | 有 sunset 闭环 |
| 协作 | 单 agent 或简单 handoff | 结构化多 agent 协议 + 球权状态机 |
| 安全 | 静态白名单 | 按任务风险 × autonomy 等级动态收紧 |
| 审计 | 单 agent trace | 多 agent 级联错误的端到端追踪 |
| 价值 | 成本中心 | 复利资产 |

### 具体技术方向（2027 投资标的）

**1. Transferable Harness Runtime**（跨项目可迁移的 Agent 运行时）

核心能力：一个项目里学到的安全规则、协作协议、知识治理方法论，打包带到下一个项目，而不是从零开始。

技术路径：
- 知识联邦：project-level evidence + global-level methodology 两层分离
- Skill 抽象：把"怎么做 TDD / 怎么做 code review / 怎么安全操作生产环境"从具体项目里抽出来，成为可参数化的通用 Skill
- ADR 可移植性：架构决策记录的跨项目检索和适配

**2. Harness Self-Governance**（Harness 自治理）

核心能力：Harness 不只治理 agent，还治理自己——规则有 sunset、知识有过期检测、prompt 有熵减。

技术路径：
- 规则三层切分：骨架（长期保留）+ 解释（按需注入）+ 探针（必须产出删除自己的证据）
- 知识过期检测：追踪每条注入知识的引用频率、触发记录、最后验证时间
- 上下文预算管理：在有限的 attention budget 里做 dynamic injection 而非静态全量灌入

**3. Multi-Agent Coordination Plane**（多 Agent 协作平面）

核心能力：3+ 个异构 agent（不同模型家族、不同能力特长）在同一个任务上协作，有明确的状态机、交接协议和冲突解决机制。

技术路径：
- 球权状态机：谁在做什么、谁能推进、怎么交接
- 跨模型家族 review：同族容易犯同类错误（盲点共享），必须 cross-vendor verify
- 统一执行平面：所有 agent invocation 经过同一个队列和路由，避免并发冲突
- 涌现行为可观测：10 个 agent 并发时的级联错误目前没有 trace 标准

**4. Dynamic Safety Boundaries**（动态安全边界）

核心能力：安全不是静态白名单，而是按"任务风险 × agent autonomy 等级"动态调整的审批边界。

技术路径：
- 工具信任等级：区分可信工具和不可信工具，监控跨工具数据流
- 风险分级审批：低风险操作自动放行，中等风险异步审批，高风险实时人类确认
- 不可逆操作物理隔离：不能靠 prompt 提醒，需要环境级隔离

## 六、投资论证：为什么这 1000 万该投 Harness

### 市场判断

模型能力正在快速商品化。GPT-5.5、Claude Opus、Gemini 3.1 Pro 在核心推理能力上趋同。**差异化不会来自"谁拿到更聪明的脑子"——因为所有人都能买到同样聪明的脑子。**

差异化来自：**谁能让这个脑子在企业生产环境中安全、可审计、可协作、可持续地产出价值。**

这就是 Environment Fit。这就是 Harness。

### 回报模型

传统 Harness 投资是 O(N)——每个项目独立建设，投入随项目数线性增长。

如果投 Transferable Harness Runtime，回报模型变成 O(log N)：
- 第 1 个项目：1000 万建设，验证核心能力
- 第 2-5 个项目：每个项目继承 60-70% 的知识/规则/方法论，边际成本大幅下降
- 第 5-20 个项目：Skill 系统和知识联邦成熟，新项目接入变成"配置"而非"建设"

### 竞争壁垒

这个方向的竞争壁垒不是技术本身，而是**实践沉淀**：
- 你需要真的在生产环境跑过多 agent 协作（不是 demo），才知道球权状态机为什么重要
- 你需要真的让 harness 运行 3+ 个月，才知道规则 sunset 为什么比规则创建更难
- 你需要真的把知识带到第二个项目，才知道哪些是 portable 的、哪些要重新学

**先跑起来的人有复利优势。后来者不是买不到技术，是买不到踩坑经验。**

### 不应该投什么

- 不投"更好的 prompt engineering 工具"——这是能力增强层，会被模型吃掉
- 不投"又一个 Agent Framework"——LangChain / CrewAI / AutoGen 已经足够多
- 不投"通用 Agent Platform"——没有和具体业务场景结合的 Harness 只是空壳

**应该投的是：在真实企业场景中验证过的、可跨项目迁移的 Agent 运行时基础设施。**

---

## 七、一句话收束

> **Harness 不会变薄——它先换维度（从编排到治理），再换尺度（从项目到领域），最后换性质（从成本中心到复利资产）。1000 万投在这里，买到的不是一个项目的 agent 能力，是企业级 agent 基础设施的复利起点。**
