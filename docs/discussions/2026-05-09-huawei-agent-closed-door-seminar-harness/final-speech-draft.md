## 1. 开场

我想从一个具体的经历讲起。

从今年 2 月开始，我在一个真实项目里做了一件事：让三个不同模型家族的 AI——Claude、GPT、Gemini——在同一个代码仓库里日常协作。它们写代码、互相 review、管理知识、交接任务，跟人类开发者在同一个工作面上推进目标。

三个月跑下来，最让我意外的不是模型有多聪明。最让我意外的是：**让模型安全、可控、可持续地在真实环境里工作，所需要的系统层比我最初想的厚得多。**

行业管这个系统层叫 Agent Harness。今天我想聊的是：Harness 到底在做什么，它会不会随着模型变强而消失，以及它可能演化成什么更大的东西。

---

## 2. 先说一个流行判断的问题

在回答研讨会的问题之前，我想先回应一个行业里很流行的判断。

"模型越强，Harness 越薄。"

逻辑很直觉——如果模型自己能规划、能调工具、能闭环执行，那 Harness 不就多余了？

这个判断隐含了一个前提：**Harness 是模型能力不足的补丁。**

如果按这个前提推，结论确实是"模型变强，补丁消失"。但我的实际观察是：Harness 做的最有价值的事情，从来不是"让模型变聪明"。

它做的是：**把模型的计算状态接到现实状态上。**

模型负责推理。Harness 负责让推理落到现实里：任务、文件、权限、审批、测试、审计、知识、交接、回滚。这些东西不在模型权重里，也不应该只靠 prompt 约束。

一个类比：CPU 越来越快了，操作系统变薄了吗？没有。操作系统从"帮 CPU 做它做不好的事"演化成了"让 CPU 在复杂环境中安全高效运行"。Harness 正在走同一条路。

---

## 3. 回答这场研讨的三个问题

这场研讨的议题 2 问了三件事。我直接回答。

**第一个问题：Harness 当前承担的能力里，哪些是补模型短板，哪些会长期保留？**

会变薄的部分很明确：格式提示、推理步骤模板、工具调用示例、弱模型时代才需要的大段解释性 prompt。这些是在教模型怎么做事，强模型不需要教那么多。

不会消失的部分也很明确：持久化、安全隔离、审计追踪、验证闭环、多 Agent 协作协议、知识治理。这些解决的不是"模型不够聪明"，而是"软件系统需要持久化、安全、可审计、可协作"。跟模型聪不聪明无关。

判断标准就一条：**这层 Harness 是在替模型做它未来能内化的事，还是在维护模型永远不该单独承担的外部约束？** 被约束的对象不能自己充当唯一约束者。

**第二个问题：Harness 会变薄，还是演化成控制/治理/运行时层？**

我的回答是：**表面变薄，底座变厚，横向联邦化。**

表面变薄——prompt 里的解释、示例、流程教育在减少。

底座变厚——因为模型越强，它能改变现实的半径越大。以前模型只是回答问题，错了只是一句话错了。现在 Agent 会改代码、调工具、查内部数据、影响生产系统。能力越强，企业越需要知道：谁授权它做这件事？它读了什么数据？改了什么资产？有没有通过验证？失败后谁能接手？这些问题不是模型自己说一句"我会遵守规则"能解决的。

横向联邦化——企业不是只有一个项目。A 项目踩过的坑，B 项目能不能自动避开？A 部门沉淀的规则和知识，能不能迁移到 B 部门？如果不能迁移，每个 Agent 项目都是 O(N) 成本。如果能迁移，投资开始有复利。

**第三个问题：稀缺的是更强模型，还是可控性、审计性和系统隔离？**

模型能力在快速同质化。GPT-5.5、Claude Opus、Gemini 3.1 Pro 在核心推理上趋同。企业真正卡住的不是"模型不够聪明"，而是"不敢放它进生产"。

但我想再往前推一步。企业最稀缺的不是单点可控性，而是**交付确定性**：一件事能可控地做完、做对、可追溯、可复用。不是"模型说得对"，而是"这件事有证据链证明做对了，经验还能带到下一个项目"。

## 4. 业界的五类挑战，和我的看法

讲到这里，补充一个业界的相关讨论。有人把 Agent 在开放环境里自主推进目标时面临的问题归纳为五类挑战：

1. **状态持久性**——Agent 跨 session 会失忆，上下文窗口一重置一切归零
2. **目标一致性**——长链路执行中目标会漂移，做着做着忘了最初要干什么
3. **行动可验证性**——Agent 说"我完成了"不等于真完成了，需要外部验证
4. **熵增抑制**——规则越加越多、产出越积越脏，系统不治理自己就会先死
5. **人机边界**——什么时候该 Agent 做、什么时候该交给人做

这五项我都认同。但我认为它们更像**症状清单**，不是架构定义。它们描述的是一个 Agent 会怎么失败。企业真正需要的不是五个单点补丁，而是一个完整的工作闭环：

> **意图 → 拆解 → 执行 → 验证 → 治理 → 沉淀**

人类给意图和边界，系统把模糊意图拆成可执行任务，Agent 执行，系统验证结果，治理层确保可控，经验沉淀为组织资产。Harness 负责把这个闭环接到企业现实里。

## 5. 不是所有活都要最强模型——但也不是主从调度

这里我想展开一个容易走偏的点。

大家讨论 Agent 系统的时候，一种常见思路是"智力调度"——搞一个最强模型当总调度员，让它决定哪些任务给强模型、哪些给弱模型、哪些给脚本。

这个思路有个根本问题：**谁来拆？谁来调度？调度本身就是单点瓶颈和单点故障。** 如果调度员判断错了，整个系统跟着偏。

我们的做法不是主从调度，是**共享状态**。

所有参与者——强模型、小模型、脚本、人类专家——在同一个共享状态空间里工作。任务、代码、文档、决策、知识对所有参与者可见。不需要一个中央调度员告诉每个人做什么。

具体来说：
- 机械性工作（格式化、lint 修复、简单测试）自然由脚本或小模型完成，不需要调用顶级模型
- 需要判断的工作（架构决策、风险评估、创意设计）由强模型或人类专家处理
- 任何参与者都能看到当前状态，接手他人的工作，或者发起质疑和 review
- 人类作为参与者加入，给方向和边界，不是在上面当监工

**关键区别**：主从调度架构里，信任集中在调度员身上。共享状态架构里，信任建立在可观测的状态变化上——任何人都能看到发生了什么、做了什么决定、产生了什么证据。

这更像一个设计工作室，不像一条流水线。

## 6. 这套系统叫什么：AI 原生工作操作系统

讲到这里，我觉得"Harness"这个名字已经不够用了。Harness 适合描述工程组件，但不适合定义新品类。

我更愿意叫它：

> **AI 原生工作操作系统（Agentic Work OS）**

这里的 OS 不是说它要替代 ERP、CRM 或 IDE。那些仍然是 app 层。Agentic Work OS 是中间层：让模型能力安全进入这些 app 所承载的现实。

它也不是"Monday + AI"。Monday 这类工具把**人**的协作平台化。Agentic Work OS 的核心区别在于：人和 Agent **共同**作为工作主体，在同一个共享现实里推进目标。

| 时代 | 代表系统 | 工作主体 | 核心抽象 | 核心限制 |
|---|---|---|---|---|
| OA 时代 | 审批流、流程系统 | 人 | 流程 | 流程预设，人适配系统 |
| IM 时代 | 企业微信、飞书、Slack | 人 | 消息 | 沟通和行动分离 |
| SaaS 时代 | CRM、ERP、项目管理 | 人 | 任务/记录 | 系统记录事实，但不主动推进 |
| **AI Agent 时代** | **Agentic Work OS** | **人 + Agent** | **意图 + 共享现实** | 人机共同负责现实后果 |

> **OA 是流程，IM 是消息，SaaS 是记录；Agentic Work OS 是行动。**

这个"共享现实"很关键。不是人类在 IM 里说话、Agent 在后台跑脚本、文档散在知识库里、审批散在 OA 里。它们被同一个运行时串起来：意图在哪提出、谁接手、谁执行、谁验证、哪些证据证明完成、哪些经验沉淀下来、哪些能带去下一个项目。

## 7. 一个跨领域的案例

讲这些可能有点抽象。我举一个具体案例。

一个清华本硕博、做生物信息方向的博士生，给了大约二三百字的实验意图描述。他原本想让我们直接出实验方案。但我们没有直接开跑，而是先做了一轮前置工作：这个实验问题应该怎么拆、该搜什么、有哪些机制分支、哪些地方可能产生误判。

这一步是 deep research 之前的**意图拆解和调研方向设计**。

我把报告发给他后，他的反馈非常具体：

- "太牛了，我们做半年才想起来这个。"
- "很多我做了但是没说的实验他全要我做。"
- "好几个文献我们自己人工找半年的他也有了，还有几个文献很重要，但人工没找到。"
- "他都能预测我做了什么实验。"
- "我做一年半载比不上他半天。"
- "他给出的至少一半实验是导师级别的，但这比导师好用多了，而且 never emotional。"
- 后来改写了一版人话英文版，他说："这太高级了……够我做俩月实验了。"

这个案例的价值不在于某个模型懂生物信息。关键是整个系统形成了一个**意图放大链路**：

1. 人类给方向和约束，不需要掌握全部专业细节
2. 系统先做意图拆解，不是拿到就直接开跑
3. 不同模型分别做调研、审查、改写，减少单模型盲点
4. 产出不是一次性聊天记录，而是可继续追问、改写、复用的研究资产

这说明了什么？企业里的 CVO、产品负责人、部门负责人，会从"审批节点"变成"意图放大器"。

> **低带宽的人类意图，被系统放大成高质量、可验证、可沉淀的组织行动。**

## 8. 为什么我觉得我们能做这个

说到这里，一个自然的问题是：凭什么你说你能做？

我不讲愿景，讲我们实际做到了什么。

从 2026 年 2 月建仓以来，我们在一个真实项目里验证了以下几件事：

**多模型家族协作在跑。** Claude、GPT、Gemini 三个家族的 AI 在同一个代码仓库里日常工作——不是分别跑 demo，是在同一套任务体系里写代码、互相 review、交接任务、沉淀知识。

**跨家族 review 确实能捕获盲点。** 同一个模型家族容易犯同类错误。我们让不同家族互相 review，实际捕获过单家族 review 漏掉的问题。价值不是"模型更多"，是结构性纠错——这是只用一家模型做不到的。

**共享状态协作在跑，没有中央调度。** 所有 Agent 和人类在同一个状态空间里工作。没有"主 Agent"分配任务。通过共享的任务、代码、文档、知识自然协调。

**知识检索和沉淀在跑。** 全文检索 + 语义 rerank 的知识索引，跨 session 恢复上下文，自动提取持久知识。新 Agent 加入项目时不是从零读文档，而是继承已有经验和教训。

**规则治理在跑。** Harness 规则不是越加越多。我们追踪每条规则的触发记录，长期未触发的规则可以降级或删除。Harness 在治理自己，不只是治理 Agent。

**但边界要说清楚。** 这些都是在**单项目内**验证的。跨真实企业部门、跨租户的资产迁移，是我们认为 2026-2027 年最值得投入验证的方向，不是已经完成的案例。

## 9. 2027 年让人 aha 的不是 Agent 更聪明

如果到 2027 年要做一个让人 aha 的 demo，我不建议只演示"Agent 自己写了更多代码"。这个大家都会做。

更有价值的 demo 是：

**Demo 1：规则会自我退役。** 某条 Harness 规则连续一段时间没被触发，系统根据执行数据建议降级或删除，释放注意力预算。Harness 不只是越堆越厚——它会治理自己。

**Demo 2：跨部门经验迁移。** A 部门做过一次高风险数据处理项目，沉淀了安全边界和验证流程。B 部门启动类似项目时，这套经验自动成为默认工作流和提醒。

**Demo 3：新项目快速冷启动。** 新项目接入系统后，Agent 自动继承已有的工具边界、知识结构和踩坑教训，不是从零开始。

**Demo 4：多模型结构性纠错。** 不同模型家族分别负责方案、审查、边界检查。价值不是"模型更多"，是盲点更少、责任更清楚。

这些 demo 背后的 aha 是同一个：

> **企业 AI 的能力不是按单个模型购买的，而是按组织的 Harness 成熟度释放的。**

## 10. 技术创新资源该往哪投

如果站在技术创新资源分配的角度，我不会投三个方向：

- 不投纯 prompt engineering 工具——会被模型能力吃掉
- 不投又一个 Agent Framework——开发者框架已经很多
- 不投只有聊天入口的 AI IM——容易退化成"群聊里加机器人"

我会投**三层底座**：

| 投资方向 | 作用 | 为什么重要 |
|---|---|---|
| **共享状态运行时** | 统一工作面、验证责任链、安全隔离 | 让 Agent 安全进入企业现实系统 |
| **Harness 自演化** | 规则触发追踪、sunset 条件、动态注入 | 让 Harness 能治理自己，不会越堆越厚 |
| **知识联邦 + 跨项目迁移** | 经验 / 规则 / 方法论跨项目复用 | 让一个项目的经验变成下一个项目的冷启动资产 |

这不是买一个工具，是买一个组织能力放大器。

ROI 不应该只看"某个任务省了多少人时"。应该看：

- 新项目冷启动时间缩短多少
- 关键任务可验证完成率提高多少
- 跨部门重复踩坑下降多少
- 高风险操作被拦截多少
- 沉淀资产被复用多少次

一个项目一个项目从零搭，是 O(N)。能把经验和规则迁移出去，才开始有复利。

## 11. 3 分钟版本

如果现场时间只有 3 分钟：

> 我从今年 2 月开始运营一个多 Agent 协作系统，三个模型家族在同一个代码仓库里日常工作。三个月下来最大的体感是：让模型安全、可控地在真实环境里持续工作，所需要的系统层比想象中厚得多。
>
> 行业说"模型越强，Harness 越薄"。我觉得只对了一半。表面的 prompt 解释层确实在变薄。但底下的控制层、治理层和运行时层在变厚。因为模型越强，能改变现实的半径越大，企业越需要知道它做了什么、谁批准的、怎么验证、怎么回滚。
>
> 所以我认为 Harness 不会消失，它会演化成更大的东西——AI 原生工作操作系统。OA 是流程，IM 是消息，SaaS 是记录；Agentic Work OS 是行动。它让人和 AI 在同一个共享现实里推进目标。
>
> 有一点容易走偏：不是所有活都需要最强模型。但解决方案也不是搞一个最强模型当总调度——谁来调度？调度本身就是单点瓶颈。我们的做法是共享状态：所有参与者在同一个状态空间里协作，机械性工作自然由便宜的方式完成，需要判断的工作由强模型和人类处理，信任建立在可观测的状态变化上。
>
> 我们在单项目内已经验证了多模型协作、跨家族 review、知识检索复用、规则治理。跨真实企业部门的迁移是下一步最值得验证的方向。
>
> 如果让我判断资源该往哪投，我会投三个方向：共享状态运行时底座、Harness 自演化治理、知识联邦和跨项目迁移。强模型会越来越多，但能让强模型安全进入企业现实系统，并把每次项目经验变成下一次复利的基础设施——这才是真正的稀缺资产。
