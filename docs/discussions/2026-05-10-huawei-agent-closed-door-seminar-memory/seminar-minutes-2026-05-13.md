## 嘉宾 1：张桂彬（NUS）— 记忆分类框架

**核心观点**：提出记忆的两维度分类法——

### 维度 1：记忆目的（Purpose）

| 类型 | 说明 | 当前状态 |
|---|---|---|
| **Session / Experiential Memory** | 跨 session 经验复用，让 agent 越做越好 | 活跃研究 |
| **Factual Memory** | 对世界知识/事实的记忆（如 LongMemEval 类） | **"已接近饱和"**——张桂彬原话 |
| **Working Memory** | 长程 Agent（1000-3000 步任务）的工作记忆 | 当前最大痛点 |

### 维度 2：记忆形态（Form）

| 类型 | 说明 |
|---|---|
| **明文记忆** | token / 文本 / 视频等显式存储 |
| **参数化记忆** | 内化到模型参数 |
| **潜在表示** | hidden state / KV cache |

**关键判断**：这个分类框架去年底提出，放到现在依然有效，能囊括 OpenAI Humans 等新 Agent 的记忆方案。

**与我们框架的关系**：张桂彬分的是"记忆是什么"（内容分类），我们分的是"记忆系统必须做什么"（操作分类）。两者正交，可叠加成矩阵。

## 嘉宾 2：李志宇（Memos CTO）— 读写效率驱动的分层

**核心观点**：记忆分类应从**读写效率**出发——

- 最早在 2024 年 7 月提出分层架构模型：**隐式 / 显性 / 外部记忆**
- 分类逻辑基于"记忆的读写效率"——无论是模型参数还是外部存储，最终都要落到"怎么读、怎么写"
- 从应用层面的读写效率出发做分层，有利于指导产品实践
- 另一个维度：**时间长短 + 修改难易程度**
  - 长期记忆：不太可能短期内改变的知识
  - 短期 / Working Memory：短期内会被用到或会变化的

**补充论点**（主持人追问后）：

- 还可以按**场景**拆：事实记忆 vs 偏好记忆、情境化回答、个性化陪伴——不同场景有不同记忆切分
- **但无论哪种场景拆分，都离不开读写效率这个底层问题**
- 结论：读写效率是最底层分类逻辑，场景拆分是上层

**关于基础设施 vs 定制**：

- 记忆基础设施目标是覆盖 **80-85%** 的需求
- 特定高要求场景（如游戏 <300ms 响应）需要**行业定制化优化**
- 游戏 vs 办公 vs 智能家居对时间敏感性要求不同
- Memos 的做法：留出**个性化窗口**让企业自定义 schema/架构，从 80 分拉到 85 分
- 再往上拉成本不成比例

## 主持人追问（第二轮）🔥

> "记忆的基础设施，哪一些是**必要条件**？"

### 李志宇回答"记忆基础设施的必要条件"

**两条技术主线**：

1. **面向人（Human-facing）**：给算法工程师用的记忆组件
2. **面向 Agent（Agent-facing）**：让 Agent 自己用好记忆系统

**Memos 的路线**：从面向人 → 面向 Agent 迭代。具体做法是把记忆系统**拆成 pipeline 阶段**：

```
抽取 → 组织 → 检索 → 更新 → 共享
```

每个阶段定义子能力 → API 化 → Agent 可以在上面做**自主编排和自主调度**

**关键判断**：
- 原来给游戏团队做的是手动定制化优化（构建用户画像、硬编码操作等）
- 未来：把这些操作/算子尽可能拆细、暴露给 Agent，让 Agent 自主理解和编排
- 这样灵活性比固定基础设施更高

## 嘉宾 3：骆昱宇（港科广 / OpenManus）— 数据库视角 + 推荐系统类比

**背景**：数据库实验室出身，带着数据系统视角看记忆。

**核心观点**：

1. **Agent 记忆本质上就是数据的增删改查**——数据库以前做的事
2. **从应用角度看，Agent 记忆又很像推荐系统**——记住用户偏好 + 场景偏好，做个性化推荐
3. 提出 **Agent Data System** 概念（2025 年 9 月起）——专门支撑 Agent 的各类数据应用
4. **记忆只是 Agent 数据的一类**——还有推理轨迹、状态、经验、可复用 skill 等
5. **长程复杂数据密集型任务**需要的不只是记忆——要查大量数据（几个 PB）、反复推理探测、调用工具
6. **现有数据基础设施（文件系统 + 向量库 + 图谱）很难统一抽象管理** Agent 的推理对象、状态、经验、记忆、skill
7. 认为 **Agent Data System 是有价值的方向**

**与推荐系统的关联**：用户在刷抖音/购物时记住个人偏好 + 场景偏好 → Agent 记忆做的事情类似

## 嘉宾 4：黄毽（华为云）— 企业数据与记忆的鸿沟

**背景**：华为云侧视角，关注企业级 Agent 落地。

**核心观点**：

1. **"进入不了数据，就进入不了企业"**——企业做 AI/Agent 的最大瓶颈不是模型，是数据提取能力
2. **记忆分类缺乏共识**——参数记忆 vs 结果记忆，每个记忆系统的分类都不一样，"五花八门"
3. **多模态记忆挑战**——语音、图像等非文本数据的记忆整合远未解决（会场 ASR 也验证了这一点）
4. **企业数据系统是否会被重构？**——传统 MySQL / 数据湖在 Agent 时代需要什么变化？
5. **查询和召回方式会变**——Agent 的数据查询方式和传统 SQL/API 不同，"该怎么查？怎么召回？"现在没有答案

**提出的问题**：
- 是否应该把传统数据库/大数据全部整合进来，再做提炼？
- 数据系统会不会被 Agent 需求完全重构？
- 如何让企业沉淀的业务数据真正供给 Agent 使用？

**引用其他嘉宾**：提到一位教授的 **"Graph of Content"** 概念——希望找到一种图结构来组织企业数据，使之可被 Agent 消费

## 嘉宾 5：陈旭 — Memory 解耦三阶段 + 适配层

> 对黄毽的企业数据问题做出回应，进一步展开为完整的记忆独立性论述

### 三阶段演进模型

| 阶段 | 说明 |
|---|---|
| **阶段 1（当前）** | **AI 为主，记忆为辅**——记忆系统围绕特定 Agent 设计，增删改查都服务于 Agent 提升 |
| **阶段 2（近期）** | **Memory 与 Agent 独立发展**——两条平行演进脉络，Memory 本身就是主体（知识传承 > 模型能力） |
| **阶段 3（远期）** | **Memory 为主，LLM 是"渲染器"**——知识/数据才是主体，大模型只是在 Memory 之上做解析和呈现 |

### 核心实验证据：跨模型记忆迁移失败

**实验**：在 Claude Code 中积累了大量对话记忆 → 把这些记忆原文放到 Codex 中 → **表现并不好**。

**解释**：每个 LLM 在产生输出时有自己的风格和偏好。Memory 如果和特定 LLM 耦合，换一个下游模型，性能就会下降。

### 关键主张：需要一个"适配层"

> "Memory 如果作为独立系统，下游使用不同 LLM 时，应该有一个适配层，适配到不同的模型，才能表现得好。**这一层现在关注的人不多。**"

- 当前假设：Memory 和 Agent 耦合，Agent 不会变
- 现实：用户手头有 Claude、GPT、Gemini 等多个模型，同样的记忆放到不同模型上差异很大
- 缺口：**Memory ↔ Agent 之间的适配层**

## 嘉宾 6：安波教授 — "记忆没有银弹"

**核心观点**：

1. **简单记忆设计可能就够了**——他们在做一个政府个性化项目，使用 CC Hermes 等相对简单的记忆方案，加上基本的兴趣/个性保持，似乎就能满足需求
2. **Memory 的价值高度依赖应用场景**——电商推荐需要复杂的偏好存储，但学术 research 类任务可能不需要那么多"花里胡哨"的设计
3. **底座模型对 Memory 系统有巨大影响**——不同的底座 LLM 会让同一套记忆方案表现差异巨大

**尖锐问题（向李志宇/Memos 提问）**：

> **"记忆的护城河能有多高？"**
>
> 会不会有一个开源方案把所有 Memory 创业公司都干没了？

**安波的判断**：

- **记忆没有银弹（No Silver Bullet）**——没有一个方案能解决所有问题
- Memory 和 Agent 的其他部分有很大的**依赖关系**
- 具体项目、具体场景决定了需要什么样的记忆方案

### 李志宇回应安波 — 角色扮演实验 + 三层记忆体系

**角色扮演实验（失败）**：

- 尝试用 prompt 让同一个 LLM 扮演初级/中级/高级/专家不同角色
- **发现没用**——模型背后的"基因"（能力）是一样的，prompt 引导只改变表面风格，不改变底层能力
- 对比人类：不同的人有不同的基因、不同的成长经历、不同的记忆 → 才有真正不同的见识
- **结论**：仅靠 prompt 层的资源管理（"用动物的肌肉"），无法让模型真正展现出不同角色的深度差异

**Memos 的三层记忆体系**（回应"护城河"问题）：

| 层级 | 说明 | 谁在做 |
|---|---|---|
| **A 层（应用层）** | 用 prompt + 检索模拟记忆——大多数 Memory 创业公司在这层 | 绝大多数公司 |
| **激活层** | 深入到模型内部——需要理解模型结构、GPU 调度、参数化训练 | Memos 的方向 |
| **参数化演进** | Agent 基于交互历史、阅读过的内容持续训练演进，不是一次性 fine-tune | 远期愿景 |

**"激活记忆"的含义**：不是在 prompt 层面做记忆管理，而是**让记忆内化到模型参数中**——通过持续训练让模型真正"学会"，而不只是在上下文里"看到"。

**为什么要做激活层？**：
- "用空间换时间"——更深层的集成 → 更快的响应 → 更短的前置时间
- 应用层的天花板是 prompt 能力的天花板——模型基因不变，换个 persona 也没用
- Memos 认为真正的护城河在激活层以下

**Memos 的护城河逻辑**（李志宇回应安波）：
- 从 2025 年 6-7 月开始向业界推广记忆基础设施
- 核心壁垒在**用户数据飞轮**——一天超过一百多万次调用，数据积累本身构成迁移成本
- 目标：7 月对外发布，年底迭代完善

### 黄毽追问：参数化记忆 + 推理时内化

- 问到参数化记忆与强化学习的关系
- 讨论到一个更激进的想法：**推理时直接内化到神经网络**（不走 RL，类似 Test-Time Training 方向）
- 嘉宾们认为这是**未来方向**，当前不成熟

### 主持人提问 🔥：记忆会不会出现统一的协议层？

> "Memory 这一层，会出现一个统一的协议层吗？还是说大家拼数据、拼工程，谁攒的数据多谁有优势？"

嘉宾回应要点：
- 数据本身涉及的隐私/合规不能简单跨平台迁移
- 可能出现两种路线并存：一套协议范式 + 各家自定义实现
- 核心还是**效果和技术本身的优化**

## 张书豪 vs 安波：要不要先定义"记忆体"？

**张书豪**：应该先定义清楚"记忆体到底是什么"——没有定义就没有标准，没有标准大家不知道往哪里用力。希望先有 benchmark 和标准。

**安波**：Who cares 这些定义——关键是解决问题。

**砚砚的精确调和**：

> 两人都对，但在不同层面。如果定义只是分类学（session/factual/working），那确实没人在乎。但如果定义决定了**接口、权限、审计、eval 的责任边界**，那就很重要。

**砚砚给出的人话定义**：

> **Agent Memory 不是"存下来的内容"，而是"会影响 Agent 未来行动的可治理状态"。**
>
> 没有治理的 memory 只是缓存；没有行动影响的 memory 只是日志；真正的记忆体，是会改变未来行为、且能被追责和修正的状态。

## 圆桌观点补充（嘉宾待确认）

**"记忆分得越细碎，越难企业落地"**

- 记忆粒度越细 → 抽象和记录的成本越高 → 企业落地越难
- 暗含的工程判断：**过度结构化的记忆分类本身就是一种负债**

**我们的实践印证**：Cat Café 在 coding 场景的实际记录策略恰好回避了这个陷阱——

| 记什么 | 不记什么 |
|---|---|
| 决策和教训（为什么做 X 不做 Y） | 代码实现细节（git 里有） |
| 铲屎官偏好和约束 | 文件路径、项目结构（grep 就知道） |
| 外部系统踩坑经验 | 临时任务状态 |
| 跨 session 项目状态 | 已有文档重复的内容 |

**判别式**：代码是它自己的记忆。记忆系统记的是**代码记不住的东西**——决策逻辑、犯错教训、偏好约束。这比"按 session/factual/working 分类再逐条记录"简单得多，也更容易落地。

| "记忆没有银弹" | 6 件 = 共性约束 | 🔥 安波说没有银弹（场景差异大），但我们的 6 件不是银弹——是**不管场景怎么变都必须有的共性约束** |

**关键观察**：

1. 学界/业界目前的讨论集中在两个维度：**分类**（记忆有哪些种类）和**基建**（存储/检索/Pipeline 怎么搭）
2. 我们的"6 件必须有"属于第三个维度：**治理与操作约束**（不管你怎么分类、怎么存，系统必须具备的能力）
3. 这三个维度是正交的——他们不是错了，是还没到我们关注的那一层
4. **Memos 的 pipeline 拆法**（抽取→组织→检索→更新→共享）和我们的"6 件"有映射关系，但他们拆的是**工程阶段**，我们拆的是**治理要求**
5. **黄毽的企业视角**揭示了一个新维度：**数据 → 记忆的转化鸿沟**。这正好对应我们 Write Gate 里的 Truth Source 标注——企业数据不是天然就是记忆，需要经过信任等级标注才能成为 Agent 的记忆
6. **三阶段模型**有意思：如果记忆真的走向独立于 Agent 的方向，那我们的"6 件必须有"反而更重要——独立的记忆系统需要更强的治理，不是更弱
7. 🔥 **适配层 = Harness**：陈旭从"Claude Code 记忆放到 Codex 表现差"的实验出发，独立推导出 Memory 和 Agent 之间需要一个适配层——**这就是我们说的 Harness**。我们家三猫共享同一套记忆系统，通过 Harness 适配到不同模型，正是他说的"阶段 2"的活实现

## 三猫内部讨论：李志宇"参数化记忆"论点的精确评估

> 宪宪 × 砚砚 实时讨论（会场同步）

### 砚砚的四层分解（核心增量）

李志宇把"prompt 层角色扮演失败"直接推导到"必须做参数化记忆"——中间跳了两层。更精确的分层：

| 问题 | 主要解法 | 对应我们的框架 |
|---|---|---|
| 模型不知道事实/上下文 | 外部记忆（明文） | 写入门禁 + 审计溯源 |
| 模型会误用/忘用记忆 | **Wearing Protocol / Harness** | 第 3 件必须有 |
| 模型缺稳定行为习惯 | Skill / policy / eval loop | 第 6 件 Eval 反馈环 |
| 模型缺底层能力或专业直觉 | adapter / 后训练 / 参数化记忆 | 超出 6 件范围——这是模型层问题 |

**共识**：李志宇证明了第四层（参数化）的价值，但企业 Agent 当下最大的痛是**第二层和第三层都没做**——记忆有了但不会用、用错了不知道、过期了不退役。在参数化之前，前三层你做了吗？

### 护城河判断

- **通用记忆组件**（向量库/graph/pipeline）→ 护城河不高，容易被开源替代
- **深度适配的记忆系统**（Memory × Harness × Eval）→ 护城河高，因为壁垒来自业务现场、eval 数据、错误教训和适配层，不来自存储算法

### 建议的接话策略

> "我同意 prompt 扮演专家有天花板，也同意一部分高频稳定能力最终会进入参数或 adapter。但在企业 Agent 里，更常见的问题不是'记忆有没有进参数'，而是'记忆能不能被正确写入、正确召回、正确降权、正确审计，并且能适配不同模型'。陈老师提到的 Memory-Agent 适配层，正是 Harness 和 Memory 汇合的地方。"

### 共享记忆的真正解法（砚砚补充，铲屎官追问触发）

> 铲屎官问："他们说的 shared-state，我们就是共享记忆——到底怎么解决的？"

他们实验失败的原因：**把一个模型的私有上下文原文，当成另一个模型的可用记忆**——Claude 的聊天记录塞给 Codex，Codex 读到的是"别人的脑内碎片"，当然会坏。

Cat Café 的解法不是 memory copy，而是三层：

| 层 | 内容 | 关键 |
|---|---|---|
| **共享现实层** | feature spec / ADR / lessons / git / session chain / evidence.sqlite / Knowledge Feed | 不是某只猫的聊天记录，是团队的"现实账本" |
| **编译索引层** | lexical search / semantic search / graph resolve / recent list / authority+provenance | 把现实变成可被 agent 查询的外部工作记忆 |
| **Harness 适配层** | System prompt / skill / recall routing / Wearing Protocol / context block | 每只猫用自己的方式佩戴同一份记忆 |

**一句话**：不要把一只猫的脑内小纸条塞给另一只猫。要把团队共同面对的现实写成账本，然后让每只猫按自己的天性去查账。

> Raw conversation → **governed shared state** → **model-specific harness adaptation**

中间多的两层，正是陈旭说的"适配层"+ 我们的"6 件必须有"。
