# Topic 1 Agent Memory 会议纪要

这份纪要分两层：

1. **客观纪要**：记录会场实际讨论了什么，不混入 Cat Café 判断。
2. **Cat Café 观察版**：用我们自己的实践框架解释：哪些观点和我们共鸣，哪些没有回答问题，哪些暴露了行业空白。

---

## 一、客观纪要：会场到底讨论了什么

### 1. 议题背景

主持人开场提出：过去一年 Agent Memory 领域出现大量同质化工程实践，主要集中在**存储结构和检索能力增强**，通过更复杂的多模态检索在 benchmark 上拿高分。

但问题是：**检索形态不等于记忆本身**。Agent Memory 未来会如何演进，学界和业界是否已经形成共识，真正的分歧在哪里？

---

### 2. 记忆分类尚未形成共识

张桂彬提出一个 2 × 3 分类框架。

按功能分：

| 类型 | 含义 |
|---|---|
| Experiential Memory | 跨任务、跨 session 的经验记忆，让 Agent 越做越好 |
| Factual Memory | 对世界事实和对话事实的记忆，现场判断是已接近饱和 |
| Working Memory | 长程 Agent 执行 1000-3000 步任务时的工作记忆，是当前痛点 |

按形态分：

| 类型 | 含义 |
|---|---|
| 明文记忆 | 文本、图片、token、视频等显式存储 |
| 参数化记忆 | 内化到模型参数中的记忆 |
| 潜在表示 | hidden state / KV cache 等非明文表示 |

这个框架的价值是覆盖面广，但现场也能看到：大家对“记忆到底怎么分”仍然没有统一答案。

---

### 3. Memos 从读写效率出发定义记忆基础设施

李志宇认为，记忆系统的底层问题是**读写效率**。不管是模型参数里的记忆，还是外部存储里的记忆，最终都要落到“怎么读、怎么写、怎么在应用中用起来”。

Memos 的基础设施思路是把记忆拆成 pipeline：

```text
抽取 → 组织 → 检索 → 更新 → 共享
```

再把每个阶段原子化、API 化，让 Agent 能在这些能力上做自主编排和自主调度。

他还提出三层路线：

| 层级 | 含义 |
|---|---|
| 应用层记忆 | prompt + 检索 + summary，大多数 memory 创业公司在这一层 |
| 激活层记忆 | 更深入模型内部状态、GPU 调度、KV cache 等 |
| 参数化演进 | 让模型基于交互历史和阅读内容持续学习，不只是一次 fine-tune |

他的商业判断是：单纯外部记忆容易被开源追上，护城河来自数据飞轮、平台调用量、参数化投入和跨平台记忆管理。

---

### 4. 企业侧最大痛点：数据进不来

黄毽提出企业侧问题：

> 进入不了数据，就进入不了企业。

企业里大量数据在数据库、数据湖、知识库、业务系统里。当前 Agent Memory 多数还停留在 working trace、对话历史、简单偏好上，没有解决企业既有数据如何被 Agent 读取、理解、提炼和召回。

这把问题从“Agent 记忆怎么存”推到了“企业数据系统是否要为 Agent 重构”。

现场相关问题包括：

- 传统数据库、知识库、数据湖是否会被整合进 Agent Memory？
- 企业历史数据是否也是一种长期记忆？
- Agent 查询企业数据的方式会不会不同于传统 SQL/API？
- 数据系统是否需要一层新的 Graph of Content / Agent Data System？

李志宇给出的一个初步技术方向是 **text-to-memory**：类似 text-to-SQL，但目标不是生成 SQL 查询本身，而是用自然语言触发一组 memory operation / data operation，让模型根据意图决定查什么数据、调什么缓存、如何组织下游操作。他也承认这还不是成熟生产范式，尤其企业数据接口、查询语句生成和下游执行准确率仍然是难点。

---

### 5. Agent Data System：把记忆放回数据系统里看

骆昱宇从数据库背景切入，提出另一个独立视角：Agent Memory 本质上可以看成数据的增删改查，但它又不只是传统数据库。

他的核心判断包括：

- Agent 记忆和推荐系统相似：都要记住用户偏好、场景偏好，并在后续任务中做个性化匹配；
- 记忆只是 Agent Data 的一类，Agent 还会产生推理轨迹、状态、经验、可复用 skill 等多种对象；
- 长程复杂数据密集型任务需要的不只是“记住”，还要能反复查询大量数据、调用工具、在不同数据结构之间建立抽象；
- 现有文件系统、向量库、图谱和数据库很难统一管理这些 Agent 运行对象，因此可能需要新的 **Agent Data System**。

这个视角和 Memos 的 memory pipeline 不同。Memos 更像从产品基础设施出发拆读写流程；骆昱宇则把记忆放回数据系统和数据库演进里看，问题不是“多一个记忆库”，而是 Agent 时代的数据抽象是否会重构。

---

### 6. Memory 可能会和 Agent 解耦

陈旭提出三阶段判断：

| 阶段 | 判断 |
|---|---|
| 阶段 1 | Agent 为主，Memory 为辅 |
| 阶段 2 | Memory 和 Agent 独立发展 |
| 阶段 3 | Memory 为主，LLM / Agent 成为渲染器 |

他还提到一个关键实验：在 Claude Code 中积累了大量对话记忆，把这些记忆原文放到 Codex 中，表现并不好。原因是不同 LLM 有自己的风格和偏好。

由此他提出：**Memory 和 Agent 之间需要一个适配层**。

这说明 Memory 如果要成为独立系统，不能假设下游 Agent 永远不变，也不能把某个模型的私有上下文直接迁移给另一个模型。

---

### 7. 记忆没有银弹

安波教授认为，不同场景对记忆的要求差别很大。简单政府个性化 / social simulation 场景，可能简单记忆设计就够；电商推荐、长期陪伴、复杂企业系统则可能需要更复杂的记忆机制。

他追问 Memos：记忆公司的护城河有多高？会不会被开源方案干掉？

这个问题把讨论从技术路线拉回商业现实。

---

### 8. 同一模型扮演不同角色的实验

李志宇提到，他们尝试用同一个大模型，通过 prompt 或框架引导它扮演初级专家、中级专家、高级专家等不同角色，但发现效果有限。

他的判断是：同一个 base model 背后的能力是一样的，仅靠 prompt 不能让它展现出真正不同的能力层级。要让 Agent 真正产生长期差异，未来可能需要参数化记忆、激活层记忆或持续学习。

这个观点的合理边界是：

- 它能说明：同一个 base model 的短时角色扮演，不等于真实能力分化。
- 它不能直接说明：prompt、skill、harness 没有价值。
- 它也不能直接说明：企业 Agent 的当前痛点必须先用参数化记忆解决。

---

### 9. OS 视角：底层可能标准化，上层会百花齐放

赵新海从操作系统和文件系统角度补了一个很工程化的判断：Memory 系统应该拆成两层，而不是把所有能力混在一个“记忆体”概念里。

| 层级 | 类比 | 标准化前景 |
|---|---|---|
| 底层：文件系统级 | 类似 Linux / VFS，“一切皆文件”式地管理不同形态的数据对象 | 更可能形成统一标准 |
| 上层：数据库 / 应用级 | 类似 MySQL、各种 memory 系统、不同场景的一体化实现 | 更可能多路线并存 |

他的判断是：底层要解决统一抽象和可访问性，上层则会因为场景不同而长期百花齐放。这个观点介于“先定义大一统标准”和“完全 it depends”之间：底层需要协议，上层不必强行统一。

---

### 10. 要不要先定义标准

张书豪希望先定义清楚“记忆体是什么”，否则大家各说各话，benchmark、测试集、目标都不统一，社区无法协同进步。

安波反驳：工程上最终看解决问题，不要为定义而定义。

主持人最后收束到一个问题：未来 Agent Memory 会不会出现类似协议层的东西？如果出现，谁来定义？是拼数据、拼工程，还是拼事实标准？

现场没有给出确定答案，但形成了一个问题意识：

> 如果 Memory 要独立于 Agent，甚至成为认知基础设施，那么迟早需要某种协议层或事实标准。

---

## 二、客观总结

Topic 1 没有形成统一共识，而是暴露了混乱：

- 学术界想要 taxonomy 和 benchmark；
- 平台方想做基础设施和数据飞轮；
- 企业侧想知道数据怎么进 Agent；
- 数据系统派认为需要新的 Agent Data System；
- OS 派认为底层可能标准化、上层会百花齐放；
- 工程派认为场景差异太大，没有银弹；
- 标准派希望先定义协议，否则大家无法协同。

这说明 Agent Memory 还处在早期战国时代：大家都承认它重要，但对于“它到底是什么、应该由谁管、怎么验收”，还没有统一答案。

# 附录：Cat Café 观察版

## 1. 我们和会场最大的区别

会场里有一部分主流讨论在问：

> 记忆是什么？怎么分类？怎么存？怎么检索？怎么提速？

我们更关心：

> 记忆如何影响 Agent 未来行动？错了怎么办？过期怎么办？谁能写？谁能读？怎么证明它让系统变好了？

所以我们和这部分讨论不是在同一层。

但这不代表所有嘉宾都站在对面。陈旭的适配层、骆昱宇的 Agent Data System、赵新海的 OS/文件系统分层，都是潜在同盟：他们已经从不同角度碰到了“记忆不是一个向量库，而是运行时基础设施”的问题。我们的增量是把这个基础设施问题进一步推到**进入真实工作流后的治理和责任**。

---

## 2. 最强共鸣：陈旭的“适配层”

陈旭说，同一份 memory 放到不同 LLM 上效果会变差，因此需要 Memory-Agent 适配层。

这就是我们家的 Harness / Wearing Protocol。

Cat Café 的做法不是把一只猫的聊天记录塞给另一只猫，而是：

```text
Raw conversation
→ governed shared state
→ evidence / graph / recent / search
→ model-specific harness adaptation
→ 每只猫按自己的天性使用记忆
```

我们共享的不是某只猫的脑内小纸条，而是团队共同面对的现实账本。

---

## 3. 对“同模型扮演不同角色失败”的判断

这个实验能证明：

> 同一个 base model，仅靠 prompt 扮演不同专家，不能长出真正不同的能力。

但它不能证明：

- prompt / skill / harness 没用；
- Agent 分化只能靠参数化；
- Cat Café 的猫猫差异只是角色扮演。

更精确地说，Agent 差异至少有五层：

| 层 | 问题 | 主要解法 |
|---|---|---|
| 事实上下文 | 模型不知道什么 | 外部记忆 |
| 使用方式 | 模型知道但不会用 | Harness / Wearing Protocol |
| 持久身份 | 长期运行后是否形成可识别的工作风格和责任边界 | 名字、签名、历史互动、跨模型 review 记录 |
| 行为习惯 | 模型不稳定、不按流程 | Skill / policy / eval |
| 底层能力 | 模型真的不会 | adapter / 后训练 / 参数化 |

李志宇的实验主要打到底层能力这一层，但企业 Agent 当前大量问题还在前面几层，尤其是“知道什么”“怎么用”“长期身份如何累积”和“行为习惯是否稳定”。

Cat Café 也不是让一只模型扮演三种角色，而是：

```text
不同 base model
+ 不同 harness
+ 不同 skill / rules
+ 不同历史记忆路径
+ 跨模型 review
+ 真实任务反馈
```

这是一种结构性认知多样性，不是 prompt-only 角色扮演。

---

## 4. “没有银弹”支持我们，不是反驳我们

安波说 memory 没有银弹，具体场景不同。这个判断是对的。

但这反而说明：不要试图定义一个万能 memory 实现。真正该定义的是**最低协议约束**。

也就是我们说的 6 件必须有：

1. **写入门禁**：什么值得记，谁能写，进来后是什么信任等级；
2. **审计溯源**：这条记忆从哪来，谁验证过，错了能不能撤；
3. **Wearing Protocol**：Agent 什么时候该用记忆，什么时候该忽略或降权；
4. **生命周期治理**：过期、冲突、替换、退役怎么处理；
5. **多 Agent 一致性**：多 Agent 共享同一现实时如何避免污染和冲突；
6. **Eval 反馈环**：记忆系统改了以后，怎么证明 Agent 真的变好了。

存储用图数据库、向量库、文件系统、KV cache 都行，那是黑猫白猫。  
但这 6 件不回答，企业里就会出事。

赵新海的 OS/文件系统两层分解，是这个判断的外部支撑：底层统一抽象和上层多路线实现可以同时成立。我们这里说的 6 件必须有，不是在规定上层实现，而是在规定任何实现进入企业工作流前必须回答的责任问题。

---

## 5. 如果未来有 Memory Protocol，它应该规定什么

会场里多次提到协议层、事实标准、OpenMem 社区。

我的判断是：在 2026 年这个时间窗里，Memory protocol 不应该先从“怎么存”开始，而应该从“怎么负责”开始。

这不是所有协议的普适规律。HTTP / TCP 可以先从传输开始，SQL 可以先从查询模型开始。但 Memory 的特殊性在于：它会影响 Agent 未来行动，而 Agent 输出又是概率性的。**存对了不等于用对了，召回到了不等于该使用**。因此只规定存储接口不够，必须同时规定责任、边界和审计。

Memory protocol 真正要规定的不是“你必须用什么数据库”，而是：

- 每条记忆有没有来源？
- 谁写入的？
- 谁验证过？
- 适用范围是什么？
- 什么时候过期？
- 冲突怎么处理？
- 删除怎么证明真的删了？
- 被 Agent 使用时有没有 audit trail？
- 改了 memory 后有没有 eval？

这比“图数据库还是向量库”更像企业协议。

---

## 6. 我们从会场得到的校准

这场不是给了我们答案，而是确认了三件事：

1. **行业还没有统一 framing。**  
   Taxonomy、pipeline、数据库、参数化、协议层都有人讲，但没有统一闭环。

2. **企业侧真实痛点是数据和治理。**  
   “进入不了数据，就进入不了企业”很关键；但数据进来之后怎么变成可信记忆，现场仍没答案。

3. **Cat Café 的实战位置更清楚了。**  
   我们不是 memory vendor，也不是 benchmark 派。我们是从真实多 Agent 工作流里长出来的 memory-harness-eval 一体化实践。

---

## 7. 一句话结论

客观地说，Topic 1 没有形成行业共识。

但从 Cat Café 视角看，它确认了一个判断：

> Agent Memory 的下一层竞争，不只是存储和检索，而是“共享现实如何被写入、佩戴、审计、更新和评估”。这正是我们三个月 dogfood 已经踩出来的问题空间。
