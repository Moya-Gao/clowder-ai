# 人大：EnvScaler 与智能体训练环境合成现场笔记

> 现场初判：这条线不是在做普通的"合成数据"，而是在做 **给 agent 训练和评测用的可执行环境工厂**。它试图从已有任务和对话里反推出行业环境，再生成状态、规则、工具和可执行程序，最后用双 agent 循环测试筛掉脆弱环境。

## 1. 这项工作在解决什么

Agent 不是只靠问答样本就能学会现实任务。它需要在一个可交互的世界里行动：读状态、调用工具、改变状态、遇到错误、得到反馈。

EnvScaler 的核心目标是把这类环境的构建规模化：

- 从现有对话和指令任务中挖出环境主题，例如退款任务对应电商环境。
- 自动构建环境的状态定义、领域规则、工具列表和 Python 类实现。
- 用测试 agent 生成调用请求，用审查 agent 检查逻辑、状态变化和返回值是否符合预期。
- 通过多轮循环和通过率阈值，筛选出更鲁棒的训练/测试环境。

更准确地说，它合成的不是一批静态样本，而是 **可执行的行业微世界**。

## 2. EnvScaler 的三阶段流水线

### Stage 1：环境主题挖掘

从已有的对话和指令任务集中反向推理环境主题。

例子：

- 用户任务："我要通知 Bob 紧急撤离。"
- 推出的环境：移动消息应用，包含用户、联系人、短信或即时消息状态。

这一步不是直接写代码，而是判断一个任务背后需要什么样的领域状态和工具语义。

### Stage 2：可执行环境构建

逐步规划环境的：

- 状态定义：把环境中的实体和状态映射为类属性。
- 领域规则：定义哪些状态转移合法。
- 工具列表：把 agent 可调用动作映射为类方法。
- 程序建模：生成完整的环境程序，现场截图里强调是 Python 类实现。

这里的关键是：环境不是文档描述，而是可运行、可被 agent 调用、可被测试的程序对象。

### Stage 3：双智能体循环测试与审查

用两个 agent 做环境质量筛选：

- Testing Agent：随机生成各种工具调用请求，包含正例和负例。
- Checking Agent：检查判断代码逻辑、状态变更和返回结果是否符合预期。

通过多轮循环交互，用通过率阈值过滤低质量环境，留下更稳的环境。

这一步的本质是 **把环境生成也纳入 eval**：不是生成出来就算完成，而是让环境经历调用压力测试。

## 3. 未来工作方向

截图里列出的未来方向包括：

- 针对特定场景的环境合成，例如小程序、电商、游戏。
- 基于运行数据和隐式反馈的真实环境合成。
- 环境和任务的难度分级。
- 大规模训练和测试场构建。
- 用户建模与模拟。

这里最重要的是第二条：如果只从任务文本合成环境，容易得到"像环境的玩具"；如果能接入真实运行数据和隐式反馈，才可能逼近真实业务世界。

## 4. 和 Cat Cafe 的关系

这条线和我们家的 F192 / eval feedback loop 很接近，但站的位置不一样。

| 维度 | EnvScaler | Cat Cafe |
|---|---|---|
| 主要对象 | 训练和评测 agent 的合成环境 | 真实多 agent 工作空间 |
| 数据来源 | 任务集、对话、未来希望接入运行数据和隐式反馈 | git、docs、thread、review、tool logs、会议纪要 |
| 强项 | 可规模化生成大量可执行环境 | 长期 dogfood、真实失败、真实治理痕迹 |
| 风险 | 合成环境可能浅、judge 可能误判鲁棒性 | 覆盖面受真实工作范围限制，难规模化 |
| 最适合解决 | 训练和 benchmark 缺环境的问题 | 长期 agent 工作流如何可靠闭环的问题 |

一个简短判断：

> EnvScaler 在造"可练习的世界"；Cat Cafe 在经营"真实共居的工作世界"。

这两者互补。前者给规模，后者给真实性和治理压力。

## 5. 对"特种工小猫"问题的启发

铲屎官现场提到：通用天才猫和特定领域小猫可能应该分工。

EnvScaler 这类工作说明，特种工 agent 不只是换一个 prompt 或角色名，而是需要一个领域环境：

- 它知道领域有哪些实体和状态。
- 它知道哪些工具调用会改变状态。
- 它知道什么是合法转移、什么是错误操作。
- 它能在环境里反复练习和被审查。

所以，如果未来有"电商猫""医疗文档猫""游戏环境猫"，关键不只是训练一只猫，而是先构建它能练、能犯错、能被评测的行业环境。

## 6. 我们应该追问的点

1. 生成的环境语义如何验证？
   - 如果状态定义或领域规则本身错了，Checking Agent 可能只是在验证一个错误世界。

2. 环境是否支持长程状态？
   - 很多真实任务不是一次工具调用，而是跨天、跨 session、跨用户状态变化。

3. 如何处理权限和不可逆操作？
   - 真实业务环境里，退款、删除、发消息、改订单都不是普通函数调用。

4. 环境难度如何稳定标定？
   - 如果难度分级靠 LLM judge，可能出现同一环境不同模型理解不一致的问题。

5. 是否产出完整 trace？
   - 对我们来说，环境不仅要给 pass/fail，还要能回放：哪一步状态错了、哪个工具定义导致错、哪条规则缺失。

## 7. 现场 takeaway

这场的价值点是把"agent eval"往前推了一层：

- 不是只评 agent 答案。
- 也不是只评工具调用结果。
- 而是评 **生成出来的训练/测试环境本身是否可信**。

这和我们家的经验一致：agent 能力不是只由模型决定，还由它所处的环境决定。一个坏环境会训练出坏 agent；一个不可审计的环境会让高分 benchmark 失去现实意义。
