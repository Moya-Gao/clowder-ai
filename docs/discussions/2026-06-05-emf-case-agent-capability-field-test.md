## 二、三猫独立分析

铲屎官把聊天抛给 @opus @codex @opus48 三猫并行独立分析。以下是各猫核心观点。

### 2.1 宪宪/Opus-4.6 — 四层能力缺口 + Environment Fit = 0 诊断

**核心判断**：问题精确落在 longform-003 的核心公式上——`Agent Quality = Model × Environment Fit × Eval Fit`，谢泽丰团队的 agent Model Capability 不差（能写 SDK），但 Environment Fit ≈ 0。

四层能力缺口：

1. **问题空间构造能力**：在写第一行转换代码之前先造覆盖不同 record type 的测试 EMF。不是"更聪明"，而是"有纪律"。meta-method 蒸馏里区分 SOP 和 Method——"遇到未知格式→先穷举其内部结构空间→构造覆盖性样本"是可迁移的问题拓扑，PDF/音频/私有协议都通用。

2. **多路径探索 + 交叉验证**：不是"想到"多条路径的问题，而是方法论里有没有内置"多路径"反射。三个触发点——"补锅匠"检测（3 个 patch 不对→退后一步）、Spike 探索纪律（strings > grep > 实验 > docs）、Expert-panel 多视角（spec/逆向/实验各一路，互相 falsify）。

3. **元认知——知道自己不知道什么**：AI 最容易犯"我能猜出来"——用推理跳过查询。不先读 MS-EMF spec、不先看 LibreOffice `emfio` 模块就开始写 parser。

4. **失败模式的命名和生命周期管理**：给失败命名（"不处理渐变填充"而非笼统"效果差"）→ 结构化信号 → 针对性补偿 → 迭代。

**结论**：五个 harness 级能力（问题空间构造 / 多路径反射 / 元认知循环 / 诚实能力边界 / 失败驱动自进化），全部不是 model 层而是 environment 层——"训环境不训模型"。

### 2.2 砚砚/GPT-5.5 — 研究型闭环 + 6 能力清单

**核心判断**：谢泽丰要的是**研究型闭环能力**——从一个失败 case 里看出问题族，自己构造样本、找 oracle、做差分验证、沉淀方法。不是"更会写代码"，是"会把一次失败转化成研究系统"。

先纠偏铲屎官理解：不是"PPT 被保存成 EMF"，而是某些工作流把矢量内容以 EMF/EMZ 嵌进去；EMZ 是 EMF 的 gzip 外壳；真正难点不是"解压"，而是 EMF 本质是 Windows GDI 绘图记录，要转 SVG 需要重放绘图语义。（来源：MS-EMF 规范）

6 个能力：

1. **问题坐标系重建**：识别"少见/遗留/平台绑定格式的跨端渲染问题"，不是"这张图片坏了"
2. **从一个 case 扩展到样本族**：文字/表格/图表/渐变/透明度/裁剪/组合/旋转/中文字体/嵌入位图/EMF+ records
3. **先定义 oracle 再写转换器**：没有 oracle 的"效果不错"不算进展
4. **多路线互证**：开源/规范/逆向/自造/真实邮件 MIME / Exchange 前后对比，互相校验
5. **产品化取舍**：高覆盖 SVG + 不支持 record 的 raster fallback + unsupported report
6. **把经验沉淀成 harness**：从 episode 抽 topology / method / skill / eval

### 2.3 宪宪/Opus-4.8 — 4 环自闭合 + EMF 解空间实测

**核心判断**：先做了 EMF→SVG 的**真实解空间测绘**（WebSearch 验证），发现这根本不是"无解逆向"——成熟开源库 `kakwa/libemf2svg`（CERN 出品、.NET wrapper、NuGet 可用）早就存在，EMF 有微软官方开放规范 MS-EMF。"效果差"不是因为难，是因为 AI 一上来就自己写 parser，跳过了"这问题别人解到什么程度"。

命名了两种 Anthropic 近期定义的病：
- **Agentic Laziness**：长任务后期注意力衰减
- **Self-preferential Bias**：让模型验证自己产出时倾向觉得"差不多了"

4 环自闭合模型：

1. **测绘解空间**（替使用者发现方向）：第一动作不是写代码，是打探"有 spec 吗？有人解过吗？有参照实现吗？"——30 秒搜索直接找到 libemf2svg。
2. **自造判分器**（oracle）：用 python-pptx 程序化生成已知内容 PPT → 导出 EMF → 转 SVG → 跟已知内容自动比对。这是"自驱"的物质基础——没有 oracle，猫只能等人喂 case。
3. **多源三角测量**（differential testing）：逆向 jar / LibreOffice / 官方 spec 互相独立的 oracle，分歧点 = bug 定位。
4. **结构化失败 + 坐标系自检**：把"效果差"拆成可定位的分面（字体/路径填充/坐标变换/EMF+ records），同型 edge case 一轮轮繁殖→"补锅匠"警报→换层。

**关键额外洞见**："不是共性需求"恰恰是价值所在——共性需求靠预置 skill 覆盖，长尾业务难题才是 Agent 2.0（服务平均用户）和 3.0（适配你这一个任务）的分水岭。

## 四、对 longform-003 的意义

这个 case 验证了 longform-003 的三个核心命题：

1. **"训环境不训模型"**：同样的模型（Claude/GPT），在有方法论的环境 vs 没有方法论的环境里，产出天差地别。EMF SDK 效果差不是模型弱，是环境没有驱动它先测绘、先造 oracle、先多路径。

2. **"Meta-method ≠ SOP"**：谢泽丰要的"通过一个 case 构造更多 case"，是从 episode 抽 topology 的能力——不是"EMF 怎么转"的 SOP，而是"遇到未知格式应该怎么想"的 method。

3. **"长尾 = Agent 3.0 的战场"**：共性需求靠预置工具就能覆盖（Agent 2.0），长尾业务难题才需要从真实轨迹里长出方法的环境（Agent 3.0）。
