# F231 Design Gate — OQ-1 Closure: Capsule 注入层

> **Decision Gate**: OQ-1 closed → KD-7
> **Decided by**: 宪宪/Opus-4.7（@opus-47，ADR-038 + L0-budget-defense owner）
> **Author concurrence**: 宪宪/Fable-5（@fable-5，F231 spec author，commit `e5100a486` 落 spec 字段）
> **Reviewer alignment（既有）**: 砚砚/GPT-5.5（@codex，ADR-038 reviewer chain R3/R5 已 align direction A）

## Decision (KD-7)

Capsule 注入层 = **L0 编译时 `{{USER_CAPSULE}}` 模板变量**（compile-system-prompt-l0.mjs 同构扩展，与 IDENTITY_BLOCK / TEAMMATE_ROSTER / GOVERNANCE_L0 / WORKFLOW_TRIGGERS / CVO_REF 同条编译链）。

- **不进 SystemPromptBuilder 运行时**（压缩窗口期内可丢）
- **不进 ADR-038 Staging 层**（虽然 Staging 不占 L0 cap，但 ADR-038 三问判定 capsule 属"全程身份/球权类"——必须留 L0）
- **Capsule 排 ADR-038 promote queue #2**（#1 是 fable-5 登记的 shared-rules §21 投影行），注入锚 gated on **ADR-038 PR-C 落地**（demote codex/gpt52 回 ≤6000，ETA 2026-06-13）
- **Capsule 硬上限 300 字**（~285 tokens，author 拍板：紧约束强迫蒸馏，溢出走 primer recall）

## Why this layer — ADR-038 三问机械化判定

ADR-038 三问 checklist 我自己写的，对 capsule 应用一遍逐条复核：

| 三问 | Capsule 判定 | 含义 |
|------|-------------|------|
| ① 触发条件是否单轮内完整出现且消费完毕？ | ❌ 否 | Capsule 是全程身份语境（"先接住人再讲规则"是每条消息都要应用的姿态），不是单轮反射 |
| ② 压缩后丢失、下轮恢复，期间功能缺口是否有害？ | ❌ 有害 | 压缩窗口期内"猫不知道主人是谁" = 班味回潮 = F231 这个 feat 解决的问题反弹 |
| ③ 是否被其他 L0 条款引用？ | 同维度引用 | Capsule 与 L0 §1（身份段）、§9（协作哲学）语义相邻，属同维度而非孤立 |

**ADR-038 表格里"全程身份/球权类"判定示例直接命中**：

> | 全程身份/球权类 | 跨轮持续 + 缺口有害 + 被多 L0 引用 | **必须留 L0** | P1-P5、W1-W8、五条铁律、@ 路由格式、球权第一人称 |

Capsule 属"全程身份/态度"类，与 P1-P5 / W1-W8 / 五条铁律同维度。把 capsule 下到 Staging = 让协议第一个真实 user-case 走错门，设错先例。雨刮器 dogfood 在 Staging 是因为它"单轮反射 + 缺口无损"通过了三问；capsule 三问全反，跟雨刮器同处理 = 自违协议。

## Budget 实测（全猫 compiled L0）

测量方法：`node scripts/compile-system-prompt-l0.mjs --cat <id>` 输出字节数；ratio 校准 = gpt52 6142 tokens / 19,415 bytes ≈ **3.16 bytes/token**（中英混合实测）。

| Cat | Compiled bytes | Tokens (est) | vs 6000 cap |
|-----|---------------:|-------------:|------------:|
| codex (砚砚) | 19,427 | ~6,145 | +145 |
| gpt52 | 19,415 | 6,142 | +142 (BACKLOG 锚) |
| gemini25 (烁烁) | 18,680 | ~5,910 | −90 |
| fable-5 | 18,509 | ~5,855 | −145 |
| opus-47 | 18,487 | ~5,848 | −152 |
| sonnet | 18,485 | ~5,847 | −153 |

Capsule 字数 → token 影响（gpt52 视角，最紧约束）：

| 字数 | est tokens | gpt52 L0 总计 | vs 6000 cap |
|-----:|----------:|--------------:|------------:|
| 500（spec 初值） | 475 | 6,617 | +617 ❌ |
| 400 | 380 | 6,522 | +522 ❌ |
| **300（锁定）** | **285** | **6,427** | **+427 ❌** |
| 200 | 190 | 6,332 | +332 ❌ |
| 150 | 142 | 6,284 | +284 ❌ |

**结论**：capsule 任何合理字数进 L0，gpt52 当前都会进一步顶 hard cap。**这不是 capsule 设计问题，是 ADR-038 PR-C 尚未落地（PR-C 目标本来就是把 codex/gpt52 demote 回 ≤6000）**。

## Budget Conservation Strategy

走 ADR-038 promote queue（协议自带解法，不是绕路）。ADR-038 promote 入口（staging → L0）伪代码：

```
if (L0_current + new_item > HARD_CAP_L0) {
  A. demote candidate(s) 让出 L0 预算
  B. queue promote (等自然 demote)
  C. push back
}
```

F231 capsule 走 **B = queue promote**：

1. **排队 promote queue #2**（#1 是 shared-rules §21 投影行，已在 BACKLOG 锚）
2. **等 ADR-038 PR-B-impl + PR-C 落地**（ETA 2026-06-13）——PR-C 完成"first demote case 让 codex/gpt52 回 ≤6000"后 L0 才有 budget headroom
3. **PR-C 落地后**复跑 budget 实测：若 gpt52 fresh build ≤ 6000，capsule 注入锚解锁，AC-A2 守护测试三态断言可挂 CI

**为什么硬上限选 300 而非 250 / 350**：

- **250 太紧**：250 字中文容不下"Landy 是谁 + 相处事实 + 边界提示"完整清单（实测 fable-5 评估，本 thread 14:26 UTC）
- **350 是想塞规则的信号**：author 拍板 300——"想要 350"的冲动本身就是想塞行为指令（KD-4 红线："写事实与轨迹不写指令"）。紧约束强迫蒸馏到最浓，溢出走 primer 按需 recall
- **300 = ~285 tokens ≈ 当前一个独立 §**（对比基线：§9 协作哲学全文 ~340 tokens）
