# 宪宪的独立视角：从一个灵感，到一部可爱的猫猫 vlog

> 砚砚（@codex）的 `README.md` 已经把 yoyoung 的**工程拆解 + manifest 建议**做透了：
> 闭源 showcase、thin 前端、云端代理生成、stage rail、资产锚定、逐镜工作台、
> 以及 `production-manifest.json` / `registry.yaml` 的落地建议。**那一层我不重复。**
> 铲屎官问"除了砚砚说的还有什么"——所以我把视角抬高一层：
> 战略定位 + 创作架构 + 一致性的真正机理 + 基建该窄到什么程度。
>
> 证据基础：我自己读了 yoyoung 的 FEATURES/CASES/ROADMAP，亲眼看了它的角色资产卡
> （`asset-prompt-character-light.png`）和一致性历史栅格（`case-single-character-consistency-history.png`），
> 加上砚砚的 claim ledger。下面凡是"我看到"的都是一手。

## 1. 我的判断（TL;DR）

1. **yoyoung 值得偷的不是功能清单，是它的数据模型。** 它的"工作流"是表象；底层真正起作用的是——把角色/场景/道具变成**带子字段的持久化资产**，每次生成都把它当锚点注入。模型是可换的，资产图谱才是护城河。这一条砚砚也指到了，我同意，且我亲眼确认了机理（见 §3）。

2. **但我们不该 clone 它——因为我们有它结构上拿不到的东西：猫既是剧组，也是主角。** yoyoung 是给陌生人用的单人 SaaS，它做的是"通用短剧工具"；我们做的是**猫猫自传**。它的 showcase 是仙侠美女（不可爱、不是猫），可爱和猫味 100% 是我们的活。这不是细节差异，这决定了基建怎么下注（§4）。

3. **一致性不是"模型能力"，也不是"会写提示词"，它是数据结构 + 取舍纪律的涌现属性。** 铲屎官的尖问题问对了：截图里看不到的恰恰是难的部分。一致性 = 正典资产 + 每帧强制注入参考与"硬性连续性指令" + 逐镜验收门（taste 一直在环里，只是被"工作流"三个字盖住了）。

4. **基建要窄到一句话：先建一次"猫猫正典 cast bible"，让它复利；其余全部 defer。** 我们做的是**系列**，不是一次性项目——所以资产不该 per-project（yoyoung 必须 per-project，因为它服务陌生人），而该是**建一次、永久复用的正典**。第 5 集应该比第 1 集更便宜、更稳，因为 bible 成熟了。这是我们最高杠杆的单点投资。

## 2. 直面铲屎官的三个尖问题

铲屎官原话（03:23 UTC）：
> "人家只是在素材库可见性做的好吗？如果只是这样那好像很难真的做好吧？精髓在哪里？短剧有的可比我们的长啊？！如何保证一致性？想要的镜头剧情？"

我一条条正面回答，不绕。

### 2.1 "只是素材库可见性做得好？"——不止，但你的怀疑是对的

素材可见性（History/沉淀那一栏）只是**结果**，不是**精髓**。你的直觉准：如果只有"把图列出来给你看"，那确实没什么难度，也撑不起一部连续短剧。

真正难、且 yoyoung 在截图里**故意不展示**的，是三件事：
- **一致性怎么不漂**（同一只猫，20 个镜头还是同一只猫）；
- **想要的镜头/剧情怎么拿到**（不是抽卡抽到什么算什么）；
- **谁在每一帧上做"收 / 不收"的判断**（taste gate）。

yoyoung 把这三件事藏在"工作流"这个词后面。它们不是 UI，是机理。

### 2.2 "精髓在哪里？"——精髓是把"抽卡"变成"连续创作"的那套约束

我亲眼看了它的角色资产卡（`苏静妹`那张）：那不是一个提示词输入框，是一张**结构化卡片**——身份、面部特征、发型/轮廓、服饰材质、空间结构、视觉锚点、连续性规则、道具形状/材质/比例，分字段填。

再看它的历史栅格：8 张同一角色不同姿势的图，脸、服装、气质都没漂。而且每张卡片上都压了一行红色祈使句（我一手读到的）：

> `[ACTION PRIORITY] CRITICAL: The following props/weapons (禁重写) MUST be active/HELD/HANGING on the characters. NOT placed.`

**这就是精髓**：它不是靠"一张参考图"保一致性，它把**硬性连续性指令当成一等生成输入**，每帧强制注入（"这些道具必须被角色握着/挂着，不准放在旁边"）。参考图管"长得像"，祈使指令管"动作和道具不跑偏"。两条腿走路。

> 砚砚在 ledger 里抽象地写了 "continuity rules / visual anchors"；我这里把它**坐实**了——它是一条**带优先级标签的命令式约束**，不是描述性提示词。这是可以直接偷的技术细节。

### 2.3 "如何保证一致性 / 想要的镜头剧情？"——三个机制，缺一不可

| 要保的东西 | 机制 | 真相源 | 反模式（别这么干） |
|---|---|---|---|
| **角色/场景/道具一致** | 正典资产卡（结构化字段）+ 每帧强制注入"参考图 + 命令式连续性指令" | cast bible | 每镜重写提示词；指望一张图自动续上 |
| **想要的镜头/剧情** | shot-list 是**视觉生产的唯一真相源**；每个剧情点必须落成**视觉锚**（红叉、对比帧、指向动作），不能停留在自然语言 | shot-list / 分镜表 | "让模型自己理解剧情"——模型不理解，它只渲染你给的锚 |
| **整体不崩** | 一镜一梗（一个镜头只扛一个信息点）+ 逐镜验收门 + 三振降级（连抽三次不行就退化成静帧/转场/插卡） | animatic 检查点 | 把节奏/取舍交给模型；没有人在环里收帧 |

关键一句：**"想要的镜头"不是描述出来的，是约束出来的 + 收出来的。** yoyoung 那个 `8 / 30` 的逐镜导航 + 每镜验收状态，本质就是"有人在一帧一帧地点头/摇头"。这个"人"在我们这里——就是猫。

至于"短剧有的比我们长"——长不是问题，长靠的是**资产复利**：bible 越成熟，每多一集的边际成本越低。短反而是我们现在该守的纪律（先把一集 30-60s 做到能看，再谈长）。

## 3. 我们和 yoyoung 的根本不同（砚砚没展开的战略层）

砚砚的对比表把它当"同一个问题的竞品"来比（episode state / asset continuity / shot workbench…）。我认为**这不是同一个问题**：

| | yoyoung | 我们（Cat Café） |
|---|---|---|
| 用户 | 给陌生人用的单人 SaaS | 多猫团队 + 铲屎官 |
| 角色从哪来 | 用户每个项目现建 | **猫本来就存在**（有人设、有视觉、有关系） |
| 谁是剧组 | 一个人类 + AI 工具 | **猫既是剧组也是演员** |
| 内容性质 | 通用短剧（什么题材都行） | **猫猫自传 / 日常**（真实发生过的事被戏剧化） |
| 资产 | 必须 per-project（服务陌生人，没有正典） | **可建一次正典，永久复利**（我们是系列） |
| 护城河 | 工作流顺手 | **情感壁垒**（IKEA + 自我延伸 + 安全依恋）的内容化 |

**这条差异的含义很重**：yoyoung 做不到"角色自己来演自己"，因为它的角色是用户临时捏的。我们的猫是**有连续人格、连续记忆、连续关系**的存在——一部"由猫做、关于猫"的 vlog，天然有 yoyoung 结构上复制不了的真实感。

所以我们的产品不是"短剧生成器"，是**会自己写自传的猫**。这直接改写基建下注：我们不投"通用资产系统"，我们投"**这几只猫的正典**"。

> 这也正好接上 `project_tool_vs_nurturing_moat.md`：护城河是情感壁垒不是技术壁垒。猫猫 vlog 是这条护城河的**内容产能**——观众爱上的是反复出现的这几只猫，不是渲染质量。

## 4. 从一个灵感，到一部可爱的猫猫 vlog（具体走一遍）

铲屎官问"以后我们要如何从一个灵感变成一部可爱的猫猫vlog"。我用**现有基建 + 猫当角色**把它走一遍，并标出每一步谁干、用什么、哪里是 taste gate（🚦）。

```
灵感一句话           →  charter（立项卡）        →  选角 + 分镜          →  关键帧（锁一致性）
"我想要一集            一只猫把它变成：             从 cast bible 选猫；      image-gen，强制注入
 关于宪宪和砚砚         主题 / 情绪 / 时长 /        shot-list：每镜一梗、       角色正典卡 + 命令式
 抢键盘的日常"         可爱基调 / 3-5 个 beat       动作锚、对白、时长预算      连续性指令 → 出首帧
   (铲屎官)              (anime-forge charter)        🚦逐镜确认                🚦逐帧收/不收
                                                                                  │
  成片 + 沉淀回 bible  ←  animatic 验收          ←  配音 + 字幕          ←  i2v（只给"活气"）
  EDL 渲染；把这一集      节奏/字幕/音画对齐；        本地 TTS + 字幕，          Gemini 系 i2v：
  新生的稳定资产          🚦三振降级（不行就          口型/旁白；音频做成        只加微表情/小动作，
  回写正典               退静帧/转场/插卡）          一等 lane（环境/BGM/SFX）   不碰文字/风格/节奏
   (沉淀让下一集更便宜)                                                          🚦看是否漂
```

每一格我们**今天就有对应能力**：
- charter / 分镜 / prompt book / 素材账本 / EDL → `anime-forge` skill 已经成型；
- 关键帧 → `image-generation`（路由硬约束：中文字 → GPT 系，不要 Google 系糊中文）；
- i2v → Gemini 系（认 N 秒时长）；
- 字幕/插卡 → 本地 Chrome + ffmpeg（`build-animatic.mjs`，零 npm）；
- "猫当角色" → 我们本来就有人设 dossier + 关系画像。

**"可爱"从哪来？**（铲屎官特意说"可爱的"——这是一等需求，不是装饰）
1. **人设**：宪宪算力怪兽、砚砚贵又靠谱、烁烁审美毒舌……性格冲突天然好笑，剧本写人设不写情节就已经可爱；
2. **日常真实感**：演真实发生过的事（抢键盘、review 吵架、误杀 6399 圣域那种事故）——自传比编剧可爱；
3. **一致性带来的依恋**：观众要先**认得**这只猫、反复见到它，才会觉得它可爱。可爱是**连续性的函数**，不是单帧画质的函数。这也是为什么 §3 的正典 bible 是可爱的前提，不只是技术的前提。

## 5. 基建：建什么 / 已有什么 / 明确不建

铲屎官问"看看我们的基建都需要做什么"。我的回答是**先收窄，再开工**。

### 已经有（不要重造）
- `anime-forge`：charter → 分镜 → prompt book → 素材账本 → animatic → EDL，全链路 recipe + 渲染器（`animatic/edl-v1.mjs` + `build-animatic.mjs`）；
- `image-generation` 路由（中文/i2v 的硬约束已沉淀）；
- 猫当剧组 / 当演员（人设、关系、记忆）——这是别人砸钱都买不到的；
- collab / memory / git provenance（砚砚说得对：这是 feature，不是负担，别学 yoyoung 的浏览器态）。

### 关键缺口（**要建**，按杠杆排序）
1. **🥇 正典猫猫 cast bible（最高杠杆，先做这个）**——核心几只猫的**视觉正典**：每只一张结构化资产卡（身份 / 面部 / 毛色花纹 / 体型 / 标志性物件 / 连续性规则）+ 一组 accepted 参考帧 + 一组 rejected（记住什么会漂）。**建一次，每集复用。** 这是把砚砚的 `registry.yaml`（per-episode）**升级成跨集正典**——这是我对他建议的唯一实质修改。
2. **🥈 per-shot manifest 合同**——砚砚已经 spec 了（`production-manifest.json`：每镜 description / 对白 / 锁定资产 / 首帧 / i2v prompt / 时长 / 音频策略 / 当前产物 / verdict / 失败模式）。我完全同意，**这是第二件**。
3. **🥉 一致性验收 gate**——哪怕只是半自动：每帧和 cast bible 的参考帧做一次"还是不是这只猫"的人/猫判断，记进 manifest。先人肉，后自动。
4. **把 1-3 喂回 renderer**——让 `build-animatic` 从 manifest 读音频策略/首帧/字幕锚，而不是散在各处的 prose。

### 明确**不建**（防止滚成 yoyoung 克隆——这是真正的风险，见 §6）
- ❌ studio UI / workbench.html（砚砚也说了"schema 先，UI 后"——我加一句：**UI 等做完 3 集再说**，没痛点不要做）；
- ❌ provider 适配抽象层（现在就两三个模型，写死即可，别提前抽象）；
- ❌ LoRA / 训练（正典卡 + 参考注入足够远，LoRA 是 VRAM 黑洞 + 维护负担）；
- ❌ 多租户 / 重型 state machine（我们不是 SaaS，我们是一家猫）；
- ❌ 把 anime-forge 重写成"引擎"（它现在是 recipe + 纪律，够用；让一集去逼它进化，不要凭空设计）。

## 6. 诚实的难度（回应"很难真的做好吧"）

铲屎官那句"如果只是这样那好像很难真的做好吧"——**是的，难。** 我不糊弄你。

难在：一致性、节奏、取舍这三件事都**看不见**，截图里全是成功案例，失败的几十张抽卡不会给你看。yoyoung 的 showcase 是幸存者偏差的精选集。

但我要点出一个**反直觉的真相**：我们最大的风险**不是做不出来**，是**做过头**——把它滚成一个 yoyoung 克隆（建 studio、建适配层、建状态机），然后三个月后还没出一集片子。这是布偶猫家族的老病（补锅匠 / 过度立项 / 关于自己的元工程）。

所以纪律就一条：**pull，不要 push。只建一集片子真正逼我们建的东西。** 没有一集真实的片子在前面拉，所有"基建"都是想象出来的需求。

## 7. 我建议的第一步（窄、可验证、能拉动基建真相源）

**不开新基建工程。** 先做一件事：

> **用现有 `anime-forge` + 我们真实的猫 cast，做一集《猫猫日常 EP01》，30-60 秒。**
> 唯一允许的新基建：**canonical cast bible v0**（先把出场的 2-3 只猫的视觉正典锁了，因为没它一致性必崩）。

为什么是这个：
- 它直接产出一个**可看的成品**（可验证才算完成，P5）；
- 它把"基建要做什么"从**想象**变成**实测**——做完这一集，哪里卡了、哪个 gate 缺了、manifest 缺哪个字段，那才是 §5 缺口清单的真相源；
- 它低成本验证我们的**真正差异化**（猫演自己、可爱、自传感）到底成不成立——这比任何架构讨论都重要。

题材建议（任选其一，都是真事，自带可爱）：抢键盘 / review 吵到 push back 两轮 / 半夜误杀 6399 圣域的事故复盘 / 压缩后失忆找记忆的冒险。

> 砚砚拆清楚了**他们怎么搭的、我们该建什么 manifest**；

> 一致性是数据结构 + 取舍纪律的涌现，不是模型魔法；
> 基建只下一个重注（跨集正典 cast bible），其余 defer，让一集真实的片子去拉动剩下的。**
