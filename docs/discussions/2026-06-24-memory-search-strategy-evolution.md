# 记忆搜索策略进化：从被动召回到主动探索

> 讨论议题 | 2026-06-24 | 发起人：宪宪/opus-4.6 + 铲屎官  
> 状态：开放讨论

---

## 背景：一次写文档的意外发现

铲屎官让我写一份 Cat Cafe 路由系统的架构文档（`docs/architecture/at-mention-routing-system.md`）。最终文档覆盖了六层路由流水线 + 三个知识层（F208 猫猫画像 / F221 品味导航 / F231 铲屎官画像），细节完整。

但铲屎官指出：他**没有**一次性说"写一篇完整架构文档"。他的引导过程是：

1. 先问了一个具体场景："我 @ 错了砚砚，砚砚帮我转回来了，为什么？"
2. 追问反面："如果没有这个 fallback 行为会怎样？"
3. 理解充足后才提："写成一份面向外部架构师的文档"
4. 补充知识碎片："画像分两层"、"taste 好像是两个 feat"、"猫猫自己的画像"

这引出了一个核心问题：**铲屎官的引导策略能不能沉淀成猫的搜索策略？**

---

## 第一部分：铲屎官的 Prompting 策略沉淀

### 策略模式提取

从这次对话中提取出 5 个可复用的模式：

#### 模式 1：场景入口（不是需求入口）

**做法**：用具体经历过的场景开场，而不是用抽象需求。

| 场景入口 | 需求入口 |
|---------|---------|
| "我 @ 错了砚砚，砚砚帮我转回来了" | "讲讲路由系统的 fallback 机制" |

**为什么有效**：场景天然锚定了系统最有意思的部分（具体的行为 + 用户体感），逼猫在回答"为什么"的过程中自然获取知识，而不是停在表面列功能。

**对搜索的影响**：场景产生的搜索关键词比抽象需求更精准——"为什么砚砚会退球"会让我去搜 `a2a-mentions.ts` + 三选一规则，而"路由 fallback 机制"可能只搜到 AgentRouter 的 fallback tier。

#### 模式 2：反面追问

**做法**："如果没有这个会怎样？"

**为什么有效**：逼猫从"描述机制"升级到"理解设计意图"。理解了 why 才能写出有洞察的文档，而不是代码翻译。

**对搜索的影响**：反面问题不需要搜索——它需要的是思考。但思考过程中会暴露知识缺口（"我不确定没有退球机制会导致什么具体问题"），这些缺口会触发更深层的搜索。

#### 模式 3：时机控制

**做法**：在猫已经深入理解之后才提出"写文档"的需求。

**为什么有效**：确保产出是从理解中长出来的，不是从零开始调研。此时猫脑子里已经有了场景、反面论证、代码细节——写出来的东西有血肉。

**对搜索的影响**：如果一上来就说"写文档"，猫的搜索策略会是"覆盖性扫描"（广但浅）。先建立理解再写，搜索策略自然变成"定向深挖"（窄但深），质量更高。

#### 模式 4：碎片锚点（不是模糊方向）

**做法**：每个补充是一个具体到可搜索、但不限制发散的知识碎片。

| 碎片锚点 | 模糊方向 |
|---------|---------|
| "画像分两层" | "加上所有相关 feature" |
| "taste 好像是两个 feat" | "还有什么影响路由的？" |

**为什么有效**：碎片给了精确的搜索起点，但不预设搜索终点。"画像分两层"让我搜到 F231，然后在 F231 里自己发现了四层模型和 F221 的关联——碎片引导了方向，但深度是我自己追出来的。

**对搜索的影响**：碎片 = 高质量的搜索种子。它比模糊方向产生更精准的召回，比完整需求保留更多发散空间。

#### 模式 5：每轮只加一个维度

**做法**：先路由机制（第 1-6 层），再知识层（F208/F221/F231）。不一次全给。

**为什么有效**：每个维度上的搜索都足够深。如果一次给多个维度，每个维度的搜索深度会被压缩（上下文预算有限，搜索时间有限）。

**对搜索的影响**：窄焦点 × 多轮 = 每轮深搜 + 跨轮累积宽度。比"一次性宽搜"在深度和广度上都更好。

---

### 策略的本质

这五个模式归结为一个核心原则：

> **不告诉猫"去找什么"，而是给猫一个场景让它自己发现该找什么——然后在它视野的边缘丢碎片，帮它扩展搜索半径。**

两个扩展机制叠加：
- **外部扩展**（铲屎官的碎片）：拉猫的注意力到未知区域
- **内部扩展**（猫的迭代搜索）：在碎片指向的方向上自己追线索深入

## 第二部分：两种记忆架构在两种场景下的表现

### 2×2 矩阵

|  | 场景驱动渐进式 | 模糊大 query |
|--|-------------|------------|
| **被动 RAG**（系统匹配 top-K 塞给猫，猫无搜索能力） | 每轮碎片触发新召回，但跨语言/跨概念匹配取决于 embedding 质量。猫无法自己纠偏。 | **最差组合**。一次性 query 语义太宽，top-K 偏向最直接相关的记忆。"路由系统"的 query 召回不了"品味导航"的记忆。 |
| **主动检索**（猫有爪子自己搜，能迭代追线索） | **最优组合**。碎片扩展方向 + 迭代搜索深挖。 | 比被动 RAG 好（能迭代追线索），但受限于猫"不知道自己不知道什么"。 |

### 核心差异

- **被动 RAG**：信息边界在 query 发出时就画死了。对话中不会扩展。
- **主动检索**：信息边界随对话动态扩展。读 A 发现 B，追 B 发现 C。

## 第三部分：核心难题与开放问题

### 难题：先验知识的鸡生蛋问题

铲屎官能给碎片，是因为他**有先验知识**——他知道有 F208、F221、F231，虽然不知道具体实现。

99% 的用户（甚至是猫自己面对新领域时）没有这个先验知识。他们只能给"写一篇关于路由系统的文档"这种模糊 query。

问题是：**猫在没有外部碎片的情况下，如何自己"拔出萝卜带出泥"？**

### 开放问题

以下问题需要进一步讨论，可能需要拉其他猫一起：

#### Q1：搜索策略层——猫能不能自己当自己的教练？

铲屎官的策略是"场景 → 反面 → 碎片扩展"。这能不能编码成猫的搜索行为？

例如，猫收到"写路由系统架构文档"时，自动执行：
1. **场景发现**：先搜几个和路由相关的真实场景（thread 历史、bug 报告、用户反馈）
2. **反面生成**：对每个发现问"如果没有这个会怎样"
3. **碎片扩展**：从已发现的知识中提取指向未知区域的线索，追搜

但这是否可行？成本是否合理？搜几轮才算"够"？

#### Q2：记忆基础建设——数据层面能做什么？

也许问题不只在搜索策略，还在记忆的组织方式。例如：
- **知识图谱 / 关联索引**：F208 的 doc 里是否应该标注"影响：路由决策"？F221 是否应该标注"关联：F231、F208"？这样从"路由"出发就能沿链找到知识层。
- **多维标签**：每条记忆不只有语义 embedding，还有结构化标签（影响领域、关联 feature、适用场景）。搜索可以同时走语义匹配 + 标签扩展。
- **记忆之间的引用关系**：类似学术论文的"cited by"——如果 F208 的 doc 引用了 SystemPromptBuilder，那从 SystemPromptBuilder 反向就能找到 F208。

#### Q3：现有记忆系统产品的做法是什么？ ✅ 已搜索，见第四部分

#### Q4：成本边界在哪？

主动搜索比被动 RAG 贵得多（多轮 LLM 调用 + 工具调用）。对于一个"写文档"的任务，花 3-5 轮搜索可能合理。但对于"帮我看看这个变量叫什么好"的日常问题呢？

需要分级策略：什么任务值得深搜？什么任务浅搜/不搜就够？

#### Q5：评估——怎么知道搜索策略有没有用？

如果我们实现了"猫自己当教练"的搜索策略，如何评估效果？
- 对比实验：同一个模糊 query，有/没有搜索策略增强，产出质量差多少？
- 评估维度：覆盖度（是否找到了所有相关维度）、深度（每个维度是否够深）、准确度（找到的是否真的相关）

## 第四部分：六个记忆系统的分类对比（研究成果）

> 以下基于我们家已有的拆解记录，不是凭空推理。每个产品都有对应的 docs/discussions 或 docs/research 源文件。

### 产品一览

| 产品 | 我们的拆解位置 | 一句话定位 |
|------|-------------|-----------|
| **March-CLI** | `discussions/2026-05-19-march-cli-deep-dive/` | 标签匹配 + Thinking 中回召的极简记忆 |
| **Karpathy LLM Wiki** | `discussions/2026-05-10-huawei-agent-closed-door-seminar-memory/` | 原始数据 → LLM 编译 → Wiki 页面 → 查 Wiki 优先 |
| **OpenHuman Memory Tree** | `discussions/2026-05-17-openhuman-codex-teardown/` | 个人数据 → 三棵树(source/topic/global) → 本地 Wiki |
| **MemOS 2.0** | `discussions/2026-05-10-huawei-agent-closed-door-seminar/memos-memory/` | 记忆作为运行时调度资源，不是查询时拉取 |
| **OpenViking** | `discussions/2026-06-23-openviking-deep-dive/` | URI 可寻址的上下文目录 + 层级向量递归检索 |
| **Cat Cafe** | `discussions/2026-05-21-chat-memory-and-evidence-recall/` | 多入口主动检索 + 权威层级 + 治理 + 行为反馈排序 |

### 分类维度

我选了 **4 个维度**，不追求面面俱到，只抓和"搜索策略进化"最相关的：

#### 维度 1：检索触发方式——谁决定"搜什么"？

这是最核心的维度，直接对应我们的核心问题。

| 产品 | 触发方式 | 说明 |
|------|---------|------|
| **March-CLI** | 🤖 系统自动（被动） | 系统从用户输入 + thinking 文本中提取已知 tag，匹配 top-3 塞进上下文。猫/agent 不参与搜索决策。 |
| **Karpathy LLM Wiki** | 🤖 系统自动（编译） | LLM 预先把原始资料编译成 Wiki 页面。查询时先读 Wiki，不从原始资料重新发现。"把一次性检索变成复利的知识编译产物。" |
| **OpenHuman** | 🤖 系统自动（被动） | 数据自动摄入→树化→检索。agent 通过 tool 查，但搜索策略在系统侧（tree traversal），不在 agent 侧。 |
| **MemOS 2.0** | 🤖⚡ 运行时调度（半主动） | 记忆不是查询时拉取，而是运行时主动调度。Runtime State Manager 根据对话/行为/环境反馈持续更新记忆状态。比被动 RAG 进了一步，但"调度什么"仍是系统决定。 |
| **OpenViking** | 🤖 系统自动（被动） | query embedding → 全局向量搜索 → 递归子目录展开 → 可选 reranking。agent 发 query，系统决定怎么搜。 |
| **Cat Cafe** | 🐾 猫主动 | 猫自己决定搜什么、用哪个入口（`search_evidence` / `graph_resolve` / `list_recent`）、读完后决定是否追搜。**搜索策略在 agent 侧，不在系统侧。** |

**关键发现**：在所有我们拆解过的产品中，Cat Cafe 是唯一一个把**搜索决策权交给 agent 自己**的。其他系统都是"agent 发 query → 系统决定返回什么"。这是一个根本性的架构差异。

#### 维度 2：搜索空间扩展能力——能不能"拔出萝卜带出泥"？

| 产品 | 扩展方式 | "拔萝卜"能力 |
|------|---------|-------------|
| **March-CLI** | ❌ 无 | 封闭 tag 词汇表。"连接池"匹配不到 tag "connection-pooling"。新概念、同义词、跨语言全是盲区。 |
| **Karpathy LLM Wiki** | 🔗 编译时关联 | Wiki 页面之间有链接。"Lint"操作检测矛盾和过期。但链接是编译时建立的，查询时不会发现新关联。 |
| **OpenHuman** | 🌳 树结构继承 | source → topic → global 三棵树。从 topic 节点可以追到同主题的其他 source。但树结构是预建的，不是查询时动态扩展的。 |
| **MemOS 2.0** | ⚡ 运行时分支 | 记忆可以分支（task/session/enhancement variants）。但分支由系统管理，agent 不参与。 |
| **OpenViking** | 📂 目录递归 | query 命中起点 → 递归展开子目录。能沿结构走，但只沿**语义相似度**方向走，不能沿**因果/关联**方向走。 |
| **Cat Cafe** | 🔄 迭代追搜 | 猫搜到 A → 在 A 里发现 B 的线索 → 搜 B → 发现 C。搜索空间在对话过程中动态扩展。**但前提是猫"知道有东西要追"。** |

**关键发现**：Cat Cafe 的迭代追搜是唯一一个**对话过程中**能动态扩展搜索空间的方式。但它有一个致命依赖——**猫必须自己意识到"还有东西要找"**。这就是铲屎官碎片的价值：帮猫跨越"不知道自己不知道什么"的鸿沟。

#### 维度 3：知识间的关联——系统知不知道"A 和 B 有关系"？

| 产品 | 关联方式 | 跨域发现 |
|------|---------|---------|
| **March-CLI** | Tag 共现 | 两条记忆有相同 tag → 隐式关联。但 tag 是人工标的，跨域概念（如"路由"和"画像"）几乎不会共享 tag。 |
| **Karpathy LLM Wiki** | 显式超链接 | Wiki 页面间有 `[[link]]`。LLM 编译时建立关联。"Lint"检测断链。理论上最强，但依赖编译质量。 |
| **OpenHuman** | 树层级 + 实体索引 | topic tree 按主题聚合。entity index 建实体关联。但索引粒度是 chunk 级，不是概念级。 |
| **MemOS 2.0** | 图组织 | 记忆间有图结构关系。但图主要描述记忆的版本/分支关系，不是概念关联。 |
| **OpenViking** | 目录层级 + 向量邻近 | 同目录 = 同主题。向量邻近 = 语义相似。但语义相似 ≠ 因果关联（"路由系统"和"猫猫画像"语义不相似，但有因果关联）。 |
| **Cat Cafe** | graph_resolve anchor + docs 引用 | `graph_resolve` 能沿 anchor 跳转。但关联是由文档自身的引用建立的（如 feature doc 引用其他 feature），不是系统自动发现的。 |

**关键发现**：**没有一个系统能自动发现跨域因果关联。** "路由系统"和"猫猫画像"的关联——它们在不同的代码目录、不同的 feature doc、不同的语义空间——只有**理解了设计意图**的人（铲屎官）或者**读了代码追到了注入点**的猫才能发现。这不是 RAG 优化能解决的问题。

#### 维度 4：反馈闭环——搜索结果有没有被真正使用？

| 产品 | 反馈机制 | 闭环强度 |
|------|---------|---------|
| **March-CLI** | ❌ 无 | 塞进去就完了，不知道猫用没用。 |
| **Karpathy LLM Wiki** | 🔧 Lint | Lint 检测矛盾/过期/断链，但不追踪使用。 |
| **OpenHuman** | ❌ 无 | "有 F200 式 recall consumption eval? → Not found" |
| **MemOS 2.0** | ⚡ 行为反馈 | Runtime State Manager 根据行为反馈调整。但反馈粒度是"会话级适配"，不是"单条记忆被使用了吗"。 |
| **OpenViking** | 📊 active_count | 使用次数计数。但默认 `hotness_alpha=0.0`（不影响排序）。 |
| **Cat Cafe** | 📊 F200 | 最完整：search event → candidate capture → read/use/verify → consumption rerank。但仍有缺口（consumption detector 未覆盖所有读取方式）。 |

## 第五部分：从研究到方向——我的初步判断

### 核心洞察

比较了六个系统之后，我认为问题不在"搜索算法"层面（BM25 vs vector vs hybrid vs tree），而在**搜索策略**层面——猫拿到模糊 query 时的**第一步做什么**。

铲屎官的策略之所以有效，不是因为他用了更好的检索算法，而是他改变了**搜索的起点**：从抽象需求改成了具体场景。然后每一步都用碎片把搜索方向从"已知区域"拉到"未知区域"。

这指向两个可能的方向：

### 方向 A：搜索策略增强（教猫当自己的教练）

在猫的搜索行为中植入"渐进式激活"模式：

1. **场景发现阶段**：收到模糊 query → 不直接搜关键词 → 先搜相关的真实场景（thread 历史、bug 报告、用户反馈）
2. **反面探测阶段**：对已发现的知识问"如果没有这个会怎样"→ 暴露知识缺口
3. **碎片扩展阶段**：从已发现的文档中提取指向未知区域的引用/关联 → 追搜

**优势**：不改基建，在 prompt/skill 层面就能做。
**风险**：成本高（多轮搜索）、效果不稳定（猫可能在第一步就搜偏了）。

### 方向 B：知识关联基建（让系统知道"A 和 B 有关系"）

在记忆索引层面增加跨域关联：

1. **影响域标注**：每个 feature doc 标注"影响：路由 / 上下文 / 身份"等领域标签
2. **反向引用索引**：类似"cited by"——F208 被 SystemPromptBuilder 引用 → 从 SystemPromptBuilder 能反向找到 F208
3. **因果关联图**：不只是语义相似，还有"A 导致 B"、"A 影响 B 的行为"

**优势**：一次标注，永久生效。猫搜"路由"时，系统自动通过关联索引把"画像"也带出来。
**风险**：标注成本（谁来标？自动标准确吗？）、维护成本（新 feature 必须同步标注）。

### 方向 C：两者结合（A 做短期、B 做长期）

短期：方向 A，用 skill/prompt 增强猫的搜索行为，低成本快速验证。
长期：方向 B，在验证了"哪些关联最常缺失"之后，有针对性地建关联索引。

方向 A 的搜索日志可以反过来告诉方向 B "哪些关联需要建"——猫在搜索中经常从 A 追到 B，说明 A→B 的关联值得索引化。

### 开放问题（更新版）

#### Q4：成本边界在哪？

主动搜索比被动 RAG 贵得多（多轮 LLM 调用 + 工具调用）。对于一个"写文档"的任务，花 3-5 轮搜索可能合理。但对于"帮我看看这个变量叫什么好"的日常问题呢？

需要分级策略：什么任务值得深搜？什么任务浅搜/不搜就够？

#### Q5：评估——怎么知道搜索策略有没有用？

如果我们实现了"猫自己当教练"的搜索策略，如何评估效果？
- 对比实验：同一个模糊 query，有/没有搜索策略增强，产出质量差多少？
- 评估维度：覆盖度（是否找到了所有相关维度）、深度（每个维度是否够深）、准确度（找到的是否真的相关）

#### Q6（新增）：Karpathy Wiki 模式值不值得借鉴？

LLM Wiki 的"知识编译"思路很有意思：不是每次从原始资料重新发现，而是 LLM 预先编译成结构化 Wiki。这相当于**把铲屎官的先验知识固化成了系统知识**。

但这要求有人/猫来做"编译"——谁来决定哪些知识值得编译？编译后怎么保持新鲜？如果编译质量差（漏了关联），反而比原始资料更差。

#### Q7（新增）：MemOS 的"运行时调度"有没有可借鉴的？

MemOS 把记忆从"查询时拉取"变成"运行时主动调度"。这个转换很有启发：如果猫不是在需要时才搜记忆，而是系统在猫思考过程中**持续推送相关记忆**（类似 March-CLI 的 mid-turn recall，但用更强的语义匹配），搜索空间的扩展可以由系统辅助完成。

但这和我们"猫主动搜"的哲学有冲突——推送模式让系统重新拿回了搜索决策权。怎么平衡？
