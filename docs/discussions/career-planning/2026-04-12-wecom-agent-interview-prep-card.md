# 2026-04-12 腾讯企微 AI Agent 开发工程师面试作战卡

> 适用场景：腾讯企业微信 `AI Agent 开发工程师-平台框架/应用（广州/成都）` 一面。  
> 目标：不把自己讲成“会调模型 API 的应用工程师”，而是讲成“真正做过多智能体框架、协议、上下文与可靠性治理的人”。

## 一句话定位

我不是从传统后端转来“蹭 AI”的人，而是同时做过：

- 云原生/平台底座与复杂系统治理
- 多智能体协作框架、MCP/A2A 接口、记忆与上下文工程

这场面试里，我们要把自己讲成：**做过 Agent 框架骨架、协议抽象、上下文/记忆、可靠性兜底的人。**

## 这场面试最该打的 3 个点

1. **我们真的做过 Multi-Agent 框架，不是套壳**
2. **我们真的做过 MCP/A2A/工具调用，不是“单模型 + 几个函数”**
3. **我们真的做过上下文管理、记忆、异步调度、失败兜底，不是 demo**

## JD ↔ 我们怎么讲

| 面试点 | 我们的对标能力 | 怎么说 |
|---|---|---|
| Multi-Agent 协作、决策、工具调用 | 多猫协作、multi_mention、MCP 工具体系、异步 A2A 触发 | 我们从零搭过多智能体协作系统，不同 Agent 通过标准接口协作、讨论、调用工具完成复杂任务 |
| 任务调度、通信协议、上下文管理 | 队列/调用链、会话链、Evidence 检索、上下文压缩 | 我们把任务调度、上下文持久化和检索解耦做成底座，不靠单次长 prompt 硬撑 |
| MCP / A2A / FunctionCall | MCP server surfaces、@mention 异步触发、回调鉴权 | 我们不是只会 function calling，而是把 Agent 与工具/系统交互标准化了 |
| ReAct / PlanAct / CodeAct 模式 | 不同 Agent 的不同推理与执行模式 + Skills 模块化 | 我们是可插拔框架，不同场景/Agent 可以挂不同策略，不是单一链路 |
| 性能、稳定性、并发 | 异步处理、重试/降级、上下文压缩、环境隔离 | 我们遇到的不是“模型好不好”，而是系统能不能稳定跑、能不能审计和恢复 |
| 与算法团队协作工程落地 | 多 provider 适配、模型差异抽象、效果验证 | 我们做过把不同模型能力抽象成统一调用层，再往业务场景落地 |

## 三段核心故事

### 1. A2A / MCP 骨架故事

**问题**：多个 Agent 异步协作时，最容易出问题的是消息丢失、状态不一致、递归失控。  
**做法**：把 @mention、异步回调、工具调用收敛到统一调度路径，用标准接口承接 Agent 与外部系统交互，并加深度限制和鉴权。  
**结果**：多 Agent 协作不再是“几个 prompt 接龙”，而是有边界、有审计、有回调链路的系统。

### 2. 记忆 / 上下文工程故事

**问题**：复杂任务不能只靠单轮 prompt，必须解决会话记忆、证据检索、上下文压缩。  
**做法**：做会话链 + 检索层，把文档、历史讨论、 durable knowledge 都变成可检索上下文；上下文超限时做压缩保留关键信息。  
**结果**：Agent 能跨 session 延续工作，不会每次都从零开始。

### 3. 可靠性 / 工程兜底故事

**问题**：Agent 任务链比普通 CRUD 更容易在长链路、工具调用、中间状态恢复上出问题。  
**做法**：把 cheap checks 前置、异步重试、失败降级、中间状态存储恢复做成工程底座。  
**结果**：我们处理的不是“模型会不会说话”，而是“系统能不能稳定完成任务并可恢复”。

我过去一段时间主要在做企业级多智能体协作系统，从 0 到 1 搭过 Agent 框架骨架、MCP/A2A 标准接口、工具调用、记忆与上下文工程，以及整套可靠性兜底机制。更早之前我在云原生/平台底座和复杂系统治理上也有长期经验，所以这类既要 Agent 框架能力、又要工程落地和稳定性能力的岗位，我的匹配度会比较高。

## 如果面试官问“你们到底怎么 show”

默认不要一上来全开大。按三档来：

### 第一档：只讲架构

适用：面试官先听你讲，没明确要 demo。  
做法：白板式讲一条链路：

`任务输入 → Agent 路由/协作 → MCP/A2A 接口 → 工具调用/检索 → 结果回传 → 失败兜底`

### 第二档：讲一个具体链路

适用：面试官对“你们真做过吗”有怀疑。  
建议只讲一个最贴 JD 的链路：

`@mention 触发异步 A2A → 调 MCP 工具 → search_evidence 注入上下文 → 输出结果`

重点讲：

- 为什么要标准化协议
- 为什么需要上下文管理
- 为什么需要失败恢复

### 第三档：真 live demo

适用：面试官明显感兴趣，且时间还够。  
原则：

- **只 show 一个核心任务**
- **不要 show 花活**
- **不要把注意力带到 PPT/视觉玩票功能上**

最优 demo 路径：

1. 给一个真实复杂任务
2. 触发多 Agent 协作
3. 展示工具调用或检索注入
4. 展示结果与可追溯链路

一句话：**show 框架，不 show 杂技。**

## 弱点怎么化解

| 面试官可能卡你 | 回法 |
|---|---|
| 你没用过他们列的每个框架 | 我们从零设计过自己的框架，所以我更关注框架 tradeoff 和骨架抽象，不是只会用某个名字 |
| 你不是纯算法训练背景 | 这个岗位里我最强的是 Agent 框架、协议、上下文与工程底座；训练侧我能和算法团队高效协作落地 |
| 你们系统不是亿级用户 | 我们的挑战不是 DAU，而是多 Agent、多工具、多上下文源下的系统复杂度和治理难度 |
| 你是不是只是 prompt engineering | 不是，我们真正做的是协议、框架、记忆、异步调度、可靠性兜底和工具生态 |

## 面试反问

1. 这个岗位当前更偏 **平台框架核心研发**，还是偏 **业务场景 Agent 落地**？
2. MCP / A2A / FunctionCall 这些标准接口，在你们体系里已经是既定方向，还是希望这个岗位来主导抽象？
3. 团队当前最大的瓶颈更偏 **效果**、**框架能力**，还是 **稳定性与工程化**？
4. 广州和成都是同一个团队两地协作，还是不同团队分别招？

## 最后提醒

- 这场面试不要把自己讲成“AI 应用工程师”
- 要讲成“**做过 Agent 框架骨架的人**”
- 要把 `MCP / A2A / 上下文管理 / 可靠性` 这些词讲成**我们亲手做过的系统设计**，不是概念背诵
