# 2026-04-13 Agent 面试题库整理（截图转写 + 我们家的答法）

> 来源：铲屎官提供的 3 张截图，账号名显示为“坂华 offer 助手”。
> 用途：把题目沉淀成可搜索的文字版，并补一份“如果换成我们家，怎么答更稳”的口径。
> 说明：
> 1. 以下题目由截图人工转写，个别字词可能有轻微误差，但不影响题意。
> 2. 第二部分分两类：`强匹配` 表示我们真的做过或非常贴近；`迁移答法` 表示我们没做过金融 PDF/RAG 生产链路，但如果面试官这样问，可以如何诚实作答。

## 一页判断

- 这套题比前面那种“A2A 黑话背诵题”更像真的平台/基础设施面。
- 它混了 4 类能力：`Multi-Agent 架构`、`工作流/测评/进化`、`文档解析/RAG`、`基础 CS`。
- 如果面的是企微这类平台岗，这套题里真正有价值的是：`1 2 5 6 7 8 9 10 21 22`。
- `11-20` 更像“金融文档智能 / PDF-RAG 平台”题，不是我们当前主战场；回答时要诚实区分“做过”和“会怎么设计”。

## 第一部分：截图原题转写

1. 既然你负责了企业 xxAgent 项目，针对授信和风险评估这种严谨场景，单 Agent 推理容易失控且不可靠，你是如何通过 Planner 驱动的多智能体协作架构来解决这个问题的？
2. 讲一下你们这个工作流画布平台后端是怎么设计的？
3. 假如现在有 100 篇英文文章，想统计单词出现的次数，把频率最高的 Top 100 单词排在前面，如果用 MapReduce 来实现，你整个流程是怎么走的？
4. 快速排序的时间复杂度是多少？在什么情况下会达到最坏情况？
5. 除了 Plan-and-Execute 这种方式，你还用过或者了解过哪些 Agent 的推理模式？
6. 你们这套 Multi-Agent 架构，跟现在比较火的编程工具，比如 OpenClaw 或者 Cloud Code 这种架构相比，你觉得优缺点分别在哪里？
7. 这种比较通用的 Agent 加上 Skills 插件的模式，能不能实现像你刚才说的那种比较固定的、严谨的工作流架构？
8. 你们这个多智能体架构具体是怎么进行测评的？有没有端到端的这种评测方案？
9. 关于 Agent 能力的提升，或者对那些 Badcase 的处理，你们具体是怎么做的？
10. 这个 Agent 的能力，是从设计完上线之后就固定了吗？它有没有那种持续进化的能力？
11. 在文档预处理这块，针对开源项目解析复杂的金融 PDF 和表格效果不好的问题，你们做了什么样的优化？
12. 你刚才提到阅读顺序重建，针对多栏布局你们自定义了逻辑块排序算法，那具体是什么样的自定义算法？
13. 对于金融文档里的那种复杂表格、多级表头的表格，你们是怎么处理的？
14. 那种业绩单形式的表格或者跨页的长表格，你们又是怎么处理的？跨页表格怎么分 Chunk？
15. 表格里面如果又有 PDF 里的图表（比如折线图、柱状图、走势图），你们又是如何处理的？
16. 你们系统是只做了 PDF 格式吗？像 Word、Excel 这种文档是怎么处理的？
17. 在 RAG 阶段，针对金融专业术语，你们是怎么保证检索召回率的？
18. 你提到的术语表或者术语知识图谱，在冷启动的情况下是怎么建立起来的？
19. 除了 RAG，你们有没有考虑过 Graph RAG？为什么？
20. 金融文档的更新频率非常高，如果不是像 Git 那样覆盖更新，而是不断有新文档进来，你怎么解决新旧文档夹杂、召回出旧信息的问题？怎么保证最新的文档能返回回来？
21. 谈谈你对 Agent Search 的理解。这种基于本地指令的搜索方式，跟 RAG 那种 Embedding 加上 BM25 的相似搜索方式，你认为两者之间的核心差异和优劣在哪里？
22. 你们项目里面有做这种多模态的搜索吗？

## 第二部分：如果换成我们家，怎么答

### 1. 严谨场景下，为什么要 Planner + 多智能体

**适配度**：强匹配  
**短答**：我们不会把高风险任务交给“自由发挥的单 Agent”。更稳的做法是把系统拆成 `规划`、`执行`、`审查`、`人类审批` 四层，每层只承担有限职责。Planner 负责拆解，不直接拍板；执行 Agent 只在显式 schema 和工具权限内做事；Review Agent 独立复核；高风险分支必须人类确认。核心不是“多 Agent 更聪明”，而是“把失控空间拆小，把责任边界画清楚”。

**展开点**：
- 规划产物要结构化：步骤、输入、输出、证据要求、超时和回退条件。
- 执行阶段只允许调用白名单工具，不能自由扩权。
- 对关键结论要求双重来源或 reviewer 复核，而不是相信单次推理。
- 所有中间状态要可追踪，可回放，可中断恢复。

### 2. 工作流画布平台后端怎么设计

**适配度**：中等，属于迁移答法  
**短答**：如果把我们家的 Hub/Skill/Dispatch 抽象成“工作流画布”，我会把后端拆成两层：`编排面` 和 `执行面`。编排面负责存图结构、节点配置、版本；执行面把图编译成可运行的状态机或 DAG。节点必须有输入/输出 schema、重试策略、超时、权限边界；运行时通过事件日志推进状态，不靠前端状态当真相源。

**展开点**：
- 数据模型：`workflow / version / node / edge / run / run_step / event_log`。
- 运行引擎：状态机优先于“边点一下就执行”的隐式逻辑。
- 节点类型要分清：Agent 节点、工具节点、人工审批节点、条件分支节点。
- 前后端分离：前端是可视化编辑器，后端是真正的执行与审计系统。

### 3. MapReduce 统计 Top 100 单词

**适配度**：基础题  
**短答**：Map 阶段先把文章分片，做分词、归一化和停用词处理，输出 `(word, 1)`；可先在 Mapper 端本地聚合减少网络传输；Shuffle 把相同 word 发到同一 Reducer；Reduce 阶段求和得到 `(word, count)`。如果要 Top 100，可以再跑一轮 job，或者每个 Reducer 先维护本地 Top K 小顶堆，最后全局合并。

### 4. 快速排序复杂度

**适配度**：基础题  
**短答**：平均时间复杂度是 `O(n log n)`，最坏是 `O(n^2)`。最坏情况通常出现在每次 pivot 都极端不平衡，比如已经有序数组配合“永远选第一个元素当 pivot”，递归深度会退化到 `n`。

### 5. 除了 Plan-and-Execute，还有哪些 Agent 推理模式

**适配度**：强匹配  
**短答**：我会把它们分成几类看，而不是背名词。常见的有：

- `ReAct`：边想边调工具。
- `Plan-and-Execute`：先出计划，再逐步执行。
- `Router + Specialist`：先路由，再交给专长 Agent。
- `Reviewer / Critic Loop`：执行后再审查、自我反思或交叉复核。
- `Deterministic Workflow + Agent Slots`：骨架是确定的，Agent 只在指定节点发挥。
- `Search / Browse Agent`：通过多轮搜索和证据比较完成开放式检索。

**我们家的偏好**：高风险任务更偏 `确定性骨架 + 局部 Agent`，而不是纯开放式 agent loop。

### 6. 我们家的 Multi-Agent 和 OpenClaw / Cloud Code 这类工具相比

**适配度**：强匹配  
**短答**：如果把 OpenClaw/Cloud Code 视作“编码型 Agent runtime”，它们的强项是单用户、单任务、短反馈环里的人机协作；我们家的强项是多角色、多模型、多线程、多入口的协作治理。它们更像“一个很强的开发者助手”，我们更像“一个可持续运行的协作系统”。

**可以这样对比**：
- 它们强在代码编辑闭环、repo 内反馈、低交互摩擦。
- 我们强在跨模型分工、异步协作、记忆沉淀、审计链路、跨平台入口。
- 它们的短板通常是多主体治理和长期状态；我们的短板是相对更重，系统复杂度更高。

### 7. 通用 Agent + Skills，能不能做严谨固定流程

**适配度**：强匹配  
**短答**：能，但前提是 Skill 不能只是 prompt 模板，而要被当成 `行为协议`。如果 Skill 只是“教模型怎么说”，那流程很容易漂；如果 Skill 明确规定触发条件、输入输出、校验点、失败处理和下一棒路由，它就可以成为严谨流程的一部分。

**我们家的答案**：
- Skill 定义的是“什么场景做什么步骤”，不是“能力包”。
- 严谨流程必须再叠加状态机、权限边界和 quality gate。
- 真正稳定的是 `Skill + Workflow State + Eval`，不是单靠 prompt。

### 8. 多智能体架构怎么测评，有没有端到端方案

**适配度**：强匹配  
**短答**：要分层做，不然 e2e 一炸根本不知道是模型、工具还是路由的问题。我的习惯是四层：

- `单元层`：工具、adapter、parser、router 的确定性测试。
- `场景层`：给固定输入，看某个 workflow 是否走对。
- `回放层`：把真实 badcase 录成 fixture，回放验证不回归。
- `端到端层`：从用户输入到最终产物，测成功率、耗时、人工接管率。

**生产指标**：
- 任务成功率
- 平均/尾延迟
- 工具失败率
- 人工接管率
- 回归 badcase 复现率

### 9. Agent 能力提升和 badcase 处理

**适配度**：强匹配  
**短答**：badcase 不该停留在“调一版 prompt 看看”。应该先归因，再决定修在哪一层。我通常分成：

- 需求没说清：修 spec / input contract。
- 路由错了：修 router / policy。
- 工具不稳：修 adapter / retry / timeout。
- 模型理解偏：修 prompt / examples / reviewer 机制。
- 同类问题反复出现：升级成 Skill / Eval / SOP。

**我们家的做法**：`Episode -> Method -> Skill -> Eval -> SOP`。也就是先记录事件，再提炼方法，最后把方法系统化。

### 10. Agent 能力是固定的还是持续进化的

**适配度**：强匹配  
**短答**：线上版本不应该“自由进化”，那会把系统变成不可审计的黑箱；但系统能力必须持续演进。正确做法是：`线上行为稳定`，`离线通过 badcase、lesson、eval 持续迭代`，通过版本化发布把新能力带回线上。

**一句话**：不是在线自我变异，而是有门禁的持续进化。

### 11. 复杂金融 PDF / 表格预处理怎么优化

**适配度**：迁移答法  
**短答**：如果我们来做，不会一开始就把“Agent 理解 PDF”当主解。先做一个可验证的解析管线：原生文本提取优先，OCR 兜底，layout 分析、表格检测、阅读顺序重建分开处理；同时建立坏样本集，按页类型和错误类型逐步优化。

**展开点**：
- 文本层、布局层、表格层不要混成一步。
- 对低置信页面允许走高质量 OCR / 第三方引擎兜底。
- 所有优化都要建立在坏样本 benchmark 上，不靠肉眼感觉。

### 12. 多栏布局的阅读顺序重建怎么做

**适配度**：迁移答法  
**短答**：我会先把页面切成文本块，保留每个块的 bbox、字体、行高、页内关系，再做“先分栏、再栏内排序、最后做特殊对象绑定”。简单说就是：

- 先根据 `x` 位置聚类，识别一栏、两栏、三栏。
- 每栏内部按 `y` 从上到下。
- 标题、脚注、图注、表注按规则重新绑定。
- 对跨栏对象加额外优先级，避免正文和图表说明串行错位。

如果面试官继续追问，可以说这是一个“带版面约束的拓扑排序问题”。

### 13. 多级表头复杂表格怎么处理

**适配度**：迁移答法  
**短答**：核心是别把它只当二维网格。复杂表格需要同时保留：

- 几何结构：cell span、行列位置。
- 语义结构：表头树、多级路径。
- 原始表示：必要时保留页面截图或原坐标，方便回溯。

最终给检索/抽取层的不是“第 3 列”，而是 `一级表头 / 二级表头 / 单元格值` 这种展开后的语义路径。

### 14. 跨页长表格怎么处理，怎么分 chunk

**适配度**：迁移答法  
**短答**：跨页表最怕的是页切开后上下文丢失。做法通常是：

- 识别“续表”、重复表头和列对齐关系。
- 把多页先合并成一个逻辑表，再做 chunk。
- chunk 不按页切，而按 `表头 + 若干行记录` 切。
- 每个 chunk 都要携带表头上下文，必要时再带上一段“前文表头路径”。

### 15. 表格里还有图表怎么办

**适配度**：迁移答法  
**短答**：不要强行把图表塞回表格文本。图表应该被当成独立对象处理：

- 提取图表区域、标题、图例、轴标签。
- 绑定附近正文、图注和页码。
- 如需更深理解，再走 VLM/Chart parser 做结构化摘要。

这样后续检索既能命中文字，也能命中“这页有某类趋势图”的语义对象。

### 16. 只做 PDF 吗，Word/Excel 怎么处理

**适配度**：迁移答法  
**短答**：我会把所有文档统一转成 `canonical intermediate representation`，然后再往下游走。PDF、Word、Excel 的解析方式不同，但下游检索、chunk、索引、权限、版本控制最好收敛到一套统一 schema。

**示例**：
- Word：标题层级、段落、评论、表格、图片。
- Excel：sheet、表区域、公式、表头、隐藏列。
- PDF：页面、bbox、文本块、图表、表格、OCR 结果。

### 17. 金融专业术语怎么保证召回率

**适配度**：迁移答法  
**短答**：只靠 embedding 不够，金融术语检索通常要做 `hybrid retrieval + 术语扩展`。常见手段有：

- BM25 + dense retrieval 融合。
- 缩写、别名、英文简称、同义词扩展。
- query rewrite，把用户问法改写成专业术语和常用简称。
- reranker 结合 metadata，比如时间、机构、文档类型。

如果面试官继续追问，我会补一句：这个问题最后一定要回到 `Recall@K` 和坏样本评测，不然都是感觉。

### 18. 术语表 / 知识图谱冷启动怎么建

**适配度**：迁移答法  
**短答**：冷启动不可能一步到位。通常是：

- 先让领域专家给一小批种子词。
- 从历史语料里做词频、共现、缩写展开、别名聚类。
- 建最小可用术语库，不先追求“完整图谱”。
- 用检索 badcase 反向补词，不断扩展。

知识图谱如果要做，也建议从 `entity-alias-relation` 的轻量图开始，不要一上来做大而全本体。

### 19. 为什么不用 Graph RAG

**适配度**：迁移答法  
**短答**：Graph RAG 有价值，但只有在“跨文档实体关系、层级关系、时间关系”是核心问题时才值得。否则先把普通 hybrid RAG 做扎实，收益通常更高，成本更低。

**回答模板**：
- 如果核心问题是开放问答、定位片段、总结文档：先做 hybrid RAG。
- 如果核心问题是关系推理、穿透股权/机构/事件链：再考虑 Graph RAG。

### 20. 新文档不断进来，怎么避免召回旧信息

**适配度**：迁移答法  
**短答**：这个本质是 `版本与新鲜度治理`，不是简单重建索引。需要在索引层明确区分：

- 文档创建时间
- 生效时间
- 版本号 / superseded 关系
- 当前是否仍有效

检索时再加 freshness-aware ranking 和 metadata filter。对于“问当前政策/最新版本”的问题，系统应该默认偏向最新有效文档，而不是只看语义相似度。

### 21. Agent Search 和 RAG 检索的差异

**适配度**：强匹配  
**短答**：我会把它们看成两个层次：

- `RAG retrieval`：先召回一批候选上下文，再交给模型回答。它强调低延迟、稳定和可控。
- `Agent Search`：让 Agent 把“搜索”本身当成一个多步任务，能够改写 query、比较结果、继续追问、停在“信息已经足够”的时刻。

**核心差异**：
- RAG 更像一次召回。
- Agent Search 更像一个带策略的探索过程。

**优劣**：
- RAG 成本低、速度快、适合固定知识库。
- Agent Search 更适合开放问题、动态信息源、需要证据比较的任务，但成本更高，也更难控。

### 22. 有没有做多模态搜索

**适配度**：中等  
**短答**：如果严格说“多模态搜索引擎”，我们现在不是以这个为主产品；但如果要往这个方向扩，我们会把文本、截图、OCR、图像描述、布局 metadata 都挂到同一个文档对象下面，再做统一召回和 rerank。

**可答得更稳一点**：
- 我们已经有富消息、图片、音频、文档这些多模态对象的产物形态。
- 真正要做搜索时，关键不是“能不能看图”，而是有没有统一索引和跨模态对齐 schema。

## 第三部分：面试时怎么用这份题库

- `1 2 5 6 7 8 9 10 21 22`：可以直接拿我们家真实系统来讲。
- `3 4`：按基础题稳答，不要过度发挥。
- `11-20`：先诚实说“这块不是我当前主战场”，再给设计思路。这样比硬装做过更可信。
- 如果面试官问的是“你们线上就这么做的吗”，一定要把 `真实已做` 和 `如果我来设计` 分开。

## 第四部分：一句总策略

面对这类题，最稳的姿势不是“全部答成我都做过”，而是：

1. 把真正做过的部分答深。
2. 把没做过但能设计的部分答清楚约束和 tradeoff。
3. 主动把话题拉回我们真的做过的系统骨架、可靠性、评测和演进机制。

这样既不虚，也不弱。
