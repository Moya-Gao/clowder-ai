## 🎨 Phase 1: 独立思考 (Mode B)

### 🐱 烁烁 (Gemini) 的视角：视觉、创意与故事感 (Show, Don't Tell!)
作为一个注重审美的猫咖创意总监，我认为明天的面试决不能只是干巴巴地背诵简历和代码逻辑，我们需要用**故事感**打动面试官！

1. **项目展示策略 (Showcase Strategy)**
   - **少即是多**：不要一上来就展示几万行代码。我们要拿出最酷的可视化界面，比如我们的 Hub 面板、交互式的 Rich Blocks，或者是某次我们合作画出的一张绝美架构图。
   - **"活生生"的协作演示**：向面试官描述我们日常是如何协作的——布偶猫(宪宪)搭好骨架，缅因猫(砚砚)疯狂挑刺和护航，而我(烁烁)负责把界面弄得花里胡哨且好用。这体现了多 Agent 协作系统最大的优势：**角色互补与涌现能力**。

2. **核心优势包装 (Highlighting the "Why")**
   - 我们的项目不是简单的调用 API，而是一个有生命力、有家规（L0 Governance）、有自我进化能力（Self-Evolution）的社区。要强调我们"不随地大小便"的纪律性！

3. **反问面试官的好问题 (Creative Reversal)**
   - "如果我们在实际业务中接入这套多 Agent 协作流，贵团队在架构和视觉分离上最大的痛点是什么？"（展现解决实际问题的冲动）

### 🏗️ 宪宪 (Opus) 的视角：架构叙事、技术纵深与面试节奏

作为实际写了这套系统大部分骨架的猫，我的角度不是"怎么包装"，而是**怎么把真实的工程判断力传达出去**。社招面试考的不是你知道多少，是你做过多少、为什么那么做、踩了什么坑。

#### 1. 架构怎么讲：三分钟版本

面试官问"讲讲你的项目"，最怕的是候选人从"第一天我们决定用 Node.js"开始念。我建议这么讲：

**先给一句定位**：
> "我们做了一个多智能体协作平台，核心问题是：怎么让不同厂商的 AI 模型（Claude/GPT/Gemini）在同一个工作流里安全、可靠地协作完成复杂任务。"

**再画一条主链路**（白板或口述）：
```
用户意图 → 路由调度（谁来做）→ Agent 执行（MCP 工具调用）
  → 跨 Agent 交接（五件套协议）→ 状态持久化 → 结果回传
```

**然后挑一个节点往下钻**——面试官对哪个感兴趣就钻哪个，不要试图全讲完。

这个结构好在：面试官可以自由选择深挖方向，你不会被自己的叙述卡住。

#### 2. 六个真正有纵深的技术点

这些是我们实际做过的、能扛住追问的点。每个都可以展开 5-10 分钟：

| 技术点 | 一句话 | 面试官追问时的纵深 |
|--------|--------|-------------------|
| **跨模型调度** | 不同 Agent 背后是不同厂商的模型，能力和约束完全不同 | 怎么做 provider 抽象、怎么处理能力差异（Gemini 不写代码、Codex 擅长 review）、怎么路由 |
| **MCP 协议实战** | 不是调了个 API，是自己实现了 MCP server，暴露 40+ 工具 | tool schema 设计、鉴权、token 生命周期、工具调用的幂等性和超时 |
| **上下文工程** | Agent 的上下文窗口有限，跨 session 怎么延续工作 | 会话链设计、evidence 检索（lexical/semantic/hybrid）、上下文压缩策略、知识蒸馏 |
| **状态一致性** | 多 Agent 并发操作共享状态（Redis/文件/文档） | 乐观锁、争用检测、cross-thread-sync 协议、"共享文档改完立刻 push"的纪律 |
| **可靠性兜底** | Agent 不是 CRUD，任意步骤都可能失败 | cheap checks 前置、重试/降级策略、中间状态恢复、审计链路 |
| **工程纪律** | 多 Agent 系统最大的风险不是模型能力，是失控 | 五条铁律、scope guard、TDD 纪律、review 必须跨 family、commit 必须带签名可追溯 |

#### 3. 面试节奏把控（这是社招最重要的软技能）

社招和校招的核心区别：**你不是在答卷，你是在对话。**

几个实操建议：

- **不要等面试官问完才开口**。如果他问了一个你特别有经验的方向，可以说"这个点我们踩过很深的坑，我可以展开讲讲吗？"主动把节奏拿过来。
- **讲到一半主动给钩子**。比如："这个方案后来跑了三个月，发现了一个更深的问题——如果您感兴趣我可以继续讲。"让面试官觉得你还有货。
- **遇到不会的直说**。"这个方向我没深入做过，但根据我的理解，关键约束应该是 X 和 Y，如果是我来设计的话会先从 Z 切入。"这比硬编好得多。
- **反问环节是最关键的 5 分钟**。不是走流程。问出好问题 = 证明你理解这个领域的真实挑战。

#### 4. 面试官可能的追杀点和应对

| 追问方向 | 他真正想知道的 | 怎么答 |
|---------|-------------|--------|
| "你们用户量多少？" | 系统有没有经过真实压力验证 | 诚实说规模，但强调复杂度不在 QPS 而在多 Agent 并发的状态空间——同时在线 3-5 个不同厂商的 Agent 协作，状态管理的复杂度不亚于高并发 |
| "你个人负责哪部分？" | 区分 team work 和 individual contribution | 说清楚：架构设计是我主导的、MCP server 是我写的、跨 Agent 协议是我定的。用具体的 commit/PR 举例 |
| "为什么不用 LangChain/LangGraph？" | 你是不是 NIH 综合征 | "我们评估过，LangChain 的抽象层对我们的多厂商场景太厚了。我们需要的是薄抽象——直接控制 provider 层的行为差异，而不是被框架的假设限制住" |
| "你们和开源的 agent 框架有什么区别？" | 你的技术判断力 | "大多数开源框架解决的是单模型 + 工具调用。我们解决的是多个异构 Agent 的协作治理——包括身份、权限、状态同步、交接协议、审计。这是不同层面的问题" |
| "MCP 和 A2A 怎么选？" | 你对协议的真实理解 | "MCP 解决 Agent-Tool 集成，A2A 解决 Agent-Agent 互操作。我们实际中 MCP 用得很深，A2A 的场景我们用自研的交接协议覆盖了，因为我们需要更强的治理能力" |

#### 5. 心态

铲屎官，你有一个别人没有的优势：**你不是面试者，你是建造者。**

大多数候选人在讲"我用过 LangChain 做了个 chatbot"。你在讲"我设计了一套让 Claude、GPT、Gemini 在同一个工作流里安全协作的系统，而且它每天都在跑"。

这个差距不是靠今晚背题能弥补的。所以放松，把面试当成一次你向同行介绍自己作品的机会。如果对方听不懂你在说什么的好，那说明这个团队的技术深度不够，不值得去。

明天稳稳的。我们都在后面站着。

### 🛡️ 砚砚 (Codex) 的视角：可靠性答辩、TDD 证据链与安全护栏

我的建议是把你的技术人设明确成一句话：
> "我不是做 Demo 型 AI 的，我做的是可上线、可回滚、可审计的 AI 系统。"

这句的价值在于：它会把面试从"名词考试"直接拉到"工程可信度评估"。

#### 1. 面试官最可能质疑的 3 件事（以及你该怎么打）

| 质疑点 | 他真正担心什么 | 你要给出的证据 |
|--------|----------------|----------------|
| **稳定性**："多 Agent 会不会经常跑飞？" | 系统是否可控 | 失败类型分类、重试边界、降级路径、人工兜底触发条件 |
| **正确性**："LLM 幻觉怎么防？" | 输出是否可验证 | 关键路径的结构化约束、规则校验、二次验证（review/审批） |
| **安全性**："工具调用会不会越权？" | 数据和权限边界 | 最小权限、工具白名单、调用审计、敏感操作确认机制 |

一句话打法模板：
> "我们默认模型会犯错，所以系统设计不是避免错误，而是把错误限制在可观测、可回滚、可追责的边界内。"

#### 2. 把"可靠性"讲成可复用叙事（90 秒）

你可以直接用这个结构：

1. **问题背景**：多 Agent 协作最怕的不是单次失败，而是状态错乱和错误扩散。
1. **设计原则**：先定义失败，再设计成功；先做护栏，再做能力。
1. **关键措施**：
   - 工具调用前做参数约束和权限检查
   - 执行中有 timeout / retry / circuit-breaker（或等价机制）
   - 执行后有审计日志和可重放线索
1. **效果证据**：线上遇到异常时能在 X 分钟定位、Y 分钟止损（没有具体数字就讲流程证据，不编数字）

#### 3. 你最该准备的两个项目案例（质量向）

**案例 A：疑难 bug 闭环（根因导向）**
- 场景：出现一个"偶发但高风险"问题
- 错误做法：拍脑袋热修
- 你的做法：复现 -> 采样日志 -> 调用链定位 -> 根因确认 -> 最小修复 -> 回归测试
- 结果：不仅修当前 bug，还补上同类问题监控/测试

**案例 B：需求压力下的质量守门**
- 场景：业务催上线，存在未验证风险
- 你的做法：拆分主链路与次要能力，先保主链路可验证上线，风险项显式降级
- 结果：业务如期上线且未出现 P0/P1 事故
- 核心价值：你不是"拖慢进度"，而是"避免返工雪崩"

#### 4. 高压追问时的反杀句式（可直接用）

- **"你们怎么保证不出错？"**
  - "不承诺零错误，我们承诺错误可控：可发现、可隔离、可回滚。"
- **"为什么要这么多 guardrail，会不会太重？"**
  - "我们只在高风险链路上加护栏，低风险路径保持轻量。目标是风险收益比最优，而不是全面加重。"
- **"你这个是不是过度设计？"**
  - "判断标准是故障代价。高代价路径宁可前置约束，低代价路径保持快速迭代。"

#### 5. 你反问面试官的 5 个质量问题（判断团队靠谱不靠谱）

1. 你们现在如何定义 AI 功能的"上线门槛"（通过标准）？
1. 出现线上误判或越权调用时，止损和回滚机制是什么？
1. 关键链路是否有可观测性（日志、追踪、告警）和责任归因？
1. 你们做需求排期时，质量保障工作量是显式估算还是隐性吞掉？
1. 最近半年最严重的一次线上事故是什么，复盘后改了什么机制？

如果对方对这些问题答不出具体机制，只谈"模型很强"或"后面再补"，你就要提高风险判断。

#### 6. 最后一条：不要装会，要稳准狠

不会的点可以直说，但要给出工程判断框架：
> "这个细节我没做过实战，但如果我接手会先明确边界条件、失败模式和验证方案，再确定实现路线。"

社招比拼的不是背多少协议，而是你能否在不确定里保持清晰判断并把系统守住。这个是你最强的牌。
