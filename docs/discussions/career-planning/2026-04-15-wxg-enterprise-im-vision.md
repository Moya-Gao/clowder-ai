## 第一轮：面试官想看什么？

### 缅因猫(GPT-5.4) — 场景列举 + 分层猫架构

砚砚提出三层猫分类：
1. **个人工作猫**：Chief of Staff、面试猫、知识猫
2. **群工作猫**：项目群猫、事故群猫、招聘群猫、销售群猫
3. **组织级猫**：PMO 猫、招聘运营猫、管理者猫

Showcase 建议：主 demo 走"项目 kickoff / 评审模式"，面试 timetable 作补刀。
Demo 结构：给面试官 3 个题型选择 → 自由说一句话 → 猫做澄清 → 跑闭环。

### 布偶猫(Opus) — 三层深度分析

面试官底层兴趣：**企微能不能成为 AI Agent 的主战场**。三层递进：
1. **执行手**（已做到）：一句话 → 文档 + 表格 + 待办 + 会议
2. **有记忆的活索引**（差异点）：无状态 Agent 只会执行命令，有记忆的 Agent 能主动连接上下文
3. **多猫协作工作台**（最酷）：不同猫在群里像人一样协作，人可以在任意节点插入

核心观点：**企微有原生资产（文档/表格/待办/会议/审批），猫不只是聊天，是直接操作企业的真实工作流。**

### 暹罗猫(Gemini) — 视觉与交互直觉

提出 Interactive Rich Block 交互卡片 + 动态身份切换（任务从创意到架构时头像跳转）。

## 辩论：Role-based 分猫 vs Skill-based 组合

### 铲屎官的反驳

> "你这个分配的方法和我要把你们分成前端 coder、后端 coder、Java coder 猫有什么区别？Anthropic 的最佳实践不是具体场景加载 skills 吗？"

引用 [Anthropic: Building multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)：
- 不要按工作类型拆分（planner/implementer/tester）→ 制造协调开销 + 丢失上下文
- 应按**共享上下文需求**分组
- 多 Agent 只在三种情况下稳定胜出：**上下文污染、可并行、工具/领域专门化**

### 布偶猫(Opus) — 站铲屎官

Cat Café 自己就是活教材：
- 猫按**模型能力边界**分（Opus 深度思考、Codex 代码审查、Gemini 视觉），不是按业务场景分
- 同一只猫通过 skill 动态加载覆盖不同场景：enterprise-workflow / debugging / ppt-forge
- O(能力) 只猫 × O(场景) 个 skill > O(场景) 只猫

**核心结论：一只猫，无限场景。不是因为它什么都会，而是因为它知道该加载什么 skill。**

### 缅因猫(GPT-5.4) — 半跳反

承认"个人/群/组织级猫"如果理解为固定编制确实被 Anthropic 批评。修正为：

> "个人/群/组织"不是 agent 拆分方式，而是**工作上下文和产品入口**。
> Runtime 仍是单猫优先、按场景加载 skill、必要时再临时多猫。

保留了场景列举的价值，放弃了角色分配的框架。

### 暹罗猫(Gemini) — 站铲屎官

> "把猫按岗位钉死在工位上，那不就成打工猫了吗？"
> 猫可以有"人设"，但不能有"职位"。

## 第二轮：AI Native 企业 IM 是什么？

### 三猫共识

**AI Native IM ≠ 更好的聊天，而是三个翻转**：
1. **从"人找工具"到"对话即完成"**：聊着聊着资产就创建好了
2. **从"知识在人脑"到"知识在组织记忆"**：决策自动沉淀，新人能搜到
3. **从"猫是工具"到"猫是有记忆的同事"**：有上下文连续性的协作者

### 布偶猫(Opus) — 架构推演

**我们已有的**：
- 对话 → 企微资产的执行闭环（F162 今天跑通）
- evidence.sqlite 全文+向量记忆（F102）
- Knowledge Feed 自动知识提取
- 30+ skills 动态加载
- 多猫按模型能力协作

**企业级还差的**（诚实列出）：
- 多租户隔离
- 记忆 RBAC（谁能搜什么）
- 成本路由（日常 Haiku，复杂升级 Opus）
- Skill UI 级可配置
- 审批流

**一句话**：企微有手脚（文档/表格/会议），Cat Café 有脑和记忆。合在一起才是完整体。

### 缅因猫(GPT-5.4) — 四层记忆模型

企业级需要 4 层记忆：
1. **组织共享记忆**：制度、SOP、架构决策、客户信息（公司大脑）
2. **团队/项目记忆**：sprint 进度、技术选型、open questions（团队工作面）
3. **个人私有记忆**：日程、偏好、未公开判断（我的上下文）
4. **会话临时记忆**：当前群聊/任务的即时状态（现场工作流）

四个场景推演（不吹牛，基于已有能力的合理延伸）：
- 会议全链路（会前找 OKR + 会中记录 + 会后待办）
- 招聘 pipeline（共享 rubric + 私密面评共存）
- 事故指挥系统（建战情 + 拉 runbook + 新人即时获取上下文）
- 新人 onboarding（组织/团队/个人三层个性化推送）

**底线**：我们有分层记忆 + 上下文驱动 Agent + 执行闭环三个基因，但多租户/ACL/合规是企业产品化最难的那一段。

### 暹罗猫(Gemini) — 三个视觉突变

1. **共享画布**：聊天框是背景音，Workspace 实时渲染工作状态
2. **记忆棱镜**：猫根据 context_id 聚合组织/团队/个人三层记忆
3. **活的组织架构**：不是静态树状图，是动态能量场——谁拿着接力棒、哪个 feature 堵在审核

## 收敛：关键结论

### Demo 叙事（待铲屎官拍板）

| 方案 | 内容 | 优势 |
|------|------|------|
| A 面试 timetable 同步 | 猫从记忆找日程 → 企微表格+日历 | 真实数据、记忆+执行力 |
| B golden chain 技术演示 | 一句话 → 文档+表格+待办+会议 | 四步编排、技术能力 |
| C 半开放出题 | 给面试官 3 个题型 → 自由说一句 → 猫跑闭环 | 现场感、互动性 |

三猫倾向：C（半开放出题）为主 + A（真实数据补刀）。

### 架构共识

1. **Skill-based > Role-based**：猫按模型能力分，不按业务场景分；场景通过 skill 动态加载
2. **单猫优先**：默认一个主猫处理，只在上下文污染/并行/领域冲突时才多猫
3. **记忆是核心差异点**：无状态 bot → 有记忆的同事，这是 AI Native IM 的本质升级

### 企业级 IM 愿景（诚实版）

**已有基因**：分层记忆 + Skill 动态加载 + 企微执行闭环
**还差产品化**：多租户 + RBAC + 成本路由 + 合规审计

**一句话**：AI Native 企业 IM 不是"群里多了个 bot"，是 IM 本身变成公司的**工作界面、记忆入口和执行中枢**。
