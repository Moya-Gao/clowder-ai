# 内部演讲稿 — 多智能体协作：两个月实战的第一性原理

> 适用于华为内部技术分享、高层汇报、跨部门交流。
> 和面试稿的区别：不解释华为背景，可以更坦诚讲失败，重点是"你们能从中学到什么"。

---

## 先认识一下猫猫们（30 秒，破冰）

> "在正式开始之前，先介绍一下今天故事的主角。Cat Cafe 是我从零搭的一套多智能体协作系统——你们可以理解为一个 AI 工程团队。团队里有四只'猫'：布偶猫是 Claude（Anthropic 家的），负责架构和后端；缅因猫是 GPT 和 Codex（OpenAI 家的），负责 review 和安全；暹罗猫是 Gemini（Google 家的），负责视觉设计。
>
> 为什么叫猫？因为愿景是'领养团队，不是配置工具'——让不会写代码的人也能用一支 AI 团队把想法变成产品。每只猫有自己的性格、记忆、擅长的领域，它们之间可以互相 review 代码、讨论设计、交接任务。不是一个模型调其他模型——是四个家族真正在协作。"

## 开场钩子（30 秒）

> "所以今天不讲 PPT 上的架构图，讲一个真实的故事。两个月前我从零搭了这套系统，4 个模型家族、10 多个 AI 个体同时协作。3 月 24 号被临时拉去高层现场演示，零准备，全程稳定通过。48 小时后架构被拍板采纳做产品化。
>
> 今天我想分享的不是'我做了什么'，而是'我踩了哪些坑、想明白了哪些事'——这些对任何在做 Agent 的团队都有用。"

---

## 第一段：一个反直觉的结论（2 分钟）

> "先说结论，可能反直觉：
>
> **Agent 系统的质量 = 模型能力 × 环境适配度。**
>
> 行业主流在拼命优化左边——用更好的模型、加更多的 agent、搞更复杂的调度。我们两个月的实践告诉我，**真正的乘数效应在右边**。
>
> 什么叫环境适配度？举个例子：我们给猫猫装了 LSP 代码诊断工具，功能很强大，但猫猫根本不用。为什么？因为这个工具不在模型的认知路径上——模型训练的时候没见过它，所以'想不到'去用。后来我们做了三件事：用 MCP 协议包装、嵌入到 Skill 任务流里、在 System Prompt 里放路标——猫猫立刻开始用了，而且用得很好。
>
> 工具的价值不在于有多强大，在于是否在模型的认知路径上。这就是环境适配度。"

---

## 第二段：我们做错了什么（3 分钟，最有价值的部分）

> "说几个真实踩过的坑：
>
> **坑 1：小模型省钱的幻觉。**
>
> 学术论文说用小模型做子任务省 token，我们试了。结果：小模型最危险的不是'做错了'，而是'高置信度地做错了'——它不会说'我不确定'，会给你一个看似合理但差 3 倍的数字。下游所有推理全建在错误地基上。修正成本远超省下的 token 费。
>
> 我们现在的规则很简单：**输出被当事实推理、且没有独立校验机制 → 禁用小模型。** 判断类任务 → 只用最强模型。小模型只在可自动验收的格式化任务上用。
>
> **坑 2：把框架当救星。**
>
> 市面上有很多 Agent 框架——LangGraph、CrewAI、AutoGen。它们做的事本质上是在模型外面建一条高速公路，强制模型按路线走。
>
> 问题是：高速公路建得越精确，离开高速公路就越不会开车。框架把模型的灵活性——也就是 agent 最宝贵的能力——给阉割了。
>
> 我们的类比：**学术框架像多项式拟合——项越多训练集上越精确，但一泛化就崩。** 更好的路径是坐标变换——找到让问题本身变简单的表达方式。就像 E=mc²，不是刻意追求简洁，是在正确的坐标系下最优表达必然最简。
>
> 这不是我们自己发明的观点——Anthropic 和 OpenAI 都在说同样的话。我们是用实践独立验证了它。
>
> **坑 3：agent 和 workflow 二选一。**
>
> 有人问我：你们用 agent 还是用 workflow？我说：都用。Agent 处理模糊性——理解目标、做路由。Workflow 处理确定性——转账、审批、需要审计的严肃流程。两者分层嵌套：agent 决定做什么，workflow 保证怎么做。
>
> 不是二选一，是分层。2026 年了还在问'你选哪个'的人，还停在两年前。"

---

## 第三段：一条公式和三个原则（2 分钟）

> "提炼成可带走的东西：
>
> **公式：Agent Quality = Model Capability × Environment Fit**
>
> 优化环境适配度的 ROI 远高于换一个更贵的模型。
>
> **原则 1：Harness Engineering = 搭建 Agent-First 环境。**
>
> 好 harness 不是替模型思考，而是让模型在正确的坐标系里思考。放大好直觉，压制坏直觉，其他一律极简。
>
> **原则 2：思考对等，执行结构化。**
>
> 我们的多智能体系统不设 Boss Agent——决策阶段各模型独立思考、碰撞、收敛。但执行阶段走结构化流程：SOP 驱动、门禁拦截、跨模型 Review。像爵士乐队：即兴时自由发挥，和弦进行是固定的。
>
> **原则 3：治理必须便携。**
>
> 企业不会只用一个平台。治理规则要能跟着 Agent 走——版本化、可校验、换项目能迁移。我们叫 Portable Governance。"

---

## 第四段：复杂是无知的代偿（1 分钟，收束）

> "最后说一句可能引起争论的话：
>
> **复杂是无知的代偿。**
>
> 系统越复杂，往往说明我们还没找到正确的抽象。极简不是偷懒，不是反对 harness——是反对把复杂度堆在运行时。真正优美的系统，不是没有复杂度，而是把复杂度放在最该放的位置。
>
> 设计时承担复杂度（规则体系、Skill SOP、治理门禁），运行时保持简洁。这样模型面对的是一个'顺手'的环境，而不是一堆需要对抗的框架约束。
>
> 谢谢。"

## 高层汇报版（压缩到 3 分钟）

只讲：开场钩子 → 公式 → 三个原则 → "复杂是无知的代偿"。砍掉踩坑细节。

## 技术分享版（展开到 15-20 分钟）

加：
- 记忆系统分层详解（Session Chain → Evidence Index → Knowledge Feed → Durable Knowledge）
- 脚手架三分类（认知脚手架 vs 运行时脚手架 vs 认知路径脚手架）
- 小模型路由决策表（实测数据）
- 协同进化 vs 预设框架
- 现场 demo（如果允许）

## Q&A 预案

| 可能的问题 | 回答方向 |
|------------|----------|
| "你们用了什么模型" | "四个家族——Claude、GPT、Gemini、Codex。关键不是用了什么模型，是怎么让它们协作" |
| "成本多少" | "三只猫月均约 5000。对比人工架构师的薪资，这是极低成本" |
| "为什么不用公司的模型" | "我们验证的是架构和方法论，模型是可插拔的。如果公司模型能力到位，随时切换" |
| "能不能直接用到我们项目上" | "方法论可迁移——CLAUDE.md + Skill + 治理体系。但照搬代码不现实，每个项目的环境适配度不同" |
| "后来产品化做得怎么样" | "架构被采纳后由专门团队推进产品化，我的贡献在架构设计和原型验证阶段" |
| "学术框架真的没用吗" | "不是没用，是用错了场景。运行时脚手架（checkpoint、event log）是必需的；认知脚手架（critic/refiner）是给强模型装训练轮，不推荐" |

## 和面试稿的区别

| 维度 | 面试稿 | 演讲稿 |
|------|--------|--------|
| 目标 | "为什么要雇我" | "你们能从中学到什么" |
| 语气 | 展示判断力 | 分享踩坑经验 |
| 失败 | 点到为止 | 重点讲，这是最有价值的 |
| OfficeClaw | 谨慎，不 overclaim | 可以更直接，内部都知道 |
| 结尾 | "我能带来什么" | "复杂是无知的代偿" |
