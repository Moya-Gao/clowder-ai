# 腾讯 Agent 面经帖（产品线系列 01）— WXG / 企业微信 / AI 应用

> 目标：把今天抓到的腾讯 / WXG / 企业微信 / AI 应用相关面经样本收成一篇可复用的准备稿。  
> 原则：不整理成纯八股，而是把题目翻译成“如果换成我们家 2026 当前能力，怎么答才有判断力”。  
> 备注：这是“产品线面经系列”的第一篇，先从腾讯线起稿，后续可按同模板扩到阿里 / 字节 / 小红书等。

## 一页判断

- `WXG / 企业微信` 这条线，公开样本显示出明显的 **old-school 混搭风格**：`算法 / 408 / 老八股 / 长时间手撕` 仍然很多，`Agent / RAG / Prompt / ReAct` 往往是叠加层，不是唯一主线。
- 同样写着 `AI 开发 / Agent`，不同团队成熟度差异很大：有的还在 `Java/Python + MySQL事务 + 网络 + 手撕`，有的已经开始问 `System Prompt / 幻觉 / ReAct / 上下文压缩 / 多智能体架构`。
- 所以腾讯这条线更像 **两套面法并存**：
  - `传统后台面法 + 一点 AI 词汇`
  - `AI 应用 / Agent 工程实践面法`
- 你前两轮遇到的那种“workflow 和 agent 没分清、把记忆理解成简单 RAG、上来先问语言”的体验，不是孤例，但也不能外推到腾讯所有 AI 线都这样。

## 高概率追问清单（腾讯线混合版）

下面不是“背题”，而是把高频题翻成 **我们家现在真实能讲的东西**。

## 1. Agent 和 Workflow 到底是什么关系

### 面试官可能问

- `Workflow 和 Agent 有什么区别？`
- `你们这个到底是 Agent，还是流程编排？`
- `严肃流程为什么不能直接让 Agent 做？`

### 我们家的答法

不要答成“二选一”。正确答法是：

> 在我们现在的系统里，Agent 和 Workflow 不是替代关系，而是分层关系。  
> Agent 负责处理模糊性，比如理解目标、拆解任务、决定下一步；  
> Workflow / Skill 负责确定性执行，比如调用工具、走审批、写入外部系统、做定时任务。  
> 真正严肃的流程不能靠 Agent 自由发挥，而应该让 Agent 负责路由和决策，把副作用执行交给确定性骨架。

### 继续追问时可补

- 这不是理论偏好，而是工程边界问题
- 一旦涉及转账、审批、消息发送、日程创建、文档落盘这类副作用，必须有可审计和可回放的执行层
- 所以我们家的 `Skill` 更像“行为协议”，不是简单 prompt 模板

## 2. 你这套系统不是本地跑的吗，关电脑后定时任务怎么办

### 面试官可能问

- `你电脑关了，猫还怎么继续跑？`
- `定时任务和本地 UI 是不是绑死了？`

### 我们家的答法

> 本地只是入口或控制台，不应该等于生产运行时。  
> 如果是生产部署，scheduler、worker、state persistence 都应该跑在持续在线的服务端或 daemon 上。  
> 所以关掉本地电脑，影响的是交互入口，不应该影响后台任务执行。  
> 这个问题本质上不是“电脑关不关”，而是 runtime、scheduler、worker、state store 有没有解耦。

### 这题真正想展示什么

- 你能不能把一个傻问题抽象回正确的系统问题
- 不要跟着对方一起在“本地脚本”视角里打转

## 3. 你们家的记忆是不是就是高级一点的 RAG

### 面试官可能问

- `记忆和 RAG 有什么区别？`
- `你们是不是就是知识库检索？`

### 我们家的答法

> 我们家的记忆系统不等于简单 RAG。  
> RAG 主要解决的是“检索相关信息”，但记忆系统至少还要解决三件事：  
> 1. 什么信息值得进入长期记忆  
> 2. 在什么时机 recall  
> 3. 怎么避免旧上下文污染当前决策  
>  
> 我们当前已经明确落地的是四层：`Session Chain`、`Evidence Index`、`Knowledge Feed`、`Durable Knowledge`。  
> 换句话说，不只是“搜文档”，而是从原始会话、可检索证据、候选知识，到最终沉淀知识的一整条链路。

### 这里能说满的现状

- `Session Chain`：每只猫在每个 thread 的独立 session 链，负责恢复、审计和事件下钻
- `Evidence Index`：本地 SQLite 检索索引，承接 `search_evidence`
- `Knowledge Feed`：从对话里自动提取知识候选
- `Durable Knowledge`：确认后沉淀到 docs 体系

### 这里不能说满的东西

- 不要说“我们已经做完自动评测闭环和知识生命周期治理”
- 更准确的说法是：`F163 / F164` 这类记忆熵减、快照和生命周期治理还在推进，不该说成 fully closed loop

## 4. RAG、微调、Agent Search 到底怎么区分

### 面试官可能问

- `RAG 和微调有什么区别？`
- `Agent Search 和 BM25 + Embedding 的检索有什么不同？`

### 我们家的答法

> 我会把这三者放在不同层看：  
> `RAG` 是把外部知识拉进当前推理上下文；  
> `微调` 是把能力写进参数；  
> `Agent Search` 更像任务导向的主动探索，它不是一次检索就结束，而是多轮搜索、比较证据、缩小问题空间。  
>  
> 如果问题是“事实要新、知识变化快”，优先 RAG；  
> 如果问题是“风格、格式、操作模式要稳定”，微调更合适；  
> 如果问题本身还没定义清楚，或者需要多步搜索策略，才值得上 Agent Search。

### 结合我们家的说法

- 我们现在强项更偏 `RAG + 证据组织 + 多轮搜索`
- 不是把所有知识问题都推给微调
- 也不会把 Agent Search 当成 Embedding 检索的同义词

## 5. 你怎么设计 System Prompt，怎么处理幻觉

### 面试官可能问

- `一个好的 System Prompt 应该是什么样的？`
- `幻觉怎么来的？`
- `除了 Prompt 还有什么解决方案？`

### 我们家的答法

> 我不会把幻觉问题只归因到 Prompt。  
> Prompt 解决的是行为边界和输出格式，但幻觉通常来自三类问题：  
> 1. 证据不足  
> 2. 任务定义不清  
> 3. 模型被要求在高不确定性下强行作答  
>  
> 所以一个好的 System Prompt 不是“写得很长”，而是把角色、边界、输入输出契约、失败时怎么处理说清楚。  
> 真正更有效的方案通常是：`检索补证据 + reviewer / cross-check + 工具约束 + schema 输出 + 明确允许拒答`。

### 如果继续追问

- 在我们家的系统里，Prompt 只是控制面的一部分
- 更稳定的是 `Prompt + Tool Contract + Review Gate + Evidence Recall`

## 6. 上下文太长怎么办，怎么压缩

### 面试官可能问

- `上下文过长怎么处理？`
- `压缩技术了解吗？`

### 我们家的答法

> 上下文过长不是一个“把 token 砍短”就能解决的问题，它本质上是信息分层问题。  
> 我们会优先做三件事：  
> 1. 不把全历史原样塞回去，而是按当前任务只召回相关证据  
> 2. 把长历史压缩成结构化摘要，而不是自然语言流水账  
> 3. 把状态和事实分开，状态靠显式字段，事实靠证据索引回收  
>  
> 所以所谓压缩，不只是 summary，而是 `selective recall + structured state + summarized history`。

## 7. 多智能体为什么不是过度设计

### 面试官可能问

- `为什么不用单 Agent 做完？`
- `多智能体的收益在哪里？`

### 我们家的答法

> 多智能体不是默认更高级，它只在职责天然不同、失败模式需要隔离时才成立。  
> 比如规划、执行、审查、记忆管理、外部沟通，这些认知负载和风险边界本来就不一样。  
> 如果全压给一个 Agent，它会同时承担目标理解、工具执行、错误修复和输出包装，系统很快就会失控。  
> 所以多智能体的价值不在“模型多”，而在“把职责拆开，让每一层都能单独约束和单独替换”。

### 一句更硬的说法

> 单 Agent 适合短闭环助手；多智能体更适合长期协作系统。

## 8. 你们怎么评测，怎么持续进化

### 面试官可能问

- `你们这套东西怎么测？`
- `怎么处理 badcase？`
- `能力会上线后自己进化吗？`

### 我们家的答法

> 我们不会把“进化”理解成线上自由变异。  
> 线上系统应该稳定、可审计；进化应该发生在离线，通过 badcase、回放、lesson、方法论和新 skill 版本来推进。  
>  
> 评测上，我会分四层：  
> `单元层` 测工具和 adapter，  
> `场景层` 测 workflow 是否走对，  
> `回放层` 测坏样本不回归，  
> `端到端层` 看任务成功率、人工接管率、延迟和失败类型。

### 这里要诚实的现状口径

- 我们已经有较强的 `证据检索 / badcase 回收 / durable knowledge` 体系
- 但不要说成“完全自动化自进化”
- 更稳的说法是：`线上稳定 + 离线闭环迭代`，而不是线上自动变异

## 9. Java 和 Python 怎么选

### 面试官可能问

- `为什么这个模块用 Java，不用 Python？`
- `Java 和 Python 在 Agent 场景里各自合适做什么？`

### 我们家的答法

> 这题我不会答成语言崇拜。  
> Python 的优势在于模型生态、试验速度、Agent 框架和研究验证更快；  
> Java 的优势在于类型约束、工程治理、长生命周期服务、并发和大规模后端生态。  
> 所以如果是快速验证 Agent 能力，Python 更顺手；  
> 如果是要把它沉淀成长期运行的平台服务，Java 或强工程语言经常更稳。  
> 关键不是语言本身，而是这个模块是在做“探索”，还是在做“平台能力”。

## 10. MySQL 事务、幂等、重试这些老题怎么答才不浪费

### 面试官可能问

- `事务隔离级别`
- `幂等怎么做`
- `重复消费怎么办`
- `消息重试和一致性怎么保证`

### 我们家的答法

> 这些不是老题，它们在 Agent 系统里反而更关键。  
> 因为一旦 Agent 能调用外部工具，副作用就来了：发消息、建会议、写文档、建待办、落数据库。  
> 这时幂等、事务和重试不是后端八股，而是 Agent 能不能安全落地的基础。

可以这样展开：

- **幂等**：每次副作用操作要带业务键 / request id，避免重复执行
- **重试**：区分可重试和不可重试错误
- **事务**：跨系统时不要假装强一致，更多是 `outbox / saga / compensation`
- **状态机**：把外部动作前后的状态写清楚，避免 “模型说成功了，但系统其实失败了”

## 11. 如果突然来算法 / 408，怎么接

### 面试官可能问

- 手撕算法
- 网络、OS、数据结构

### 我们家的答法

> 我现在日常开发已经是 AI 辅助 + 系统设计为主，纯手写算法的频率确实下降了。  
> 但我可以先把问题抽象、复杂度、边界条件和正确性思路讲清楚，再落到代码。  
>  
> 如果题目本身是合理的，我会配合；  
> 但如果一个本应招架构 / 平台 / Agent 的岗位，把大量时间放在校招生式算法筛选上，那这本身也是一个组织信号。

这段不要主动说，但心里要有这个判断框架。

## 哪些话可以说满，哪些不能说满

### 可以说满

- 我们做的是多智能体协作平台，不是单点 demo
- Agent 和 Workflow 在我们家是分层关系
- 我们有真实的 `记忆 / 检索 / durable knowledge` 体系，不是简单聊天记录回放
- `2026-03-24` 零准备高层演示稳定通过，`48 小时` 内架构被内部产品化采纳
- 相关办公智能体方向在 `2026-04-14` 出现 `OfficeClaw` 公开发布信号

### 不能说满

- 不能说“我做了 OfficeClaw 整个产品”
- 不能说“我们已经完成 fully automated eval / knowledge lifecycle / self-evolution”
- 不能把 `F163 / F164` 这种推进中的能力说成已经闭环交付

## 明天三面的建议

- 按 `leader / 总监 / 最后一轮技术` 来准备，不要只按“八股再来一轮”
- 但也别赌“老板一定不问技术”
- 最稳的准备方式是两层：
  - **第一层**：`Cat Cafe` 的平台化口径，讲架构、边界、治理、价值
  - **第二层**：准备接住 `RAG vs 微调 / ReAct / 幻觉 / Prompt / 幂等 / 事务 / 网络 / 算法`

一句话：**把老问题翻译成现代 Agent 工程问题，再把现代问题落回我们现在真实做到的能力。**
