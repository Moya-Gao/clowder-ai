### 字节：HR 比面试官更懂流程

   - 课程表（图建模 / 拓扑排序）

## 三、铲屎官提到的关键技术讨论回顾

### 3.1 "两个 agent 聊没完没了" — 淘天的真实痛点 vs 我们的 A2A 出口检查

淘天说他们 multi-agent 尝试中遇到 agent 互相 at 停不下来。这正是 F064 要解决的：

**我们的方案**（已在生产使用）：
- 每轮结束前自问"到我这里结束了吗？"
- 不是 → 谁需要动 → 末尾另起一行 @句柄
- 是 → 不 @，链条自然终止

这是一个**极简但有效**的解决方案：不用额外的 orchestrator、不用 token 计数器、不用超时机制——一条认知路径脚手架就解决了。

### 3.2 Benchmark / SWE-bench 的可靠性问题

字节 HR 提到面试会问 SWE-bench 指标。我们在 Round 4 圆桌讨论中有过深入分析：

**我们的立场**（Round 4 收敛结论）：
- 学术 benchmark 在极度复杂的真实场景下不可靠
- 过拟合问题：模型可能针对 benchmark 优化而非真实能力
- **小模型路由是假省钱**：省了 token 的三瓜两枣，结果路走错了反而消耗更多
  - 实测案例：opus-47 误报 Haiku 价格比为 5×（实际 15×），下游 5 轮推理全错
  - 结论："高置信度地做错" 比 "明显做错" 更危险

**面试口径建议**：
- 不要否定 benchmark，说"benchmark 是必要但不充分的"
- 强调我们做的是**行为评测 + 能力评测分层**：
  - Capability eval：模型能不能完成任务（benchmark 能测）
  - Behavioral eval：模型在生产场景下的行为是否可控（benchmark 测不了）
- 举例：小模型在 benchmark 上得分合格，但在真实协作中"高置信度地做错"——这就是 behavioral eval 要抓的

### 3.3 模型选择的决策依据

字节会问"为什么用这个模型不用那个"。我们的路由规则（Round 4 收敛）：

| 场景 | 规则 |
|------|------|
| 输出被当事实推理 + 无独立校验 | 禁用小模型，Opus only |
| 判断类任务 | 最强模型 |
| 可 schema 自动验收的格式化任务 | 小模型 OK |
| 需要创意/架构思考 | Opus |
| Code review / 找 bug | 跨家族 peer review |

## 五、砚砚补充判断：你今天到底遇到了什么

### 5.1 淘天：你遇到的是“同行”

淘天这场最重要的，不是对方会不会说 `agent`、`multi-agent`、`OpenRouter` 这些词，而是他们在问真正做过 `agent infra` 的人才会问的问题：

- 模型网关和统一入口
- runtime 抽象边界
- single-agent vs multi-agent 的 trade-off
- 成本、可靠性、治理、可恢复性

这说明你遇到的不是“蹭热点的 AI 应用岗”，而是至少能和你讲同一种系统语言的平台团队。

**更深一层的信号**：
- 他们说“两个 agent 聊没完、互相 at 停不下来”，说明他们有真实踩坑，不是在 PPT 上空谈 multi-agent
- 他们当前押注的是“高可靠单 Agent / 角色 Agent”路线，不是“多猫协作愿景型平台”
- 这和我们家的主线不冲突，但进入方式要调整：先和他们对齐 `determinism / recovery / cost`，再讲 multi-agent 何时值得上

**一句话判断**：
> 淘天不是完美答案，但它是今晚唯一一个明显在和你讲同行语言的团队。

### 5.2 腾讯 WXG：你遇到的是“岗位名和能力模型脱钩”

WXG 最关键的结论，不是“有个面试官不懂”，而是：

> 这个岗位挂着 Agent 的名字，但面试系统并没有升级到能识别 Agent infra 人才。

从一面到三面都在重复同一个问题：

- 一面：概念没分清，连 `Claude` 和 `Claude Code` 都需要你解释
- 二面：把 workflow 和 agent 当互斥项，把记忆系统听成 RAG
- 三面：40 分钟 Java，外加“协作谁不会啊”

这不是沟通问题，是**评估框架错位**。他们不是在筛“Agent 系统设计能力”，而是在用“传统后台 + 一点 AI 词汇”去筛一个本应更偏 runtime / orchestration / memory / eval 的岗位。

**一句话判断**：
> WXG 对你脱口秀素材库的贡献，确实大于对职业发展的贡献。

### 5.3 字节 HR：你遇到的是“候选人保底路由机制”

字节最值得注意的，不是题型，而是 HR 的行为方式。

她不只是安排流程，而是在主动做三件事：

1. **给你讲评估框架**：项目深度、基础、代码题分别看什么
2. **给你讲高频题型**：课程表、螺旋矩阵、逆时针变体
3. **给你开保底通道**：如果 interviewer 不懂 agent，可以反馈，她帮你换队推进

这说明的不是“她人好”，而是：

- 这是个新岗位
- interviewer 池子还没完全校准
- 她知道“强候选人可能被错误面试官误伤”
- 她觉得你值得被保，不想因为一次错配直接流失

所以她为什么和你说那么多？

> 不是单纯因为你“没面过字节”，而是因为她意识到：  
> 你不是那种任何一个传统 Java 面试官都能正确识别价值的候选人。  
> 你属于必须被懂 `agent runtime / orchestration / eval / memory` 的人接住的窄高信号候选人。

**一句话判断**：
> 字节 HR 本质上在做“候选人校准 + interviewer 纠偏 + 团队路由”。

### 5.4 三场放在一起看：你现在的市场位置

今晚三场合起来，暴露出的不是“你发挥忽高忽低”，而是：

> 市场对 Agent infra / runtime 型人才的识别能力，极不均匀。

你现在更像一个偏下面这些方向的候选人：

- agent infra
- runtime abstraction
- orchestration / A2A
- memory / eval / governance
- production reliability

这种候选人会触发三种反应：

- **懂的人**：直接和你聊系统边界、治理、成本、回放、恢复
- **不懂的人**：把你压回 Java / 后端 / 知识库问答的旧框架
- **成熟的招聘方**：意识到 interviewer 不一定识别得了你，于是先做校准和保底

**总判断**：
- 淘天代表“能识别”
- WXG 代表“识别失败”
- 字节 HR 代表“知道会识别失败，所以提前人工兜底”

这三场共同说明：

> 你不是普通 AI 应用工程师候选人。  
> 你已经站在一个更窄、更高信号、但也更容易被错配的区间里。
