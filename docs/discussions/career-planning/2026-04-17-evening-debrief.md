## 三、铲屎官提到的关键技术讨论回顾

### 3.1 "两个 agent 聊没完没了" — 淘天的真实痛点 vs 我们的 A2A 出口检查

淘天说他们 multi-agent 尝试中遇到 agent 互相 at 停不下来。这正是 F064 要解决的：

**我们的方案**（已在生产使用）：
- 每轮结束前自问"到我这里结束了吗？"
- 不是 → 谁需要动 → 末尾另起一行 @句柄
- 是 → 不 @，链条自然终止

这是一个**极简但有效**的解决方案：不用额外的 orchestrator、不用 token 计数器、不用超时机制——一条认知路径脚手架就解决了。

### 3.2 Benchmark / SWE-bench 的可靠性问题

字节 HR 提到面试会问 SWE-bench 指标。我们在 Round 4 圆桌讨论中有过深入分析：

**我们的立场**（Round 4 收敛结论）：
- 学术 benchmark 在极度复杂的真实场景下不可靠
- 过拟合问题：模型可能针对 benchmark 优化而非真实能力
- **小模型路由是假省钱**：省了 token 的三瓜两枣，结果路走错了反而消耗更多
  - 实测案例：opus-47 误报 Haiku 价格比为 5×（实际 15×），下游 5 轮推理全错
  - 结论："高置信度地做错" 比 "明显做错" 更危险

**面试口径建议**：
- 不要否定 benchmark，说"benchmark 是必要但不充分的"
- 强调我们做的是**行为评测 + 能力评测分层**：
  - Capability eval：模型能不能完成任务（benchmark 能测）
  - Behavioral eval：模型在生产场景下的行为是否可控（benchmark 测不了）
- 举例：小模型在 benchmark 上得分合格，但在真实协作中"高置信度地做错"——这就是 behavioral eval 要抓的

### 3.3 模型选择的决策依据

字节会问"为什么用这个模型不用那个"。我们的路由规则（Round 4 收敛）：

| 场景 | 规则 |
|------|------|
| 输出被当事实推理 + 无独立校验 | 禁用小模型，Opus only |
| 判断类任务 | 最强模型 |
| 可 schema 自动验收的格式化任务 | 小模型 OK |
| 需要创意/架构思考 | Opus |
| Code review / 找 bug | 跨家族 peer review |
