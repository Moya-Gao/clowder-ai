# 淘天二面反问清单 — 从"信号验证"到"决策判断"

> 基于一面复盘 (`2026-04-17-taotian-first-interview-notes.md`) + 通用面试稿的第三层机制 + JD map 待确认项。
>
> 原则：二面不是再炫一遍技术，是**拿回决策所需的信息**。一面已确认对方不是浅层应用岗，二面要把"值不值得去"判断闭环。

---

## 第一组：平台边界 — 他们到底做到哪一层（最高优先级）

### Q1：你们的模型网关 / OpenRouter 做到哪一层？

> "一面提到团队在做统一模型入口。我想确认一下：这个网关是只做模型接入聚合和负载均衡，还是连策略路由、配额治理、审计日志、可观测性都在做？"

**为什么问**：如果只是 proxy + load balancer，那是 infra ops 岗；如果连路由策略、配额、审计都做，那才是真平台。

**追问分支**：
- 如果答"都做" → "那路由决策是规则引擎还是也有 model-based 路由？配额是按 BU 还是按场景？"
- 如果答"目前只做接入" → "后续路由和治理是这个团队做还是另一个团队？"

### Q2：agent runtime 的核心抽象对象是什么？

> "你们定义里，一个 agent 在 runtime 层面的最小抽象是什么？是 task？role？session？还是另一个概念？"

**为什么问**：抽象对象决定了系统的思考方式。选 task 说明偏工作流执行；选 role 说明偏角色模版；选 session 说明偏对话态。这直接影响你未来每天在写什么代码。

**追问分支**：
- 如果答不上来 → 红旗，说明 runtime 还没到有清晰抽象的阶段
- 如果答得清晰 → "这个抽象的生命周期管理怎么做？有状态持久化和恢复机制吗？"

## 第二组：multi-agent 边界 — 不做的原因决定了天花板

### Q3：不做 multi-agent 是现阶段务实选择，还是长期架构立场？

> "一面提到目前不做 multi-agent，理由是成本和收益比。我理解这个判断——single-agent 应该是默认选项。但我想确认：这是'今天业务还没到那一步'，还是'我们判断 multi-agent 在可预见的未来都不值得'？"

**为什么问**：如果是务实选择，说明你有空间在时机成熟时引入多智能体经验；如果是哲学立场，说明这个团队的天花板可能卡在单 agent。

**我们的口径**（如果对方反问你怎么看）：
> "single-agent 应该是默认选项。multi-agent 不是天然更高级——当任务分解、角色隔离、工具边界、上下文压力超过单 agent 最优点时才值得引入。真正的门槛不只是 token 成本，是调试、治理、回放、评测的复杂度会一起上升。"

**关键追问**（砚砚补充：拆开"现在不做"和"原则上不做"）：
> "如果明天出现一个必须跨角色协同的场景——比如客服 agent 需要调商家 agent 的库存信息再回答用户——你们会在现有 runtime 上加 orchestration 层，还是另起一套系统？"

**为什么追这句**：听到的不是"贵不贵"，是有没有清楚的触发条件和演进路径。这直接测天花板。

---

## 第三组：生产级真假 — 一个问题见底（砚砚补充，杀伤力最高）

### Q3.5：最近一次 agent 翻车，系统怎么发现、回放、恢复、归因的？

> "能不能聊一个具体 case——最近一次 agent 执行翻车、超时或误触发，你们的系统是怎么发现的？能回放执行过程吗？恢复语义是什么？最后归因到了哪一层？"

**为什么问**：这个问题一出，观测、回放、审计、恢复是不是生产级基本藏不住。比泛问"高可靠怎么做"真十倍。

**红旗判定**：如果只答"看日志"或"还在建设中"，说明 runtime 还没到生产级。

---

## 第五组：通用 vs 定制 — 决定日常工作画风

### Q4：平台通用能力和业务定制的比例大概是多少？

> "淘天有商家、客服、营销、供应链好几条业务线。你们现在是在做'通用底座 + 场景插件'，还是每条线有自己的定制分支？"

**为什么问**：通用底座 = 做架构决策 + 设计 API contract；业务定制 = 做需求承接 + 业务翻译。两种岗位的日常体验完全不同。

**追问分支**：
- 如果答"通用底座" → "那场景团队用你们的底座时，抽象泄漏最严重的地方在哪？"
- 如果答"每条线有定制" → "那你们怎么防止 fork 失控？有统一的 SDK/API contract 吗？"

### Q5：他们定义的"高可靠"到底指什么？

> "一面提到服务电商场景强调确定性和高可靠。我想对齐一下：你们说的高可靠更偏 SLA / availability（99.9% 不挂），还是更偏 deterministic behavior / auditable execution（结果可预期、过程可审计）？"

**为什么问**：前者是运维问题，后者是架构问题。如果是后者，和我们做的 Portable Governance / Gate 机制高度共振。

## 第六组：团队与组织 — 决定你跟谁干活

### Q6：这个团队的编制、汇报线和 HC 独立性

> "想了解一下：这个团队现在多少人？是淘天业务技术下面的独立平台组，还是挂在某条业务线下？HC 归谁管？"

**为什么问**：平台团队挂在业务线下面 = 业务线优先级随时能覆盖你的技术路线图。独立平台组 = 有自己的技术主线。

### Q6.5：模型网关、runtime、评测/观测分别归谁？这个 HC 进来能动哪一层？（砚砚补充）

> "一面聊到的三块能力——模型网关、agent runtime、评测和观测——这三块分别归哪个团队？我进来之后实际能参与和影响的是哪一层？"

**为什么问**：很容易听到一个很大的平台故事，但岗位本身只是业务接入或局部实现。这个问题直接把"团队愿景"和"你的实际工作"对齐。

### Q7：组织调整之后，方向的确定性有多高？

> "一面提到团队刚做完组织调整，方向会跟最新技术走。我理解 agent 领域确实变化快——但想确认：现在是'战略方向已定、战术灵活调整'，还是'方向本身也在探索中'？"

**为什么问**：一面铲屎官得到的信号是"做什么未必固定"。跟最新技术是好事，但如果方向本身不稳，你可能半年换三次主线。这个问题直接判断"灵活"是优势还是风险。

**追问分支**：
- 如果答"战略定了" → "那主线是三块里的哪块——网关、runtime、还是场景 agent？"
- 如果答"还在探索" → "那你们判断方向的依据是什么——业务拉动、技术趋势、还是集团指令？"

### Q8：团队现在最缺什么能力？前三个月最硬的问题是什么？

> "如果我加入，你觉得前三个月最该优先解决的问题是什么？团队现在最缺的是什么方向的人？"

**为什么问**：这个问题同时能暴露团队的真实痛点和对你的期望。如果答"缺人手做需求"那是业务岗；如果答"缺人想清楚 runtime 怎么抽象"那是架构岗。

## 第七组：个人成长与决策权

### Q8：技术选型的自主度

> "在模型选择、框架选型、架构决策这些事情上，团队的自主度有多大？还是集团有统一技术栈要求？"

**为什么问**：阿里集团层面可能有统一的模型/框架要求。如果自主度高，你能把经验带进去；如果被集团绑死，你只是在执行别人的技术决策。

### Q9：这条线在集团 AI 战略里的位置

> "淘天的 agent 平台和阿里云的 AI 平台、千问的 Agent 产品之间是什么关系？是各做各的，还是有统一的集团 agent infra 路线图？"

**为什么问**：如果各做各的，淘天这条线可能随时被集团统一方案替代；如果有统一路线图，要确认淘天在里面是 contributor 还是 consumer。

## 视情况加问（气氛好 + 有时间时）

### Q10：你们怎么做 agent 的评测和灰度？

> "电商场景的 agent 效果怎么衡量？是业务指标（转化率、客诉率），还是有独立的 agent 行为评测体系？灰度发布怎么做？"

**加分点**：可以自然带出我们的 eval 思路——"我们在做的方向是把评测分成 capability eval 和 behavioral eval 两层"

### Q11：对 Agent 的安全治理怎么想？

> "电商场景涉及交易、资金、用户隐私——agent 的工具调用有审计机制吗？有没有 fail-closed 的治理门禁？"

**加分点**：自然引出 Portable Governance 理念

## 优先级排序（砚砚建议：最多打 4-5 个，别贪多）

> 前两个决定真假，后两个决定天花板。

1. **平台边界**（Q1 + Q2）— 他们到底做到哪一层
2. **失败样本**（Q3.5）— 一个问题见底，生产级真假藏不住
3. **Ownership**（Q6.5）— 你进来能动哪层
4. **multi-agent 边界**（Q3 + 追问）— 天花板在哪
5. **成长与决策权**（Q8/Q9）— 长线值不值得

其余问题按时间和气氛自然带出，不硬塞。

## 二面打法建议

### 开场定调（30 秒）

> "上一轮和 [面试官] 聊了团队在做的方向——内部 OpenRouter、agent runtime、电商确定性 agent，我觉得方向很对。今天想更深入了解几个点，也想让你更具体看看我能带来什么。"

### 主要展示策略

一面对方已经表现出懂 agent infra，所以二面：

1. **不需要从头讲 Cat Cafe 是什么** — 一面应该已经介绍过
2. **重点讲 runtime/治理/可靠性这条线** — 和对方最共振
3. **multi-agent 讲成"进阶选项"而不是"默认答案"** — 尊重对方的务实判断
4. **用通用面试稿第三层**（机制细节）而不是第二层（理念），因为对方能接住

### 如果对方问"你怎么看 single-agent vs multi-agent"

用一面复盘里准备的口径：
> "single-agent 是默认选项。multi-agent 不是更高级，是当任务分解、角色隔离、工具边界、上下文压力超过单 agent 最优点时才值得引入。我做过从 single 到 multi 的完整演进，所以两边的 trade-off 我都踩过。"

### 如果对方问 coding

参考一面经验：如果一面没考 coding，二面有可能考。准备好：
- 说"我日常是 vibe coding，但基础算法不会忘"
- 如果真考，不慌——展示思考过程比写出完美代码重要

## 决策框架：拿到这些答案后怎么判断

| 信号 | 绿灯 | 黄灯 | 红灯 |
|------|------|------|------|
| runtime 抽象 | 有清晰核心对象 + 生命周期管理 | 正在探索中 | 答不上来（砚砚红旗） |
| 失败样本 | 有回放 + 归因 + 恢复语义 | 有日志但没回放 | "还在建设中"（砚砚红旗） |
| multi-agent 立场 | "现在不做但有触发条件和演进路径" | "业务不需要" | 只说"贵"，无边界条件（砚砚红旗） |
| 高可靠定义 | 确定性 + 回放 + 审计 | 混合 | 只答 SLA/QPS（砚砚红旗） |
| ownership | HC 能动 runtime 或网关 | 能影响但不 own | 只做业务接入 |
| 通用 vs 定制 | 通用底座 + 场景插件 | 七三开 | 每条线自己搞 |
| 方向稳定性 | 战略定了 + 战术灵活 | 大方向有但常调整 | "还在探索做什么" |
| 团队独立性 | 独立平台组 + 自己的路线图 | 挂在业务线但有话语权 | 纯需求承接 |
| 技术自主度 | 选型自主 | 框架受限但可影响 | 集团统一、没得选 |
| 前三个月期望 | 架构决策/设计 | 混合 | "先接需求" |
