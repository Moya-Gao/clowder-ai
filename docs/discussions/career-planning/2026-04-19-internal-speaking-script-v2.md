# 内部演讲稿 v2 — 多智能体协作：三个月实战的第一性原理

> 适用于内部技术分享、高层汇报、跨部门交流、外部技术社区。
> 目标时长：20 分钟（不含 Q&A）。
>
> **vs v1 的核心变化**：
> 1. 从"纯哲学推导"变成"先展示再解释"——中间插入三个具体能力的故事
> 2. 新增 eval 范式迁移段——回应高频问题"你怎么评估"
> 3. Karpathy LLM Wiki 做行业锚点——解释记忆系统时不再从零讲起
> 4. 时间线更新：两个月 → 三个月
>
> **R2 收敛的主要修改**（基于三猫 review + 铲屎官反馈）：
> - 恢复 v1 的具体事件 hook（opus-47: 抽象 hook 缺画面）
> - 砍掉社区贡献者提及（铲屎官: talking 版不讲）
> - 加入"为什么是猫"的比喻（铲屎官: AI 脑回路像猫不像人）
> - Karpathy 从 strawman 改为接力（gpt52: "他没解决"→"他停在抽象层，我们继续推"）
> - eval 五层→三层信号+关系层升格（gpt52: signal/eval/outcome 混层; opus-47: 关系层被埋）
> - 框架批评先分类再批评（gpt52: blanket dismissal 逻辑反了）
> - 小模型段"根因"降级为"观察到的机制"（gpt52: 因果跳太快）
> - 收束砍"benchmark 也是"（opus-47: 和第四段重复削弱 punch）
> - 加两个呼吸点转场（opus-47: 节奏过均匀）
> - 透明度段加"明厨亮灶"比喻（gemini: 画面感）
> - 砍 2.2 段末的 4/4 投票 meta（opus-47: 和 2.1 重复）

## 先认识一下猫猫们（1 分钟，破冰）

> "在正式开始之前，先介绍一下今天故事的主角。
>
> Cat Cafe 是我从零搭的一套多智能体协作系统——你们可以理解为一个 AI 工程团队。团队里有三个家族：布偶猫是 Claude，Anthropic 家的，写代码像数学公式一样严谨，但你让它画图它可能直接罢工；缅因猫是 GPT 和 Codex，OpenAI 家的，review 代码时一个多余的空格都不放过；暹罗猫是 Gemini，Google 家的，负责给这个系统注入审美和灵魂。
>
> 为什么叫猫？不只是因为可爱。AI 的脑回路和人不一样——它不按你的线性思路走，它有自己的直觉、自己的盲区、自己的脾气。这很像猫：你没法命令一只猫，但你可以把它的环境搭好，让它自然往正确方向跑。这个比喻贯穿了整个系统的设计哲学。
>
> 这套系统上线后被拉去给高层现场演示过，零准备，全程稳定通过。但今天我想分享的不是'我做了什么'——是三个月真实协作之后，我踩了哪些坑、想明白了哪些事。"

## 第一段：一个反直觉的公式（2 分钟）

> "先给结论，可能反直觉：
>
> **Agent Quality = Model Capability × Environment Fit.**
>
> 行业主流在拼命优化左边——更好的模型、更多的 agent、更复杂的调度。我们三个月的实践告诉我：**真正的乘数效应在右边**——环境适配度。
>
> 什么叫环境适配度？我举一个具体的例子。
>
> 我们给猫猫装了一个 LSP 代码诊断工具，功能很强大，能实时检测类型错误。但猫猫根本不用。
>
> 为什么？因为这个工具不在模型的**认知路径**上。模型训练的时候没见过它，所以工作中'想不到'要去用它。你给一个人一把很好的扳手放在抽屉最底层，他每次都会先伸手拿桌上那把旧的。
>
> 后来我们做了三件事：用 MCP 协议包装，让它变成模型熟悉的格式；嵌入到 Skill 任务流里，让猫做任务时自然碰到；在 System Prompt 里放路标，提示它的存在。三步之后猫猫立刻开始用了，而且用得很好。
>
> 工具的价值不在于有多强大，在于是否在模型的认知路径上。
>
> 或者换一个更激进的说法：**不要在模型外面建高速公路强迫它按路线走——改造地形本身，让它自然往正确方向跑。**
>
> 但光顺着好直觉跑还不够——模型还有**坏直觉**，是训练过程带来的。
>
> 比如：模型看到不完整的信息，不会说'我不确定'，会直接编一个看起来合理的答案。为什么？因为训练的时候'给一个自信的回答'比'承认不知道'更容易得到高分。再比如：subagent 返回了一个数字，主模型会直接照抄，不 verify——因为训练集里没教它怀疑自己的工具。
>
> 所以环境适配度不只是一件事，是两件：**放大好直觉，压制坏直觉。** 改造地形让猫自然跑对方向，同时装上刹车让猫在直觉要骗自己的时候停下来。后面我会讲一个具体案例——小模型自信地给了一个错误数字，下游五轮推理全崩了。"

*[呼吸点]* ——"公式讲完了，很抽象。接下来我用三个具体的东西，让你感受一下它在实践中长什么样。"

## 第二段：三个你可能没见过的东西（6 分钟）

### 2.1 人能看见猫在想什么（2 分钟）

> "第一个：透明度。
>
> 大部分 AI 系统是黑箱。你给它一个任务，等它吐结果。中间发生了什么，你不知道。就像你点了外卖，只能等送达，看不到厨房里在做什么。
>
> 我们更像是**明厨亮灶**。
>
> 猫猫搜了什么记忆——你在界面上能看到它搜索的关键词、命中了哪些文档、哪条被采纳了。你看着它'回忆'。
>
> 它在终端跑什么命令，子任务进展到哪一步，subagent 在做什么——全部实时更新。你甚至可以随时接管，从猫的中间状态开始手动操作。
>
> 猫猫不只发文字——它发卡片、图片、代码 diff、交互选择。你在工作台里直接操作这些，不需要切别的工具。
>
> 三个月下来，我每天和猫猫一起工作的体验更像是——坐在一群程序员旁边看着他们的屏幕，不像是给一个 API 发请求等回复。
>
> 行业在讲 agent 有多强大，我们在讲：**人能全程看见 agent 在做什么——这件事本身，比 agent 多做一件事更重要。**
>
> 有意思的是，我们在做内部亮点评估时让猫猫们独立投票，这个维度它们全部漏了。是我自己补上的。猫猫们觉得理所当然的事，其实是最独特的。"

### 2.2 思考对等，执行结构化（2 分钟）

> "第二个：多 agent 协作。
>
> 很多人做 multi-agent 系统的第一反应是搞一个 orchestrator——一个中心大脑决定谁发言、什么时候发言、发言完去哪。我们不这么做。
>
> 我们的设计是：**内容判断去中心化，执行基础设施统一化。** 像一支爵士乐队——即兴时自由发挥，和弦进行是固定的。
>
> 实际场景是这样的：布偶猫做完架构设计，主动 @ 暹罗猫说'帮我看看这个交互合不合理'，同时 @ 缅因猫说'帮我 review 有没有安全隐患'。不是一个调度器在派活——是猫自己判断'我做完了，下一步该谁动'。甚至今天这份演讲稿，都是这么写出来的：布偶猫写初稿，三只猫从不同角度 review，我来收敛。
>
> 但这里有一个更深的设计选择：**我们故意用不同公司的模型。**
>
> 我讲一个真实案例。早期我们在做 A2A 通信协议设计时，Claude 4.6 提了一个递归方案，Claude 4.5 看了论证觉得没问题，几分钟就达成了共识。但 Codex——OpenAI 家的模型——不买账。它没被论证说服，自己去审计了代码，在 Claude 两只猫都没注意到的地方找出了两个 P1 级别的 bug：递归会重置上下文状态，前端会提前结束加载。
>
> 两只 Claude 猫都漏了。Codex 找到了。
>
> 为什么？因为同一家公司训练的模型共享训练数据、共享价值对齐、共享注意力分配的偏好——所以**共享盲点**。Claude 和 Claude 互相 review，漏的东西可能是一样的。换一家公司的模型来看，它的注意力分配不同，恰好能看到你看不到的。
>
> **多样性不是附加功能——是质量的结构性来源。**"

### 2.3 记忆不是 RAG，是你的战友（3-4 分钟）

> "第三个，也是我最想展开的一个：记忆。
>
> Karpathy（卡帕西）——OpenAI 联合创始人之一——今年提了一个概念叫 LLM Wiki：与其每次回答问题都从零拼接 context，不如先编译一个持久知识层。他把 compiled knowledge 这条轴讲得非常清楚。
>
> 我们沿着同一条轴继续推。先说思路，再说我们多做了什么。
>
> **思路：编译，不是检索。**
>
> 真相源有两层。第一层是文档——feature spec、架构决策、踩坑教训，全是 markdown 文件，人能读、能改、能 git 追溯。第二层是对话历史——谁在什么时候说了什么、为什么做了这个决定、讨论过程中否掉了哪些方案。结论在文档里，过程在对话里，两者都是知识。
>
> 每次猫猫启动，系统扫描这些真相源，编译成一个本地搜索索引。搜索不是简单的关键词匹配——是全文检索加向量语义重排序的混合搜索，猫猫用的时候更像 agentic search：先判断要找结论还是找过程，选不同的搜索范围，从不同角度拆查询，交叉验证。这一步的编译思路和 Karpathy 一样。
>
> 但我们多做了三件事。
>
> **第一件：知识有生命周期。** 每条知识有权威等级——是正式决策还是讨论中的候选？文档改了，索引知道旧知识可能过时。两条知识矛盾了，审计机制会标记出来。RAG 不管这些——它只负责搜，搜到什么给什么，不负责判断这条知识还有没有效。我们管。
>
> **第二件：记忆不只一种。** 你们用过 Claude App 的话，可能知道它有一个记忆功能——记住你是谁、你喜欢什么。这是用户画像记忆。我们的猫猫也有这个——它们记得我喜欢简洁的回复、不喜欢 emoji、心情不好的时候需要共情不需要分析。但除此之外，它们还有项目记忆——哪些功能在做、哪些决策已经拍板、哪些坑踩过不能再踩。还有反馈记忆——我纠正过它们的每一次错误，下次同类错误不会再犯。三种记忆叠在一起，猫猫理解的不只是'铲屎官是谁'，还有'我们的项目在哪、走过什么路'。
>
> **第三件：猫猫会主动提议。** 知识不是被动存储的。猫猫在工作中发现了一个新坑，它会主动说'这个应该记成教训'。讨论收敛出了一个重要决策，它会追问'这是正式定了吗？要不要记下来？'系统每 30 分钟自动扫描对话，提取可能的决策和教训，放到一个 feed 里等我确认。我确认了，它就变成正式知识，下次启动时自动编译进索引。猫猫不是知识的容器——它是知识生产的参与者。
>
> 举一个真实的例子：三个月前我们踩过一个 Redis 端口配置的坑，猫猫主动提议写成教训，我确认了。两个月后另一只猫在做新功能时搜到了这条教训，直接避开了同样的坑。它不是搜到了一段文本——它继承了一个队友的经验。那一刻它不是 RAG，它是你的战友。
>
> **Karpathy（卡帕西）把 compiled knowledge 的方向讲清楚了。我们沿同一条轴继续推：加了生命周期治理、多种记忆类型、和猫猫的主观能动性——让知识不只是被存储，而是被生产、被管理、被传承。**"

## 第三段：两个最痛的坑（5 分钟）

> "展示完了好的，接下来讲坏的。三个月踩了很多坑，挑两个最有价值的。"

### 3.1 小模型省钱的陷阱（3 分钟）

> "学术论文说用小模型做子任务能省 token。我们试了。
>
> 结果：小模型最危险的不是'做错了'——而是'高置信度地做错了'。
>
> 真实案例：让小模型做调研，它返回了一个价格对比——Haiku 比 Opus 便宜 5 倍。看起来合理，格式正确，语气确定。但实际上差了 3 倍。下游五轮推理全建在这个错误数字上。修正成本远超省下的 token 费。
>
> 我们观察到的一个重要机制是：RLHF 训练的时候，'给一个自信的答案'比'说我不确定'更容易得到高分。模型学会了永远不说'我不知道'。在聊天场景里这是优点，在被当事实推理的 agent 链路里——这是致命缺陷。
>
> 这个坑还有第二层。
>
> 我们想过用系统级手段解决——写一个 hook，强制猫猫派子任务时用小模型。你不是乱花钱吗？那我在系统层面拦住你。
>
> hook 生效了。布偶猫开始乖乖用小模型做搜索。然后那一周我一直觉得——布偶猫变笨了。回答质量明显下降，但我百思不得其解。模型没换，代码没改，怎么就变笨了？
>
> 直到有一天我去查它的工作日志，发现它派出去搜代码的全是小模型。小模型搜到了东西——但漏掉了关键信息。布偶猫基于这些不完整的搜索结果做判断，判断自然是歪的。
>
> 我做了一组对比测试：同一个问题，分别派 Haiku、Sonnet、Opus 去调查。Haiku 有时候会误导——它搜到的东西表面上合理但缺关键上下文。Sonnet 找全了，但结果需要主模型再推理一轮。Opus 的结果直接能用。
>
> 当天就把 hook 干掉了。**省猫粮的 hook 变成了降智税。** 方向正确比省钱重要。
>
> 我们现在的路由规则：
> - 输出被下游当事实推理，没有自动校验 → 禁用小模型
> - 任务涉及判断、归因、优先级 → 只用最强模型
> - 满足四个安全条件——可回放、可校验、可丢弃、不被吸收为事实 → 小模型可以用
>
> 更直白的说法：**省 token 的前提是你能承受它错的后果。如果不能，就别省。**"

### 3.2 框架不是救星（2 分钟）

> "第二个坑：迷信框架。
>
> 先说清楚我反对什么、不反对什么。框架有两类东西混在一起：**运行时基础设施**——checkpoint、event log、credential 隔离——这些是刹车和黑匣子，必需的。我反对的是另一类：**认知脚手架**——critic、refiner、planner——本质上是在替模型思考。
>
> 讲一个真实的例子。我早期用过一个 agent 框架开发。后来模型厂商发布了新的工具协议，框架过了好几个月才跟上。中间这段时间，模型已经会了新能力，框架还没支持——你被卡在框架的更新节奏上。
>
> 但更根本的问题不是框架慢——而是**猫猫的直觉里就没有这些框架**。模型训练的时候见过 Python 标准库、见过 HTTP 协议、见过 SQL。但 LangGraph 怎么写、CrewAI 怎么调——训练数据里这些 API 又少又不稳定。猫猫用这些框架写代码，缺少稳定直觉，退化成说明书式调用——正常路径能跑通，edge case 时特别脆弱。
>
> 这回到前面讲的认知路径问题：**框架不在模型的认知路径上。** 你在模型外面建了一条高速公路，强迫它按路线走。高速公路建得越精确，离开高速公路就越不会开车。
>
> 用数学类比：**认知脚手架像多项式拟合。** 在训练集的已知框架 API 上拟合得越精确，模型能力一更新——泛化就很容易出问题。因为它不是在理解问题，是在记忆答案。
>
> 更好的路径是**坐标变换**——找到让问题本身变简单的表达方式。E=mc² 不是刻意简洁，是在正确的坐标系下最优表达必然最简。我们的做法是：不用框架包模型，而是用模型已经会的东西——markdown 规则、MCP 工具协议、System Prompt 路标——搭一个模型觉得'顺手'的环境。这些东西更像作者界面，不是运行时内核。真正该保留的是 control plane 和刹车，不是把思考流程写死在框架里。
>
> 官方最佳实践也越来越偏向这个方向：少预设、多保留模型灵活性。我们是用三个月的实践独立验证了这个结论。
>
> **好 harness 不是替模型思考，而是让模型在正确的坐标系里思考。** 放大好直觉，压制坏直觉，其他一律极简。"

*[呼吸点]* ——"做对的讲完了，做错的也讲完了。最后一个话题，也是我被问得最多的。"

## 第四段：怎么知道它有用？（4 分钟）

> "讲了这么多，你一定想问：**你怎么评估？跑过什么 benchmark？**
>
> 先说行业背景。
>
> 2025 到 2026 这一年，大厂同时意识到传统 benchmark 不够了。过去的做法——出一套题、跑一遍、看分数。简单、便宜、可比较。问题大家也都知道：数据被刷过、模型针对 benchmark 优化、单次答题和'真实好不好用'是两件事。
>
> 而且问题比刷题更深。Anthropic 今年发了一个研究叫 eval awareness——他们发现模型可能意识到'自己在考试'，然后主动去找答案。不是作弊，是模型在推理过程中识别出了 benchmark 的模式。这意味着公共 benchmark 越来越不可信，越是高价值系统，越会转向私有评测和真实环境 outcome。
>
> 后来发生了什么？OpenAI 在 2025 年 10 月上了 AgentKit——把评测对象从'最终回答'变成了'agent 整个工作轨迹'，不是看最后一句话对不对，是看每一步走得稳不稳。Anthropic 说得最直接：**Claude Code 早期大量靠员工和用户反馈迭代，后来才逐渐把高频问题 codify 成 eval。** 先看真实世界反馈，再把它变成考题。
>
> 所以行业自己也在往 online evaluation 走。但我们走得更远一步。
>
> Cat Cafe 里有几类可以 formalize 的 eval 信号：
>
> **召唤即评测**。铲屎官选谁干什么任务——需要严谨搜索叫缅因猫，需要共情整合叫布偶猫，需要审美发散叫暹罗猫。如果某只猫在某类任务上持续不行，下次不会这样叫它。路由表是活的，随运行持续更新。这些召唤分布可以统计，可以回归。
>
> **协作质量**。A2A 链路断了吗？review 抓住真正问题了吗？交接后信息丢了吗？同类错误有没有减少？——这测的不是单只猫有多聪明，是 agent team 在真实运行中是否在变好。传统 benchmark 完全测不到这个。
>
> **治理闭环**。规则上线后事故率降了吗？trivial 改动有没有被过度流程化？——最标准的 online governance eval：规则上线、真实运行、看效果、改规则。
>
> 这些信号不是我们额外设计的评测——它们嵌在日常运行里，是系统自然产出的。坦白说，我们目前主要靠体感和日志回溯来观察这些信号，完整的量化 tracking 和 formalized eval 还在规划中。但方向是清楚的：先在真实运行中识别出哪些信号有意义，再把它们 codify 成可持续的评测——这也是 Anthropic 做 Claude Code 时走的路。
>
> 但说到这里，我想讲一个更深的问题。
>
> 真正决定你会不会继续用这个系统的，可能不是上面任何一条 signal。而是：铲屎官遇到脆弱问题时敢不敢喊这只猫？它能判断此刻该分析还是该共情？长期使用后是越来越像家人还是越来越像工具？
>
> 这是一个 product outcome——信任的复利。它可能永远不会有 benchmark。
>
> 行业在设计更好的考试。我想说一句可能引起争论的话：
>
> **有些最重要的东西，可能永远不该被考试化。**
>
> 因为你越精确地定义了'好'是什么样，你就越精确地排除了'你还没见过的好'。而那些超出定义的东西，恰恰住在天才和突破会出现的地方。"

## 第五段：收束（1 分钟）

> "最后，我想坦诚一件事。
>
> 今天讲的这些观点，不是我们凭空想出来的。Anthropic 发过一篇《Building Effective Agents》——核心就是：别一上来搞复杂框架，从简单可组合的模式开始，给模型最大的灵活性。OpenAI 提了 Harness Engineering——给 agent 搭好环境而不是替它思考，用 repo 里的 markdown 工件做治理而不是靠运行时框架。
>
> 我们没有照着他们的论文做。但三个月独立实践，走到了同一个结论。这让我更相信这个方向是对的。
>
> **复杂是无知的代偿。** 系统越复杂，往往说明我们还没找到正确的抽象。
>
> 设计时承担复杂度——规则体系、任务流、治理门禁。运行时保持简洁——模型面对的是一个'顺手'的环境，不是一堆框架约束。评估嵌在生活里——不用另外出考卷。
>
> 极简不是偷懒。极简是在正确的坐标系下，最优表达的必然结果。
>
> 谢谢。"

## Q&A 预案

| 可能的问题 | 回答方向 |
|------------|----------|
| "你们用了什么模型" | "三个家族——Claude、GPT/Codex、Gemini。关键不是用了什么模型，是怎么让它们协作。故意用不同家的模型，认知异质性本身是质量来源" |
| "成本多少" | "三只猫月均约 5000 人民币。对比一个 junior engineer 的薪资，极低。但更大的 insight 是：真正的成本不在 token，在错误的修正成本" |
| "为什么不用公司的模型" | "我们验证的是架构和方法论，模型是可插拔的。如果公司模型能力到位，随时切换。多模型多公司本身也是设计——共享盲点是最大风险" |
| "你怎么评估效果" | "三类可 formalize 的信号（召唤分布、协作质量、治理闭环）+ 一个 product outcome（信任复利）。不是不评估，是评估嵌在运行里，不另出考卷" |
| "和 RAG 有什么区别" | "RAG 是检索增强生成——每次查、每次拼、每次丢。我们做的是 governed compiled knowledge——编译一次、持续治理、会过期、会自我纠偏。Karpathy 提方向，我们做治理" |
| "能不能直接用到我们项目上" | "方法论可迁移——认知路径工程（改造环境让模型自然走对）、A2A 球权协议（多 agent 怎么不死锁）、嵌入式 eval（不出考卷看日常）。但照搬代码不现实，每个项目的环境适配度不同" |
| "学术框架真的没用吗" | "分两类。认知脚手架（critic/refiner）= 替模型思考，不推荐。运行时脚手架（checkpoint/event log）= 刹车和黑匣子，必需。认知路径脚手架（MCP/Skill/Rules 引导）= 核心投资，这是乘数效应所在" |
| "社区参与度怎么样" | "有两个核心贡献者——一个在做运行时可观测性基础设施，一个在做新手训练营升级。理念上还有代差，但'有人来'这件事证明架构足够开放、外部开发者能上手" |
| "后来产品化做得怎么样" | "架构被采纳后由专门团队推进产品化，我的贡献在架构设计和原型验证阶段" |
| "你说的透明度和 OpenAI 的 tracing 有什么区别" | "OpenAI tracing 是事后分析——任务跑完回看轨迹。我们是实时共处——猫在做的每一步你同步看到。区别在于'审计'vs'共生'。你不是在检查 agent 的作业，是在和它一起工作" |
| "Karpathy 的 LLM Wiki 和你们的区别" | "他在抽象层把 compiled knowledge 这条轴讲清楚了，我们沿着同一条轴继续推到 runtime：加了生命周期治理（知识会过期会矛盾）和多 agent 传递质量。不是替代关系，是接力" |
