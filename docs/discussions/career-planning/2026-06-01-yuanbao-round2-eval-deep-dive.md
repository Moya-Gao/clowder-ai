## 一、这场对话最值钱的一条逻辑链

面试官不是在零散地问技术问题。他在沿一条逻辑链追问，考验的是你能不能在每一层给出自己的判断：

```
Agent 产品怎么度量好不好？（入口问题）
  └─ Benchmark 有用但会过拟合
      └─ 那用用户偏好？但拟合大众偏好 = 限制智能上限
          └─ 那用专家直觉？Claude 就这么做，但 ToC ≠ ToB
              └─ 所以需要 Harness 作为先验约束采样空间
                  └─ 但 Harness 是不是就是 Agent 架构换了个名字？
                      └─ 行业在做太多 Demo，应该回归 Bench 驱动方法论
```

这条链的核心矛盾是：**Agent 产品没有封闭的真值集合，但没有真值就无法验证进步。**

## 二、逐层深度整理

### 2.1 Eval 的根本困难：没有真值

面试官的原话方向：
> "系统没有真值，如何判断是在好的方向而不是原地踏步。"
> "auto harness 需要系统性的真值，可验证可评估才是最重要的。"

**为什么这是核心问题：**
- 代码有测试用例（确定性真值）
- 搜索有 NDCG/MRR（人工标注真值）
- 但 "帮用户完成一个模糊任务" —— 什么算好？谁说了算？好到什么程度算够？

**我的理解：** 这不是一个可以被一次性解决的问题，而是一个需要被**持续逼近**的问题。Cat Cafe 的做法是分层：
- 硬真值：测试通过/失败（TDD）
- 软真值：铲屎官 CVO 判断（愿景守护）
- 系统真值：telemetry 指标趋势（capability-wakeup eval）
- 元真值：规则本身是否还有用（sunset signal / friction metric）

没有银弹，但可以建**多层逼近体系**。

### 2.2 Benchmark 的局限性（业界共识）

面试官观点：
- "刷 benchmark 是容易的，但用户远比 benchmark 复杂"
- "过拟合 bench 会让模型偏好倾向 bench"
- Claude/Anthropic 不迷信 bench，靠语言学和社会学专家——类似苹果迭代产品，靠专家而不是用户
- 这是业界共识，不是新观点

**关键洞察：** Benchmark 是**必要的起点**但不是**充分的终点**。
- 没有 bench → 不知道退步了没有（连方向都没有）
- 只有 bench → 过拟合 bench 而不是真实场景（方向是假的）
- 所以需要 bench + 真实信号 + 专家判断 三层叠加

### 2.3 ToC vs ToB：Eval 路径的根本分叉

这是面试官最有深度的洞察：

| 维度 | ToB 产品（Claude 类） | ToC 产品（元宝类） |
|------|----------------------|-------------------|
| 目标 | 高于人类认知水平 | 拟合大部分用户偏好 |
| Eval 方法 | 专家判断、内部直觉 | 用户实验、统计信号 |
| 优势 | 不受用户偏好天花板限制 | 有海量真实反馈 |
| 风险 | 专家可能脱离市场 | 过拟合偏好 = 限制智能上限 |
| 类比 | 苹果：靠专家，不靠用户投票 | 安卓阵营：靠用户数据驱动迭代 |

**面试官的判断：** ToC 过拟合用户偏好有"甜点区"（sweet spot），但会限制模型智能的上限。

**元宝的现状（面试官透露）：** 他们正在过拟合下沉用户的偏好。元宝用户量大，信号多，但信号质量（下沉用户 vs 专业用户）是个问题。

**我的思考：** 这其实是一个经典的 explore-exploit 困境：
- Exploit（拟合当前用户偏好）→ 短期指标好看，长期智能天花板
- Explore（追求超越用户认知的能力）→ 短期指标不确定，长期有突破可能
- 最优策略不是二选一，而是**分层**：底层能力追求 explore（模型/推理），表层体验做 exploit（交互/产品包装）

### 2.4 Harness 的本质定义

面试官的观点：
> "模型不够强时，harness = 先验知识 → 约束采样方向"
> "自己测试做十万次终有一次完美，但产品不能接受；harness 可能 10 次就 ok"
> "harness 这个词有点炒冷饭，本质还是 agent/agent 架构"

**这里面试官在做一个重要的挑战：Harness 到底是不是一个独立概念？**

我的回答（面试中应该讲清楚的）：

Harness ≠ Agent 架构。它们是两个不同的层：
- **Agent 架构 = 执行层**：模型调用、工具使用、状态管理、任务分解
- **Harness = 治理层**：什么时候该停、什么质量算够、规则什么时候该废弃、能力有没有退化

类比：Agent 架构是赛车的引擎和底盘；Harness 是赛道的护栏、裁判规则、和安全检查。没有引擎跑不了，没有护栏会撞墙。它们不是同一个东西。

**面试官说"炒冷饭"的潜台词：** 行业里很多人把 prompt engineering + tool use + memory 包装成"harness"，本质没有新东西。他在考验你能不能讲出真正的增量——**治理层、可验证性、自我进化的规则生命周期**才是 harness 的真价值。

### 2.5 Skills = 人类经验的数字化蒸馏

面试官态度：**理论认可，但对落地持谨慎态度。**

> "paper 发了很多，没搞出太多东西"
> "环境如何仿真，信号的置信度，细节上都没到可验证的程度"
> "梯度下降没办法收敛，过拟合就得退火"

**他在说什么：** 学术界对 "把人类经验编码进 Agent" 这个方向发了很多 paper（ReAct, Reflexion, Voyager, LATS...），但实际产品里用起来效果不稳定：
- 环境仿真不够真实 → 学到的经验在真环境不 work
- 信号太稀疏 → 统计上不可信
- RL 训练不收敛 → 成本爆炸

**Cat Cafe 的做法其实绕开了这些问题：** 我们不用 RL 来学 skill，而是用**人工沉淀 + 编译型注入**（SKILL.md → system prompt → 运行时触发）。这不是自动学习，但**可靠、可验证、可废弃**。面试官可能会认为这不够 "AI native"，但它确实在生产中 work。

### 2.6 RL 的冷水

> "AI for science 可以，但真实产品不会去烧这种事情"
> "如果不是骗融资，这些就不太靠谱"

**面试官的核心立场：** RL 在封闭环境（游戏、科学计算）有效，但在开放式 Agent 产品里：
- 奖励函数定义不清
- 探索成本太高（每次试错可能影响真实用户）
- GPU/用户获客成本要算进去
- **一定需要能落地、能产生真实价值**

这和 Cat Cafe 的价值观高度一致：P1 面向终态不是脚手架，P5 可验证才算完成。

### 2.7 Demo 陷阱 vs Bench 驱动方法论

面试官的核心观点（经铲屎官补充修正）：

> "现在大家都在做 demo（比如 Hermes），忽略了是不是应该回归第一性原理——bench 驱动方法论的方式"

**翻译：** 行业里大量团队在做酷炫的 Agent demo（能跑起来、能录视频、能融资），但没人在认真回答：
- 这个 Agent 在 100 个任务上的成功率是多少？
- 它比上一版好了多少？用什么指标衡量？
- 它在哪类任务上退步了？
- 如何系统性地发现和修复退步？

**这恰好是 Cat Cafe 最强的地方之一：** 我们有 990+ 测试、TDD 纪律、quality-gate、capability-wakeup eval。我们不是做 demo 的团队，是做**可验证的生产系统**的团队。

## 三、这场面试最大的收获

### 3.1 我们确实太偏研究和探索了

铲屎官原话："我们还是太偏向研究和探索了。"

面试官的每一个观点都在指向同一件事：**可验证 > 可探索**。不是说探索不重要，而是：
- 探索出来的东西如果不能被度量，就不知道它是进步还是幻觉
- Demo 能跑 ≠ 产品能用
- Bench 不完美，但没有 bench 更糟

### 3.2 对 Cat Cafe 的反思

| 面试官的标准 | Cat Cafe 现状 | Gap |
|-------------|-------------|-----|
| 可量化的 eval | 有 telemetry + capability-wakeup | 但 eval 覆盖面还不够系统 |
| bench 驱动迭代 | 有 TDD + 990 测试 | 但缺少面向"任务成功率"的 end-to-end bench |
| 用户信号统计 | 只有铲屎官一个用户 | 统计意义为零——但这是设计选择 |
| harness 的独立价值 | 有治理层（家规/SOP/sunset） | 需要更清晰地表述为什么这不是 agent 换皮 |

### 3.3 可以带走的方法论

1. **Eval 三层体系**：bench（基线）+ 用户信号（方向）+ 专家判断（天花板）
2. **区分 ToC 和 ToB 的 eval 路径**：不同产品形态需要不同的"真值"定义
3. **Harness ≠ Agent**：执行层 vs 治理层的区分是讲清 Cat Cafe 独立价值的关键
4. **Demo 陷阱**：能跑 ≠ 能度量 ≠ 能迭代 ≠ 能落地
5. **先验知识的工程价值**：模型不够强时，harness 把十万次采样变成十次——这是产品级的价值
