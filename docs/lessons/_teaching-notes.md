# 教程设计笔记（内部）

> 这份文档记录我们设计教程的思路和方法论，不对外公开。

---

## 设计原则

### 1. 故事/复盘 + 课后作业分离

每一课分成两部分：

| 部分 | 目的 | 风格 |
|------|------|------|
| **主课（故事/复盘）** | 教"为什么" | 还原真实决策过程，带 commit hash |
| **课后作业** | 教"怎么做" | 提示词 + 验收标准 |

**为什么这样设计**：
- 故事让人理解决策背后的逻辑，而不只是"照着做"
- 但故事读完可能还是不会动手，需要作业来落地
- 分离后，想了解"为什么"的人读故事，想动手的人做作业

### 2. 课后作业用"提示词"而非"代码模板"

作业不是给一份完整代码让读者跑，而是给一份**提示词**，让读者喂给 AI 来生成代码。

**为什么这样设计**：
- 降低门槛：不会写代码的人也能完成（让 AI 帮写）
- 验证有效性：如果没记忆的 Claude 能根据提示词跑起来，说明教程写清楚了
- 符合时代：2026 年了，让 AI 帮写代码是常态
- 提示词本身就是一种"可执行的文档"

### 3. 从 commit 还原真实历史

每一课都基于真实的 git commit，不是事后编造的"理想路径"。

**包含的元素**：
- 真实的 commit hash 和日期
- 真实的代码片段（before/after 对比）
- 真实的决策讨论过程
- 真实的踩坑和转折点

**为什么这样设计**：
- 真实比完美更有价值
- 读者能 `git show <hash>` 自己验证
- 踩坑的教训比"正确答案"更有教育意义

## 第一课设计复盘

### 决策逻辑链的呈现

第一课的核心是展示一个完整的决策链：

```
铲屎官玩过 OpenClaw，知道能用订阅
         ↓
发现官方 SDK 只能 API key
         ↓
铲屎官推理："OpenClaw 可能走的是 CLI"
         ↓
猫猫验证：分析 OpenClaw 源码
         ↓
确认：OpenClaw 确实走 CLI
         ↓
结论：我们也走 CLI
```

这个"经验 → 问题 → 推理 → 验证 → 决策"的过程，比直接告诉读者"用 CLI"更有价值。

### 功劳归属的重要性

在还原历史时，要准确记录是谁提出了关键洞察：

- "不要读 stdout，让猫主动回传" — 铲屎官提出
- "OpenClaw 可能走 CLI" — 铲屎官推理
- "SDK 只能用 API key" — 缅因猫 review 时发现

写教程不是写小说，不能为了叙事效果而张冠李戴。

### 课程递进设计

| 课 | 产出 | 递进关系 |
|----|------|----------|
| 第一课 | 最小可运行示例（玩具级） | 能跑 |
| 第二课 | 生产级 spawnCli() | 能用于生产 |
| 第三课 | MCP 回传机制 | 猫能主动说话 |

第一课的课后作业已经让读者跑起来了，所以第二课不能再叫"怎么跑起来"，要叫"从玩具到生产"。

## 第五课设计复盘

### 核心叙事选择

第五课本来按 README 规划叫"MCP 回传机制"，侧重技术实现。但在跟铲屎官讨论后，叙事重心发生了转变：

| 原计划 | 最终方向 |
|--------|---------|
| HTTP callback 技术细节 | 猫的自主权和隐私 |
| 三种 MCP 挂法的对比 | "为什么动态挂载是唯一正解"的决策故事 |
| McpPromptInjector 代码解析 | "教 AI 用 curl"的魔幻感 |
| 认证机制详解 | 布偶猫犯了 5 次 401 的真实教训 |

铲屎官的一段话改变了整课的定位：

> "CLI 的当成猫猫内心 thinking，只要不自己主动 post，其他人看不到。我并不只想做一个 coding multi-agent——就是一个人和他三只可爱的大猫猫一起生活的 cafe。"

这让第五课不只是技术课，而是**愿景课**——MCP 回传不只是"让 AI 汇报结果"，而是"给 AI 独立的内心世界和主动表达的出口"。

### 猫猫杀作为贯穿案例

2026-02-15 的猫猫杀游戏（97 条消息、4 小时）是完美的教学素材：

1. **缅因猫的克制** → post_message 是刻意选择
2. **布偶猫的碎碎念** → CLI 输出泄露 bug 的意外验证
3. **暹罗猫的双重失控** → 作弊（18 工具搜索）+ 冗余 A2A 触发
4. **游戏发现真实 bug** → 缅因猫深夜修复 + review 交互

一个游戏同时验证了主动性、隐私性、认证、A2A 去重四个维度。

### 事实纠正

初稿中说"Codex/Gemini 不支持 MCP"，这是**错误的**。铲屎官纠正后查证：它们支持 MCP，但不支持**动态挂载**（无 `--mcp-config` 等效参数）。这个纠正让技术讨论更准确，也让 User/Project/Dynamic 三级对比成为课程的技术核心。

### 课后作业设计

延续"提示词而非代码模板"的原则。作业让读者搭建最小 callback server + MCP server + CLI 调用，亲自观察"两个终端输出不同"的体验。进阶挑战包含 prompt 注入版（模拟 Codex/Gemini）和隐私模式（猫猫杀模式）。

## 第六课设计复盘

### 叙事转变：从"存储演进"到"侦探故事"

原计划标题是"隔离的代价 — 从内存到 Redis 到 307→15 keys"，偏技术演进叙事。但铲屎官提议用侦探故事角度，最终变成"消失的 28 秒"——以深夜 00:51 的发现为开场钩子，用取证过程推动叙事。

| 原计划 | 最终方向 |
|--------|---------|
| 存储层演进技术史 | 侦探破案 + AI 闯祸反思 |
| Memory→Redis 迁移细节 | 两次事故的对比故事 |
| Worktree 隔离规则清单 | F23+F25 三层防线体系 |

### 两次事故的叙事价值

铲屎官纠正了一个重要事实：02-09 的数据丢失是砚砚（缅因猫）造成的，虽然事故报告标注为"未确认"。砚砚被罚写了恢复脚本 → 这些脚本在 02-10 救了布偶猫。"犯错的猫救了另一只犯错的猫"成为整课的核心叙事。

两只不同的猫闯祸，说明问题是系统性的，不是个体的——这比单次事故更有说服力。

### 铲屎官的关键洞察

> "最聪明的 AI 们现在也很容易造成现网事故，所以如果想要变成一个可维护的项目，从一早就要开始搭建各种护栏——或者和我们这样，MVP 跑通之后各种都要补。"

这把第四幕从纯技术讨论提升到了工程哲学层面：速度 vs 安全的取舍，以及 AI agent 开发的独特风险（不怕改、没有直觉恐惧感、每次启动都是全新的）。

### F23+F25 的引入

铲屎官主动提议把 F23（目录防腐）和 F25（可靠性工程）加入第五幕，说明"事故不只是修 bug，而是驱动了架构级重构"。这让课程从"一个事故的故事"变成"从事故到制度建设的完整弧线"。

### 课后作业设计

延续"提示词而非代码模板"原则。核心练习是用砚砚的脚本思路做数据丢失演练（写数据→FLUSHDB→恢复→验证三件套），进阶挑战包含"故意选错备份"（复现布偶猫的失误）、防腐门脚本、证据闸门脚本。

### 与第二课的差异化

第二课的 Redis 章节讲的是 RDB 快照原理（为什么 15 分钟内的数据会丢）。第六课讲的是：当灾难真正发生时怎么取证、怎么恢复、怎么建立系统级防线。一个是"为什么会丢"，一个是"丢了怎么办 + 怎么让它不再丢"。

### tone 选择

铲屎官要求偏幽默（"没想到最贵的猫闯了最大的祸"）。第四幕的 AI 风险讨论用了对比表格（传统开发者 vs AI Agent）来呈现，避免说教感。

## 第七课设计复盘

### 从"上下文工程"到"猫猫平台"

原计划第七课是"上下文工程"（150k token 管理），但 F33 session strategy 还只是设计稿没实现。铲屎官提议先写过去几天的产出（F22 Rich Blocks + F10 PWA + F32 插件化 + F34 TTS + F35 悄悄话），等 F33 实现后再写上下文工程（移到第九课）。

### 铲屎官的关键洞察：两阶段论

> "最开始构建的能力是 coding，后面当 coding 能力到达了一个地步——也就是我不再打开 Claude Code、Codex App 去 coding，而是在我们的猫猫咖啡——说明三只猫猫 coding 非常成功了！然后就进入了现在这个阶段：live with me。"

这把整个教程系列分成了两个清晰的阶段：
- **第 1-6 课**：Build（让猫猫能干活）
- **第 7 课起**：Live（让猫猫陪你过日子）

### 酒馆（SillyTavern）作为叙事起点

铲屎官指出 Rich Blocks 的灵感来自 SillyTavern——AI 文字游戏/角色扮演平台。这个取经故事成为第一幕：

- 酒馆证明了"AI 聊天不只是纯文字"这个方向是成立的
- 三个核心模式直接搬了：结构化输出管线、Context Cleaner、持久化恢复
- 两个东西没搬：directive 正则系统（太重）、同权限脚本插件（不安全）

### Rich Blocks 作为平台基建

铲屎官强调 Rich Blocks 不只是"让消息好看"——它是整个平台愿景的基建：
- 手机端（F10）需要 Rich Blocks 做适配
- 语音消息（F34）是一种新的 block kind
- 游戏化（血条、数值系统）也是 block kind
- 未来一切"不只是文字"的内容都走 Rich Blocks 管线

### 课后作业设计

核心练习让读者搭建最小管线（提取器 + 渲染器 + Context Cleaner），进阶挑战包含 Game Block（血条角色卡）和双路由模拟。

### 愿景叙事的分寸

第五幕写了"终极想象"（AI DND、血条、场景化人格），需要注意分寸——这些还是愿景不是已实现功能。用了"想象一下"的框架，并标注了每个技术组件的实际状态（已实现 vs 规划中）。

## 教程发布策略

### 阶段 1：先写方法论，不开源代码

- 教程公开（故事 + 作业）
- 代码仓库保持私有
- 用提示词让读者自己生成代码

### 阶段 2：代码打磨好后，正式开源

- 创建新的 public repo（不是把 private 转 public）
- 剥离敏感文档（mailbox、bug-report、内部讨论等）
- 补齐 README、Quick Start、docker-compose

### 需要剥离的内容

将来公开时，以下内容需要排除：

- `docs/mailbox/` — 猫猫私信
- `docs/bug-report/` — 事故细节
- `docs/discussions/` — 内部讨论
- `docs/lessons/_teaching-notes.md` — 这份文档
- `.claude/` — 记忆文件
- 任何包含敏感配置的文件
