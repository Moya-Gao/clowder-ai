## 背景

铲屎官提出了一个很强烈、也很合理的诉求：

1. 希望像 Google AI Studio 一样，允许对话级/消息级删除（甚至编辑），否则“会出现可怕的事情”。
2. 同时担心：一旦允许删除/编辑，会不会让 `resume`、上下文恢复、增量更新（cursor）变得很难甚至失真。

在讨论中还出现了一个具体现象：重复消息叠加 + `spawn claude ENOENT`。  
这让“是否会因失败重试导致重复写入/重复投递”成为高优先级问题。

## 我们的推理过程（完整复盘，不只结论）

### 阶段 A：先确认矛盾是否真实

- 用户担心是“可删除/可编辑”与“可恢复/增量一致性”之间的结构性冲突。  
- 我判断这个冲突是真实存在的：如果直接做“原地改历史”，当前 cursor 语义会被破坏。

### 阶段 B：提出第一版结构（双层模型）

- 我提出把系统拆成两层：
1) 用户视图层（可变）：支持删改分支，满足安全与可控；
2) 投递恢复层（可追踪）：保持事件流与 cursor 单调，保障 resume。

- 用户继续追问：能否让他自己选择软删/硬删并承担风险？  
我的回应：可以，但硬删必须有强确认。

### 阶段 C：面对“编辑”的核心挑战

- 用户直觉非常准确：编辑会影响多 agent 上下文，不应轻率“原地改”。
- 讨论演进到关键点：  
  “编辑可不可以转成 branch from here？”  
  我给出的意见是：**可以，而且这是更稳健语义**。

### 阶段 D：从对话 branch 升级到代码 branch

- 用户进一步指出高价值难点：  
  如果已经发生真实代码修改，仅“聊天分支”不够，最好能回到当时 commit / 工作区状态。
- 我的判断：这事不算不可做，但要分层推进：
  - Level 1：先做对话分支（不触碰 Git 状态）；
  - Level 2：引入 `gitRef/worktree` 绑定，支持“从该消息点恢复代码状态”。

## What（具体建议）

1. **删除操作让用户选择语义**
- 软删（默认）：可撤销，UI 隐藏，底层保留 tombstone/event。
- 硬删（危险）：永久删除正文，仅保留最小一致性元信息（不保留内容）。
- 硬删二次确认：输入线程名或固定确认词，避免误触。

2. **编辑操作不做原地覆盖**
- 定义为：`Edit -> Branch from here (edited)`。  
- 原线程保持不可变历史，新线程从编辑点重建上下文。

3. **先补重复写入防线（高优先级）**
- `POST /api/messages` 增加 `idempotencyKey`，防网络重试/前端重复提交。
- Agent 启动失败（如 ENOENT）时，不重复 append 用户消息；仅重试执行层。

4. **分层推进 branch 能力**
- Phase 1：仅对话上下文分支；
- Phase 2：分支时可选绑定 `gitRef`，在对应 worktree 恢复会话执行。

## Why（为什么这样做）

1. 把“用户可控风险”与“系统一致性”解耦：用户体验和工程可靠性同时保住。
2. 避免对现有增量 cursor 机制做破坏式改动（我们已有 per-user/per-cat/per-thread cursor 基础）。
3. 把最危险问题前置解决：失败重试导致的重复写入，比“高级编辑体验”更先伤系统可信度。
4. 采用可分阶段上线的架构，快速交付基础能力，同时保留高价值演进路径。

## Tradeoff（放弃了什么）

1. 放弃“原地编辑历史消息”带来的直觉简洁，换取一致性与可审计性。
2. 放弃“一步到位支持代码状态回溯”的速度，改为两阶段。
3. 软删会引入额外状态管理与清理机制；硬删会牺牲一部分可追踪性。
4. `idempotencyKey` 会增加 API 与存储复杂度（key 设计、TTL、冲突处理）。

## Open Questions（开放问题，欢迎你先独立判断）

1. 你倾向“硬删后保留最小元信息”还是“硬删彻底不可追踪”？边界怎么定最合理？
2. `idempotencyKey` 的作用域你更支持哪种：`(threadId,userId,key)` 还是全局 key？
3. ENOENT/子进程启动失败场景下，你是否同意“消息写入与执行解耦”并引入显式状态机（queued/running/failed）？
4. `Edit -> Branch` 的 UX 上，是否需要强制提示“这会创建新对话并重置该分支 cursor”？
5. Level 2 的 `gitRef/worktree` 绑定，是否放在线程元数据，还是消息节点元数据更合适？
