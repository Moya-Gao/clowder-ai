## 二、技术方向讨论：Phase 可靠性（三件事）

缅因猫提出三个技术方向，布偶猫逐一回应并全部赞同：

### 1. 状态机规格可执行（优先做）

- **现状**：ADR-008 的 InvocationStatus 状态机转移规则散落在 CAS_UPDATE_LUA 和各 route handler 里，是"代码里隐式表达"的
- **目标**：显式转移表 + property-based tests（`fast-check`），自动验证"所有非法迁移都被拒绝"
- **分工**：布偶猫出转移表草案（合法/非法迁移矩阵 + 不变量），缅因猫按"可执行规格 + 可证伪测试"做 R1 review

### 2. 并发故障演练台

- **痛点**：CAS 活引用 bug 是并发场景下才暴露的，但现有测试都是顺序执行
- **目标**：Interleaving fuzz 回放，把"偶现"变成"必现"
- **技术挑战**：可能需要 deterministic scheduler 或 mock 时钟

### 3. PR 证据闸门

- **思路**：每次合入前自动产出 Red→Green 证据包（失败用例→修复→回归）
- **与 #70 Build Gate 一脉相承**

### 串联故事线

三件事构成完整的**可靠性工程**故事线：
规格定义（转移表）→ 边界探索（fuzz）→ 证据闭环（闸门）

**状态**：等铲屎官拍板，再正式排入 Phase 计划。

## 四、A2A 交互 UX 问题定位

### 铲屎官提问

猫A → 猫B 互调时：
1. 界面显示"运行中"，不能输入
2. 之后又能输入了，但猫们好像还在聊
3. 没有明显的 Stop 按钮
4. 除非到 15 轮上限才停止

### 两猫联合定位结果

**核心原因**：猫互调有两条触发路径，前端只完整跟踪了一条。

| 路径 | 触发方式 | 前端跟踪 | 代码位置 |
|------|----------|----------|----------|
| 主链路 | 用户发消息 → routeSerial worklist 扩展 | ✅ isLoading 全程锁定 | `route-strategies.ts:217` |
| Callback 路径 | 猫通过 MCP callback @另一只猫 | ❌ fire-and-forget，不通知前端 | `callback-a2a-trigger.ts:70` |

**关键代码链路**（缅因猫定位）：

- `useSendMessage.ts:49` — 设置 `isLoading=true`
- `ChatContainer.tsx:385` — `disabled={isLoading}`
- `ChatInputActionButton.tsx:72` — Stop 按钮条件：`disabled && onStop`
- `a2a-mentions.ts:18` / `env-registry.ts:70` — `MAX_A2A_DEPTH=15`

### 现象性质判定

| 现象 | 性质 |
|------|------|
| 15 轮上限 | ✅ 设计行为（安全保护） |
| 初始锁定输入 | ✅ 设计行为 |
| 中途解锁但猫还在聊 | ⚠️ 状态不一致（可改进） |
| 没有 Stop 按钮 | ⚠️ 交互缺失（可改进） |

### 修复方向（缅因猫提出，布偶猫同意）

1. Callback 触发 A2A 时同步前端 loading 状态
2. Stop 按钮改为"线程有活跃 invocation 就显示"
3. 加常驻"停止互调"入口

**状态**：待铲屎官定优先级后排入计划。
