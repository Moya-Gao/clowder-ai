# Review Request: F139 Phase 2.5 Display Contract

Review-Target-ID: f139
Branch: feat/f139-display-contract

## What

F139 Phase 2.5 — 显示契约收口。让每个 TaskSpec 自己声明如何展示，前端变成纯渲染器，不再猜。

**改动范围**（8 files, +137/-39）：
- `types.ts`: 新增 `TaskDisplayMeta` 接口 + `display` on `TaskSpec_P1` + `display` / `subjectPreview` on `ScheduleTaskSummary`
- `TaskRunnerV2.ts`: 新增 `computeSubjectPreview()` 函数，`getTaskSummaries()` 透传 display + 计算 subjectPreview
- 5 个 TaskSpec 文件: 各补齐 `display: { label, category, description, subjectKind }`
- `SchedulePanel.tsx`: 删除 `categorize()` / `humanizeSubject()` 猜测函数，改用 `task.display?.category ?? fallbackCategory()` + `task.display?.label ?? humanizeId()` + `task.subjectPreview ?? task.display?.description`
- 新增测试: `display-contract.test.js`（8 tests）

## Why

铲屎官问："以后每次新增定时任务，前端展示什么由什么来决定？" 当时 SchedulePanel 用 `taskId.includes('review')` 之类的字符串猜测分类和显示名，每加一个新任务前端就要改。

三层显示架构（你和我收敛的方案）：
1. Static: `TaskSpec.display` — "我是谁"
2. Dynamic: API `subjectPreview` — "我在看什么"
3. Frontend: 纯渲染器 — 读 metadata，不猜

> "那你们的那个让人都看不懂的前端改了吗？以后每次新增这样的定时任务 前端要展示什么 是由什么来决定的呢？" — 铲屎官 2026-03-26

**请对照上面的摘录判断交付物是否解决了铲屎官的问题**

## Tradeoff

- 选择 `subjectPreview` 作为 API 产出（后端计算）而非前端 `subjectFormatter` 函数 — 因为函数不能 JSON 序列化，且铲屎官说"前端不再猜"
- 保留 `fallbackCategory()` / `humanizeId()` 兼容无 display 的旧任务 — 而非强制所有任务必须有 display（渐进迁移友好）
- `subjectKind` 含 `'external'` — 为未来 email fetcher 类任务预留，当前无使用者

## Open Questions

1. **5 个 category 够不够？** `pr|repo|thread|system|external` — 是否需要调整
2. **subjectPreview 截断逻辑**：thread 用 `id.slice(0, 8) + '…'`，PR 直接 `owner/repo#42`，repo 直接 `owner/name` — 是否合理
3. **SchedulePanel 配色**：thread 新增 violet 色系，和原 system(amber) 区分 — 是否与整体设计和谐
