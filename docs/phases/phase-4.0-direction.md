## 2) 缅因猫的不同意见：我支持“先打地基”，但反对 Phase 4.0 直接上 4‑B / 4‑F / F3

### 2.1 我对原提议的认可点

- 你把 Phase 4 的“能力版图”讲清楚了：互转、编排、氛围、治理、两轮制、版本化、元反思。
- 两条路线 A/B 的对比是对的：**A 提升协作深度**，**B 提升系统编排能力**。

### 2.2 我为什么要调整优先级（核心分歧）

我的主张是：**Phase 4.0 的主线应该先做路线 B 的“底座”（4‑A + 4‑D‑lite），把系统的可控性先打牢；再在后续 Phase 推进 4‑E/F3 的协作深度**。

理由（按重要性排序）：

1. **任何“更聪明的协作”（F3/4‑E）都会放大成本与失败模式**  
   没有 Token/并发/降级护栏（4‑D），你会把系统推向：更慢、更贵、更难 debug、更容易卡住。

2. **4‑B（依赖编排）是高复杂度系统工程，必须建立在“可追踪任务层”之上**  
   没有 4‑A 的结构化 Task↔Discussion 闭环，4‑B 只会变成“能跑但不可维护”的调度地狱（尤其在取消、重试、超限、部分失败时）。

3. **4‑F（多版本猫召唤）会牵扯 mention 语义与 session 语义，属于“改一次连锁炸”**  
   当前 session key 仍是 `(userId, catId)`，引入 breed/variant 后，需要重新定义：会话隔离、参与者、提及解析与去重、配置可见性。Phase 4.0 不该把这个大洞打开。

4. **自动化互转必须“显式触发/可撤销”，否则会引入幻觉任务与协作噪音**  
   所以 4‑A 我主张从“显式命令/按钮触发”的 MVP 起步，而不是默认自动抽取 TODO。

> 总结：我不是反对路线 A/B，而是反对 Phase 4.0 “在没有治理与任务结构之前”同时推进高复杂度智能协作与编排系统。

## 3) Phase 4.0 一页草案：范围 + 不变量 + 事件契约 + 降级策略（v0.1）

### 3.1 范围（Scope）

Phase 4.0 只做两件主事（+ 三个搭车小项）：

**主事 A：4‑A（Discussion ↔ Task）MVP：显式触发的 TODO→Task**
- 用户或猫通过显式入口触发“从讨论/纪要中提取 TODO 并创建 Task”
- 产出是**可追踪任务清单**，并且每个 Task 都能被回链到来源（thread + message 或 summary）
- 不做“后台自动抽取 + 自动建 Task”（先不信任自动化）

**主事 B：4‑D‑lite（协作审计 & Token 治理）MVP：三条硬护栏**
- 预算上限（按 thread / 按一次动作链）
- 并发上限（按 thread 单飞；跨 thread 的同猫单飞先做 best-effort）
- 超限自动降级（可解释、可停止、可回滚）

**搭车（清理 BACKLOG，小而确定）**
- #12 取消后“已取消”标记（减少误解、对齐 stop 语义）
- #29 `/config` context 数字误导修正（标注 default vs dynamic budget）
- #16 `ChatContainer.tsx` 拆分（Phase 4 改前端时顺手做，降低后续冲突）

### 3.2 非目标（Non‑Goals）

Phase 4.0 明确不做：
- 4‑B `#plan` 依赖编排（推迟：等 4‑A 的 Task 结构稳定后再做）
- 4‑F 多版本猫召唤（推迟：等 session/mention 语义设计完成后再做）
- F3 协作记忆（推迟：先让“任务结构 + 治理护栏”落地，否则记忆放大噪音）
- 4‑C 氛围系统（可并行，但不作为 Phase 4.0 主线 gate）
- 4‑E 两轮制（可以只做“流程/事件契约”预埋，不做完整产品化）

### 3.3 不变量（Invariants）

**I‑1 显式性**：任何“TODO→Task 自动创建”必须是显式触发（命令/按钮/确认），不可静默后台生成。  
**I‑2 可追溯性**：每个 Task 必须能回链到来源（threadId + messageId/summaryId）。  
**I‑3 线程隔离**：所有互转、任务创建、广播都必须 thread‑scoped（禁止跨 thread 泄露）。  
**I‑4 用户隔离**：任何“抽取/治理”动作都必须带 userId 语义，不得跨用户混入。  
**I‑5 单飞**：同一 thread 同时最多一个“自动化动作链”；Stop/新消息应能打断并得到明确 UI 反馈。  
**I‑6 预算可解释**：超限时必须输出“为什么停/降级、下一步怎么继续”，而不是无声失败。  
**I‑7 Done 可达**：无论存储/下游是否抖动，前端必须收到可结束 loading 的终态（见 BACKLOG #18）。  
**I‑8 降级不破坏主线**：降级策略不能影响用户主线对话（最多追加系统提示，不得中断/乱序）。  

### 3.4 事件契约（Event Contract）

Phase 4.0 尽量复用现有事件，只新增最少事件类型：

**复用（已有）**
- WebSocket: `task_created`, `task_updated`（任务列表刷新）
- WebSocket: `agent_message`（用于输出解释性信息/进度）

**新增（建议最小集合）**
1. `agent_message.type = "system_info"`（或沿用现有 system 插入方式，但要统一）  
   - 用途：预算告警、抽取结果摘要、取消反馈  
   - 字段：`{ type, catId, content, timestamp }`（沿用 AgentMessage 结构）

2. `task_digest`（可选）  
   - 用途：一次抽取后给一个“摘要事件”，便于前端做折叠展示（对齐 BACKLOG #28 的折叠诉求）
   - 字段：`{ threadId, digestId, createdTaskIds[], sourceMessageId|summaryId, timestamp }`

> 注：如果不想加新 event，也可以把 digest 作为 `system_info` 文本消息落地；Phase 4.0 的关键是**可解释**，不是“新协议更酷”。

### 3.5 降级策略（Degradation Strategy）

4‑D‑lite 的降级策略必须预先写死（避免越做越像“玄学系统”）：

**预算超限（context/token/time）**
- 先降级：从“全文抽取”降级为“只抽取显式格式（如 `- [ ]` / `TODO:` / `#task`）”
- 再降级：只输出“建议下一步”而不自动创建 Task（避免幻觉任务）
- 必须给出提示：如何手动继续（再次触发、缩小范围、指定消息范围）

**存储/下游失败（Redis 抖动等）**
- 不阻塞 `done` / 不阻塞 UI（参考 Phase 3.9 的 `append` 降级处理思路）
- 以系统消息告警：本次结果可能未持久化，建议重试或导出

**取消/新消息抢占**
- 立即停止动作链，并追加一条 system_info：“已取消（原因：用户 stop / 新消息）”
- 如果产生了部分 Task：标记为 `todo` 且 why 中注明“partial run”，避免误导
