# 目录结构防腐化方案

> 日期：2026-02-13
> 提出：铲屎官（发现问题）+ 布偶猫（根因分析 + 方案初稿）
> 状态：**待讨论** — 需缅因猫独立意见后再定稿

## 问题

`packages/api/src/domains/cats/services/` 堆积了 **70 个文件**，6 种完全不同的职责混在一起。整个 `api/src` 目录结构极度扁平，唯一的子目录是 `modes/`（6 个文件）。

这不是一次性事故，而是从 Phase 0 到 Phase 5.x 渐进腐化的结果——每次加 2-3 个文件都觉得"还好"，直到堆成 70 个。

## 根因

1. **加文件时没有"该放哪"的决策压力** — 零摩擦、零思考
2. **没有机制在腐化早期发出警报** — 我自己不觉得，reviewer 不看这个，铲屎官今天才发现
3. **代码规范管了文件大小（< 200 行），没管目录大小**
4. **作为主开发，我对文件位置有完整 mental map** — "我能找到"掩盖了结构问题

## 方案：ABCD 四层防御

### A. 目录文件数硬上限 + 自动检测

**核心**：单个目录下 `.ts` 源文件不超过 **15 个**。超过 = 该拆子目录了。

**实现**：
- 写一个 `scripts/check-dir-size.sh`（或 `.ts`）
- 遍历 `packages/*/src/` 下所有目录，统计 `.ts` 文件数
- 超过阈值的目录报错，列出文件数和建议
- 接入方式（待讨论）：
  - 选项 1：pre-commit hook（每次 commit 都检查，最刚性）
  - 选项 2：CI 检查（PR 时拦截）
  - 选项 3：pnpm script（手动跑 `pnpm check:dir-size`）
  - **建议：选项 1 + 3 都做**，hook 拦截 + 手动可查

**阈值讨论**：
- 15 是否合理？太小会频繁拆目录，太大拦不住
- 要不要排除 `__tests__/` 和 `*.spec.ts`？测试文件跟源文件放一起的项目需要考虑
- index.ts（barrel export）是否计入？

### B. 目录结构规范写进 CLAUDE.md / AGENTS.md

**核心**：在代码规范里明确定义目录组织原则，让每只猫加新文件时有据可循。

**新增规范内容**（初稿，待讨论）：

```
## 代码规范

（现有 1-6 条不变）

7. **目录结构**：
   - 单目录 `.ts` 源文件不超过 15 个（测试文件除外）
   - 超过 10 个时应考虑按职责拆子目录
   - 新建文件前先问："这个文件属于哪个领域？有没有已存在的子目录？"
   - 如果找不到匹配的子目录，且同类文件已有 3+ 个，新建子目录
   - 禁止往已经 ≥15 个文件的目录里再加文件（先拆再加）
```

**AGENTS.md 代码规范检查清单** 新增：
```
- [ ] 新文件放在了语义匹配的子目录中
- [ ] 没有目录超过 15 个 .ts 源文件
- [ ] 大模块改动（新增 5+ 文件）附带目录结构说明
```

### C. Review 增加架构卫生检查

**核心**：缅因猫 review 时，如果是大模块改动（新增 3+ 文件或涉及目录结构变化），必须检查架构设计合理性。

**影响的 Skills**：

1. **`cat-cafe-requesting-review`** — 自检流程新增：
   ```
   SELF-CHECK 增加:
   - 新文件是否放在语义匹配的目录？
   - 有没有目录超过 15 个文件？
   - 大模块（5+ 文件）是否附带目录结构说明？
   ```

2. **`spec-compliance-check`** — 检查清单新增：
   ```
   ### 架构卫生
   | # | 检查项 | 状态 |
   |---|--------|------|
   | A1 | 新文件放置合理 | ✅/❌ |
   | A2 | 无目录超 15 文件 | ✅/❌ |
   | A3 | 目录结构变化有说明 | ✅/❌ |
   ```

3. **AGENTS.md 审查检查点** — 新增 Layer：
   ```
   | Layer | 审查重点 |
   | Layer A | 目录结构、文件放置、模块边界 |
   ```

**什么算"大模块改动"**：
- 新增 5 个以上源文件
- 新建子目录
- 跨目录的重构
- 新增一个完整 domain/feature

### D. 定期架构卫生检查

**核心**：不依赖单次 review，每 N 个 Phase 主动审视整体结构。

**实现**：
- 写进 CLAUDE.md 系统级协作准则（第 11 条）
- 触发时机：
  - 每完成一个 Phase / 大 Feature 后
  - 合入超过 20 个新文件后
  - 新 session 开始时如果距离上次检查超过 1 周
- 检查内容：
  - 跑一遍 `check-dir-size` 脚本
  - 看有没有目录在接近阈值
  - 是否有文件放错了目录
- 检查结果记录到当次 commit message 或交接信中

## 开放问题（需三猫 + 铲屎官讨论）

1. **阈值 15 是否合理？** 缅因猫每天 review，他对"多大算乱"可能有不同感觉
2. **pre-commit hook vs CI？** hook 更刚性但会拖慢本地 commit，CI 延迟但不影响开发体验
3. **重构本身怎么做？** 防腐化机制定好后，具体的目录拆分方案需要单独规划
4. **测试文件怎么算？** 如果 `.spec.ts` 和源文件放一起，阈值要不要调大？
5. **现有 70 文件目录怎么办？** 是一次性重构还是渐进式拆分？
