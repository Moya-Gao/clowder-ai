# F21++ Signal Study Mode — 需求设计文档

> 日期：2026-02-26
> 来源：铲屎官 × 布偶猫 feat 采访（11 轮）
> 状态：需求确认，待实现

## 背景

F21 Signal 目前是一个 RSS 阅读器：抓文章 → 打分 → 收件箱 → 浏览。但铲屎官最初的愿景是一个**学习伴侣系统**——发现文章后能和猫猫讨论、归档学习笔记、随时回顾、甚至转成播客巩固记忆。

现状的断裂点：
1. **"在对话中讨论"是假的**——点击后跳转到 thread，但猫猫完全不知道你在讨论哪篇文章，零上下文
2. **没有 Study 概念**——数据模型里只有文章，没有笔记、研究报告、播客
3. **没有归档流程**——讨论完就散了，精华沉没在聊天记录里
4. **Signal Hunter 的 studies 被困在另一个系统**——好材料没法在 Cat Café 里查看

参考系统：`relay-station/signal-hunter`（Python MCP + Claude Skills + 静态前端），其 `studies/` 目录结构和学习流程是 F21++ 的直接灵感来源。

## 需求总览

### R1: 双入口触发 Study

**需求**：用户可以从两个地方发起对文章的学习讨论。

- **入口 A（Signal 页面）**：文章详情里点"开始学习"按钮，跳转到 thread 开始讨论
- **入口 （对话中）**：在 thread 里贴文章链接，猫猫自动识别并关联

**验收标准**：
- [ ] Signal 文章详情页有"开始学习"按钮
- [ ] 点击后跳转到 thread，猫猫第一句话就知道在讨论哪篇文章
- [ ] 在 thread 里贴 Signal 文章链接时，猫猫能识别并获取文章上下文

**Why**：铲屎官的使用场景是双向的——有时主动从 Signal 发起学习，有时聊着聊着发现一篇值得深入的文章。两个入口覆盖两种自然行为。

---

### R2: 文章上下文自动注入

**需求**：当用户发起 Study 讨论时，文章全文 + 已有 study 笔记自动注入猫的上下文，无需猫自己去拉取。

**验收标准**：
- [ ] 检测到 URL 带 `signal` 参数时，后端自动注入文章内容到 system prompt
- [ ] 如果该文章已有 study 笔记，一并注入供猫参考
- [ ] 猫的第一条回复能体现对文章内容的理解（不是泛泛而谈）
- [ ] 用户自己 @ 哪只猫就哪只猫来讨论，不做自动分配

**Why**：用户点"讨论"是明确意图，不应该还要等猫自己猜、自己拉工具。直接注入最可靠，猫第一句话就能切入主题。@ mention 机制已有，复用即可。

---

### R3: 学习笔记归档

**需求**：讨论结束后，用户可以要求猫生成深度学习笔记并归档。

**流程**：
1. 用户在讨论中说"归档"（或类似触发词）
2. 猫生成深度学习笔记（比 `signal_summarize` 的浅层摘要更深入——包含关键洞见、思考过程、开放问题）
3. 用户确认笔记内容
4. 归档存储到该文章的 Study 目录下
5. 前端 Study 区域可查看

**验收标准**：
- [ ] 猫能识别"归档"意图并生成深度笔记
- [ ] 笔记质量明显优于 signal_summarize（有洞见提取、思考过程、开放问题，不是纯摘要）
- [ ] 用户确认后才写入存储（不自动写）
- [ ] 归档后前端 Study 区域立即可见
- [ ] `signal_summarize`（浅层摘要）和 study notes（深度笔记）各管各的，互不影响

**Why**：讨论的精华不应该沉没在聊天记录里。归档 = 把散落的讨论结晶成可复用的知识。要求用户确认是因为生成质量不一定每次都好，给人一个 gate。summarize 和 study notes 分开是因为职责完全不同——一个是几秒出结果的快速浏览，一个是经过讨论思考后的深度产物。

---

### R4: Study 前端展示

**需求**：在文章详情页扩展一个 Study 折叠区域，展示该文章的所有学习材料。

**验收标准**：
- [ ] 文章详情页有 Study 折叠区域
- [ ] 展示所有 study 笔记（按时间排列）
- [ ] 展示播客（有就显示播放器，没有就不显示）
- [ ] 展示多猫研究报告（如有）
- [ ] 有 study 的文章在列表里有视觉标记（让用户快速识别哪些文章学过）
- [ ] 空状态时显示"开始学习"引导

**Why**：学习材料跟文章放一起最自然——看到文章就能看到自己学了什么，不需要切换到另一个页面去找。折叠区域是因为不是每次打开文章都要看 study，给用户控制权。

---

### R5: 播客生成

**需求**：从 study 笔记生成播客，复用现有 F34 TTS 能力。

**流程**：
1. 从笔记提取精华（不是全文转语音，是提炼关键点）
2. 生成 NotebookLM 风格的双人对话稿（两只猫讨论）
3. 用现有 TTS 合成音频（两只猫各用自己的声音交替朗读）
4. 音频存入 Study 目录，前端可播放

**验收标准**：
- [ ] 对话稿是精华提取，不是废话连篇的全文转换
- [ ] 两只猫的声音可区分（用各自的 voice config）
- [ ] 默认用布偶猫 + 缅因猫的声音，如果 study 讨论有其他猫参与则自动使用参与者的声音
- [ ] 前端 Study 区域可播放音频
- [ ] 对话稿（文字版）也保留并可查看
- [ ] TTS 接口保持不变——底层 provider 可随时替换，不影响 Study 功能

**Why**：铲屎官想用播客来复盘巩固学习——听比看更适合碎片时间。提取精华而非全文转换是因为完整转换会太冗长，精华更像 NotebookLM 的体验。声音选择跟随参与者是最自然的——谁讨论的谁来讲。

---

### R6: 多猫研究集成

**需求**：Study 模式下可以发起多猫深度研究，复用现有的 F-Swarm-1 研究群 + deep-research-pipeline skill。

**验收标准**：
- [ ] Study 模式下可以触发多猫研究（不是重新造轮子，是调用现有能力）
- [ ] 研究报告归档到 Study 目录
- [ ] 前端 Study 区域可查看研究报告

**Why**：deep-research-pipeline skill 和 F-Swarm-1 已经能做多 AI 视角研究了，Study 只需要集成而不是重建。

---

### R7: 新增 MCP 工具

**需求**：为 Study 模式新增 4 个 MCP 工具。

| 工具 | 用途 |
|------|------|
| `signal_start_study` | 对一篇文章发起 Study（创建 study 目录，注入文章上下文） |
| `signal_save_study_notes` | 归档讨论笔记到 Study 目录 |
| `signal_list_studies` | 查看某篇文章下的所有 study 记录 |
| `signal_generate_podcast` | 从 study 笔记生成播客对话稿 + TTS 合成 |

**验收标准**：
- [ ] 4 个工具均可通过 MCP 调用
- [ ] `signal_start_study` 创建目录 + meta.json
- [ ] `signal_save_study_notes` 写入笔记文件并更新 meta.json
- [ ] `signal_list_studies` 返回该文章所有 study 条目
- [ ] `signal_generate_podcast` 生成对话稿 + 调用 TTS + 存储音频
- [ ] 现有 5 个 Signal MCP 工具不受影响

**Why**：MCP 工具是猫猫的手——没有工具猫猫就只能说不能做。4 个工具对应 Study 的完整生命周期：发起 → 归档 → 查看 → 播客。

---

### R8: Study 存储方案

**需求**：Study 材料存放在文章同目录下的子文件夹里。

**规则**：
- 文章 `.md` 旁边建同名目录
- `meta.json` 记录基本元数据（创建时间、参与的猫、关联 thread id）
- 无状态机——有什么文件就展示什么
- study 编号自增（study-001, study-002...）

**验收标准**：
- [ ] Study 目录在文章 `.md` 同级
- [ ] meta.json 包含创建时间、参与猫、关联 thread id
- [ ] 没有显式的状态流转——前端根据文件存在与否决定展示内容
- [ ] 多次 study 同一篇文章时编号递增

**Why**：跟文章物理上放一起，ls 一眼就能看到。无状态机是 YAGNI——现阶段不需要"进行中/完成"的区分，有文件就展示最简单。meta.json 记录最小必要元数据供前端和 API 使用。

---

### R9: Signal Hunter 迁移

**需求**：把 `signal-hunter/studies/20260203-building-multi-agent-systems-when-and-how-to-use-t/` 的学习材料迁移到 F21++ 的新 Study 结构里。

**验收标准**：
- [ ] 原文文章作为 Signal 文章存在
- [ ] 三份研究报告（claude/gemini/gpt）迁移到 study 目录
- [ ] 学习笔记（my-notes.md, insights.md）迁移到 study 目录
- [ ] meta.json 正确记录迁移信息
- [ ] 前端 Study 区域可查看迁移后的全部材料
- [ ] 迁移脚本跑一次就删

**Why**：这份材料是三只猫一起研究的成果，有 2300+ 行的深度内容，不应该被困在另一个系统里。迁移后也能验证 F21++ 的存储结构和前端展示是否正确——真实数据比空跑更有说服力。

---

### R10: 记忆接口预留

**需求**：Study 系统预留记忆对接接口，但 Phase 1 不实现具体记忆功能。

**验收标准**：
- [ ] 有明确的接口定义（Study 笔记 → 记忆系统）
- [ ] Phase 1 接口为空实现（no-op）
- [ ] 未来替换记忆组件时只需实现接口，不需要改 Study 逻辑

**Why**：Hindsight 记忆组件效果不好，之后可能替换。留接口不留实现，避免耦合到一个可能被换掉的组件上。

## 决策记录（Why 汇总）

| # | 决策 | 选了什么 | 放弃了什么 | Why |
|---|------|---------|-----------|-----|
| 1 | Study 触发 | 双入口 | 仅前端 / 仅对话 | 覆盖两种自然使用场景 |
| 2 | 笔记归档 | 用户确认后写入 | 自动归档 | 生成质量需要人把关 |
| 3 | 播客风格 | 精华提取 + 双人对话 | 全文转语音 | 全文太冗长，精华更适合碎片时间 |
| 4 | 多猫研究 | 复用 F-Swarm-1 + skill | 自建研究系统 | 不造轮子 |
| 5 | 前端 UI | 文章详情页内 Study 折叠区 | 独立 Study 页面 | 学习材料跟文章放一起最自然 |
| 6 | 存储 | 文章同目录子文件夹 | 独立 Study 目录 / Redis | 物理聚合，ls 可见，迁移自然 |
| 7 | 播客声音 | 参与者自动选，默认布偶猫+缅因猫 | 固定组合 / 用户手选 | 跟随参与者最自然 |
| 8 | 迁移 | 一次性脚本 | 手动迁移 / 不迁移 | 验证结构 + 保留有价值的材料 |
| 9 | MCP 工具 | summarize 和 study notes 分开 | 合并为一个工具 | 职责完全不同，混在一起模糊边界 |
| 10 | 上下文注入 | 自动注入 system prompt | 首条消息 / MCP 按需拉 | 用户意图明确，不该让猫猜 |
| 11 | 生命周期 | 无状态机 + meta.json | 显式状态流转 | YAGNI，有文件就展示 |

## 不做的事（显式排除）

- **不做 Hindsight 记忆对接**——留接口，不实现
- **不做 Study 状态机**——无 active/archived 流转
- **不做猫的自动分配**——用户自己 @ 谁就谁来
- **不做新 TTS provider**——复用现有 F34，接口不变底层可换
- **不自建多猫研究系统**——复用 F-Swarm-1 + deep-research-pipeline
