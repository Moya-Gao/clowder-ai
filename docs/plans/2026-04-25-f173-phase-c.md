# F173 Phase C — Hydration 简化 + 读侧 selector 迁移 + 历史 dup 视觉合并

**Feature:** F173 — `docs/features/F173-frontend-message-pipeline-unification.md`
**Goal:** 前端 thread-runtime state 单一真相源 — 所有读侧组件改 thread-scoped selector，hydration 单一路径走 ThreadRuntimeWriter；historical dup 在 hydration 时视觉合并；F164 IDB cache 被新 GET 响应正确覆盖；useSocket-background 的 hydration 协助函数砍掉变 dead code（为 Phase B-2 = 删整文件铺路）。
**Acceptance Criteria:**

- [ ] AC-C1: 关键读侧组件（ChatContainer/MessageList/RightStatusPanel/MissionHub/**ChatInputActionButton**）改为 thread-scoped selector（`subscribeWithSelector + shallow`）
- [ ] AC-C2: F5 后 0 ghost bubble（fixture 含 race window）
- [ ] AC-C3: socket reconnect 期间收的 events 在重连后正确合并到现有 bubble，不裂
- [ ] AC-C4: cross-post + 当前 thread stream 同时进行不裂
- [ ] AC-C5: `mergeReplaceHydrationMessages` 简化（移除 ghost-tolerance 分支）
- [ ] AC-C6: cancel 按钮一致性（fixture 验证 socket-drop / F5 / reconnect 三场景）
- [ ] AC-C7: queue gating 一致性（fixture 验证）
- [ ] AC-C8: F081 AC-B2 (Remaining Gaps) 关闭
- [ ] AC-C9: 历史 dup tolerance — hydration 阶段对同 (cat, thread, time-window <5s, content-prefix-overlap) 不一致 invocationId 的 record 视觉合并，不动持久化数据
- [ ] **AC-C10（新）**：F164 IDB cache 被 hotfix3 后端过滤新数据**覆盖**而不是**合并**（hotfix3 实机暴露的 bug，docs/features/F173 timeline 2026-04-25 09:03 记录）
- [ ] **AC-B2 收尾**：Phase C merge 后 `useSocket-background.ts` 的 hydration 协助函数（`recoverStreamingMessage` / `ensureBackgroundAssistantMessage` / `markThreadInvocationActive/Complete`）成为 dead code → 同 PR 删除（不留 shim，end-state 0 行）

**Architecture:**
- Hydration 单一入口：`ThreadRuntimeWriter.hydrate(threadId, source)` — 从 `messageStore` (server GET) + `draftStore` (live socket) 合成 thread timeline，**覆盖** IDB cache（非合并）
- 读侧 selector：`useThreadMessages(threadId)` / `useThreadLiveness(threadId)`，组件不再读 flat
- 历史 dup 视觉合并：`mergeHistoricalDupBubbles(timeline)` 在 hydration 末端跑，对 (cat, time<5s, content prefix overlap) 但 invocationId 不一致的记录合成 1 个 visual bubble，记录 `_collapsedFrom: [otherInvocationId]` 给 debug
- Liveness reconcile：socket reconnect + fetchQueue 都通过 `ThreadRuntimeWriter`，单一路径

**Tech Stack:** Next.js 14.2.35 + zustand `subscribeWithSelector` + shallow + `idb` (`openDB`，见 `packages/web/src/utils/offline-store.ts`)

**前端验证:** **Yes** — reviewer 必须用 Playwright/Chrome 实测 cancel button / queue gating / F5 后 0 ghost / thread switch / socket reconnect 五场景

## Straight-Line Check (A → B)

**A（当前）**：
- 读侧组件混用 flat (`useChatStore().hasActiveInvocation`) + thread-scoped (`threadStates[tid]`)
- Hydration 三条路径并行：GET `/api/messages` (useChatHistory)、IDB cache (F164)、socket events (useSocket-background)
- `mergeReplaceHydrationMessages` 含 ghost-tolerance 分支（hotfix2 之前留的兜底）
- IDB cache 合并而非覆盖 → hotfix3 后端过滤了 orphan，IDB 旧数据残留 → 前端仍显示
- `useSocket-background.ts` 630 行（recoverStreamingMessage 等 hydration 协助函数和 socket 实时收口混在一起）

**B（end-state）**：
- 所有读侧组件走 `useThreadMessages(threadId)` / `useThreadLiveness(threadId)` selector
- Hydration 单一入口 `ThreadRuntimeWriter.hydrate()`，覆盖 IDB cache
- `mergeReplaceHydrationMessages` 删 ghost-tolerance 分支（来源已修，不需要兜底）
- 历史 dup 在 hydration 末端视觉合并（不动 Redis 持久化数据）
- `useSocket-background.ts` 的 hydration 协助函数成为 dead code → 删整文件
- Liveness 单一真相源（writer 主导）

**Terminal schema:**
```typescript
interface ThreadRuntimeWriter {
  hydrate(threadId: string, sources: { server: ChatItem[]; idb?: ChatItem[]; draft?: DraftRecord[] }): void;
  applyStreamEvent(threadId: string, msg: AgentMessage): void;
  reconcileLiveness(threadId: string, activeInvocations: Record<string, InvocationInfo>): void;
}

interface ThreadScopedSelectors {
  useThreadMessages(threadId: string): ChatMessage[];
  useThreadLiveness(threadId: string): { hasActive: boolean; catStatuses: ...; activeInvocations: ... };
  useThreadCatStatus(threadId: string, catId: CatId): CatStatusType | undefined;
}
```

每个 step 的产出**留在 final system**，不会被后续 step 重写。

**Spike**（time-boxed 1 day）：历史 dup 视觉合并算法的边界（time window 5s 是否足够 / content prefix overlap 阈值）— 需要拉真实数据看分布。

## Task 0: Spike — 历史 dup 视觉合并算法边界

**目标**：决定 time-window / prefix-overlap 阈值，不写实现代码。time-boxed 1 day，输出决策记录到本 plan。

**Steps**:

1. 在主仓 main 跑 bounded read-only script dump runtime Redis (6399 圣域，**只读** 操作可以) thread `thread_moay5tqumsbu17yr` 等历史 thread 的 messageStore，找 OUTER/INNER pair 实例。
   - **真相源**：`packages/api/src/domains/cats/services/stores/redis-keys/message-keys.ts` — thread key = sorted set `msg:thread:{threadId}`，详情 = hash `msg:{id}`，prefix `cat-cafe:`
   - **API**：优先复用 `RedisMessageStore.getByThread(threadId, limit, userId)`（`packages/api/src/domains/cats/services/stores/redis/RedisMessageStore.ts:430`）
   - **禁止 KEYS \***（阻塞 runtime Redis）。手查只用 `SCAN MATCH ... COUNT 100` + 明确 pattern + bounded limit
   ```bash
   # 只读 bounded examples（最多 100 ids per call）
   redis-cli -p 6399 ZCARD 'cat-cafe:msg:thread:thread_moay5tqumsbu17yr'
   redis-cli -p 6399 ZRANGE 'cat-cafe:msg:thread:thread_moay5tqumsbu17yr' -100 -1
   redis-cli -p 6399 HGETALL 'cat-cafe:msg:{specific-id}'
   redis-cli -p 6399 SCAN 0 MATCH 'cat-cafe:msg:thread:*' COUNT 50
   ```
2. 分析 pair 的 timestamp 间距分布（5s 是否覆盖 99%）
3. 分析 content prefix overlap 长度（10/50/100 chars 哪个阈值能区分 dup vs distinct）
4. 写决策到本 plan 末尾的 "Spike Result"

**完成条件**：本 plan 加 "Spike Result" 段，含：
- time-window 最终值（默认 5000ms）

### Finding (~~original~~ → corrected)

~~**F164 IDB messages cache 是 dead code（只写不读）**~~ — **错误 finding，已撤回**。

宪宪原 grep `loadThreadMessages\(` 漏了 `useChatHistory.ts:13` 的 `loadThreadMessages as loadCachedMessages` 重命名 import + `:776` 的 `await loadCachedMessages(threadId)` 调用。砚砚 GPT-5.5 在 PR-B worktree 实地验证：**IDB snapshot 有真实读路径**（bootstrap 时 preview）。

### Corrected understanding

- F164 IDB cache 是 **read-then-overwrite-by-server-GET** 模式：bootstrap 时读 snapshot 做 preview，server GET 回来后理论上要覆盖旧 snapshot
- hotfix3 实机暴露的"前端 cache 残留 orphan draft"根因仍待 spike，但**不能排除 IDB snapshot 路径**（preview-then-merge 失败可能让旧 orphan 残留）

### AC-C10 重新定义（砚砚拍板，宪宪同意）

**Old**：F164 IDB cache 被 hotfix3 后端过滤新数据**覆盖**而不是**合并**

**New**：**Server GET 是 authoritative source；IDB snapshot 只能临时 preview。GET 回来必须通过 ThreadRuntimeWriter 覆盖/清理旧 snapshot，而不是与之合并。** 如果未来重构真的要删 IDB reader，那就 read+write 一起删——不能只删 write 半边。

### Hydration 路径分析（PR-B 实施前的设计准备，2026-04-25 21:48）

`useChatHistory.ts` 的 `bootstrap()` 当前路径（line 771-792）：

```typescript
if (!hasCachedMessages) {
  // 1. IDB preview
  const idbSnapshot = await loadCachedMessages(threadId);
  if (idbSnapshot && idbSnapshot.messages.length > 0) {
    replaceMessages(idbSnapshot.messages, idbSnapshot.hasMore);  // 写入 chatStore
    setOfflineSnapshot(true);
  }
  // 2. Server fetch with replace: true
  const fetchOk = await fetchHistory(undefined, { replace: true });
  // 3. Clear offline badge after success
}
```

**hotfix3 实机 cache 残留真根因**：
- Step 1 把 IDB snapshot 写入 `chatStore.messages` (state.messages)
- Step 2 `fetchHistory({ replace: true })` 内部调 `mergeReplaceHydrationMessages(historyMsgs, currentMsgs, currentCatInvocations)`
- `currentMsgs` = chatStore 现有 messages = **IDB snapshot 写入的旧数据**
- `mergeReplaceHydrationMessages` 的 ghost-tolerance 分支会把旧 IDB orphan **merge 回 final timeline**

**结论**：删 `mergeReplaceHydrationMessages` ghost-tolerance 分支（Task 9）= 实机 cache 残留主修。`ThreadRuntimeWriter.hydrate()`（Task 5+6+7）= 结构性收口让 hydration 走单一 writer 入口（所有数据进 chatStore 必过 writer）。

**Method**：bounded read-only on Redis 6399，sample last 200 msgs of `thread_moay5tqumsbu17yr` (total 466)，pipeline HMGET catId/timestamp/extra，extract `extra.stream.invocationId`。

**Findings**：
- 88 assistant msgs with invId
- 10 candidate dup pairs（same catId, ts gap ≤60s, diff invId）
- **ts gap distribution**: p10=15389ms, p50=31260ms, p90/95=42847ms, p100=52070ms
- **0 真实 race dup pair**（无任何 < 5s 的 pair）—— spec 的 "time-window <5s" 阈值在真实数据里**不存在**
- 所有 candidate pairs 都是 user-driven conversation flow（用户连续 15-50s 内多次发消息，触发多个独立 invocation），不是 race-induced OUTER/INNER pair

**Decision**：

1. **AC-C9 算法重新设计** — 不用 "time-window + prefix-overlap 模糊匹配"（容易误合并 user-driven 多次回复）。
   改用**精确 metadata 识别**：
   - 优先：通过 invocation record 的 `parentInvocationId` 关系识别 OUTER/INNER pair（hotfix2 之后这种 metadata 是闭合的）
   - 次选：同 `userMessageId` 触发的多个 invocation
   - 兜底：ts gap < 100ms（race 时间窗）+ content prefix 近 100% overlap

2. **AC-C9 降级可能性**：hotfix2 部署后**不再产生**新的 race dup；历史脏数据数量小（本 thread sample 0 个）；**历史 dup tolerance 也许不需要专门的视觉合并层** —— 用户清 site data 即可（与 AC-C10 IDB cache 覆盖一起处理）。
   
   待定：跑更多 thread sample（特别是 hotfix2 之前的旧 thread）看历史 race dup 总量；如果 < 100 个，直接用 "清 site data" 文档指引 + 后端一次性 cleanup script，不开发视觉合并层。

   - **Task 8（历史 dup 视觉合并）**：暂缓，等扩大 sample 决策后实施或删除
