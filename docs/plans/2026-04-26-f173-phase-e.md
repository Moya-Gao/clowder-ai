# F173 Phase E Implementation Plan — KD-1 Handler Unification

**Feature:** F173 — `docs/features/F173-frontend-message-pipeline-unification.md`
**Goal:** 把 `handleBackgroundAgentMessage` (~634 行 useSocket-background.ts) 业务逻辑迁到 thread-aware `useAgentMessages`，消除 active vs background event handler 双路径，单一 handler 处理任意 thread 的 agent_message 事件。
**Acceptance Criteria:**
- AC-E1: `useSocket.ts:485-534` 的 `if (isActiveThreadMessage) ... else handleBackgroundAgentMessage(...)` 双路径合并为单一 thread-aware handler 调用；`useSocket-background.ts` 整文件删除
- AC-E2: 5 场景 fixture 复用 PR #1391/#1413/#1416 + 新增 cross-thread message handoff fixture
- AC-E3: thread_mo6 复现的"前端渲染裂气泡"消失（active path + background path 各创建一份 bubble id 的 race 从结构上不再可能）
**Architecture:** useAgentMessages 抽 `processAgentMessage(msg, { threadId, isActiveThread })` 纯函数；useSocket.ts 不再分叉，直接 `processAgentMessage(msg, { threadId: msg.threadId, isActiveThread: msg.threadId === currentThreadId })`。所有 writer 走 thread-scoped (F173 PR-A/B/C 已 KD-2 mirror)。stream key 追踪从 useSocket-background 的 module-local Map 移到 thread-scoped map (per thread+cat key)。
**Tech Stack:** React hooks / Zustand store / TypeScript
**前端验证:** Yes — reviewer 必须在 worktree 跑 thread-switch fixture 全套 (PR #1391/1413/1416 fixtures + 新 cross-thread handoff fixture)。

## Straight-Line Check (B 终态)

**B 定义**: useSocket.ts 接收 agent_message 事件 → 调 ONE thread-aware handler → handler 根据 `msg.threadId` 路由到 thread-scoped writer。`useSocket-background.ts` 文件不存在。

**Terminal schema**:
```typescript
// useAgentMessages.ts 暴露:
function processAgentMessage(
  msg: AgentMessage,
  ctx: {
    threadId: string;
    isActiveThread: boolean;
    streamRefs: Map<string, BubbleRef>;  // shared map (前 bgStreamRefs)
    finalizedRefs: Map<string, string>;
    nextSeq: () => number;
    addToast: (toast: Toast) => void;
    clearDoneTimeout?: (threadId: string) => void;
  },
): void;

// useSocket.ts agent_message handler:
socket.on('agent_message', (msg: AgentMessage) => {
  const ctx = useAgentMessagesContext();  // hook 暴露
  processAgentMessage(msg, {
    threadId: msg.threadId ?? threadIdRef.current,
    isActiveThread: msg.threadId === useChatStore.getState().currentThreadId,
    ...ctx,
  });
});
```

- ✅ 删掉这步成本？跳步 = handler 双路径残留 + KD-1 没收口 + 裂气泡持续

## Spike (DONE 2026-04-26 11:55)

grep `deriveBubbleId` 两个 handler 关键发现：**两边主路径都已用 `deriveBubbleId(invocationId, catId)` → `msg-{inv}-{cat}` 确定性 id**。差异仅在 invocationId 缺失时的 **fallback 命名前缀**:

| Handler | invocationId 主路径 | invocationless fallback |
|---------|---------------------|------------------------|
| useAgentMessages (active) | `deriveBubbleId(inv, cat) → msg-{inv}-{cat}` | `msg-{ts}-{cat}` / `msg-{ts}-{cat}-cb-{seq}` |
| handleBackgroundAgentMessage (bg) | 同上 | `bg-{ts}-{cat}-{seq}` / `bg-tool-*` / `bg-cb-*` / `bg-err-*` / `bg-sys-*` |

**裂气泡真凶**：invocationId 缺失时同一 server message 走两条 path → 两个不同 fallback id（`msg-1700...-opus` vs `bg-1700...-opus-3`）→ store 看作两条 → 渲染两个气泡。这就是 thread_mo6 现象的直接因果链。

**Spike 决策（已采纳）**:
1. **统一 fallback 规则**: 删 `bg-*` 前缀系列，全部用 `msg-*` 命名（保留语义后缀: `msg-cb-*` / `msg-tool-*` / `msg-err-*` / `msg-sys-*`）。
2. **主路径不变**: deriveBubbleId 已是 single source of truth，两 handler 在 invocationId 在场时本来就生成同一 id（store merge by id 不裂）。
3. **业务逻辑差异表**（实施时按表迁）:

| 事件 | useAgentMessages | handleBackgroundAgentMessage | 迁移策略 |
|------|------------------|------------------------------|----------|
| text | tool_use→text path、existing-bubble patch、replyTo/replyPreview、metadata、isStreaming、textMode='replace'、callback bubble 替换 stream | bgStreamRefs 追踪、recoverStreamingMessage、findBackgroundCallbackReplacementTarget、shouldSuppressLateBackgroundStreamChunk | useAgentMessages 接管，bg 的 stream-tracking helpers 移过去（thread-aware Map） |
| tool_use / tool_result | active 处理 | bg 不处理 | unified 后 thread 路由直接走 active 逻辑 |
| done | isFinal 清 streaming | stopTrackedStream + markThreadInvocationComplete + addToast | 都做 cat status，toast/markComplete 在 unified 里按 threadId 统一调度 |
| error | active 处理 | + toast | toast threadId 路由保留 |
| a2a_handoff | PR #1418 marker-gated insert | bg 透传 marker | unified 后 marker 字段保留作可选语义标签（hotfix transitional → core 简化） |
| provider_signal / system_info | active 处理 | bg 不处理 | unified 后所有 thread 都能收 |

**简化幅度**: 原 plan 估 ~600 行迁移，实际可能 ~300-400 行（很多业务逻辑在 active 已覆盖，bg 是子集 + 不同 fallback id）。Task 2-4 估算可下调。
