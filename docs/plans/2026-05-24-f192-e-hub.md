# F192 Phase E-hub — Eval Hub v1 Implementation Plan

**Feature:** F192 — `docs/features/F192-socio-technical-harness-eval.md`
**Goal:** Build Eval Hub v1 as the daily workflow surface for real `eval:a2a` verdict lifecycle, while reusing the System Workspace model instead of creating a separate Eval silo.
**Acceptance Criteria:** AC-E9, AC-E10, KD-14, KD-15, KD-16 (E-hub slice only)
**Architecture cell:** harness-eval
**Map delta:** update required
**Map delta why:** E-hub adds API/read-model and Console UI anchors to the existing `harness-eval` cell. No new cell.
**Architecture:** Backend read model normalizes committed live verdict docs and evidence bundles into an Eval Hub summary API. Frontend adds an Observability/Eval sub-area that shows real `eval:a2a` verdict lifecycle, status, trend, evidence, and jump actions. System Workspace is unified by shared `kind` metadata (`connector_hub` / `eval_domain`), while business semantics stay separate.
**Tech Stack:** TypeScript, Zod/local validators, Fastify route, Node fs/path, React, existing `apiFetch`, node:test/Vitest.
**前端验证:** Yes — browser validation for Observability/Eval loading, empty, error, and populated states plus jump actions.

---

## Finish Line

E-hub is done when Console has a daily workflow entry at **Observability / Eval** that renders the real committed `eval:a2a` live verdict, links to the source verdict and bundle-backed evidence, exposes the domain/system-workspace context, and provides jump buttons without taking over F188 repair controls or Settings configuration.

## Not Building

- `eval:memory`, F188/F200 adapter, or memory repair actions. That is E-scale.
- SOP compliance eval. That is E-sop.
- Community issue packet or custom external domains. That is E-community.
- A generic dashboard of scores without verdict, owner ask, and re-eval plan.
- A replacement for F188 Health Dashboard. E-hub and F188 mutually link; they do not replace each other.

## Product Decisions

- **Hub placement:** Console daily workflow path under Observability/Eval, not Settings.
- **Settings boundary:** Settings may later hold registry/frequency/owner/export policy configuration. It must not hold verdict lists, handoff lifecycle, trend review, or closure state.
- **F188 boundary:** Eval Hub may show memory-domain verdicts later, but F188 remains the live repair surface for health debt controls.
- **System Workspace boundary:** IM Hub and Eval domain threads share the system-managed workspace base via `kind`; only navigation, grouping, delete protection, and common actions are unified.

## Task 1: API Read Model for Eval Hub Summary

**Files:**
- Create: `packages/api/src/infrastructure/harness-eval/eval-hub-read-model.ts`
- Test: `packages/api/test/harness-eval/eval-hub-read-model.test.js`

**Step 1: Write failing read-model tests**

Tests:
- Reads committed `feedback_type: live-verdict` markdown from `docs/harness-feedback/verdicts/`.
- Resolves `snapshot:bundle/...` and `attribution:bundle/...` refs through the existing A2A bundle resolver.
- Returns only real live verdicts, excluding fixtures and representative contract demos.
- Produces a stable summary item with verdict id, domain id, packet id, verdict, feature/component under eval, phenomenon, owner ask, re-eval plan, evidence refs, trend window, and source paths.
- Represents the domain as `systemWorkspace.kind = 'eval_domain'`.

**Step 2: Implement narrow parser**

Use the markdown frontmatter and body emitted by `generateA2aLiveVerdict`. Do not invent missing state. If an owner response or closure record is absent, return an explicit empty state such as `not_applicable` / `not_started`, not a fake resolved state.

**Step 3: Verify**

```bash

```

  - Evidence bundle artifact.

**Step 3: Preserve boundaries**

Do not put Eval Hub under Settings configuration. Do not add F188 repair controls here; provide jumps only.
