# F192 E-sop Implementation Plan

**Feature:** F192 — `docs/features/F192-socio-technical-harness-eval.md`
**Goal:** Build the `eval:sop` domain — a domain-generic SOP compliance evaluator that reads `SopDefinition` predicates, traces session/git/env state, produces violation verdicts, and hands off to rule owners.
**Acceptance Criteria:** AC-E16 through AC-E24 (from feature doc §E-sop)
**Architecture cell:** harness-eval
**Map delta:** none
**Map delta why:** eval:sop is a new domain instance within the existing harness-eval cell — same registry / invocation / verdict / handoff patterns as eval:a2a and eval:memory. No new cell or boundary change.
**Architecture:** Extend eval domain registry to accept `eval:sop`, build a SOP trace adapter + predicate evaluator, wire weekly scheduling, reuse verdict handoff + re-eval closure.
**Tech Stack:** TypeScript, Zod, node:test, YAML (sop-definitions/)
**前端验证:** No — pure backend/infrastructure

---

## Terminal Schema

### SopTrace (adapter output → evaluator input)
```typescript
interface SopTrace {
  sessionId: string;
  sopDefinitionId: string;
  observedStage: string;
  commands: Array<{ command: string; cwd?: string; exitCode?: number }>;
  envSnapshot: Record<string, string | undefined>;
  gitState: {
    branch: string;
    ahead: number;
    behind: number;
    clean: boolean;
    worktreeRoot?: string;
  };
  handles: { author?: string; reviewer?: string; guardian?: string };
  shaContext: Record<string, string>; // e.g. { cloud_review: 'abc123' }
}
```

### SopViolation (evaluator output)
```typescript
interface SopViolation {
  ruleId: string;
  stageId: string;
  kind: 'hard_rule' | 'pitfall';
  severity: 'blocker' | 'warn' | 'info';
  predicateType: string;
  message: string;
  traceAnchor: string; // what evidence triggered this
}
```

### SopEvalResult (per-rule pass/fail/skip)
```typescript
interface SopEvalResult {
  ruleId: string;
  status: 'pass' | 'violation' | 'skipped';
  violation?: SopViolation;
  reason?: string; // for skipped (manual_only)
}
```

## What we're NOT building

- No UI changes (Eval Hub already renders any domain via systemKind)
- No new SOP definition domains at runtime (stubs are test-only, AC-E23)
- No F153 telemetry integration (SopTrace is built from structured inputs, not raw telemetry — AC-E17 says "from F153 telemetry / session events / git state" but the adapter accepts pre-structured data, leaving telemetry parsing to future phases)
- No changes to existing eval:a2a or eval:memory domains
