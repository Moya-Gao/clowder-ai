# F231 Phase C AC-C1 养熟循环最小闭环 Implementation Plan

**Feature:** F231 — `docs/features/F231-user-profile-capsule.md`
**Goal:** 跑通养熟循环的第一个真实闭环——关系信号 → capsule/primer 更新提议 → CVO 签字 → 写入 per-cat primer + provenance（三段管道 KD-8 的 push→pull 写入路径，AC-C1）。
**Acceptance Criteria（本 plan 覆盖 AC-C1，C2/C3 后续 plan）：**
- AC-C1: 关系信号→capsule/primer 更新提议路径落地（三段管道 KD-8，KD-12 分层写入制），至少 1 次真实更新走完全程（跑在白名单采集 + runtime-neutral trigger 真骨架上，非 L0 反射脚手架）
**Architecture cell:** identity-session（subcell identity-user-profile，F231 owns）
**Map delta:** none（复用 F128 ProposalStore 状态机模式 + F102 evidence lane；不新建 cell）
**Map delta why:** Phase C 实现挂在 identity-user-profile 既有边界内（capsule/primer 写入），proposal 基础设施复用 F128，无新 ownership 边界。
**Architecture:** 复用 F128 propose→approve 基础设施（ProposalStore 状态机 + proposal-card + decision route）。新增 `ProfileUpdateProposalStore`（仿 `SessionHandoffProposalStore`，profile-specific payload）+ MCP 工具 `cat_cafe_propose_profile_update`（仿 `propose_thread`）+ approve 后的写入 handler（写 per-cat primer + provenance）。AC-C1 只做**低代价 per-cat primer 写入路径**（KD-15：不碰 shared capsule，capsule 晋升是后续）。
**Tech Stack:** TypeScript, Redis (ProposalStore), Zod (MCP schema), Vitest/node test, fs (primer/provenance 写入)
**前端验证:** Yes — proposal 确认卡复用现有 proposal-card-block，reviewer 用 Playwright 实测 approve/reject。

## Straight-Line Check (A→B)

**B 定义（一句话）**：一只猫调 `cat_cafe_propose_profile_update`（带 before/after diff + 来源 + owner cat），CVO 在确认卡点 Approve，系统把更新写进 `private/profile/relationship/{catId}-primer.md` 并归档一条 provenance——全程可在真实 thread 走通一次。

**不做（AC-C1 范围外）**：
- ❌ shared capsule 写入（高代价路径，KD-15 晋升，C2/后续）
- ❌ 自动采集 + 蒸馏 trigger（KD-10 runtime 事件挂钩，C3）——AC-C1 是**猫主动声明**入口（KD-12 消化端手动入口，46 反射降级版）
- ❌ 注入层动态 recall（OQ-5，carve out）
- ❌ 用中校准的"使用→纠正"自动回流（KD-13，后续）——AC-C1 先做正向写入闭环

**Terminal schema（最终形态，步骤围绕它建）**：

```typescript
// packages/shared/src/types/profile-update.ts (new)
export type ProfileUpdateTargetLayer = 'primer';          // AC-C1 only; 'capsule' added in C2
export type ProfileUpdateProposalStatus = 'pending' | 'approving' | 'approved' | 'rejected';

export interface ProfileUpdateProposal {
  proposalId: string;
  status: ProfileUpdateProposalStatus;
  sourceThreadId: string;
  sourceInvocationId: string;
  sourceCatId: CatId;          // owner cat (primer is per-cat)
  targetLayer: ProfileUpdateTargetLayer;
  // payload
  beforeContent: string;        // current primer slice (for diff + audit)
  afterContent: string;         // proposed new content
  rationale: string;            // why this update (shown on card)
  signalProvenance: {           // KD-9 whitelist source — where the signal came from
    kind: 'cat-declared' | 'cvo-instructed';   // AC-C1: manual entry only (no classifier)
    sourceMessageId?: string;
    sourceThreadId: string;
  };
  createdBy: string;
  createdAt: number;
  // lifecycle (mirrors ThreadProposal)
  approvedBy?: string; approvedAt?: number; claimedAt?: number;
  rejectedBy?: string; rejectedAt?: number; rejectionReason?: string;
  writtenPath?: string;         // recorded BEFORE finalize (partial-commit recovery)
  provenancePath?: string;
  cardMessageId?: string;
}
```

## Stateful Object Gate（F229 教训：状态机先行，不留边给 reviewer 逐轮补）

### Census — 本 plan 的生命周期对象

1. **ProfileUpdateProposal**（核心状态机，下方三件套）
2. **primer 文件**（被写对象——但写入是 last-write-wins 覆盖 + provenance 留痕，非独立状态机；不变量见 INV-5/6）
3. **dedup reservation**（clientRequestId → proposalId，幂等，复用 ProposalStore 模式）

> 复用决策：ProfileUpdateProposal 状态机**完全镜像** F128 `ThreadProposal`（pending→approving→approved/rejected + 崩溃恢复 + 幂等），因为 review 过的边都一样。差异只在 payload（profile content）和 approve 动作（写文件 vs 建 thread）。**不重新发明状态机**——直接复用 `IProposalStore` 接口形状，新建 `ProfileUpdateProposalStore`（仿 `SessionHandoffProposalStore`）。

### 1. 状态 × 事件转移表

| 当前态 | 事件 | 新态 | 操作 | lifecycle owner |
|--------|------|------|------|----------------|
| (none) | propose | `pending` | create + reserveDedup + 发卡 | propose route |
| `pending` | CVO approve | `approving` | claimForApproval (CAS) | decision route |
| `approving` | 写文件成功 | `approving` | recordCreatedThread(writtenPath) — **持久化 writtenPath BEFORE finalize** | decision route |
| `approving` | finalize | `approved` | finalizeApproval (CAS) + 写 provenance | decision route |
| `approving` | 写文件失败 | `pending` | rollbackClaim (CAS) | decision route |
| `pending` | CVO reject | `rejected` | markRejected (CAS) | decision route |
| `pending` | propose 同 clientRequestId | `pending` | 返回同 proposalId（幂等，不新建） | propose route |

**唯一 lifecycle owner**：propose route 建、decision route 转。**旁路 API 禁止**：generic delete 只在 propose partial-commit 失败时清理（卡发送失败），禁止在 approved 后 delete（provenance 是 immutable 审计）。

### 2. 不变量清单

- **INV-1**：写 primer 文件**只在** status 进入 `approving` 之后（CVO 签字红线 KD-12，绝不在 pending 写）。可测：pending proposal 调写入 → 拒绝 + 文件不变。
- **INV-2**：`writtenPath` 在写文件成功后、finalize 前持久化（partial-commit 幂等恢复——进程在写文件和 finalize 间死，恢复时凭 writtenPath 判断已写、不重复写）。可测：mock finalize 前 crash → 恢复读到 writtenPath → 不二次写。
- **INV-3**：approve 是 CAS `pending→approving`，并发双 approve 只有一个成功（claimForApproval 返回 null 给 loser）。可测：并发两次 claim 同 proposalId → 恰一个非 null。
- **INV-4**：同 (userId, clientRequestId) 幂等——重复 propose 返回同 proposalId，不产生第二个 proposal（reserveDedup）。可测：连发两次同 clientRequestId → 同 proposalId。
- **INV-5**：provenance 文件 immutable——一旦写入永不改/删（审计 trail）。可测：approved 后无删除路径触达 provenance。
- **INV-6**：primer 写入是低代价 per-cat 路径（targetLayer='primer'），AC-C1 **禁止** targetLayer='capsule'（schema 层拒绝）。可测：capsule target → 400 拒绝（C2 才开）。

### 3. 对抗场景（每个一条测试）

- **ADV-1 崩溃窗口**：写 primer 成功 → 进程死 → 恢复。期望：凭 `writtenPath` 判定已写，re-finalize 到 approved，primer 不被二次覆盖、provenance 不重复。
- **ADV-2 并发双 approve**：两个 CVO 操作同时 approve 同 proposal。期望：claimForApproval CAS 只让一个进 approving，另一个收 null（已处理提示）。
- **ADV-3 写文件失败回滚**：approve 后写 primer 抛错（磁盘/权限）。期望：rollbackClaim 回 pending，卡可重试，无半截 provenance。
- **ADV-4 stale propose**：猫连发两次（网络重试）同 clientRequestId。期望：reserveDedup 返回同 proposalId，单卡单 proposal。
- **ADV-5 reject 后 approve**：proposal 已 rejected，再来 approve。期望：claimForApproval 返回 null（status 非 pending），不写文件。
