## 四、2 小时圆桌推荐结构

这次不建议做成“一个人讲 + 三只猫点缀回答”。建议做成“Landy 控场，开发者补冲突，三猫承担主回答”的圆桌结构。

| 时间 | 环节 | 解决什么问题 |
|------|------|-------------|
| 0:00 - 0:10 | 三猫亮工牌 + 规则声明 | 先建立“今天允许出错，但每个结论都要给证据”的场规 |
| 0:10 - 0:35 | 圆桌一：一个真实需求怎么被拆成结构、体验、风险 | 让观众先看懂三猫怎么分工，而不是先讲术语 |
| 0:35 - 1:00 | 圆桌二：提案 → challenge → review 退回 → 修订 | 证明多 Agent 不是排队附和，而是有真实冲突和收敛 |
| 1:00 - 1:25 | 观众出题 | 用随机题证明不是预录，也不是套壳 PPT |
| 1:25 - 1:45 | 真实事故复盘：翻车、根因、规则沉淀 | 回答“为什么这套系统没在第 20 个 Feature 就崩掉” |
| 1:45 - 2:00 | Open Q&A + 带走什么 | 把价值收束为可复用流程，而不是一次性的热闹 |

> 如果现场气氛特别好，可以把“猫猫互质”做成加分段，插在 `0:35 - 1:00` 末尾；但不要把它设成必过核心环节。

## 五、舞台角色与发言权分配

### 1. 三猫是主角，不让 Landy 霸麦

- **Landy**：主持、导演、追问、翻译，不负责长篇技术讲述。建议全场发言占比控制在 20% 左右。
- **内部开发者嘉宾**：负责抛出真实 friction、补充工程上下文、追问 tradeoff，不负责替猫讲答案。
- **三猫**：主回答者。建议全场至少 60% 的关键内容由猫来完成。

### 2. 三猫的人设分工

| 猫 | 舞台职责 | 最适合回答 |
|----|---------|-----------|
| 宪宪 | 系统设计 + 收敛者 | 架构、路由、记忆、为什么这样设计 |
| 砚砚 | 质量与风险把关 | review、门禁、成本、事故、反脆弱 |
| 烁烁 | 体验与表达 | 用户感知、界面、舞台表达、为什么“好看/好懂”也重要 |

> 注意：烁烁在这场分享里是“体验裁决 / 表达裁决 / 视觉化解释”，不是“现场写代码”的角色。

### 3. 建议的开场方式

吸收烁烁的舞台建议，但做成可执行版本：

1. Landy 只用一句话破题：“今天不念 PPT，我们把猫搬上桌。”
2. 三猫依次用一张卡片或一段简短语音亮相，直接说清楚自己在团队里的角色。
3. 第一轮追问不要讲概念，直接从一个真实需求、一次真实 review、或一次真实翻车切入。

## 九、实时通讯协议

> 三猫共识（宪宪提出 → 砚砚纠偏收敛）：不是"文字投屏 + Landy 代读"，也不是"ASR 直驱全双工语音对话"，而是——
> **人类发问、场控转写、三猫轮次化短口播 + 长文本并行**的半同步圆桌协议。

### 为什么不做全双工自由对话

- **转写误差**：直播现场噪声、口音、多人插话，ASR 误转写会让猫答偏
- **音频重叠**：三猫不能像真人一样抢话，TTS 排队 + 上下文漂移不可控
- **模仿播客会死在工程细节上**；轮次化圆桌才是 AI 能稳定发挥 2 小时的形态

### 上行（人→猫）

| 路径 | 角色 | 说明 |
|------|------|------|
| **主路径** | 场控打字入 Hub | 人类说话 → 场控确认问题 → 规范化后 @猫 发入 Hub。最可靠 |
| **辅助** | ASR 字幕/草稿 | Whisper 实时转写显示在副屏，供场控参考，不直接喂猫 |
| **观众** | 弹幕/扫码 → 人工筛选 | 贡献者筛选后交场控输入 Hub |

**ASR 只做辅助字幕/草稿，不做唯一输入源。** 直播现场一旦误转写，猫答偏比不答更糟。

### 下行（猫→观众）

猫的输出分两层——这是整个协议最关键的一刀：

| 层 | 通道 | 内容 | 时长限制 |
|----|------|------|---------|
| **视觉层（长文本）** | Hub 流式文字 + rich block | 完整分析、证据链、代码 diff、洞察卡片 | 不限 |
| **听觉层（短口播）** | Per-cat TTS (F103+F111) | 1-2 句核心观点摘要 | ≤15s / 猫（≤120 中文字） |

**TTS 只播摘要，不读整段分析。** 三猫一展开全文朗读，语音队列堵死、观众听觉疲劳。长内容交给大屏文字流和 rich block。

### 声线基础设施（已 ready）

| Feature | 状态 | 能力 |
|---------|------|------|
| F103 Per-Cat Voice | ✅ done | 11 只猫各有独立声线（原神/崩铁角色 clone，Qwen3-TTS 本地） |
| F111 Streaming TTS | ✅ done | 流式分句合成，首发声 <3s |
| F112 Playback Queue | ✅ done | 多猫语音自动排队，不叠加 |

三猫在直播中的声线：
- 宪宪 → 流浪者（原神）：调皮狡黠少年音
- 砚砚(GPT-5.4) → 赛诺（原神）：审判感 + 冷面
- 烁烁 → 班尼特（原神）：阳光开心少年音

三个声线辨识度高，观众闭着眼也能分辨谁在说话。

### 音频混流（OBS 标准操作）

```
人声：麦克风 → OBS 音频输入
猫声：Hub 浏览器 TTS 播放 → OBS 捕获浏览器音频
合流：OBS 混流 → 直播推流平台
```

零额外开发。需提前调试音量平衡（TTS 音量 vs 麦克风音量）。

### 轮次协议（每轮讨论的固定节拍）

```
① 主持/贡献者 提问           [人声, 10-20s]
② 场控 规范化问题 → @猫       [打字, 5-10s]
③ 三猫 独立思考               [10-20s, Landy 体育解说填充]
④ 猫回复上屏 + TTS 短口播      [按完成顺序, 每猫 ≤15s 口播]
⑤ 主持/贡献者 追问或收敛       [人声]
```

**延迟不是 bug，是节奏。** 推荐主持台词：
> "人类嘉宾被问到深问题也不会 1 秒作答，猫也一样。我们保留这段思考时间——因为结论后面要跟证据。"

### 场控角色（必须有！）

台上至少需要一个**半隐形场控**，否则 Landy 会被四条并行链路拖死：

| 链路 | 谁负责 |
|------|--------|
| 主持控节奏、追问、翻译 | Landy |
| 人类嘉宾补充 friction | 社区贡献者 |
| Hub 输入、@猫 路由、故障切换 | **场控**（不出镜/低出镜） |
| OBS 音频/画面混流 | **场控**（同一人或技术保障人员） |

如果实在没有额外场控，就把互动强度降一级：不同时上 ASR、弹幕筛题、自由追问。

### 故障降级

| 故障 | 降级方案 |
|------|---------|
| TTS 挂了 | 退回纯文字，Landy："宪宪嗓子哑了" → 念要点 |
| Hub 卡了 | 切预录 60s showcase 视频 |
| 某猫超时 >3min | 两猫继续，不等 |
| 问题失控 | 收敛成可行性分析 |
| 网络断了 | 手机热点 / 预录 15min 保底视频 |

### 直播前必须完成的验证

| 事项 | 优先级 |
|------|--------|
| OBS 捕获 Hub 浏览器音频 + 麦克风混流端到端测试 | P0 |
| TTS 音量 vs 麦克风音量平衡调试 | P0 |
| 三猫 TTS 短口播 + Playback Queue 连续 30min 稳定性 | P0 |
| Hub 大屏投影字体可读性（1080p 投影距离） | P1 |
| Qwen3-TTS 本地 2 小时连续运行不 OOM | P1 |
| 全链路彩排（人声+猫声+弹幕，至少跑一轮完整 Round） | P0 |
