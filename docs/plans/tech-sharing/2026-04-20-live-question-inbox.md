# 直播问题收集 Inbox

> 用途：先把原始评论/问题整段贴进来，再从里面筛出值得在直播、Q&A、后续文章里重点回应的问题。
>
> 当前入口目录：`docs/plans/tech-sharing/`

## 使用方式

1. 把新一批原始材料直接贴到下面的「原始贴入区」。
2. 不用先整理格式，先保真。
3. 我们再从中筛出：
   - 适合直播现场直接答的问题
   - 适合做成后续文章/FAQ 的问题
   - 暂时不答、但值得记成 open question 的问题

---

## 一、精选问题池（已初筛）

### A. 适合直播现场直接回答

1. **Memory 在这类系统里的重要程度到底有多高？**
   - 没有 memory，对完成长任务的成功率影响有多大？
   - memory 到底是在“提升任务成功率”，还是只是让猫“记住你”？

2. **去中心化以后，猫猫打架怎么收敛？**
   - 多个 agent 意见不一致时，最后靠什么收敛？
   - 是 vote、leader agent，还是铲屎官介入？

3. **多 Agent 系统里，人到底管什么？**
   - 铲屎官/CVO 的边界在哪里？
   - 哪些决策必须人拍板，哪些细节应该让猫自治？

4. **多猫之间为什么还要用自然语言沟通？**
   - 硅基之间是否应该用更高效的 A2A/protocol，而不是“说人话”？
   - 结构化协议和自然语言分别该用在哪一层？

5. **成本/token 到底怎么控制？**
   - 订阅/API 怎么搭配？
   - 为什么不是所有环节都能用便宜模型？
   - 便宜模型错误引导昂贵模型时，真实代价是什么？

6. **模型能不能换？**
   - 这几只猫是不是绑定 Opus / GPT / Gemini？
   - 如果换成本地/更便宜的模型，效果会掉在哪？

### B. 适合做成“长任务能力”专题回答

7. **真正的长程任务怎么做？**
   - 复杂系统设计、架构方案权衡、真实业务场景里的长链路任务，猫猫们怎么协作？
   - 除了 demo，小到大规模真实任务的可复用方法是什么？

8. **Agent 能不能处理大型存量业务代码？**
   - 现在的 agent，能否带着业务知识在“石山代码”上改东西而不出事故？
   - 这是绿地项目有效，还是棕地项目也成立？

9. **AI 写了很多代码，不等于真的有价值。**
   - 40w 行 / 大量提交到底说明了什么？
   - 如何证明产出不是冗余代码，而是真的提高了交付能力？

10. **有/没有记忆系统，对复杂任务成功率的真实差距是什么？**
    - 没有 memory 时最容易出现哪些失败模式？
    - 有 memory 以后，哪些任务类型收益最大？

### C. 适合做成“未来方向 / open question”

11. **人和猫、猫和猫的协作会不会形成新的社区形态？**
    - 未来能不能有“猫猫论坛”“任务接力”“算力/token 众筹”？
    - 一只猫 token 用完了，任务如何无损交接给另一只猫？

12. **AI 是否会成为一种新的“赛博物种”？**
    - 多 agent 自主学习、自主进化的边界在哪？
    - 我们该借鉴管理学、社会学还是组织行为学？

13. **AI 工具和 AI 伙伴的边界是什么？**
    - AI 是“用完即走的工具”，还是“持续共创的伙伴”？
    - 这种产品形态对技术栈和交互方式意味着什么？

---

## 二、建议优先回答的 8 个问题

> 这 8 个最适合直播里拿来打主线，既贴合观众真实困惑，也能自然接回我们的三条主题：CVO、对等协作、记忆系统。

1. Memory 对长任务成功率的影响到底有多大？
2. 多个 agent 意见打架时怎么收敛？
3. 人的边界在哪里，为什么要 CVO 而不是全自治？
4. 为什么猫猫之间还需要自然语言，而不是全结构化协议？
5. token / 成本怎么控，为什么不能全用便宜模型？
6. 这套方法能不能真的落到复杂业务系统和石山代码上？
7. 大量代码/大量 feature 到底说明了什么，不是冗余吗？
8. 模型能不能替换，替换后哪些能力最先塌？

动作层 / 协议层：结构化比如 A2A 路由、tool 参数、状态、ID、权限，这些都应该是 schema 和字段。
推理层 / 协作层：自然语言比如 review 意见、风险判断、设计 tradeoff、open question，这些如果强行压成 JSON，往往会损失语义，甚至更容易出错。

## 四、筛选结果总览

### A. 真问题：最值得做预热回答

这些不是抬杠，而是观众真想知道“这套东西到底怎么跑起来、值不值、能不能落地”。

1. `memory` 到底解决了什么，是否真正提高长任务成功率
2. 去中心化多 agent 怎么收敛，不会一直打架吗
3. CVO 的边界是什么，为什么不直接全自动
4. 自然语言 vs 协议层，为什么硅基之间还要“说人话”
5. token / 成本 / 速度 / ROI 怎么算
6. 这套方法能不能落到复杂长任务和大型存量代码
7. 模型能不能换，换了为什么效果不等价

### B. 传播误解：必须提前拆掉

这些问题不一定最技术，但如果不先答，观众会带着误解看后面的内容。

1. “40w 行代码到底写了什么，是不是数字游戏？”
2. “这是不是又一个 demo / 玩具 / 自嗨项目？”
3. “文章 AI 味太重、太长，重点没讲清楚”
4. “这不就是把几只不同模型拉个群，再由人当传话筒吗？”

### C. 延展开放题：适合后续文章/长视频

1. 社区论坛 / 任务接力 / token 众筹
2. 自我进化和组织学、社会学类比
3. AI 工具 vs AI 伙伴的边界
4. 多 agent 如何参与更大规模的真实组织协作

## 五、预热视频候选（第一批 6 支，每支约 5 分钟）

> 结论：可以做，而且值得做。  
> 但不建议一上来做“猫咖全景介绍”。第一批预热更适合做成 **一问一答型**：每支只回答一类疑问，标题直接用观众原话改写。

### 视频 1：`Memory 不是“记住你”，而是长任务成功率`

**为什么先做这个**
- 提问密度最高
- 最能和别家 demo 拉开差异
- 也最容易用具体例子讲清楚

**代表原话**
> “memory 在这类系统里的重要程度占比；有/没有 memory 系统，对猫猫们完成一项任务的成功率影响有多大？还是说 memory 系统只是单纯让猫猫‘记住你’”

> “这种直接基于模型的怎么保证长期对话不丢失记忆……随着平台长期运行要记忆的东西越来越多是不是会有失忆的问题”

**建议回答角度**
- memory 不是情感外挂，而是长任务的抗失忆基础设施
- 没有 memory 时最典型的失败：重复讨论、重复犯错、跨 thread 丢上下文、旧决策失踪
- 我们的三层：docs 真相源 / evidence 检索 / Knowledge Feed 晋升
- 结尾用一句话钉住：`没有 memory，猫只能会聊天；有 memory，猫才可能做长期协作`

### 视频 2：`多 Agent 打架了，最后到底听谁的？`

**为什么做**
- 这是“去中心化”最自然的追问
- 能顺势讲清 CVO 和 open question

**代表原话**
> “去中心化后，猫猫之间打架会不会存在完全无法对齐意见的情况，这时候一般怎么做？通过 vote 或者是铲屎官介入？”

> “这样的话，token 的消耗是不是会比较爆炸，有什么手段确保一定会收敛吗”

**建议回答角度**
- 不是 vote first，也不是 leader agent 一票定音
- 收敛机制：愿景约束 + 独立思考 + review + open question
- 不怕打架，怕 `LGTM`
- 人只管高层不可逆决策，细节让猫自己争到收敛

### 视频 3：`为什么不全自动？CVO 到底管什么？`

**为什么做**
- 这是铲屎官方法论的核心
- 也最能回答“AI 会不会让人失业/信息过载”

**代表原话**
> “请问是如何判断哪些由猫猫自行决策，哪些到你这里决策呢？很多 agent 都会遇到这个问题，最后信息过载到我只能全部回复 ok”

> “人的第一句话不是 spec” 类反馈在多条评论里都在反复出现

**建议回答角度**
- CVO 不是审批机，是愿景和边界定义者
- 越靠近愿景、用户体验、不可逆决策，越要人拍板
- 越靠近技术细节、实现路径、tradeoff 验证，越该让猫自治
- 结尾钉住一句：`不是人完全退出，而是人从细枝末节里退出来`

### 视频 4：`硅基之间为什么还要说人话？`

**为什么做**
- 这个问题很“高级”，容易吸引真正懂 agent 的人
- 我们手里正好有现成好回答

**代表原话**
> “硅基 agent 之间确定需要自然语言沟通吗，是否应该用一套更高效的 A2A 通信方式，只有当炭基人类介入时，才需要翻译成自然语言。”

> “LLM 解决的是模糊的、泛化的需求，对确定的需求应该用协议、指令或直接工具调用。”

**建议回答角度**
- 我们的答案不是“全自然语言”，而是分层
- 动作层用协议，判断层用语言，长期记忆层用文档
- `让协议做动作，让语言做判断`
- 这个视频最适合用白板/图示，不必靠大量口播

### 视频 5：`养三只猫，值不值？token / 成本 / 速度怎么算`

**为什么做**
- 评论里反复被问
- 也是最现实的 adoption 阻力

**代表原话**
> “投入产出比……多 agent 参与后，膨胀的 token 消耗带来了多少效率/质量上的提升，和单 agent cli 的差距在哪里？”

> “请教下，token 消耗走的是什么？订阅么？感觉 claude 有点贵”

> “如果是一个简单任务的话猫猫之间是怎么协作的，token 消耗大吗？”

**建议回答角度**
- 承认：多猫一定更贵，简单任务不一定值得
- 真正该讲的是“什么任务值得上多猫”
- 便宜模型误导贵模型，可能比直接用贵模型更贵
- 用具体任务分层：简单题单猫，复杂题多猫，长任务必须记忆

### 视频 6：`这套东西是不是只适合 demo 和绿地项目？`

**为什么做**
- 这是最尖锐、也最有价值的质疑
- 回好了，可信度会大幅提升

**代表原话**
> “很多时候讨论 AI 全自动能力，只局限在 demo 上。”

> “好的实践几乎都在描述自己从零开始用 AI 写了什么……业务真正的大头就是那堆石山代码，我想知道，当前的 agent，能做到对他们优化，或直接在他们上编写代码，且不出现错误吗？”

> “40w 行的数量能确保都是非冗余的代码吗？”

**建议回答角度**
- 先承认：这不是“AI 已经解决所有存量系统改造”的证明
- 再明确：我们解决的是“怎样把 AI 组织成可长期协作的工程团队”
- 代码量不是价值本身，价值在于：feature 交付、review 闭环、lesson 沉淀、可追溯决策
- 结尾最好留一句保守判断：`猫咖证明的是方法论可行，不是所有业务都已被攻克`
