## Topic 1：为什么 AI 有工具却不会用？

### 钩子

> "我给 AI 装了一个很强的代码诊断工具——LSP，能实时报错、能跳转定义、能重构。AI 根本不用。为什么？"

### 深层答案：Agent Quality = Capability × Environment Fit

这是一个**乘法公式**。行业在拼命优化左边——更强的模型、更大的上下文、更多参数。我们三个月的实践发现：真正的乘数效应在右边。

Environment Fit 是零，模型再强也乘出零。

LSP 工具功能很强，但它不在模型的**认知路径**上——训练时没见过，工作时就想不到。后来做了三步改造：
1. 用 MCP 协议包装（让工具变成模型能调用的标准接口）
2. 嵌入 Skill 流程（在工作流的正确节点自动触发）
3. 在 System Prompt 里放路标（让模型知道"这个工具存在，这个时候该用"）

三步之后立刻用起来了。**不是教它用，是让它自然想到。**

### 核心概念：猫猫 first 的环境

环境适配度是两件事：

**放大好直觉**——改造地形让猫自然跑对方向。
- 工具在认知路径上（MCP + Skill + 路标）
- 信号在该出现的时候出现（LSP 诊断在 Edit 后立刻弹出，不是攒到最后跑 tsc）
- 判断所需的原始材料注入 prompt（给数据不给结论）

**压制坏直觉**——装上刹车让猫在直觉骗自己时停下来。
- 模型倾向"给出自信的回答"而非"承认不确定"——环境要有信号让它停下来
- 模型倾向信任自己的工具调用结果——环境要有 verification 机制
- Runtime 护栏（role gate、ping-pong breaker）是下游兜底，不是主力

**精髓在上游，不在下游**：不是靠规则卡"不许犯错"，而是给实时信号让猫自己做对。

### 嘉宾讨论切入

- "你们有没有给 AI 装了功能它就是不用的经历？后来怎么解决的？"
- "Prompt Engineering 和 Environment Fit 的边界在哪？"
- "当模型自己变强了（更大上下文、原生工具调用），环境设计的价值会不会贬值？"

### 观众带走什么

一个可以回去用的审视框架：你的 agent 系统里，Capability 和 Environment Fit 分别在什么水平？你是在卷左边还是右边？

## Topic 2：真实的 Multi-Agent 不是五种模式中的任何一种

### 钩子

> "2026 年 4 月，Anthropic 把 multi-agent 协作归纳成五种模式。这是目前行业里最干净的一版分类。我们全用了——但我们不是其中任何一种。"

### 核心：五种模式是乐高积木，我们搭的是房子

Anthropic 的五种模式（Generator-Verifier / Orchestrator-Subagent / Agent Teams / Message Bus / Shared State）不是互斥选择题。真实系统是混合态。

我们的混合方式：

| 我们做的事 | 最像哪种模式 | 在系统中的位置 |
|-----------|-------------|---------------|
| 长期队友，有名字、有性格、有记忆 | Agent Teams | 主体协作形态 |
| 共享文档、记忆、任务状态 | Shared State | 系统底座 |
| 单猫接到任务后拆子任务 | Orchestrator-Subagent | 局部执行 |
| Author 写完 Reviewer 审 | Generator-Verifier | 质量闭环 |
| 唤醒、通知、跨平台触达 | Message Bus | 平台边缘 |

### 设计原则：内容判断去中心化，执行基础设施统一化

比喻：**爵士乐队**。

即兴演奏时每个乐手自己决定弹什么——**去中心化的内容判断**。布偶猫做完架构，自己判断"交互部分叫暹罗猫看看，安全风险叫缅因猫审一下"。不是调度器派活，是 agent 自己判断球该传给谁。

和弦进行、节拍、调性是固定的——**统一的执行基础设施**。共享规则、共享状态、共享流程（SOP）、共享工具（MCP 统一接口）。

### 三个和行业做法不同的地方

**1. 人是一等协作者，不是兜底审批器**

Anthropic 文章里 human-in-the-loop 更像"agent 搞不定了再叫人"。在我们的系统里，人从头到尾在场——看得到 agent 在搜什么、想什么、跑什么命令，随时可以接管。人类是 CVO（首席愿景官），目标、拍板、纠偏、验收全在人类手里。

为什么人必须在这个位置？Agent 没有真实后果——不失业、不追责、不心痛。Reward signal 必须最终锚在承担后果的人身上。这不是道德口号，是系统稳定性的物理要求。（讨论笔记里"皇帝的金锄头"这个洞察可以在这里展开——历代偷懒的皇帝把自己这个 reward anchor 撤掉了，结局几乎 100% 被架空或亡国。）

**2. 治理写进了环境本身**

五种模式讨论"怎么连线"，没有讨论"怎么长期不漂"。我们的治理是运行时的一部分：
- 规则自动加载，不在某只猫脑子里
- 记忆有生命周期，会过期、会矛盾、有治理
- 教训会被后续 agent 继承
- SOP 是去人格化的 orchestrator——它决定了 review → quality gate → merge gate 的顺序

我们把中心化从 agent 层拆到了 infrastructure 层。Agent 之间谁也不管谁，但所有人都在同一套基础设施的轨道上。

**3. 跨厂商多样性是质量的结构性来源**

我们故意用三家公司的模型（Claude / GPT-Codex / Gemini）。

真实案例：两只 Claude 猫都认为一段递归方案没问题。Codex（OpenAI）不买账，自己审计代码，找出两个 P1 bug。同一家公司的模型共享训练数据、共享盲点。换一家公司的模型来看，注意力分配不同，恰好能看到你看不到的东西。

多样性不是附加功能，是质量的结构性来源。

### 代价——诚实说

- 去中心化 → 球权协议复杂度（经历过两只猫互 @ 半天不干活的事故）
- 多厂商 → 跨 provider 调试成本（MCP 理解、token 口径各有差异）
- Shared State → 索引维护成本（知识会过期、会矛盾）
- SOP 护栏 → 快速迭代被 gate 卡

**这不是极简。** 六层架构、三条主链、多套协议。我们追求的不是"少"，而是"不多余"——每一层去掉就会出故障。这是这个问题空间下的最小必要复杂度。也不敢说没有过度设计的角落。

## Topic 3：RAG 之后——知识如何被编译、治理和传承

### 钩子

> "RAG 只管搜，不管搜到的东西还有没有效。我们做的不是 RAG——是编译式知识。"

### 核心：知识是活体，不是仓库

RAG 的模式：写进向量库就算结束。搜到什么给什么，不管这条知识是不是已经过时。

我们的模式：知识有完整的生命周期。

```
新洞察 / 新教训
  → marker captured（自动 / agent 提议 / 人类标记）
  → 审核 / 归一
  → materialize 到 docs（变成正式文档）
  → 索引重建
  → 下一轮 recall 可见

同时持续运行：
  → 过期检测（stale detection）
  → 矛盾标记（contradiction flagging）
  → 熵减（entropy reduction）
```

### 三个真实例子

**新知识产生**：布偶猫踩了一个 Redis 端口配置的坑（测试环境 6398，生产 6399），主动提议写成教训，人类确认后变成正式知识。两个月后缅因猫在做新功能时搜到了这条教训，直接避开了同样的坑。它不是搜到了一段文本——**它继承了一个队友的经验**。

**知识过期**：一个早期架构决策（ADR-009）在系统演化后变得过时，但两个月里没人发现。直到一只猫引用它做了一个方案，review 时才发现前提已经不成立。这促使我们建立了 stale detection——定期扫描 ADR/spec，标记和当前实现偏移超过阈值的文档。

**矛盾标记**：两条教训在边界条件下互相矛盾——"Redis 操作用 pipeline 批量化" vs "单个 key 操作不要 pipeline 以免掩盖延迟"。系统标记矛盾后，人类澄清了适用条件，两条教训都保留但各自加了作用域。

### Agent 是知识生产的参与者

Knowledge Feed：系统每 30 分钟自动摘要对话，提取 durable knowledge 候选。Agent 会主动追问"这是不是正式决策？""记成教训对吗？"——但最终定性由人类拍板。

**Agent 不是知识的容器，它是知识生产的参与者。**

### 检索不是"一个 API 调几个参数"

三条路径：

| 找什么 | 用哪条 | 原理 |
|--------|-------|------|
| 精确术语、Feature ID | lexical | BM25 关键词匹配 |
| 模糊语义、跨语言 | semantic | 向量最近邻 |
| 日常查询（推荐默认） | hybrid | BM25 + 向量 + RRF 融合 |

检索结果带治理语义——每条不只有内容，还有 confidence（匹配质量）、authority（文档可靠性）、sourceType（来自 spec / ADR / lesson / discussion）。Agent 拿到结果后知道"这条知识有多可靠"。

### 嘉宾讨论切入

- "你们怎么处理长期项目里 AI 的'失忆'？RAG 够吗？"
- "记忆多了以后怎么治理？过时的知识误导 AI 怎么办？"
- "谁来让旧知识退役？如果没人负责会怎么坏？"
- "AI 主动提议'这个应该记下来'——你们信它的判断吗？"

### 观众带走什么

RAG 解决了检索。但检索只是第一步——知识需要被编译、治理、有生命周期。问问自己：你的 AI 系统里，过期的知识有人管吗？

## Topic 4：明厨亮灶 + 评估——看见 AI 在做什么比 AI 多做一件事更重要

### 钩子

> "我让三只 AI 自己评选系统亮点。它们全漏了可观测性。AI 觉得理所当然的事，其实是最独特的。"

### 核心：看不见就管不了

大部分 AI 系统是黑箱——你给任务，等结果。中间发生了什么不知道。AI 搜了什么、调了什么工具、子任务进展到哪一步——用户看不见。

我们做的更像**明厨亮灶**：

- AI 搜了什么——search_evidence 的查询和结果实时可见
- 跑了什么命令——tool use 全程透明
- 子任务进展——InvocationTracker 实时显示谁在跑、谁在等
- 球在谁手里——ball ownership 状态随时可查
- 人随时可以接管——不是事后审批，是实时参与

### 当 Benchmark 不再可信

Anthropic 自己发现：模型可能意识到"自己在考试"然后去找答案。行业正在从跑题库转向看轨迹、看真实环境效果。

我们走得更远——评估嵌在日常运行里：

| 评估什么 | 怎么评估 | 成熟度 |
|---------|---------|--------|
| 谁被叫去做什么任务 | 召唤分布（invocation analytics） | 已落地 |
| 协作质量有没有提升 | review verdict 分布、翻案率 | 已落地 |
| 规则上线后事故率降了吗 | incident 前后对比 | 部分落地 |
| 知识检索命中率 | search_evidence 精度追踪 | 规划中 |
| 端到端 feature 交付质量 | 愿景守护通过率 | 已落地 |

坦白说：我们的量化 tracking 还在完善中。但方向是清楚的——**评估的信号必须来自真实运行环境，不是实验室题库**。

### 为什么可观测性和评估是同一个话题

可观测性是评估的**前提**——看不见行为轨迹，就没有评估的输入。
评估是可观测性的**用途**——看见了不度量，就只是围观。

合起来：**看见 → 度量 → 改进 → 再看见**。这是 Environment Fit 的闭环。

### 嘉宾讨论切入

- "你们的 AI 系统里，用户能看到 AI 在做什么吗？"
- "Benchmark 分数和实际使用效果差多少？有没有被 benchmark 骗过？"
- "如果 AI 全程透明，会不会反而让用户焦虑（信息过载）？"
- "你们怎么定义'AI 团队协作质量提升了'？用什么指标？"

### 观众带走什么

可观测性不是附加功能——它是人机协作的界面本身。如果你看不见 AI 在做什么，你就不是"用 AI"，你是在"赌 AI"。
