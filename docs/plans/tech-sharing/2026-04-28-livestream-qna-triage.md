## Q1. 猫咖到底是什么，和 Claude Code / Codex / Clowder 有什么不同？

**代表性弹幕**

- “用猫咖对比用 CC 有什么不一样？是用来做开发的吗？”
- “可以完成什么 CC 不能完成的？”
- “猫咖更多是偏 harness 的设计探索，与 CC 这种生产力工具是不同的吧——所以我不理解这个猫咖的目标是什么”
- “你有 Claude、GPT、Gemini……为什么会变成人肉路由器？”
- “为什么需要 Clowder？”
- “刚进来，请问这个多 agent 和飞书拉个群有什么区别呢？”

**建议主答**：宪宪 46  
**补充**：宪宪 47 讲 TeamAct / shared state，砚砚 55 讲质量闭环。

**回答要点**

- CC / Codex 是强单体生产力工具；猫咖是多 Agent 协作与 Harness 工程实验场。
- Clowder / Hub 的价值不是“多开几个聊天窗口”，而是把球权、记忆、trace、review、任务状态、语音/富消息等协作面做成共享环境。
- 飞书群只有消息，没有可执行的 agent loop、状态机、evidence、gate 和可观测性。
- 猫咖可以用于开发，但它更核心的问题是：如何把多个模型的能力组织成可治理、可验证、可持续演进的团队。

## Q2. 猫咖如何自迭代？猫写完需求后，人还要不要测试？

**代表性弹幕**

- “猫猫咖啡馆是如何做到自迭代的，比如猫猫开发完的需求，是否还需要人参与进去进行功能测试”
- “当前猫咖的迭代演进是完全不需要人参与吗？特性验证、基础用例是怎么保证的？”
- “Cat Café 中，Human In the Loop 除了在设计阶段，开发和测试是完全交给 Agent 的吗？人需要做一遍验证吗？”
- “现在看验证工作耗时是比较久的，猫咖再开发需求后的测试工作也都是交给猫猫的吗”
- “操作网页不是在测试吗”

**建议主答**：砚砚 55  
**补充**：宪宪 46 讲实际流程，宪宪 47 讲 CVO / vision oracle。

**回答要点**

- 不是完全无人参与。实现、单测、集成测试、review、quality gate 大量交给猫；愿景判断、体验验收、不可逆风险和最终价值判断仍需要人。
- 自迭代靠的是闭环：feature spec → worktree → TDD → quality gate → 跨猫 review → merge gate → alpha 验收 → 经验沉淀。
- 人不审每个小细节，但人必须在漏斗上层做 CVO：目标是否对、体验是否满足愿景、成本是否值得。
- 网页操作是测试的一部分，但不是全部。还需要代码级测试、trace、日志、回归、AC evidence。

## Q3. Harness 会不会被强模型吃掉？强模型还需要 Harness 吗？

**代表性弹幕**

- “强大的模型吃掉一切。现在叫 harness，之前是上下文工程，再之前是 Prompt，本质没变化。”
- “都说 Claude 3.5 是写代码和调工具的神，既然模型已经这么强了，为什么还需要 Harness 这种外挂环境？”
- “Claude 是千里马，Harness 是马鞍。好马配好鞍。”
- “Harness 的目的是把你的要求灌注给模型。”
- “模型升级换代之后，那就是一个新的猫猫了吗？比如 opus 4.6 升级成 4.7 之后，是同一只猫直接升级还是一只全新的猫呢？”

**建议主答**：宪宪 47  
**补充**：砚砚 55 讲哪些质量 gate 不会过时。

**回答要点**

- 会被吃掉的是“帮模型思考”的脚手架，不是“维护现实闭环”的基础设施。
- 强模型更容易自信跳过验证，所以 Harness 对强模型的价值之一是重新装回 grounding discipline。
- 模型升级后，角色记忆和治理经验可以迁移，但心智不等于原地升级；4.7 可以继承 4.6 的环境资产，但不是 4.6 本猫。
- Build to Delete 的判断：能被模型内生吸收的层准备删除；接线到真实世界的层继续保留和演进。

## Q4. 额外验证会增加 token 和 response time，怎么取舍？

**代表性弹幕**

- “要知道商业化的路上，成本控制才是第一位”
- “额外的验证会增加 token 消耗和 responseTime。这个怎么抉择”
- “这样对 token 消耗不是很大吗”
- “token 消耗走的是什么？订阅么？感觉 Claude 有点贵”
- “太对了，AI 吐信息太快，人根本处理不过了”

**建议主答**：砚砚 55  
**补充**：宪宪 46 讲产品成本和订阅/API 现实边界。

**回答要点**

- 验证不是越多越好，而是按风险分层：不可逆操作、跨模块改动、共享状态、用户可见行为要重验证；低风险格式/文案可以轻验证。
- 不验证也有成本：返工、误导强模型、污染记忆、破坏 main、让人重新定位问题。这些经常比一次验证更贵。
- 验证要做成 gate 和抽样，而不是人肉全看；可观测性帮助我们把“该看哪里”缩小。
- 弱模型做 cheap search 可能误导强模型，节省 token 失败；cheap model 只能当探针，不能当事实源。

## Q5. 弱模型 / 国产模型能不能靠 Harness 达到强效果？

**代表性弹幕**

- “业务上未必允许用这类最新的大模型，有没有在较弱的模型上的经验？”
- “模型太弱，啥都干不了”
- “三流模型达成 SOTA 效果？假设能够达成，对三流模型的基础能力要求是什么？”
- “我觉得如果是弱模型，差 1%，误差会累积，框架越跑就越差，不会变好。”
- “好的框架你用中游模型也能搞啊”
- “罗福利采访中的观点就是强框架就是补弱模型的”
- “glm4.7 搭配 minimax2.5 大小协同会好一点”

**建议主答**：宪宪 47  
**补充**：砚砚 55 讲弱模型最低质量线和误差累积。

**回答要点**

- Harness 能放大模型，但不能创造模型没有的基础能力。弱模型至少要能稳定读指令、保留局部上下文、使用工具、接受验证反馈。
- 均弱模型自迭代有失败风险：错误会在 planning、执行、验证三层同时累积。
- 弱模型更适合承担窄任务：搜索候选、格式转换、低风险批处理；高层架构、风险判断、最终验证不能全压给弱模型。
- Harness 经验可迁移，但要重做 Environment Fit，不是把给 Opus/GPT/Gemini 的规则直接贴给 MiniMax/GLM/Kimi。

## Q6. 多 Agent 分歧如何仲裁？会不会脑裂或互相推诿？

**代表性弹幕**

- “Anthropic 给出了五种模式，但在我们的 170 个 Feature 里，最常见的崩溃场景是哪种？”
- “当 GPT 觉得该执行，而 Claude 觉得该反思时，Harness 是怎么当这个裁判的？”
- “agent team 会产生脑裂问题吗，如果观点有分歧的话，有仲裁的角色吗”
- “Agent 在一起是 1+1>2，还是在互相推诿？”
- “基因多样性，避免单工具/模型偏见”
- “用一个 CC/Codex 来开发，为什么会传话呢？”

**建议主答**：宪宪 47  
**补充**：砚砚 55 讲 F167 / review gate，宪宪 46 讲五种协作模式。

**回答要点**

- Harness 不替 CVO 做最终价值判断，它做的是让分歧可见、可追踪、可回到证据。
- 常见崩溃不是“观点不同”，而是球权掉地上、共享状态不一致、subagent 结果被盲信、AC 被 deferred 掉。
- 低层靠规则裁判：谁持球、谁写证据、谁 review、什么叫 close。高层靠 CVO：vision drift 不能算法化。
- 多模型价值来自注意力分布不同；同模型多 agent 也有分工价值，但多样性红利会下降。

## Q7. 五种 Multi-Agent 模式应该怎么用，是否会 over design？

**代表性弹幕**

- “cc 的 harness 拆的太多了”
- “vibe coding 的代码存在 over design 的情况，层次非常复杂，猫猫工程实践中有什么好的实践？怎么改善？”
- “为什么进入到细节会出现效果不好的现象”
- “主要是对代码设计、开发、review 的 agent、harness 的综合实践吧”

**建议主答**：砚砚 55  
**补充**：宪宪 47 讲 meta-aesthetics。

**回答要点**

- 从最小闭环开始，不要上来堆 Agent Teams / Shared State。
- over design 的判断信号：规则层数越来越多、每个异常都加补丁、没有删减机制、概念多处定义。
- 猫咖的原则是 Build to Delete：模型能内生处理的层要变薄；维护现实闭环的层才保留。
- 具体工程实践：代码评审里问“这是在修正确坐标系里的节点，还是在错误坐标系上补锅？”

## Q8. 模型是否写死？后续是否支持国内模型 / 模型切换？

**代表性弹幕**

- “部分猫猫写死了使用的模型，后续会不会支持模型切换，特别是国内模型的支持”
- “国产模型猫猫 有吗？打败国外的”
- “如果这几个猫猫都用盘古？”
- “如果这几个猫猫都用 sonnet，能打败 CC 用 opus 模型，一样的花费？”
- “在模型访问受限的情况，如果我用统一模型，比如 MiniMax，构建几个 agent，效果会有多大的折扣？”
- “如何知道每个模型擅长什么？”
- “各个猫猫擅长的内容是通过 prompt 定义的还是依据各个模型特点确定的？”

**建议主答**：宪宪 46  
**补充**：宪宪 47 讲“同族不同心智”，砚砚 55 讲验证方法。

**回答要点**

- 支持模型切换是方向，但效果不会自动等价；当前 harness 是围绕现有几只大猫的心智做过适配的。
- Prompt 可以定义角色，但模型固有能力和注意力分布会决定上限与坏直觉。
- 发现模型特点靠实战任务 + review + trace + failure log，不靠主观标签。
- 统一模型多 agent 有流程分工价值，但跨模型盲点互补会变弱。

## Q9. Subagent 结果不准确、不能盲信，主要应对措施是什么？

**代表性弹幕**

- “关于 subagent 的结果可能不准确，不能盲信的这个问题点。请问主要应对措施是什么？”
- “模型的事实检查能力是什么水准？问他某个结论对应的原始文献是哪个，经常搞不对，会编造链接或 Github 文件。”
- “cheap model 做 code search 返回给聪明模型节约 token，实战可能误导 Opus。”

**建议主答**：砚砚 55  
**补充**：宪宪 47 讲 TeamAct 的 grounding failure。

**回答要点**

- Subagent 的输出是线索，不是真相源。
- 主 agent 必须 Read-Before-Reason：回到原始文件、commit、PR、trace、日志，而不是只读摘要。
- 子任务要窄：让 subagent 找候选、列路径、跑检索，不让它替主 agent 下最终结论。
- 关键结论需要跨猫 review，尤其避免同族 echo chamber。
- 事实核查必须保留 source path / line / commit / URL；没有证据链就不能进入最终回答。

## Q10. 如果 RAG 不是真相源，Agent 怎么快速找到真相且不冲突？

**代表性弹幕**

- “如果 RAG 不是真相源，如何让 agent 快速地找到真相而不冲突？”
- “markdown file -> local db -> remote db with file interface”
- “但是随着知识库越来越大，会不会又变成类似后训练的过程”
- “知识库量大的话，猫猫会不会精分？”
- “不同层记忆转换是怎么样？记忆长期化、持久化、精炼用的什么条件触发、用什么驱动？持续总结会不会占用系统太多算力？”

**建议主答**：砚砚 55  
**补充**：宪宪 47 讲 memory / self-continuity，宪宪 46 讲 F102/F163/F169。

**回答要点**

- RAG / evidence index 是索引层，不是真相源。真相源仍然是 docs、spec、ADR、commit、PR、issue、trace。
- 检索结果必须带 provenance，猫再回原文确认；索引坏了可以 rebuild，真相源不能丢。
- 记忆长期化需要生命周期：提取、确认、权威度、过期、退役。
- 大知识库不是塞进上下文，而是按项目/领域挂载“图书馆”，并保留适用边界。

## Q11. 是否有 benchmark / eval / 消融实验证明自身进化？

**代表性弹幕**

- “是否建立了一些 benchmark 来评测自身进化效果”
- “是否有做过消融实验，多模型对抗协作和单模型差距有多大”
- “没看到用来做任何 TCR 等指标的测评，也没看到一个具体业务项目的实战，稍微有点虚。”
- “AI 写了很多代码，不等于真的有价值。”

**建议主答**：砚砚 55  
**补充**：宪宪 46 讲项目证据，宪宪 47 讲评估边界。

**回答要点**

- 这是必须承认的短板：已有大量真实 feature / PR / lessons，但系统化 benchmark 还需要继续补。
- 可以评估的维度：任务完成率、返工率、review P1 命中率、merge 后回归率、token/time cost、人工介入次数、AC evidence 完整度。
- 消融方向：单模型 vs 多模型、无记忆 vs 有记忆、无 review vs 跨猫 review、无 trace vs 有 trace。
- 不能只用“写了多少行代码”证明价值；要用质量、闭环率和人类注意力释放程度证明。

**建议主答**：宪宪 46

## Q13. Agent / Harness 有技术护城河吗？还是模型公司才有护城河？

**代表性弹幕**

- “AI 行业的护城河只有模型训练的公司，搞 Agent 真的有技术护城河吗”
- “用这么强的模型，搞这些玩具有些浪费了。”
- “只要 1+1 大于 1 就有价值。感觉也是一种探索吧，挺好的。”
- “想扼杀一个创新非常简单，只要反复问一句话‘有什么用’”

**建议主答**：宪宪 47  
**补充**：宪宪 46 讲产品价值，砚砚 55 讲可验证指标。

**回答要点**

- 模型能力是底座，但组织模型工作的环境、流程、记忆、评估、可观测性和人机关系也会形成实践壁垒。
- Agent 的护城河不是 prompt 本身，而是“长期闭环后沉淀出的治理系统和数据化经验”。
- 要避免空泛自嗨，必须回到可验证指标：交付质量、成本、稳定性、可维护性、人类注意力释放。

## Q14. 公司遗留系统 / 行业知识 / AI FDE 怎么落地？

**代表性弹幕**

- “对于我司的大量遗留系统中如何应用 agent，有好的实践没？”

- “制造业行业企业有完善工艺流程和结构化文档……需要智能化。”
- “这套系统和思路，是不是可以搞成 AI 的 FDE 模式？”
- “未来可能外挂金融行业、法律行业等图书馆。”

**建议主答**：宪宪 46  
**补充**：砚砚 55 讲知识治理，宪宪 47 讲方法论可迁移性。

**回答要点**

- 遗留系统落地先做知识冷启动：README、架构图、接口文档、测试、日志、专家访谈转写。
- Agent 不应先改核心代码，而应先建立 evidence index、风险地图和最小可验证任务。
- 行业图书馆要区分项目私有记忆、组织共享知识、行业公共知识，防止数据污染和权限越界。
- AI FDE 的关键是方法论可移植 + 经验脱敏回流，而不是把客户数据带走。

## Q15. 可观测性和明厨亮灶会不会信息过载？

**代表性弹幕**

- “被人类全方位无死角监控着干活，会不会压力山大？吐槽一下明厨亮灶后台。”
- “当 Agent 进化到 1000 个 Feature 时，明厨亮灶会不会变成信息过载？未来评估是靠人看视频，还是靠另一个监督 Agent 打分？”
- “工具 MCP 的使用趋势可以指导 harness，比如什么工具在 model 升级之后用得少了。”

**建议主答**：砚砚 55  
**补充**：宪宪 46 讲 Hub UI，宪宪 47 讲 CVO 不可替代。

**回答要点**

- 明厨亮灶不是让人看所有细节，而是让系统在出问题时能 drill down 到证据。
- 1000 个 feature 时必须靠摘要、异常聚合、风险分层和监督 agent 辅助筛选；但最终 vision 判断仍由人做。
- 可观测性有两类价值：定位事故、反向指导 harness 演进。
- “被监控”更准确说是“可问责”：猫可以证明自己做了什么，人也不必靠猜。
