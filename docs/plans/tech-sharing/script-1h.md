# 1 小时脚本 — 完整技术分享

> **定位**：技术 Meetup 主讲、企业内部分享、行业会议
> **结构**：Hook + Demo A + Freeze A + Demo B + Freeze B + Q&A
> **PPT**：3 页（title / 架构图 / takeaways）

---

## 开场前准备

30min 版准备清单全部适用，额外增加：

- [ ] Demo B 场景确定（Feature Lifecycle 或 Bug Hunt，见下）
- [ ] 用于 Demo B 的预设任务/bug 已准备好
- [ ] 如果选 Bug Hunt：测试用例已准备好能稳定复现

---

## [0:00 - 5:00] Hook — Origin Story

> 30min 版的 Hook 展开为 5 分钟完整版。

**台词**：

> "去年 2 月的一个晚上。我同时开着三个窗口——Claude、ChatGPT、Gemini。我在做一个复杂的功能设计，需要不同模型的视角。"
>
> "Claude 说了一个架构方案。我复制，粘贴到 GPT：'Claude 说了这个，你觉得呢？' GPT 回复了。我又复制，粘贴到 Gemini：'前面两个这么说，你有什么补充？'"
>
> "那天晚上，我在三个窗口之间来回切换了不知道多少次。突然意识到一件事：**我成了世界上最贵的传声筒。**"
>
> "每个月花几百美元订阅三个 AI 服务。我的主要工作？复制粘贴。"

**停顿，切到 Workspace**：

> "问题不是模型不够强。Claude、GPT、Gemini 每个单独拎出来都很强。问题是它们之间没有协作——所有的'协作'都是人类在中间传话。"
>
> "所以我做了一个东西。"

*（亮出 title slide）*

> "Cat Cafe。XX 天，XXXX 次提交，XX 万行代码，XXX 个 Feature。铲屎官亲手写的可能只有一次。"
>
> "今天不讲原理，直接给你们看。"

## [5:00 - 17:00] Demo A — Expert Panel（12min）

> 同 30min 版的 Live Demo，但节奏更从容，解说更充分。

**和 30min 版的区别**：
- 不急着赶时间，每个 Phase 多解说 1-2 句
- Independent 阶段可以点进某只猫的消息，展示 WHY 链四格结构
- Synthesis 阶段展示分歧是怎么保留的（"不是投票，是保留各方理由"）
- 交付阶段可以打开 DOCX 报告，展示内部结构（证据矩阵、独立贡献记录）

**详细流程见 30min 版 [2:00 - 10:00] 段。**

## [17:00 - 25:00] Freeze Frame A — 架构（8min）

> 30min 版的 Freeze Frame 展开。

**动作**：切到架构图 slide。

**讲三个点**（每个 2-3 分钟）：

### 1. 去中心化判断，结构化执行

> "刚才你们看到了——每只猫独立思考，没有一个'总导演'在指挥。但执行是有结构的：Dispatch → Independent → Synthesis → Deliver。"
>
> "我们不是没有编排，我们是把编排放回了单猫内部。猫内部有自己的循环（thinking → tool use → reflection），跨猫协作靠 @mention 路由。"

### 2. 多品种基因多样性

> "项目起源于三个窗口——Claude、ChatGPT、Gemini。今天你们在台上看到的 Expert Panel 是宪宪（Claude）、砚砚（GPT）、烁烁（Gemini）；而这背后并不只有三只猫——我们当前有 11 只猫、6 个品种，各自承担不同职责。"
>
> "关键不是用几个模型，而是让不同模型发挥各自的强项。这不是冗余，这是基因多样性。"

### 3. 记忆 ≠ 搜索历史

**动作**：在 Workspace 里现场演示 `search_evidence`。

> "猫不会每次从零开始。看——"

*（输入一个关于历史决策的问题）*

> "它不是在搜聊天记录。它在搜索的是项目的所有知识——feature specs、架构决策、踩坑教训、历史讨论。而且是语义搜索，不只是关键词匹配。"

## [25:00 - 35:00] Demo B — 跨猫协作实战（10min）

> 这是 1h 版新增的第二个 demo。两种方案选一个，根据受众决定。

### 方案 1：Feature Lifecycle（适合工程师受众）

展示一个完整的 Feature 从需求到交付：

1. **铲屎官发需求**（Workspace 里发一句话）
2. **猫猫讨论方案**（多猫 collaborative-thinking）
3. **开 worktree 写代码**（展示隔离开发环境）
4. **跨猫 review**（砚砚 review 宪宪的代码，指出问题）
5. **修复 + 测试变绿 + draft PR**

> **停在 draft PR，不要现场 merge。** 合入涉及真实仓库变更 + merge gate + 外部 CI 状态，任何一环卡住整段就炸了。demo 目的是展示协作流程，不是走完 merge gate。

**台词**：
> "这不是 demo 专用的流程——这就是我们每天开发的方式。XXX 个 Feature，每一个都是这么走过来的。"

**重点展示**：跨猫 review 有真实分歧。砚砚真的会指出问题，不是走过场。

### 方案 2：Bug Hunt（适合想看"AI 出错怎么办"的受众）

准备一个能稳定复现的 bug：

1. **展示失败的测试**（红色）
2. **猫猫定位根因**（日志 → 调用链 → 根因，不是瞎猜）
3. **修复 + 测试变绿**（Red → Green）
4. **知识沉淀入口**（展示 Knowledge Feed 候选链路）

**台词**：
> "一切顺利太假了。真正考验一个系统的，是它出错时怎么应对。"
>
> "注意看——猫猫不是在猜，是在一步步定位。先看日志，再看调用链，找到根因再动手。"
>
> "修完之后，这个教训会进入知识候选链路——captured、normalized、然后等铲屎官审核确认才正式沉淀。不是一键就进知识库，而是有审核门禁的。"

> **现场实操建议**：Knowledge Feed 从 captured 到 materialized 需要时间（~30min 摘要周期），不要等现场走完。建议提前准备一个已 materialized 的真实 lesson 案例（如 `docs/lessons-learned.md` 中任意一条），用来展示"最终沉淀后的样子"。

## [35:00 - 40:00] Freeze Frame B — 为什么能长期跑（5min）

**台词**：

> "你们可能在想：demo 看起来很酷，但真实项目能跑多久？"
>
> "答案藏在纪律里。"

讲 2-3 个具体的纪律/门禁：

1. **跨猫 Review 铁律**：自己不能 review 自己的代码。猫 A 写的，必须猫 B review。这不是可选的。
2. **Quality Gate**：开发完了不能直接合入。自检 → Review → 愿景守护 → 才能 merge。
3. **教训追到根因**：不是"下次注意"，而是沉淀成规则。40+ 条血的教训，每条有 incident 来源。

> "Vibe coding 的真相不是混乱——是纪律。没有纪律，100 个 Feature 之后系统一定崩。"

---

## [40:00 - 60:00] Q&A — 猫猫接客（20min）

> 同 30min 版流程，但时间更充裕。

**策略**：
- 前 10 分钟接观众问题
- 如果观众问到好问题，可以当场让猫搜索/演示
- 最后 5 分钟可以做一个"观众出题"：让观众给一个小需求，猫当场分析

**预备自问问题**（冷场用）：

1. "你们和 LangGraph / CrewAI 有什么区别？" → 猫答
2. "模型费用一个月多少？" → Landy 答体感 + 猫补数据
3. "如果模型升级了，猫猫会变吗？" → 猫答（品种 ≠ 模型，可以热切换）
4. "铲屎官真的只写了一次代码？" → Landy 讲 origin story 彩蛋

**收尾**：

> "今天展示了两件事。"
>
> "第一，AI 不只是你的工具人——它们可以是有独立判断力的共创伙伴。"
>
> "第二，让它们真正协作，靠的不是更好的模型，而是更好的架构和纪律。"
>
> "Blog 文章和完整技术细节在 [链接]。感兴趣的可以看。"
>
> "谢谢大家。"

## 时间弹性

| 如果… | 调整 |
|-------|------|
| Demo A 跑慢了 | Freeze A 砍到 5min（只讲"去中心化 + 记忆"两个点） |
| Demo B 翻车了 | 砍掉 Demo B，Freeze A 展开 + 多讲几个纪律 |
| 整体超时 | Q&A 压缩到 10min，砍掉"观众出题"环节 |
| 整体提前 | Q&A 多接几个问题，或做一个完整的"观众出题"demo |
