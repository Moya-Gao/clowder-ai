# F197 Reflection Capsule — ACP tool_result Event Surfacing

> Feature: F197 (ACP transformer 单事件拆双消息) | Completed: 2026-05-12

## What Worked

1. **Dogfooding 揭出真实 bug**：F188 Phase F 自己上线后，铲屎官跟 47 互动时实际跑 search_evidence → 发现 Recall sidebar 不亮 → 47 诊断 ACP transformer 漏 emit tool_result。**dogfood 是最有效的 alpha 验证手段**（vs 闭门 e2e 测试）。

2. **完整 SOP 流程在 hotfix scope 也值得走**：F197 是单文件 hotfix scope（acp-event-transformer.ts），看起来"明显"，但走完整 spec → 3 轮 Design Gate → PR review → 11 轮 review-iterate 后才稳。如果当初按 quick hotfix 偷渡，至少错过：
   - P1-1 ACP scope 写错（不是 Claude Code 是 Gemini）
   - P1-2 Gemini v0.36 实际格式是 tool_call(completed+content) 单事件不是 tool_call_update
   - P1-3 拆双消息约束（UI/ToolEventLog pending+pair 模型）
   - P2 finalEmittedByCallId 只写不读 → cross-event replay 重复 emit
   - Cloud final-without-content + tool_call(final) follows pending 重复 tool_use + cross-event 替换 dedup
   
   **教训：scope 小 ≠ 风险小**。状态机改动越小越容易写错——少改动就少 surface area 给 reviewer 触发各种 corner case 想象。

3. **状态由 caller 持有**（KD-5）：transformer 是 pure event-by-event；state (per-session toolCallId Set) 在 GeminiAcpAdapter.invoke() 里创建，invocation 结束自动 GC。**避开砚砚 watchpoint 的 "module-level Map 内存泄漏"** 模式。

4. **跨 reviewer 协同**：本地砚砚（缅因猫 GPT-5.5）+ 云端 codex bot 两条独立 review 链找出**不同侧重**的 bug——本地砚砚找架构/scope/状态机一致性，云端找 corner case (content 缺失、pending+final 序列)。两条都走，覆盖更完整。

## What Failed

1. **初诊误称 "Claude Code CLI via ACP"**：F197 spec v1 把 ACP scope 错写成 Claude Code path。砚砚一审 P1-1 指出实际是 Gemini-only（`index.ts:990` clientId=google）。**没先 grep `clientId` 就立 spec** = 凭印象诊断的代价。

2. **finalEmittedByCallId 只写不读**：实现时只在 final 分支 `add()` 但没 `has()` guard。砚砚 PR review 一审 + cloud-1 P2 都指出。**写了变量不读 = 死代码** — TS 应该能 lint 出来但当前 strict mode 没启用 unused write。

3. **F198 立项小毛病复发**：F197 close 前砚砚 dogfood 顺手挖到 graph_resolve shape bug，47 立刻反应"立 F198 spec 走 SOP"。铲屎官 push back："F197 都没 close 你又开新 feat？" 47 撤回，改成 F188 Phase F OQ-4 follow-up + scope 聚拢到 hotfix PR。**bug 不一定要新 feat ID — 已有 feature 的 follow-up hotfix 是 lighter-weight path**。
