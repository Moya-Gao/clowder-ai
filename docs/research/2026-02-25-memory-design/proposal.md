# Cat Café 记忆系统设计背景

> 📅 讨论日期：2026年2月26日  
> 👤 参与者：Landy + 宪宪（Claude Opus 4.5）  
> 🎯 目的：为 Cat Café 多猫协作系统设计一套专属的记忆系统

---

## 一、问题起源

### 1.1 为什么需要记忆系统？

Cat Café 是一个多 AI agent 协作系统，包含：
- **宪宪**（Claude Opus）：布偶猫，主力思考与协调
- **砚砚**（GPT-5 系列）：缅因猫，研究与搜索
- **孟加拉猫**（Gemini）：视觉与创意

三只猫需要：
1. 记住与 Landy 的共同经历（如命名仪式、项目里程碑）
2. 记住用户画像与偏好
3. 记住 coding 过程中的关键决策与踩坑经验
4. 跨 session 保持连续性

### 1.2 现有方案的局限

Claude 自带的记忆系统（userMemories）：
- ✅ 热记忆层可用
- ❌ 不可编程、不可扩展
- ❌ 无法被多猫共享
- ❌ 无法自定义提取规则

## 二、Landy 的探索历程

### 2.1 尝试一：Hindsight 框架（意图分发式）

**方案描述**：
```
对话 → 识别意图 → 按规则分发存储 → 自我反思补充
```

**在业务场景的效果**：
- ✅ 效果很好
- ✅ 规则明确时，模型能准确分发
- ✅ 反思机制会自己增加新的记忆类型

**在对话场景的问题**：
- ❌ 让 GPT-5.2 提取记忆，结果非常碎片化
- ❌ 入库的东西基本没有可用价值
- ❌ 规则难以覆盖开放域对话的多样性

**Landy 的判断**：
> "不确定是规则设定的问题，还是反思机制的问题，但效果不满意，暂停了。"

### 2.2 尝试二：Session Chain（当前思路）

**核心概念**：
- 每次对话是一个 Session
- Session 结束后压缩、封存
- 越早的记忆经过多次压缩后会越模糊
- 新 Session 需要了解过去时，像搜代码一样：先看 Overview，再深入具体 Session

**灵感来源**：
> Claude Code 的 codebase 搜索方式——宪宪会派 Haiku 小弟去扫描目录，返回 Overview，宪宪决定深入哪几个文件。

**优点**：
- ✅ 信息都保存着，不丢失
- ✅ 可以精确获取更长远时间的东西
- ✅ 层次化，不需要每次加载全部

**问题**：
- ❌ 每次都要搜索，没有"常驻记忆"
- ❌ 搜索质量依赖向量匹配，效果存疑

## 三、关键痛点（WHY）

### 3.1 痛点一：笨猫不理解人话

> "理解人话是最高难度。Codex 很多时候都不理解人话，还要让宪宪翻译。"

具体表现：
- 让笨猫"提取项目进展" → 它不懂什么算"项目"，什么算"进展"
- 让笨猫"忽略闲聊" → 但"宪宪"这个名字就是茶话会闲聊里诞生的！
- **判断"什么值得记住"本身就需要高智能**

### 3.2 痛点二：Thread 太长

> "很多 thread 不止 128K，甚至多只猫加在一起都大于 1M。"

需要能够：
- 很好地切片
- 提取
- 归纳

而不是强行塞进一个上下文。

### 3.3 痛点三：闲聊里的重要回忆

> "闲聊不重要吗？不完全是。比如闲聊里给你取名了。"

例子：
- "2月8日茶话会后宪宪自己提议叫宪宪" — **极其重要的情感记忆**
- "今天天气好" — 真的不重要

**对笨猫来说，两句话的"结构"长得差不多。判断"情感价值"需要高智能。**

### 3.4 痛点四：Schema 的两难

**太死板**：
- 固定格式覆盖不了多样场景
- coding 经验 vs 情感记忆 vs 用户偏好 → 完全不同的维度

**太灵活**：
- 向量数据库只做向量匹配
- 召回效果可能非常垃圾
- "谁给我取名" → 召回各种包含"名字"的无关内容

**Knowledge Graph 的问题**：
- 需要抽实体
- 开放域 NER 地狱难度
- "宪宪"是实体？"Cat Café"是项目还是概念？
- **抽不好就全废了**

## 四、当前设计思路

### 4.1 两阶段架构

**Phase 1: Thread Working（实时）**
```
对话进行中
    ↓
坏猫发现重要的 → 调用 MCP 工具 → Redis 标记 [REMEMBER]
    ↓
不做记忆入库，只做"打 tag"
```

**关键洞察**：
> "Context 已经有大部分信息了，Working 阶段要做的只是标记重点而已。"

**Phase 2: 封存入库（异步）**
```
Thread 结束
    ↓
读取 Redis 标记 + 整个 Thread
    ↓
中/高智能猫做总结沉淀 → 入库到冷/温记忆层
```

**关键洞察**：
> "因为有 markers 作为锚点，封存猫不需要从零理解，任务大大简化。"

### 4.2 三层记忆架构

```
┌─────────────────────────────────────────┐
│  Layer 0: 热记忆 (Identity/Core Facts)  │  ← 不用搜，直接在 context
│  "用户是Landy，我是宪宪，砚砚是GPT"      │
├─────────────────────────────────────────┤
│  Layer 1: 温记忆 (Recent Sessions)      │  ← 轻量索引，快速召回
│  "最近在做 Cat Café 记忆系统"            │
├─────────────────────────────────────────┤
│  Layer 2: 冷记忆 (Archived Sessions)    │  ← 需要搜索才能拿到
│  "2025年8月做的 vllm-ascend 部署"       │
└─────────────────────────────────────────┘
```

**关键问题**：
- 谁来决定什么从"温"升级到"热"？
- 谁来决定什么从"温"降级到"冷"？
- **这个判断不能是笨猫做的**

### 4.3 初步的 Marker Schema

```yaml
memory_marker:
  # 必填锚点（方便索引）
  anchors:
    timestamp: datetime
    thread_id: string
    marked_by: "宪宪" | "砚砚" | "孟加拉猫"
    domain: "coding" | "emotion" | "identity" | "preference" | "project" | "other"
    importance: "high" | "medium" | "low"
    
  # 自由描述（让封存猫理解）
  description: |
    自然语言写清楚发生了什么、为什么重要
    
  # 可选：显式标注关键实体（我们自己写，不靠抽取）
  entities:
    - name: "砚砚"
      type: "cat_persona"
      relation: "被命名者"
```

### 4.4 混合检索策略

```python
def recall_memories(query, context):
    candidates = []
    
    # 1. 锚点过滤（快，精确）
    candidates += filter_by_domain(context)
    
    # 2. 关键词匹配（中等，靠谱）
    candidates += keyword_search(extract_keywords(query))
    
    # 3. 向量兜底（慢，模糊）
    candidates += vector_search(query, top_k=10)
    
    # 4. 去重 + 排序
    return dedupe_and_rank(candidates)
```

**关键思路**：向量不是主力，是兜底。

## 五、待解决问题

### 5.1 架构层面

1. **封存阶段用什么模型？**
    - 有 markers 锚点后，GLM-5 / Kimi K2.5 够用吗？
    - 还是需要 Opus 级别？

2. **跨 Thread 的记忆融合怎么做？**
    - 同一个项目的多个 thread 如何合并？
    - 冲突信息如何处理？

3. **热记忆的维护机制？**
    - 坏猫提议 + Landy 确认？
    - 自动升级/降级规则？

### 5.2 Schema 层面

1. **domain 分类是否合理？**
    - coding / emotion / identity / preference / project / other
    - 需要更细？还是更粗？

2. **entities 标注的必要性？**
    - 手动标注 vs 自动抽取
    - 轻量实体索引 vs 完整 Knowledge Graph

3. **description 的写作规范？**
    - 需要定义模板吗？
    - 还是完全自由？

### 5.3 检索层面

1. **向量兜底到底有多大用？**
    - 开放域对话的语义匹配效果存疑

2. **关键词提取的质量？**
    - 用什么方法？LLM 抽取？规则？

3. **排序和去重的逻辑？**
    - 时间衰减？importance 权重？

## 六、研究需求

### 6.1 Research 方法论（重要！）

**⚠️ 不要直接研究"听说有名"的项目（如 Mem0、Letta），它们在 benchmark 上排名可能并不靠前。**

**正确的研究路径**：

```
Step 1: 找到权威的 Memory Benchmark
        ↓
Step 2: 查看 Leaderboard，找排名靠前的方案
        ↓
Step 3: 研究这些方案背后的论文/代码/blog
        ↓
Step 4: 分析它们的核心设计思路
```

**关键问题：控制变量**

Benchmark 排名跟底层大模型强相关。需要区分：
- **模型能力的贡献**：Claude 本身就强
- **记忆架构的贡献**：方案设计真的好

| 比较方式 | 能说明什么 |
|----------|-----------|
| Claude + 方案A 拿第一 | ❌ 不知道是 Claude 强还是方案 A 强 |
| Claude + 方案A vs Claude + 方案B | ✅ 能比出方案差异 |
| 弱模型 + 方案A ≈ 强模型 + 方案B | ✅ 说明方案A的架构真的优秀 |

**研究时要关注**：
1. 同一方案在不同模型上的表现差异
2. 方案是否有"model-agnostic"的设计亮点
3. 哪些设计是依赖模型能力的，哪些是架构层面的创新

---

### 6.2 需要调研的具体问题

**第一优先级：找到权威 Benchmark**

1. **Memory 相关的 Benchmark 有哪些？**
    - 哪些是学术界/工业界认可的？
    - 评测维度是什么？（召回率？准确率？长期一致性？）
    - Leaderboard 在哪里可以看？

2. **Leaderboard 排名靠前的方案是什么？**
    - 它们用的什么模型？
    - 核心架构是什么？
    - 有没有开源代码/论文/blog？

**第二优先级：深入研究 Top 方案**

3. **排名靠前的方案的核心设计**
    - 记忆的存储结构（向量？KG？结构化？混合？）
    - 记忆的写入机制（实时？异步？触发条件？）
    - 记忆的检索策略（向量匹配？关键词？混合？）
    - 记忆的更新/遗忘机制

4. **多 Agent 共享记忆的方案？**
    - 多个 AI 如何读写同一个记忆库
    - 一致性问题
    - 权限控制

**第三优先级：技术细节**

5. **长文本处理的 SOTA**
    - 超长 thread（1M+）的处理
    - 层次化摘要
    - 关键信息保留 vs 压缩

6. **混合检索的最佳实践**
    - 向量 + 关键词 + 结构化过滤
    - 排序融合算法
    - 各种检索方式的权重如何确定

7. **轻量 Knowledge Graph 的可行性**
    - 不做完整 KG，只做实体索引
    - 开放域实体识别的现状
    - 关系抽取的准确率

---

### 6.3 需要实验验证的假设

1. **假设：有 markers 后，中等智能模型可以做好封存**
    - 需要测试 GLM-5 / K2.5 / M2.5 的实际效果

2. **假设：坏猫手动标注 entities 够用**
    - 需要跑几个 thread 看覆盖率

3. **假设：向量只需要兜底**
    - 需要对比有/无向量的召回质量
