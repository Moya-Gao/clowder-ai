## 先给结论

先纠一个型号名。按 Apple 现在这代产品线，**128GB 统一内存对应的是 M4 Max 机型，不是 M4 Pro**，而且是 16 核 CPU / 40 核 GPU 这一档。下面我都按这台 **M4 Max 128GB** 来评估。

**AIRI 公开仓库里没有一颗“本地 VTuber 神模”藏在暗门后面。** 它更像一条语音总线。README 里明确写着它支持 Web / macOS / Windows，当前 “Mouth” 能力写的是 ElevenLabs voice synthesis；provider 配置里最明确的高自然度路线也是 ElevenLabs，而且默认 `baseUrl` 指向 `unspeech.hyp3r.link/v1/`。同一个 provider store 里还能看到 OpenAI-compatible speech、Deepgram、以及 `app-local-audio-speech` 和 `browser-local-audio-speech` 这两类本地 provider 入口。`unspeech` 自己的 README 也写得很直白，它是**各种在线 TTS/ASR 的 OpenAI-compatible 代理**，不是 AIRI 自带的本地神经发声内核。

所以你们要的东西，本质上不是“找到 AIRI 同款隐藏模型”，而是把你们自己的链路做成 AIRI 那种**会呼吸的发声系统**。在 **2026、本地-only、Mac、可能要商用** 这四个条件同时成立时，我给的结论非常明确：

**首选：Qwen3-TTS 1.7B-CustomVoice on MLX-Audio**。它是这轮里自然度、情绪/韵律控制、Mac 落地、许可证、工程省心度最均衡的一条线。
**上限：CosyVoice3 0.5B via cosyvoice3.rs（Candle + Metal）**。中文上限更高，方言和中文口语味更强，但工程和首包调优更折腾。
**保底：Qwen3-TTS 0.6B-CustomVoice on MLX-Audio**。牺牲一点上限，换更轻更稳的实时体验。
**不建议进主线：Spark-TTS、ChatTTS、FishAudio-S1。** 它们各有亮点，但这轮都被许可证或 Mac 路线拖出主赛道。**GPT-SoVITS** 适合做角色声库，不适合直接当你们的日常低延迟直播引擎。

## 1. AIRI 的语音方案拆解

### 1.1 她到底用了什么 TTS

公开仓库里，**最明确、默认配置最完整的高质量 TTS provider 是 ElevenLabs**。AIRI 在 `providers.ts` 里给 ElevenLabs 配了默认 `baseUrl: https://unspeech.hyp3r.link/v1/`，还有 `similarityBoost` 和 `stability` 这类 provider 级参数。与此同时，它也预留了 `openai-compatible-audio-speech`、`deepgram-tts`、`app-local-audio-speech`、`browser-local-audio-speech` 等接口位。也就是说，AIRI 的设计重点不是“自带某个唯一模型”，而是**把不同语音后端插进统一调度层**。

### 1.2 音频 pipeline 是怎样的

AIRI 的关键不是只把整段文本丢给 TTS，而是先把文本流送进 `speech-pipeline`，再经过 `createTtsSegmentStream` 分段，然后对每个 segment 单独做 TTS，再交给 playback manager 调度播放。`tts-chunker` 这层会按硬标点、软标点、显式 flush token、词数上限去切段，默认思路大概是“**短句、早切、及时出声**”，而不是攒成一整段再一口气吐出来。playback manager 还带了 `queue`、`reject`、`steal-oldest`、`steal-lowest-priority` 这些溢出策略，所以它天生就适合“对话里有人插嘴、有人打断、有人抢话”的场景。

这恰好解释了 AIRI 为什么“更像真人聊天”。**自然度不只来自模型，还来自切句、抢占、播放策略。** 你们现在如果只是把一个更强的模型塞进现有 `synthesize() -> bytes`，但仍然整段等完再播，效果会比 Kokoro 好，却很难达到 AIRI 那种“像人在跟你对话”的活气。这个差距，不只是模型差距，也是系统设计差距。

### 1.3 有没有额外韵律/情绪控制

我在公开仓库里**没有看到一个单独的 prosody planner / emotion planner 模块**。能明确看到的是 provider 级参数，比如 ElevenLabs 的 `stability`、`similarityBoost`，以及 chunker / playback 这类系统层控制。换句话说，AIRI 公共仓库里可证实的“自然感来源”，主要是**高质量 provider + 分段 + 播控**，不是一层独立的情绪策划器。

### 1.4 它能在 Mac 上跑吗

**AIRI 这个应用能在 Mac 上跑。** 但它在公开仓库里最明确的高自然度线路，不是一个“开箱即用的本地 Mac TTS 大圣杯”，而是通过 provider 去接 ElevenLabs / Deepgram / OpenAI-compatible 等后端。本地 Mac 路线倒是留了入口，尤其是 `app-local-audio-speech` 和 `openai-compatible-audio-speech`。所以，**最接近 AIRI 公开设计、又满足你们本地-only 约束的替代方案**，就是：
**Qwen3-TTS on MLX-Audio**，或者 **CosyVoice3 on Candle + Metal**，外面再包上 AIRI 式的 chunking / playback。

## 2. 2026 年能打到“虚拟主播自然度”的候选方案

### Qwen3-TTS

**自然度：高。** 官方把它直接定位成 stable、expressive、streaming speech generation，支持自然语言控制 timbre / emotion / prosody。1.7B 系列分成 Base、CustomVoice、VoiceDesign，0.6B 也有对应轻量版。Base 支持 3 秒快速克隆，CustomVoice 主打 timbre + style control，VoiceDesign 主打“用文字设计声音”。许可证是 **Apache-2.0**。

**中文、多声线、Apple Silicon：都强。** 它覆盖 10 种主要语言，中文和中英混读本来就是主战场之一。MLX-Audio 已经把 Qwen3-TTS 接进 Apple Silicon 原生路线，Swift 原生实现也在 2026 年跟上了。官方模型页给出**端到端流式时延低到 97ms** 的说法，Apple 生态的社区项目里也已经能看到 M2 Max、M4 Pro 上接近或快于实时的实践。对你们这种“本地、Mac、要多角色”的项目，它是当下最平衡的选择。

### CosyVoice 3.0 + cosyvoice3.rs

**自然度：中文上限高。** CosyVoice 3.0 官方 README 把提升点写得很明确，content consistency、speaker similarity、prosody naturalness 都比前代更强；支持 9 种语言、18+ 汉语方言/口音、中文拼音和英文 CMU 发音修补、文本规范化、以及情绪/速度/音量等 instruction 控制。官方对比表里，0.5B 的 CosyVoice3 在中文/英文的多项指标上明显压过 Spark-TTS。许可证是 **Apache-2.0**。

**Mac 可行性：中高，但要动手。** 真正适合你们的不是重 PyTorch 路线，而是 `cosyvoice3.rs` 这条 **Candle + Metal** 的苹果路线。它官方 README 写了 macOS + Metal 安装方式、`PyDevice("metal")`、零样本克隆、instruction-guided synthesis、预提取特征复用，并给出 **M1 Pro 上约 0.3 到 0.5 RTF** 的结果，已经是快于实时。麻烦在于首包。CosyVoice3 官方宣称双向流式最低 150ms，但 issue 区能看到 1.1 到 2 秒级的首 chunk 波动，所以它是“**上限高，但要调**”的选手。

### Spark-TTS

**自然度：比 Kokoro 强很多，但不是这轮冠军。** 它支持中英双语、零样本克隆、跨语种与 code-switching、以及 gender / pitch / speaking rate 这种可控虚拟 speaker 生成。MLX-Audio 已支持 Spark-TTS，所以在 Mac 上跑起来并不难。问题是，从 CosyVoice3 官方对比表看，Spark 在 speaker similarity 和自然度指标上被 CosyVoice3 反超。更要命的是权重许可证已经改成 **CC-BY-NC-SA-4.0**，只适合内部研究或非商用。模型包体大约 **3.95GB**。

### ChatTTS

**自然度：口语味和戏感依旧很能打。** 它的出身就是对话场景，强调 dialogue-based、fine-grained prosody control，连 laughter / pauses / interjections 这种细粒度韵律都是卖点。站在“主播味”这件事上，它依然有参考价值。

**但不适合你们这条主链路。** 代码是 **AGPL-3.0**，模型是 **CC-BY-NC-4.0**，服务端集成和商业边界都很刺手。模型文件大约 **2.37GB**。所以我会把它归类成“拿来做对照试听、学表达风格”，而不是拿来做 Cat Café 的正式底座。

### Fish Speech / FishAudio-S1

**自然度：非常高。** 官方自己把 S1 的卖点写得很猛，强调 natural、realistic、emotionally rich、not robotic；支持大量显式 emotion / tone markers，比如 angry、sarcastic、whispering、laughing；10 到 30 秒参考音频就能做 voice cloning。S1 是 4B，S1-mini 是 0.5B。

**但当前不适合你们。** 代码是 Apache-2.0 没错，但**模型权重是 CC-BY-NC-SA-4.0**；官方部署描述里写的是 Linux / Windows 原生支持，**macOS support coming soon**。所以它更像一辆很会吼的赛车，但你们这条路现在还没给它铺好。

### GPT-SoVITS

**定位和上面那些不太一样。** 它的强项是 **5 秒零样本**、**1 分钟 few-shot 微调**，更像“给角色造一副稳定嗓子”的工具链。V3 版本又进一步强调 timbre similarity、更稳定、情绪更丰富。代码许可证是 **MIT**。

**Mac 能跑，但我不把它当首发引擎。** 官方测试环境里包含 Apple silicon，macOS 安装脚本支持 `--device <MPS|CPU>`；但官方同时明确提醒，Mac 上用 GPU 训练的模型当前质量会明显变差，训练更推荐 CPU。我的判断是，**GPT-SoVITS 很适合你们以后离线做三只猫的固定声库**，但不适合现在直接拿来承担“低延迟聊天 + 流式 + 播控”的日常发声。

### AIRI 使用的方案，补齐结论

如果只看公开仓库，**AIRI 的“像真人”并不等于“它内置了一个本地 TTS 王者”**。更准确的描述是：**高质量 provider + 分段 + 播放调度**。在你们的本地 Mac 约束下，最接近 AIRI 公开方案的替代，不是去复刻 ElevenLabs，而是：
**Qwen3-TTS / CosyVoice3 + AIRI-style chunker + AIRI-style playback policy。**

### 其他值得关注的

Apple 原生方向，我会盯 **swift-qwen3-tts / Speech Swift** 这类项目。它们说明 2026 年 Apple 生态已经开始把 Qwen3-TTS 之类模型往 macOS / iOS 原生流式栈里搬。研究榜单方向，则可以盯 **GLM-TTS RL** 和 **Index-TTS2**，它们在 CosyVoice3 官方对比表里都很强，但我这轮没有看到像 MLX-Audio 或 Candle+Metal 这样成熟的 Mac 原生路径，所以今天不把它们放进落地推荐。

## 3. M4 Max 128GB 的算力天花板

**统一内存不是“有 128GB 显存”，也不是“GPU 只能拿固定一小块”。** Apple Silicon 是 CPU 和 GPU 共享同一物理内存的统一内存架构，MLX 也是围绕这个模型设计的，张量天然共享内存，不需要在 CPU / GPU 之间搬来搬去。对你们来说，这意味着**没有固定 VRAM 分区**，真正的上限是系统和前台应用吃掉多少之后还剩多少。工程上我会把 **90 到 105GB** 当成比较舒服的 ML 工作区，再留 **16 到 24GB** 给 macOS、浏览器、IDE、音频缓冲和开发杂项。后面这个区间是我的工程预算，不是 Apple 公布的硬分区。

**M4 Max 40 核 GPU 这档的关键数字，是 546GB/s 内存带宽。** Apple 官方甚至拿它宣传“可与接近 200B 参数的大模型交互”。这不等于“你该拿 7B 以上 TTS 做实时聊天”，但它说明你们的瓶颈**不会先出在容量**，而更可能出在 kernel、首包时延和工程调度。Apple 在这些规格页里强调的是内存带宽与统一内存，并没有在这些官方资料里给出 GPU TFLOPS；第三方估算则把 40 核 M4 Max 放在大约 **18 FP32 TFLOPS** 的量级。对 TTS 来说，后者参考意义有，但**远不如带宽和框架实现重要**。

**能跑多大模型。** 纯按权重算，1B BF16 大约 2GB，3B 大约 6GB，7B 大约 14GB，然后再叠 tokenizer、codec / vocoder、KV cache、activations。结论很简单：
**0.5B 到 2B 是 Apple 本地 TTS 的甜点区。**
**3B 也能玩，但要问它值不值。**
**7B 不是装不下，是通常没必要。**
你们这种“聊天室里三只猫边聊边插话”的应用，真正追求的是**首包和 RTF**，不是把参数量堆成小山。

**框架怎么排。** 我给的是很实用的工程排序，不是抽象哲学。
对 **Qwen3 / Spark 这种已经有 MLX 社区权重**的模型，首选 **MLX**。
对 **CosyVoice3**，首选 **Candle + Metal**。
对 **原生 App 固化部署**，Core ML 值得中长期考虑。
**ONNX Runtime** 在 Apple 这边本质上常常是借 **Core ML Execution Provider** 起飞，所以它不是你们当前这类 frontier TTS 模型的第一选择。MLX 的强项是直接拥抱 Apple Silicon 的统一内存；Core ML 的强项是系统级 CPU / GPU / Neural Engine 调度，但前提是你已经付完模型转换和图优化这张工单。

## 4. 最终推荐

### 首选方案

**Qwen3-TTS-12Hz-1.7B-CustomVoice on MLX-Audio**

为什么是它：
它是这轮里**自然度、情绪/韵律控制、多声线、Mac 落地、许可证、工程复杂度**最平衡的一条线。CustomVoice 比 VoiceDesign 更适合你们当前这种“固定三只猫、每只猫一个声线 preset”的产品形态；如果你们后面想完全用文字设计新嗓子，再换到 VoiceDesign。

这些命令都能在官方文档或模型卡里对上。

```bash
brew install ffmpeg

python -m venv .venv
source .venv/bin/activate

pip install -U mlx-audio

# 先本地试一句
python -m mlx_audio.tts.generate \
  --model mlx-community/Qwen3-TTS-12Hz-1.7B-CustomVoice-bf16 \
  --text "今天我们三只猫一起把这个 TypeScript provider 收拾干净。"

# 再开成 OpenAI-compatible 服务
mlx_audio.server --host 127.0.0.1 --port 8000
```

**未实测预算**：我会先按 **8 到 12GB 常驻内存**、**warm RTF 约 0.4 到 0.8**、**首包 150 到 300ms** 来估。这个区间不是我在你机器上的实测，而是根据 Qwen3 官方低时延描述、社区在 M2 Max / M4 Pro 上的公开结果、以及 M4 Max 的带宽外推出来的工程预算。

**和你们现有架构的对接方式**：
最省事的做法不是重写一套，而是保留现在的 Python FastAPI server + Node.js consumer，只新增一个 `Qwen3MlxAdapter`。
但我建议你们做两个改动：

1. **TtsAdapter ABC 新增 `stream_synthesize()`**。不改这个接口，所有支持 streaming 的模型都会被你们当前 `synthesize() -> bytes` 硬生生打回“整句等完再播”。
2. **在 TTS 前加一层 spoken rewrite + segmenter**。把 LLM 的书面句改成口语句，再按 AIRI 的思路切短句。AIRI 的 chunker 本来就是沿着标点、flush token、4 到 12 词这种策略在切。

我会把三只猫先做成 3 个 preset：

* 布偶猫：温柔、松弛、轻一点、句尾略上扬。
* 缅因猫：低一点、稳一点、语速慢一点，像 senior engineer。
* 暹罗猫：亮一点、快一点、带一点吐槽感，停顿更短。

### 上限方案

**CosyVoice3 0.5B via `cosyvoice3.rs`，走 Candle + Metal**

为什么是它：
如果你们的核心语言是中文，而且要追求“虚拟主播式中文口语自然度”的天花板，CosyVoice3 更像重锤。它对中文文本规范化、数字读法、拼音修补、方言/口音、情绪指令这些生产味很重的细节更有优势。

这些安装方式和 Python 调用都是 `cosyvoice3.rs` README 里直接给出的。

```bash
python -m venv .venv
source .venv/bin/activate

# 方式 A：下载预编译 Metal wheel
pip install cosyvoice3-<version>+metal-cp310-abi3-macosx_11_0_arm64.whl

# 下载 Candle 版权重
pip install huggingface_hub
hf download spensercai/CosyVoice3-0.5B-Candle --local-dir ./CosyVoice3-0.5B-Candle
```

```python
from cosyvoice3 import CosyVoice3, PyDevice, TextNormalizer

model = CosyVoice3("./CosyVoice3-0.5B-Candle", device=PyDevice("metal"), use_f16=True)

normalizer = TextNormalizer("./wetext-fsts")
text = normalizer.normalize("2026年3月7日，价格是$100.50")

audio = model.inference_instruct(
    text=text,
    instruct_text="You are a helpful assistant. 请用轻松、自然、像直播聊天一样的语气表达。<|endofprompt|>",
    prompt_wav="cat_voice_ref.wav"
```

**未实测预算**：我会先按 **12 到 18GB 常驻内存**、**warm RTF 约 0.2 到 0.4**、**首包 0.15 到 1.0 秒** 来估。之所以首包给这么宽，是因为官方写“低到 150ms”，但 issue 区确实能看到 1 秒以上的波动。

**和你们现有架构的对接方式**：
给 FastAPI 增一个 `CosyVoice3Adapter`，重点不是每次都拿 `prompt_wav` 现算，而是**启动时就为三只猫各自预提取 prompt features**，然后走 `load_prompt_features()` / `synthesize()` 低层接口。README 里已经把这个路径给出来了。这样做能明显减少重复 embedding 的开销，也更适合你们固定角色。

## 你们现在最该做的，不是先换模型，而是把链路补齐

AIRI 这件事给你们最大的启发，不是“换成某某模型”，而是这条四段式：

**LLM 文本 → 口语改写 → 短句分段 → 流式 TTS + 抢占播放**

举个最直接的例子。

书面句：
“这个 PR 的核心问题是类型定义不一致，我们需要先重构 provider 层再继续扩展接口。”

口语句：
“这个 PR 啊，核心问题其实就一个，类型定义没对齐。先把 provider 那层收一收，再扩接口，不然越写越乱。”

同一个模型，后者通常就会比前者更像人在说话。

## 真要拍板，怎么测

我建议你们在 M4 Max 128GB 上只跑一轮很硬的基准，别靠耳朵玄学选型。测试集就 4 组：

1. **20 条中文聊天短句**，每条 8 到 25 个汉字。
2. **10 条中英混读句**，带代码词、包名、API 名。
3. **10 条情绪句**，开心、调侃、认真、吐槽、安抚各两条。
4. **5 条打断场景**，上一句还没播完，下一句高优先级插进来。

指标只看这 6 个：

* warm 首包延迟
* 全句完成时延
* RTF
* 峰值 RSS / unified memory 占用
* 打断生效时间
* 主观 AB 盲测

我的门槛会写成这样：

* **首包 < 300ms** 很好，**< 600ms** 能用
* **RTF < 0.5** 很好，**< 1.0** 及格
* 打断生效 **< 150ms** 才像聊天
* 中文短句 AB 盲测里，至少 **70% 以上** 的试听者把它评成“像人在聊天，不像读稿机”

## 最后的拍板

**今天就要选，我会这样下单：**

**第一名，Qwen3-TTS 1.7B-CustomVoice + MLX-Audio。**
它是你们现在最像“能上线的本地 AIRI 替身”。

**第二名，CosyVoice3 + cosyvoice3.rs。**
它是中文天花板冲锋车，但更像改装车间项目，不像省心家用车。

**第三名，Qwen3-TTS 0.6B-CustomVoice。**
它是稳、快、轻的保底牌。

**Spark-TTS、ChatTTS、FishAudio-S1 不进正式方案。**
理由不是它们不强，而是你们这个项目同时要自然度、本地 Mac、工程稳定和许可证干净，它们总有一条腿踩空。

下一步最合理的动作，就是先把 **Qwen3 1.7B** 跑起来，同时把你们的 `TtsAdapter` 加上 `stream_synthesize()` 和 AIRI 式短句 chunker。只换模型，不补这两刀，猫猫还是会有电子木鱼味。
