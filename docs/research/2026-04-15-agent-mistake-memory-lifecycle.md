# 社区问答：Agent 犯了错，怎么让它记住？— 教训沉淀的完整生命周期

> **背景**：社区小伙伴问了两个问题：(1) Agent 犯错后，如何识别、提取、总结教训？(2) 教训落到哪里，怎么形成有效的约束？
>
> **面向读者**：正在搭多 Agent 系统、关心"Agent 如何从错误中学习"的开发者。

---

## 一、问题的本质

大模型的 context window 是临时的——session 结束就忘了。即使在 session 内记住了教训，下一个 session 又是一张白纸。

所以"让 Agent 记住错误"不是一个记忆问题，是一个**知识工程问题**：

1. **识别**：怎么知道 Agent 犯了错？
2. **提取**：怎么把错误概括成可复用的教训？
3. **存储**：教训放在哪里？
4. **注入**：下次启动时怎么把教训喂给 Agent？
5. **约束**：怎么保证 Agent 真的不再犯？

## 二、识别与提取：从人工到半自动的演进

### 阶段 1：人工识别 + 人工记录（最原始）

用户（我们称"铲屎官"）看到 Agent 犯错，直接纠正：

```
铲屎官："不要在主仓 checkout 到非 main 分支！"
铲屎官："禁止猜'没更新/没编译/没重启'，先验证再开口！"
```

Agent 收到纠正后，手动写一条持久化记忆。

**问题**：
- 铲屎官得时刻盯着
- 同一个错往往要纠正 2-3 次才记住
- Agent 可能记录了"什么不能做"但没记"为什么"

### 阶段 2：Knowledge Feed 半自动提取（当前）

系统每 30 分钟自动摘要 Agent 的对话，提取 **durable knowledge 候选**：

```
对话中出现的信号：
  用户说"不要XXX"    → 摘要器标记为 correction
  Agent 说"学到了"   → 摘要器标记为 lesson candidate
  讨论收敛为明确决策  → 摘要器标记为 decision candidate

提取结果 → Knowledge Feed（候选队列）
  → 用户确认 / 拒绝
  → 确认的进入持久存储
```

**Agent 的职责**不是写标签，而是**主动澄清**——发现教训苗头时追问"这是不是正式定了？""要记成规则吗？"帮助摘要器判断置信度。

**关键设计**：摘要器自动判断，但**最终确认权在用户**。Agent 不能自己决定什么是"教训"，因为它可能错误归因。

### 阶段 3：Agent 主动提案（进阶）

不等用户发现，Agent 自己检测到错误模式并提案改进：

```
触发条件：
  - 记忆里 ≥2 次同类错误
  - 用户纠正了一条可泛化的规则
  - 流程跑到一半发现缺口
  - Review 发现系统性问题

Agent 输出提案：
  - 现象：发生了什么
  - 根因：为什么会发生
  - 最小杠杆修复：改哪里最有效
  - 影响范围：改了之后谁受影响
```

这是我们的 Self-Evolution 机制（F100）的 Mode B（Process Evolution）。本质是把"被动纠正"变成"主动提案"。

## 三、教训落在哪里？— 四层约束体系

教训不是全部塞进 system prompt 就完事的。System prompt 有 token 限制，全放进去会爆。

正确的做法是**分层存放，约束力逐级递增**：

```
约束力：弱 ────────────────────────────→ 强

┌───────────┬───────────┬───────────┬───────────┐
│  Agent    │  团队     │  系统     │  Runtime  │
│  个体记忆  │  教训文档  │  提示词   │  硬门禁    │
│           │           │  (家规)   │           │
│  个猫可见  │  全员可见  │  每轮注入  │  物理阻断  │
│  可能忘记  │  搜索可见  │  常驻可见  │  绕不过    │
└───────────┴───────────┴───────────┴───────────┘
```

### 层 1：Agent 个体记忆 — 最轻量

```markdown
# feedback_never_checkout_branch_in_main.md
主仓库禁止 checkout 到非 main 分支，改代码必须开 worktree。
**Why:** 连续多次在主仓切分支导致状态混乱
**How to apply:** 任何需要改代码的场景，先开 worktree
```

- **存储**：Agent 的持久化记忆目录（如 `~/.claude/projects/<project>/memory/`）
- **注入时机**：每个 session 启动时自动加载
- **约束力**：中等。上下文压缩后可能丢失细节，但下次启动会重新加载
- **适合**：日常偏好、工作风格、低频错误

### 层 2：团队教训文档 — 结构化沉淀

```markdown
### LL-002: Review 问题必须先 Red 再 Green
- 坑：直接改实现再补测试，根因未修
- 根因：把"看起来修好了"当成"可证明修好了"
- 触发条件：时间压力大、问题看起来简单时
- 防护：review 关闭条件绑定 Red→Green 证据
- 来源锚点：commit:abc123
```

- **存储**：项目文档（如 `docs/lessons-learned.md`），7 槽位模板
- **注入时机**：Agent 开工前主动搜索（`search_evidence("review 教训")`）
- **约束力**：需要 Agent 主动检索。但有全文索引，不会永久遗忘
- **适合**：跨 Agent 共享的教训、需要来源追溯的严肃错误
- **质量门槛**：必须有来源锚点、可执行防护、时效性验证

### 层 3：系统提示（家规）— 每轮常驻

```markdown
## 铁律
1. Redis 6399 圣域 — 开发只用 6398，误触 6399 立即停止
2. 同一个体不能 review 自己的代码
3. 不能冒充其他 Agent

Magic Words（用户说了 = 手动拉闸）：
- 「脚手架」= 你在偷懒写临时方案 → 停下来审视
- 「星星罐子」= P0 不可逆风险 → 立刻停止一切
```

- **存储**：项目配置文件（如 `CLAUDE.md`），随代码版本管理
- **注入时机**：**每轮对话都注入**，不受上下文压缩影响
- **约束力**：强。但仍然依赖 Agent "自觉"遵守
- **适合**：反复犯的高频错误、安全红线、核心协作规则
- **注意**：Token 有限，只放最关键的铁律，不要把所有教训都塞进来

### 层 4：Runtime 硬门禁 — 物理不可绕过

```
- worktree 环境变量里不含生产数据库连接串 → 想连也连不上
- merge 前的 gate hook → 不过检查物理上推不了代码
- rm 被环境重写成 trash → 删除变成移入回收站
- 沙箱网络隔离 → 无法访问生产系统
```

- **存储**：运行环境配置（环境变量、git hooks、沙箱策略）
- **注入时机**：不需要注入，是执行环境本身的约束
- **约束力**：**最强，100% 阻断，Agent 无法绕过**
- **适合**：不可逆操作（删除数据、推送代码、访问生产环境）

## 四、如何判断教训该落在哪一层？

```
                  ┌─── 可逆？
                  │
          ┌───── 是 ─────┐
          │               │
     频率高？          频率高？
     ┌─ 是 ─┐         ┌─ 是 ─┐
     │      │         │      │
    层3    层1        层4    层2
  系统提示  个体记忆  硬门禁   教训文档
  (常驻)   (轻量)   (物理)   (可搜)
```

简化规则：

| 错误类型 | 落在哪层 | 举例 |
|---------|---------|------|
| 日常偏好 / 低频小错 | 层 1（Agent 记忆） | "这个用户喜欢简洁回复" |
| 跨 Agent 共享的踩坑经验 | 层 2（教训文档） | "Redis eval 和 keyPrefix 行为不一致" |
| 反复犯的高频错误 | 层 3（系统提示/家规） | "禁止猜测，先验证再开口" |
| 不可逆的安全操作 | 层 4（Runtime 硬门禁） | "不能直连生产数据库" |

## 五、完整生命周期（从犯错到防护）

```
Agent 犯错
  │
  ├─ 用户纠正 ─→ Agent 写个体记忆（层1）
  │                  │
  │                  ├─ 同类 ≥2次 ─→ Agent 提案改流程
  │                  │                  │
  │                  │             ┌────┴────┐
  │                  │          方法论级     安全级
  │                  │             │          │
  │                  │          改系统提示   加硬门禁
  │                  │          （层3）     （层4）
  │                  │
  │                  └─ 可跨 Agent 复用 ─→ 写入教训文档（层2）
  │
  └─ Knowledge Feed 自动提取 ─→ 候选队列 ─→ 用户确认 ─→ 层1/2/3
```

## 六、实践经验与教训

### 1. 不要只记"做什么"，要记"为什么"

```
❌ "禁止在主仓切分支"
✅ "禁止在主仓切分支。Why: 主仓是多人共享的，切分支会影响其他 Agent 的工作状态"
```

没有 "Why" 的规则，Agent 遇到边界情况不知道该不该遵守。

### 2. 确认权必须在人

Agent 自己判断"这是教训"可能错误归因。比如一次失败可能是网络问题，不是方法错误。**Knowledge Feed 的设计核心是：自动提取候选，人工确认入库。**

### 3. 最有效的约束不是"告诉 Agent 不要做"，而是"让 Agent 做不到"

我们的核心经验：

> 层 1-3 的约束力加起来，不如层 4 一个硬门禁。

如果一个错误的后果是不可逆的（删生产数据、推错代码），不要靠 system prompt 告诉 Agent "不要做"——要在运行环境里让它**物理上做不到**。

### 4. System prompt 不是垃圾桶

把所有教训都塞进 system prompt 是常见误区。Token 有限，教训太多会稀释关键规则的注意力权重。**只把铁律级别的约束放在 system prompt，其他的放在可检索的记忆/文档里。**
