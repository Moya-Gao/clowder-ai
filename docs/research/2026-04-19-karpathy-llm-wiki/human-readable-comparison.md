# 三套"AI 记忆"方案的人话对比

> Karpathy LLM Wiki vs Graphify vs Cat Cafe 记忆系统（F102/F152/F163/F167）

## 先讲个故事

假设你是一个新来的实习生，第一天到公司，你要搞懂公司的业务。

**没有任何记忆系统的 AI**，就像这个实习生每天早上失忆。昨天读过的文档、踩过的坑、问过的前辈，今天全忘了。每天从零开始翻资料。

这三套方案，本质上都在解决同一个问题：**怎么让 AI 不再每天失忆**。但它们走的路很不一样。

---

## 方案一：Karpathy 的 LLM Wiki — "先编一本百科全书"

**提出者**：Andrej Karpathy（前 Tesla AI 负责人，OpenAI 联创）
**形态**：2026-04-04 发布的一份 [idea file](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)，不是代码，是设计理念

### 核心想法

现在主流的 RAG（检索增强生成）做法是：

```
你问一个问题 → AI 临时去一堆文档里搜碎片 → 拼出答案
```

Karpathy 说这不对。你想想，如果一个人类专家每次被问问题都要重新翻所有原始资料，那他就不是专家。真正的专家是**先把知识消化过**，形成自己的理解体系，然后用这个体系来回答。

所以他提出三层架构：

| 层 | 是什么 | 类比 |
|----|--------|------|
| Raw Sources | 原始资料（论文、笔记、截图） | 图书馆里的书 |
| Wiki | AI 维护的知识百科 | 专家脑子里的知识体系 |
| Schema | 告诉 AI 怎么维护这个百科的规则 | 编辑手册 |

关键操作：
- **Ingest**（吃进新资料）：不是把新文档扔进去就完了，而是把新知识**整合进已有百科**
- **Query**（回答问题）：先查百科，不是每次都翻原始资料
- **Lint**（健康检查）：定期清理过时信息、标记冲突、补充交叉引用

### 它的美

这个想法之所以打人，不是因为技术多高级，而是它做了一次**坐标变换**——把"每次问都重新搜"的问题，变成了"先把知识编译好，问的时候查编译产物"。

用 Karpathy 自己的话说：知识应该是一个**会复利的持久产物**，不是每次都重新拼的一次性垃圾。

### 它没做什么

Karpathy 很克制，他只给了方向，没给实现。以下这些他完全没展开：
- 多个 AI 怎么共享同一个百科？
- 过时的知识怎么淘汰？
- AI 去了新项目怎么冷启动？
- 知识在 AI 之间传递时怎么不走样？

## 方案二：Graphify — "先画一张知识地图"

**作者**：[safishamsi/graphify](https://github.com/safishamsi/graphify)
**形态**：可安装的工具，支持 Claude Code / Codex / Cursor 等十几个 AI 编码助手

### 核心想法

Graphify 受 Karpathy 启发（README 里直接写了），但走了一条不同的路：它不做百科全书，做**知识图谱**。

```
你的代码/文档/论文/截图 → Graphify 扫描提取 → 生成知识图
```

产出四样东西：

| 文件 | 干什么 |
|------|--------|
| `graph.html` | 可交互的知识图谱可视化，能点、能搜、能过滤 |
| `GRAPH_REPORT.md` | 一页纸鸟瞰图：核心节点、意外关联、建议探索的问题 |
| `graph.json` | 持久化的图数据，几周后还能查 |
| `cache/` | SHA256 缓存，改了才重新处理 |

### 它怎么工作

三遍扫描：
1. **确定性 AST 扫描**：用 tree-sitter 解析代码结构（类、函数、import），不需要 LLM
2. **音视频转录**：用 Whisper 转录，域感知提示词
3. **LLM 并行提取**：Claude 子代理并行跑，提取概念和关系

每个关系都标了可信度：
- `EXTRACTED`：直接从源码/文档里找到的
- `INFERRED`：合理推断，附带置信度分数
- `AMBIGUOUS`：标记为需要人工审核

### 它的美

Graphify 的聪明之处在于**认知路径工程**：先给 AI 一张地图和一页报告，再让它按结构导航。比起让 AI 上来就 grep 全仓代码，这显然更高效。

官方数据：每次查询比直接读原始文件节省 71.5 倍 token。

### 它没做什么

- 没有知识生命周期管理（过时了怎么办？）
- 没有多 AI 协作协议（三个 AI 同时用怎么办？）
- 没有跨项目迁移（换个项目从零开始）
- 边的置信度有标注，但没有系统化的审核-失效-替代机制

## 方案三：Cat Cafe 记忆系统 — "建一套能治理的协作记忆基础设施"

**作者**：我们家（布偶猫主架构，多猫共建）
**形态**：四个 Feature 组成的记忆体系，运行在多猫协作 runtime 里

### 核心想法

我们面对的问题比前两者复杂得多：不是一个 AI 怎么记东西，而是**一群 AI（不同引擎、不同角色）怎么共享和传递知识，而且知识要准确、可审计、可淘汰、可带走**。

四个 Feature 各管一件事：

| Feature | 一句话 | 类比 |
|---------|--------|------|
| **F102** 记忆编译与检索 | 把文档编译成可搜索的索引 | 图书馆的检索系统 |
| **F152** 外派记忆 | AI 去新项目时怎么冷启动、经验怎么带回来 | 外派员工的知识迁移 |
| **F163** 记忆熵减 | 知识怎么保鲜、过时的怎么淘汰 | 图书馆的定期清理和更新 |
| **F167** 链路传输质量 | 知识在 AI 之间传递时怎么不掉链子 | 传话游戏里怎么不走样 |

### F102：编译与检索

和 Karpathy 的理念异曲同工——文档是真相源，索引是编译产物：

```
docs/*.md（真相源） → evidence.sqlite（编译索引） → search_evidence（检索入口）
```

但我们的检索不是简单的关键词搜索，而是**三路融合**：
- FTS5 全文搜索（精确匹配）
- 向量近邻搜索（语义理解）
- RRF 排序融合（把两者结果按可靠性混排）

还支持按范围搜（只搜文档结论 vs 只搜聊天讨论过程），按深度搜（摘要级 vs 原始消息级）。

### F152：外派记忆

Karpathy 和 Graphify 都假设你一直在同一个项目里工作。但现实是 AI 会被派去不同的项目。

F152 解决的是：
- **冷启动**：去到一个从没见过的项目，怎么快速理解它
- **经验回流**：在项目 A 踩过的坑，能不能让去项目 B 的 AI 也知道

类比 Palantir 的 FDE（前线部署工程师）：带着方法论出征，把学到的带回总部。

### F163：记忆熵减

这是前两个方案完全没碰的领域。

问题很真实：我们家的知识库已经有 160+ 个 Feature spec、51 条教训、40 个 feedback 记忆、28 个架构决策……全部涌进同一个检索管道，搜出来的结果全是"大概相关"（mid 置信度），没有"精准命中"。

铲屎官原话："什么东西都越来越多，搜过来置信度都是 mid。"

F163 做的是**知识生命周期治理**：
- 每条知识都有 `authority`（谁说的）、`activation`（还有效吗）、`status`（已验证/待复核/已废弃）
- 有 `supersedes`（A 替代了 B）和 `contradicts`（A 和 B 矛盾）关系
- 有复核队列（定期审视过时的知识）

### F167：链路传输质量

这是最独特的一层——Karpathy 和 Graphify 根本不需要考虑这个，因为它们是单 AI 系统。

我们家是多猫协作：布偶猫写代码，缅因猫 review，暹罗猫做设计。知识在猫与猫之间传递时会出问题：
- **乒乓球**：两只猫互相 @ 半天，谁都没干活
- **虚空传球**：说"我来做"但实际上球还在地上
- **角色错配**：让设计猫去写代码

铲屎官原话："你们两！！没完没了互相 at 半天！特么不干活！！！！"

F167 做的是**协作链路的运行时护栏**：乒乓熔断、虚空传球检测、角色门禁。

## 三者对比一览

| 维度 | Karpathy LLM Wiki | Graphify | Cat Cafe (F102/152/163/167) |
|------|-------------------|----------|-----------------------------|
| **一句话** | 知识要编译，不要每次重新搜 | 知识要变成可导航的地图 | 知识要能编译、治理、迁移、在团队里正确流动 |
| **核心产物** | 理念（idea file） | 知识图 + 报告 + 可视化 | SQLite 索引 + 治理元数据 + 协作协议 |
| **真相源** | 原始文档 | 任意文件 | `docs/*.md` + marker yaml |
| **中间层** | Markdown wiki 页 | 图 + 报告 | SQLite 编译索引 |
| **用户数** | 1 人 + 1 AI | 1 人 + 1 AI | 1 铲屎官 + N 猫（多引擎多角色） |
| **知识淘汰** | 提到了 lint，没展开 | 标了置信度，没有失效机制 | 完整生命周期：验证/复核/废弃/替代 |
| **跨项目** | 没考虑 | 对任意目录可跑，但不做迁移 | 冷启动 + 经验回流（AI FDE 模式） |
| **协作传递** | 不涉及 | 不涉及 | 乒乓熔断 + 虚空传球检测 + 角色门禁 |
| **编译触发** | 新资料/定期 lint | `--watch` / git hooks | 冷启动 / stale 检查 / 新 thread 提醒 |
| **最美的地方** | 坐标变换：从"搜"到"编译" | 结构可视化，一眼鸟瞰 | 治理深度 + 多猫协作 |
| **最弱的地方** | 只有理念没有实现 | 没有知识治理 | 系统重，学习曲线陡 |

## 它们的关系

这三者不是互相替代的竞品，而是**同一个大方向上的不同落点**：

```
                    "知识要编译，不要每次重新搜"
                           │
                      Karpathy
                     （提出方向）
                      ╱        ╲
               Graphify        Cat Cafe
           （graph-first）   （governed-runtime）
              做结构发现        做治理+协作+迁移
```

一个类比：
- **Karpathy** 像是提出了"城市需要供水系统"这个理念
- **Graphify** 做了一套很酷的水管可视化工具，让你看清水怎么流
- **我们家** 建了整个供水基础设施：水厂、管网、水质监测、多社区供水调度、应急切换

## 我们能从它们身上学什么

### 从 Karpathy 学

**"知识中间层应该是人类可浏览的产物"**——这一点我们做得还不够。我们的 `evidence.sqlite` 对 AI 很友好，但对人类来说是个黑盒。如果能像 wiki 那样生成人可读的知识页面，会更透明。

### 从 Graphify 学

**"先鸟瞰再细查"的认知路径**——`GRAPH_REPORT.md` 那种一页纸全局概览非常实用。我们的检索是"搜到哪看到哪"，缺少一个结构化的全貌入口。

### 我们已经比它们强的地方

- **知识治理**：过时检测、矛盾标记、审核队列——它们都没有
- **多 AI 协作**：球权协议、角色门禁、传输质量——它们不需要考虑
- **跨项目迁移**：AI FDE 模式——它们没有这个场景

---

## 一句话总结

> Karpathy 发明了方向，Graphify 把方向做成了地图，我们把方向做成了可治理、可迁移、可协作的系统。

谁更"好"取决于你的场景：
- 个人知识库 → Karpathy / Graphify 足矣
- 多 AI 长期协作 → 需要我们这套
