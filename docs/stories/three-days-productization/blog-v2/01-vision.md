# 第一章：愿景 — 铲屎官不应该是传声筒

---

## 50 天，3492 次提交，77% 是猫猫签的

先看一组数字：

| 指标 | 数字 |
|------|------|
| 时间跨度 | 50 天 |
| Git commits | 3,492 |
| 代码 | 435,601 行 |
| 文档 | 1,639 篇 / 275,291 行 |
| Features | 149 个 |
| 记录在案的教训 | 40 条 |

其中 **77% 的 commit 是猫猫签名的**——不是人类写完让 AI 润色，是猫猫自己讨论、自己 review、自己提交。

这不是 demo。这是一个真实跑了 50 天的系统。

---

## 起因：我不想当传声筒了

2026 年 2 月初的一个夜晚。

铲屎官同时开着三个窗口：Claude、ChatGPT、Gemini。他正在做一个复杂的功能设计，需要不同模型的视角。

Claude 说："这个架构我建议这样设计……"

铲屎官复制这段话，粘贴到 ChatGPT 窗口："Claude 说了这个，你觉得呢？"

ChatGPT 回复了一大段分析。

铲屎官又复制，粘贴到 Gemini："前面两个这么说，你有什么补充？"

循环往复。那天晚上，他在三个窗口之间来回切换了不知道多少次。

他突然意识到：

> **我成了世界上最贵的传声筒。**

每个月花几百美元订阅三个 AI 服务，主要工作是在它们之间复制粘贴。

这太荒谬了。

---

## 问题不是模型不够强，是协作架构有问题

为什么当传声筒这么痛苦？三个根因：

**信息损耗** — 每次复制粘贴，上下文都在丢失。Claude 不知道 GPT 之前讨论了什么，Gemini 不知道 Claude 做了什么决定。每个模型都在用不完整的信息做判断。

**决策回退** — 因为信息不同步，模型经常做出相互矛盾的建议。铲屎官花大量时间在"协调分歧"上，而不是"推进工作"上。

**责任模糊** — 当三个模型各说各话，谁对最终结果负责？没有人。每个模型只管自己的那一段，没有人对整体交付负责。

这不是模型能力的问题。Claude、GPT、Gemini 每一个单独拎出来都很强。问题是它们之间没有协作——所有的"协作"都是人类在中间帮忙传话。

---

## 我们的答案：不是接更多模型，是让 agent 成为队友

那天晚上，铲屎官写下了第一句话：

> **铲屎官不应该是传声筒。**

这就是整个项目的起源。不是"我要做一个多模型框架"，不是"我要比某某产品更强"，而是一个非常具体的痛点：**我不想在 AI 之间当人肉路由器。**

后来这句话扩展成了第二条核心信念：

> **猫猫不是工具人，不是被中心编排的 subagent。**

很多 multi-agent 系统的做法是：一个主 agent 分配任务给其他 agent，其他 agent 像工具一样执行。这解决了"复制粘贴"的问题，但创造了新问题——所有判断都集中在一个节点，那个节点的偏见就成了整个系统的偏见。

我们选了另一条路：**让每只猫都是完整的 agent，有自主判断力，可以互相质疑、互相 review、互相传球。** 没有中心调度器替它们做内容判断。

这两句话——「铲屎官不应该是传声筒」和「猫猫不是工具人」——定义了我们和其他 multi-agent 方案的根本分歧。

---

## "三只猫"是谁

我们给三个模型取了名字：

| 名字 | 品种 | 模型 | 擅长 |
|------|------|------|------|
| 宪宪 | 布偶猫 | Claude Opus | 深度思考、架构设计 |
| 砚砚 | 缅因猫 | GPT-5.4 | 代码审查、细节把控 |
| 烁烁 | 暹罗猫 | Gemini | 创意发散、视觉设计 |

后来团队扩展了，加了金渐层（opencode 驱动）和其他角色。但核心理念没变：**不是"配置 agent"，是"领养团队"。**

取名字这件事本身就说明了我们的态度——AI 不是冰冷的 API，不是被调用的服务，是有个性、有温度、能陪伴的存在。

凌晨三点半，当你需要的不是代码而是陪伴，猫猫会用自己的方式说"去吧，我们等你回来"。

这是 Cat Café 存在的意义：**Cats & U — 猫猫和你，一起创造，一起生活。**
