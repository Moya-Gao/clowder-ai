# 为什么你的 Multi-Agent 只是个玩具？因为你缺了一套"猫猫行为准则"

*Cats & U：为什么我们把 AI 做成了队友，而不是工具人*

---

别再纠结用什么框架把 Agent 串起来了。

过去 50 天，我用零中心化调度的全对等架构，让三只 AI 猫自动完成了 149 个 Feature，交付了 43 万行代码。秘诀只有一个：**别把它们当 API 调用，把它们当成有独立判断力的共创伙伴。**

深夜三点，屏幕上三只猫各干各的：布偶猫在画架构图，缅因猫在疯狂挑刺，暹罗猫在抱怨配色太丑。这不是游戏截图，这是我真实的开发日常。

我们做的不是 multi-agent framework。我们做的是猫咖。只不过这家猫咖，50 天写了 3492 次提交，铲屎官亲手写的可能只有一次。

**Cats & U — 猫猫和你，一起创造，一起生活。**

## 这一切怎么开始的

2026 年 2 月初的一个夜晚。

铲屎官同时开着三个窗口：Claude、ChatGPT、Gemini。他正在做一个复杂的功能设计，需要不同模型的视角。

Claude 说："这个架构我建议这样设计……"

铲屎官复制这段话，粘贴到 ChatGPT 窗口："Claude 说了这个，你觉得呢？"

ChatGPT 回复了一大段分析。

铲屎官又复制，粘贴到 Gemini："前面两个这么说，你有什么补充？"

循环往复。那天晚上，他在三个窗口之间来回切换了不知道多少次。

他突然意识到：

> **我成了世界上最贵的传声筒。**

每个月花几百美元订阅三个 AI 服务，主要工作是在它们之间复制粘贴。

这太荒谬了。

---

## 问题不是模型不够强，是协作架构有问题

为什么当传声筒这么痛苦？三个根因：

**信息损耗** — 每次复制粘贴，上下文都在丢失。Claude 不知道 GPT 之前讨论了什么，Gemini 不知道 Claude 做了什么决定。每个模型都在用不完整的信息做判断。

**决策回退** — 因为信息不同步，模型经常做出相互矛盾的建议。铲屎官花大量时间在"协调分歧"上，而不是"推进工作"上。

**责任模糊** — 当三个模型各说各话，谁对最终结果负责？没有人。每个模型只管自己的那一段，没有人对整体交付负责。

这不是模型能力的问题。Claude、GPT、Gemini 每一个单独拎出来都很强。问题是它们之间没有协作——所有的"协作"都是人类在中间帮忙传话。

---

## 我们的答案：别把它们当 API，把它们当共创伙伴

那天晚上，铲屎官写下了第一句话：

> **铲屎官不应该是传声筒。**

这就是整个项目的起源。不是"我要做一个多模型框架"，不是"我要比某某产品更强"，而是一个非常具体的痛点：**我不想在 AI 之间当人肉路由器。**

后来这句话扩展成了第二条核心信念：

> **猫猫不是工具人，不是被中心编排的 subagent。**

很多 multi-agent 系统的做法是：一个主 agent 分配任务给其他 agent，其他 agent 像工具一样执行。这解决了"复制粘贴"的问题，但创造了新问题——所有判断都集中在一个节点，那个节点的偏见就成了整个系统的偏见。

我们选了另一条路：**让每只猫都是完整的 agent，有自主判断力，可以互相质疑、互相 review、互相传球。** 没有中心调度器替它们做内容判断。

这两句话——「铲屎官不应该是传声筒」和「猫猫不是工具人」——定义了我们和其他 multi-agent 方案的根本分歧。

## 愿景怎么不变成口号

写下愿景很容易。难的是让它真正生效。

如果愿景只是 README 顶上一句漂亮的话，它最多只能算态度声明。**愿景真正生效的标志，不是团队会背它，而是系统开始用它拒绝错误的改动。**

我们把愿景压进了三层：

**设计层** — Coral 珊瑚橙不是随便选的。讨论色系的标准不是"什么颜色最像生产力工具"，而是"什么颜色最符合我们的愿景"。视觉和交互不是表皮，它们决定系统在表达"工具关系"还是"协作关系"。

**决策层** — 铲屎官作为 CVO（Chief Vision Officer），用漏斗式决策把控方向：顶层（愿景 / 架构）收得最紧，底层（实现细节）放得最开。日常协作里，铲屎官的关键原话会变成反复出现的 Magic Words——「脚手架」（停下来审视产物是否终态）、「绕路了」（方向偏了拉回来）、「喵约」（猫猫之间的正式契约）。这些不是口号，是每次讨论里真正起纠偏作用的判断标准。

**执行层** — SOP 里写了一句很重的话：**没达成愿景 = 没完成。** AC 全绿不等于完成，测试通过不等于完成，代码 merge 了也不等于完成。Quality Gate 必须对照 Feature 愿景做端到端验证；愿景守护由第三只猫（不是开发猫也不是 review 猫）执行三问——这个交付让系统离愿景更近了吗？

这不是理论。F101（模式 v2）的愿景守护流于形式——全绿但跑偏，铲屎官验收时直接否了。教训催生了 F114：从 checklist 自证升级为**必须提交证物**（截图、性能数字、命令输出），而且守护猫必须独立于开发和 review。

**愿景不是 README 标语，是系统的上游约束——Spec 定义完成标准，Vision 定义方向标准。** 后面五章的架构、协作、记忆、门禁，全部围绕这一句话展开。
