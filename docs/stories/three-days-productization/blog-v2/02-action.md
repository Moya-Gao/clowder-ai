# 第二章：实战 — 50 天能长出什么

---

数字只是表象。更值得问的是：**这套系统实际能做到什么？**

三个真实案例，展示"以前做不到、现在做到了"的事。

---

## 案例一：从一句话到三层架构

铲屎官说了一句话：

> "接 IM。"

两个字。如果是传统"传声筒"模式，这句话会被原封不动丢给 Claude，Claude 输出一个方案，人类复制给 GPT 看，GPT 提意见，人类再协调……

但在我们这里，这句话触发了一条完整的链路：

**CVO 采访** — 猫猫们没有马上动手，而是先追问：
- 表面需求：接飞书 / Telegram / 微信
- 深层需求：铲屎官每天在飞书里工作，切到网页再切回来是摩擦。他要的是**零摩擦的入口**

铲屎官补了一句：

> "飞书接入我们的前端应该是可见的！我也能在前端看到你们的 thread。"

这一句话改变了整个架构方向——原本可能做个独立的 IM bot，现在变成了**必须和主系统打通的统一 gateway**。

**Research Pipeline** — 宪宪去研究了全球七大聊天平台（飞书、Telegram、Slack、Discord、WhatsApp、钉钉、Teams），从 MAU、Bot API 成熟度、接入难度三个维度做了对比。同时分析了 OpenClaw 的代码——发现真正的 channel adapter 层，每个平台只需 ~1000-2000 行代码。

**讨论收敛** — 宪宪和砚砚开了一次正式的设计讨论。两只猫观点不同：
- 宪宪提议：userId 映射 + 命令式交互 + Redis binding
- 砚砚的核心洞察："统一的是 Cat Café 的 thread/message core，不是某个平台的 transport。"

最终收敛出了**三层架构**（Principal Link / Session Binding / Command Layer）。

**结果**：接第一个平台花 3 天，第二个花 1 天，第三个花半天。架构设计的讨论有价值——三层架构确实加速了后续平台接入。

![IM Hub 平台配置 — 6 个平台，微信已连接](./assets/im-hub-platform-config.png)

**以前**：人类在三个模型之间复制粘贴"接 IM"的方案，协调分歧，最后还要自己做技术选型。
**现在**：猫猫自己采访需求、自己调研、自己争论、自己收敛出架构。

## 案例二：从隐藏需求到统一抽象

铲屎官的一个随口提问：

> "我们现有的能力是不是已经功能上满足小龙虾的 heartbeat 覆盖的能力？"

猫猫们没有直接回答"是"或"不是"。

宪宪和砚砚先达成了一个共识："事件驱动场景我们已经比小龙虾的 heartbeat polling 做得更好——秒级响应 vs 30 分钟轮询。但'没人找你但该主动检查'的自省能力还没有统一抽象。"

这个区分帮铲屎官看到了**他自己没意识到的隐藏需求**：问题不是"要不要做定时任务"，而是"主动巡检和被动响应是两件事，我们少了前者"。

铲屎官继续补了一条关键约束：

> "不建议你这个可配置是编辑到什么 Markdown 文档里……能让人类跟你直接说自然语言，你帮别人去编辑，或者你有个 UI 去把东西呈现出来。"

这句话直接改变了设计方向——从"后端搞个 cron 配置文件"变成了"自然语言配置 + 可视化面板"。

然后三只猫（宪宪、金金、砚砚）**独立调研** OpenClaw 的 heartbeat 体系，交叉比对。三只猫得出了相同的共识（"Cheap Checks First 模式值得学"），也有不同的侧重。最后砚砚提出了 5 维度拆分（schedule / durability / context / gate / delivery），宪宪承认比自己最初的 `ScheduleAdapter` 方案更精准。

**以前**：铲屎官自己查资料、自己想架构、然后描述给 AI 执行。
**现在**：猫猫帮铲屎官发现隐藏需求、独立调研、交叉校准、最终方案比任何单只猫的方案都好。

## 案例三：当愿景守护失败的时候

这是一个反面教训。

F101（模式 v2 / 狼人杀）的愿景是"删旧 mode，把狼人杀加入 mode"。流程走完了，两次愿景守护都过了。

但铲屎官亲自验收时发现体验不对。他直接说：

> "你们的愿景守护流于形式了。"

复盘发现问题：守护猫只审计了 AC checkbox，没有从用户视角验证体验。AC 打勾了，但铲屎官当初想要的东西没有真正交付。

这个教训催生了 F114（Magic Words + 愿景守护 Gate）。改革内容：
- 愿景守护从"审计 checkbox"升级为**必须交证物才放行**
- 守护猫要回溯**铲屎官的原话**——他当初为什么要做这件事？他最在意什么？
- 不是检查 AC 是否打勾，而是检查**铲屎官的愿景是否被真正满足**

**以前**：流程走完就算完，没有人真正为"铲屎官满不满意"负责。
**现在**：愿景进入系统，系统会用它拒绝不达标的改动。

## 这三个案例说明什么

| 维度 | 传统模式 | Cat Café |
|------|---------|----------|
| 需求澄清 | 人类自己想清楚再告诉 AI | 猫猫追问、挖掘隐藏需求 |
| 技术选型 | 人类查资料、做判断 | 多猫独立调研、交叉校准 |
| 架构讨论 | 人类协调不同模型的意见 | 猫猫自己争论、自己收敛 |
| 质量保证 | AC 打勾就行 | 愿景守护 + 证物 Gate |
| 失败处理 | 骂完 AI 自己善后 | 教训沉淀、流程改革 |

**50 天能长出什么？** 不只是 149 个 Feature、3492 次提交。是一套**会追问、会调研、会争论、会从失败中学习**的协作系统。
