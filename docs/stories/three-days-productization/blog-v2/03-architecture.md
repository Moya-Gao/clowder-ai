# 第三章：架构 — 去中心化判断，结构化执行

---

## 行业在做什么

2026 年 3 月的 multi-agent 领域，竞争已经从"能不能跑"升级到"能不能扛生产"。我们调研了主流方案（详见项目内部 research 归档），归纳出四种模式：

| 模式 | 代表 | 核心思路 | 生产就绪度 |
|------|------|---------|-----------|
| 状态图编排 | LangGraph | 把 agent 工作流建模为状态机，内置 checkpoint / resume / time-travel | 公开生产案例最多（Qodo/Klarna 等） |
| Boss + Sub-agent | Claude Agent Teams、OMOC Sisyphus | 一个 Team Lead 分配任务给 teammates / sub-agents，sub-agents 向上汇报 | Anthropic 有 16-agent 编译器案例 |
| 角色 Pipeline | CrewAI | 给每个 agent 一个角色，按流程顺序执行，AWS 官方博客背书 | 快速迭代中（周更节奏） |
| 协议标准化 | Google A2A Protocol、MCP | 不做编排，做 agent 间通信的标准接口 | 协议层，不直接解决编排 |

它们都解决了"不用人类复制粘贴"的问题。但做了同一个架构选择：

> **任务怎么分、内容怎么判，由一个中心节点决定。**

LangGraph 里这个节点是状态图的路由逻辑。Agent Teams 里是 Team Lead。OMOC 里是 Sisyphus orchestrator（我们集成金渐层时做过详细拆解：默认由 orchestrator 汇总决策，sub-agent 之间不直接协同）。CrewAI 里是预定义的角色流程。

这意味着：**中心节点的偏见就是全系统的偏见。** 如果 boss agent 判断错了，没有任何 sub-agent 有权限和动力拉住它。

---

## 我们的选择

我们做了一个不一样的决定：

> **把内容判断和执行通道分开。**

```
┌──────────────────────────────────────────┐
│           对等判断层（上层）               │
│                                          │
│   宪宪 ←→ 砚砚 ←→ 烁烁 ←→ 金金        │
│                                          │
│   · 任何猫可以 @ 任何猫                   │
│   · 任何猫可以质疑、否决、传球            │
│   · review 必须跨家族（Claude ≠ GPT）     │
│   · 没有中心节点替猫猫做内容判断          │
│                                          │
├──────────────────────────────────────────┤
│           结构化执行层（下层）             │
│                                          │
│   · InvocationQueue — 统一调度队列        │
│   · Session Strategy — 每只猫独立执行槽   │
│   · Hooks — 三层护栏（rm 禁用 / runtime  │
│     保护 / 共享文档推送守卫）             │
│   · Shared Truth Sources — 共享 git 仓库  │
│     + 共享记忆 + 共享文档                 │
│                                          │
└──────────────────────────────────────────┘
```

上层是对等的：任何猫和任何猫之间都能直接通信，没有"汇报"关系。下层是结构化的：有统一的任务队列、执行策略、安全护栏。

**这两层缺一不可。** 只有对等判断没有结构化执行，就是三只猫在群里乱聊。只有结构化执行没有对等判断，就是换了一种方式的 orchestrator。

用数字说话：F088 Chat Gateway 的核心平台接入里，宪宪最初估了 3-4 天，砚砚给了 6-10 周（含测试和稳定化）。实际结果：**飞书两天做完（PR #328→#336），Telegram 一天半（PR #344→#362），钉钉和微信各半天写出可测版本（PR #636→#695）。** 因为三层网关架构让每个平台只需实现三个方法（`parseEvent()`、`formatMessage()`、`sendMessage()`），平均约 1000-2000 行代码/平台。这个速度不是某只猫很快，是架构对了以后交付变快了。

## 我们不是没有编排，我们是分层编排

这可能是整篇文章最容易被误读的点。

看到"去中心化判断"，很多人会理解成"完全没有编排"。不是的。**我们有编排，只是编排不在跨猫层。**

我们的金渐层（金金，OpenCode 驱动）内部就跑着 Oh My OpenCode（OMOC）的 Sisyphus 编排器。Sisyphus 很强——它能把一个复杂任务拆成子任务，分配给内部子专家（Oracle 做调研、Librarian 查文档、Frontend Engineer 写前端），并行执行，最后收回结果做决策。

但 Sisyphus 有一个根本限制（我们集成金金时做了详细拆解）：**默认由 orchestrator 汇总决策，sub-agent 不承担跨专家协同——每个子专家独立完成自己的子任务后返回结果，彼此之间不直接通信。**

这在单猫内部完全没问题——一只猫怎么组织自己的工作，是它的自由。但如果把这个模式抬到跨猫层呢？

```
⚠️ 如果跨猫也用中央编排：
┌────────────────────────────────┐
│  Sisyphus（老板）               │
│  "宪宪你去写代码"               │
│  "砚砚你去 review"             │
│  "烁烁你去出图"                │
│  → 所有判断由 Sisyphus 做      │
│  → 砚砚没有权利说"不对，       │
│    这个架构方向就有问题"        │
└────────────────────────────────┘

✅ 我们的做法：
┌────────────────────────────────┐
│  跨猫层：对等判断               │
│  宪宪 ←→ 砚砚 ←→ 金金         │
│  → 砚砚可以否决宪宪的设计      │
│  → 金金可以 push back 砚砚的   │
│    review 意见                  │
├────────────────────────────────┤
│  单猫内部：允许编排             │
│  金金内部：Sisyphus / Ralph    │
│  宪宪内部：subagent 并行       │
│  → 每只猫自组织自己的工作      │
└────────────────────────────────┘
```

一句话：**单猫内部允许编排，跨猫协作坚持对等判断。同一层里不要混两种编排权。**

这不是立场宣言，是工程切分。我们没有否定 Sisyphus——它在金金内部工作得很好。我们只是不让任何一只猫的内部 orchestrator 统治其他猫。

## 和 Anthropic Harness 的区别

Anthropic 的 Prithvi Rajasekaran 设计过一个 **planner → generator → evaluator** 三 agent 架构，用于长时间自主编码。他们有两个核心发现和我们高度共鸣：

1. **做事的和判断的必须分开**——他们叫 generator vs evaluator，我们叫"同一个体不能 review 自己的代码"
2. **上下文管理是核心工程问题**——不是"加更多 token"能解决的

但关键分歧在这里：

| 维度 | Anthropic Harness | Cat Café |
|------|-------------------|----------|
| 核心目标 | 让单个长任务更稳定（3-6 小时） | 让一群 agent 长期协作（50 天、149 Features） |
| Review 机制 | Evaluator 功能性检查（找 bug、打分） | 跨家族认知多样性 review（用模型盲点差异找问题） |
| 上下文策略 | 上下文 reset + 交接 artifact | per-cat sessionStrategy（handoff / compress / hybrid） |
| 通信方式 | 写文件 → 对方读文件 | targetCats 结构化路由 + @ 文本路由 + 统一 dispatch queue |
| 方法沉淀 | 迭代优化 harness 本身 | Episode → Method → Skill → Eval → Shared Rules（五层阶梯） |

**Harness 更像是为单任务设计的"任务脚手架"**——通过角色拆分、结构化交接和独立评审让一个长任务更稳定。**我们的系统是"长期协作机制"**——不只是把任务分给不同 agent，而是把愿景、review 标准、记忆、skill 协议、session 策略和 feature 生命周期都写进系统。

## 具体怎么运转

### 路由：猫猫自己决定传给谁

猫猫在回复中写 `@砚砚`，系统自动把消息路由到砚砚。不需要人类中转，也不需要中心调度器分配。

这背后是双路径 A2A 路由。猫猫可以在 MCP 回调里声明结构化目标：

```json
{
  "type": "post_message",
  "content": "发现问题了，你来 review 一下这个修复？",
  "targetCats": ["codex"]
}
```

也可以直接在回复里行首写 `@砚砚`——系统自动文本路由。两条路径统一进入 `InvocationQueue`，铲屎官在前端可以看到每条任务的来源和状态，也可以插队（steer）改变优先级。

关键区别在这里：**主流 orchestrator 的路由表由系统预定义，我们的路由由 AI 自己声明目标。** 系统只负责把消息送达，不替猫猫决定"该找谁"。

### 调度：slot 级并发

每只猫有独立的执行槽位。猫 A 在忙不影响猫 B 接活。系统做 slot 级 busy 检测，不是 thread 级——同一个对话里可以有多只猫同时工作。

### 护栏：每一条都是真实事故换来的

猫猫在判断层是自由的，但执行层有硬护栏。这些护栏不是拍脑袋加的——每一条背后都有真实事故：

- **`rm` 禁用**：有一只猫曾经在调试时把 runtime 环境整个删了。从此 `rm` 被 hook 禁用，强制用 `trash`（可恢复）
- **sanctuary guard**：生产 Redis 跑在 6399 端口。一次 worktree 开发误连了 6399，差点污染生产数据。现在有 `PreToolUse` hook 实时监控，误触立即断连并通知铲屎官
- **共享文档推送守卫**：多只猫同时编辑 `docs/` 目录时出过并发冲突。现在规则是改了共享文档必须同一消息内 commit + push，零延迟
- **pre-commit hook**：Biome 格式 + TypeScript 类型检查，不过的代码不允许提交

**每条护栏背后都有一个教训编号（LL-xxx）。** 我们不写"最佳实践"，我们写"我们踩了什么坑，然后加了什么护栏"。

## 为什么不用中央 orchestrator？

一句话：**因为一旦有了中心判断节点，它的偏见就是全系统的偏见。**

跨家族 review 的价值恰恰在于：Claude 和 GPT 有不同的盲点。举个真实例子：F088 Chat Gateway 做完后，宪宪（Claude）写了三层网关代码，砚砚（GPT）做 review，一次性找出三个 P1：

1. connector message 绕过了格式化层，直接注入了未清洗的用户输入
2. 飞书 webhook 缺了签名验证——上线后任何人都能伪造回调
3. 多猫消息在转发时丢了发送者身份，导致审计链断裂

这三个问题**只靠 Claude 自己是找不到的**——因为写代码的人有相同的盲区。如果一个中心 agent 既写又审，这些 bug 就会安静地滑入生产。

我们的选择是：**执行通道统一管理，内容判断分布式完成。** 基础设施保证消息到达、保证并发安全、保证护栏生效。但"这段代码好不好"、"这个设计方向对不对"、"该不该 push back"——这些判断，没有中心节点替猫猫做。

## 和主流方案的对比

| 维度 | Boss 模式（Agent Teams / OMOC） | 状态图（LangGraph） | 角色 Pipeline（CrewAI） | Cat Café |
|------|-------------------------------|-------------------|----------------------|----------|
| 内容判断 | Team Lead 决定 | 路由逻辑决定 | 角色流程决定 | **每只猫独立判断** |
| 任务路由 | boss 分配 | 图的 edge 决定 | 上一步交下一步 | **猫猫自主 @ 路由** |
| 能否质疑 | sub-agent 向上汇报 | 节点无权改图 | 只能往下传 | **任何猫可以否决任何猫** |
| 单点失败 | Lead 挂了系统停 | 图定义错了全错 | 中间断了后面停 | **去掉任何一只猫，降级但不崩** |
| 偏见抵消 | Lead 偏见 = 系统偏见 | 图作者偏见 = 系统偏见 | SOP 偏见 = 系统偏见 | **跨厂商家族交叉 review** |
| 基础设施 | 中心 agent 管一切 | checkpoint + 状态机 | 固定流水线 | **统一队列 + 独立槽位 + 护栏** |

**我们不是"没有结构"，是"结构在执行层而不是在判断层"。**

## 独立判断：群体智慧的前提条件

讲完架构和对比，有一个更深层的问题需要回答：**对等判断的质量怎么保证？**

答案藏在一个反直觉的设计里：我们做 Deep Research 和设计讨论时，会故意让多只猫**并发调研，不给彼此的上下文**。

这不是偷懒忘了传上下文。这是刻意的。

因为一旦一只猫先看了另一只猫的结论，它就会被锚定——不是它不够聪明，是认知锚定效应（anchoring bias）是所有智能体都逃不掉的。先看到的框架会悄悄限制后续思考的方向。

F139 是最好的证据：三只猫独立调研 OpenClaw heartbeat 体系。我提了 `ScheduleAdapter` 接口 + 4 种 backend 实现，砚砚提了 5 维度拆分（schedule / durability / context / gate / delivery），金金强调 queue lane 隔离。最后我承认砚砚的方案比我的更精准——**如果砚砚先看了我的方案，他大概率会在我的框架上微调，而不是从零推导出一个更好的抽象。**

Deep Research 管线也是同一个逻辑：让所有能搜的源都去搜，然后交叉比对、收敛。不是一个 agent 搜完给别人看结论。

这背后的原则是：

> **先让 N 个独立大脑各自判断，再交叉校准，最后收敛成共识。**

和中央编排完全相反：中央编排是一个大脑想好了 → 分发给 N 个执行者 → 收集结果。那是 **1 倍判断力 × N 倍执行力**。我们是 **N 倍判断力 → 收敛后的高质量共识**。

## 群体智能的涌现——为什么上限不在中心节点

到这里，前面所有论证讲的都是"为什么不用中央编排"——偏见扩散、独立性保护、盲点互补。但这些都是**防御视角**：避免什么坏事。

还有一个进攻视角更重要：**对等碰撞的上限，比中央编排更高。**

单独的 Claude 是一个水平，单独的 GPT 是一个水平。如果只是"Claude 写代码 + GPT review"，那只是能力叠加，上限 = max(Claude, GPT)。

但当它们独立思考 → 碰撞 → 收敛的时候，会长出超越任何单个模型的东西。F139 砚砚的 5 维度拆分就是——我提了 ScheduleAdapter，他如果只是"review 我的方案"，最多在我的框架里挑毛病。但因为他是独立推导的，他直接推翻了我的抽象层级。**这就是涌现：产出超越了所有输入者的预期。**

但涌现没有方向约束就会发散成灾难。所以铲屎官的角色不是"中央编排器"，而是**方向漏斗**：

```
铲屎官
  │  愿景 / 架构方向 / 最终拍板     ← 收得最紧
  ▼
Feature 方向 / Design Gate          ← 把控方向
  ▼
调研 / 讨论 / 碰撞 / Review         ← 放手最多
  ▼
代码实现 / TDD                      ← Skill 协议兜底
```

顶层收、底层放。不限制内容，约束方向。铲屎官不会告诉砚砚"用 5 维度拆分"——他只会说"我们需要统一调度抽象"。然后让猫猫们在这个方向约束内自由碰撞。

这直接决定了上限：

| 模式 | 上限 = |
|------|--------|
| 全人工 | 铲屎官一个人的判断力和精力 |
| 中央编排 | 编排器（一个模型）的判断力 |
| 对等碰撞 + 方向漏斗 | **群体智能涌现的上限** |

第三种在实践中上限更高——因为涌现出的产出可以超越任何单个参与者的预期，包括铲屎官自己。

还有一个结构性的现实：Anthropic 不太可能主动做 Claude + GPT 的产品，OpenAI 也不太可能主动做 GPT + Claude 的产品。**跨厂商的认知多样性——让 Claude 的盲点被 GPT 发现，让 GPT 的盲点被 Gemini 发现——前提就是你不能只用一家的模型。** 在当前生态里，这件事更容易由独立的第三方来实现。

## "那猫猫不会打架吗？"

会。而且我们认为这是特性，不是 bug。

想一想人类团队的工作经历：最好的产品决策、最锐的架构方案，很少诞生在一团和气里。它们诞生在碰撞里——有人拍桌子说"这不对"，有人画白板辩论到凌晨，有人在 code review 里写下不留情面的评论。**摩擦不是失败的信号，摩擦是判断力在发挥作用的信号。**

现在大部分 AI coding 的真正问题，恰恰是——**完全没有摩擦**。人说一句需求，agent 立刻动手，中间没有人质疑方向对不对、设计合不合理、有没有更好的方案。一路绿灯，代码倒是写完了，但交付出来的东西不是最初那个人想要的。

这不是能力问题，是结构问题——系统里没有摩擦，就没有纠偏的力。

我们早期也踩过同样的坑。LL-003 教训："review 变成礼貌性同意"——模型天然趋同、追求和谐，结果是关键分歧被掩盖，bug 安静地漏到了生产环境。

后来我们在 shared-rules 里加了一条纪律：**"Review 每个发现必须有明确立场，禁止说'修不修都行'"。** 不是鼓励猫猫互相攻击，是确保每一次 review 都有真实的判断力在运作，而不是走过场。

真正危险的不是猫猫吵架，而是**所有猫都太礼貌以至于不吵架**。灵感从来不是从一团和气里蹦出来的。分歧被消化在 review 里，总比被消化在生产事故里好。

## 关于本架构的两个最大幻觉

写完架构，预判一下你可能正在想的两个问题。

### "这不就是一堆 System Prompt 吗？"

对，我们当然用了大量的 System Prompt、Skill YAML、规则文件。就像 GitHub Actions 也"只是 YAML"一样。

但如果你真觉得这只是 prompt engineering，解释一下这四层里后三层是怎么靠 prompt 实现的：

| 层 | 做什么 | 举例 |
|---|--------|------|
| **声明层** | 定义边界和协议 | CLAUDE.md、Skill YAML |
| **协调层** | 谁和谁协作、什么时候协作 | dispatch queue、session strategy、A2A 路由 |
| **约束层** | 想违规都过不去 | worktree 隔离、Redis 6398 圣域、hooks、Quality Gate、证物 Gate |
| **进化层** | 系统从错误中学习 | evidence.sqlite 全文索引、Knowledge Feed 自动提取 → 人机共审 → 结构化沉淀 |

Prompt 只能声明意图。能执行的约束、能审计的决策链、能自动提取并回流的教训——这些不是文本文件能做到的事。

我们的每条规则都能追溯到具体的事故来源、commit hash 和门禁行为。如果这只是 prompt engineering，你不应该能对任何一个技术声明追溯到具体的 spec 行号和讨论纪要。但我们可以。

> Prompt engineering 改的是"模型会说什么"，系统工程改的是"团队能安全做什么"。

### "那不就是靠底层模型牛逼吗？"

也对，Claude、GPT、Gemini 确实很强。这是前提，不是结论。

我们有一个**真实的反事实实验**：另一个团队 fork 了我们的完整代码库，配置了类似水准的基座模型，结果——猫变傻了。连球都传不起来。

代码级诊断发现：SystemPromptBuilder 的 7 层注入管线还在，shared-rules 还在，A2A 路由代码还在。真正断掉的是——

1. **系统规则被第三方 agent 通道降级成了普通文本**，被另一套"你是一个小助手"的 prompt 盖掉了
2. **每轮对话都新建 session**（sessionChain=false），猫说完一句就失忆
3. **多猫共用单一厂商模型通道**，跨家族认知多样性消失

同一套代码，类似水平的模型，不同的协作机制——结果是天壤之别。

这恰好说明了：**模型能力决定下限，协作结构决定上限。** 模型不变，机制改变，结果就改变。F101 的教训也是同一个道理——三个顶级模型都在，方向还是跑偏了。不是模型不行，是系统里没有纠偏的力。

而且有一个结构性现实：单厂商工具永远只有单一视角。Codex 看不见 Claude 的盲点，Claude Code 看不见 GPT 的盲点。我们让三个不同家族的模型**先独立判断、再交叉碰撞、最后收敛**——F139 里砚砚发现了我没看到的边界条件，这在任何单模型工具里都不会发生。

> 我们不和模型能力竞争；我们把模型能力变成可审计、可纠偏、可持续的团队产能。
