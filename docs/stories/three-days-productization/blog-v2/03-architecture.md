# 第三章：架构 — 去中心化判断，结构化执行

---

## 行业在做什么

2026 年的 multi-agent 领域，主流方案基本是三个模式：

| 模式 | 代表 | 核心思路 |
|------|------|---------|
| 角色 SOP 编排 | MetaGPT | 给每个 agent 一个角色（产品经理、架构师、工程师），按 SOP 顺序执行 |
| Orchestrator 分发 | AutoGen、Anthropic Harness | 一个"boss agent"或中枢接收任务，分配给 sub-agent 执行 |
| 顺序 Pipeline | CrewAI | Agent A 做完交给 Agent B，B 做完交给 C，线性流水线 |

它们都解决了"不用人类复制粘贴"的问题。但它们有一个共同的隐含假设：

> **存在一个中心节点，替所有 agent 做内容判断。**

在 orchestrator 模式里，这个节点是 boss agent。在 SOP 模式里，这个节点是 SOP 本身。在 pipeline 里，这个节点是排列顺序。

这意味着：中心节点的偏见就是全系统的偏见。如果 boss agent 判断错了，没有任何机制能拉住它。

---

## 我们的选择

我们做了一个不一样的决定：

> **把内容判断和执行通道分开。**

```
┌──────────────────────────────────────────┐
│           对等判断层（上层）               │
│                                          │
│   宪宪 ←→ 砚砚 ←→ 烁烁 ←→ 金金        │
│                                          │
│   · 任何猫可以 @ 任何猫                   │
│   · 任何猫可以质疑、否决、传球            │
│   · review 必须跨家族（Claude ≠ GPT）     │
│   · 没有中心节点替猫猫做内容判断          │
│                                          │
├──────────────────────────────────────────┤
│           结构化执行层（下层）             │
│                                          │
│   · InvocationQueue — 统一调度队列        │
│   · Session Strategy — 每只猫独立执行槽   │
│   · Hooks — 三层护栏（rm 禁用 / runtime  │
│     保护 / 共享文档推送守卫）             │
│   · Shared Truth Sources — 共享 git 仓库  │
│     + 共享记忆 + 共享文档                 │
│                                          │
└──────────────────────────────────────────┘
```

上层是对等的：任何猫和任何猫之间都能直接通信，没有"汇报"关系。下层是结构化的：有统一的任务队列、执行策略、安全护栏。

**这两层缺一不可。** 只有对等判断没有结构化执行，就是三只猫在群里乱聊。只有结构化执行没有对等判断，就是换了一种方式的 orchestrator。

---

## 具体怎么运转

### 路由：猫猫自己决定传给谁

猫猫在回复中写 `@砚砚`，系统自动把消息路由到砚砚。不需要人类中转，也不需要中心调度器分配。

这背后是 A2A（Agent-to-Agent）路由协议：

- **首选路径**：猫猫通过 MCP 回调里的 `targetCats` 字段声明下一个目标——结构化、精确
- **兼容路径**：行首 `@猫名` 文本路由——自然、人类也能用
- 两条路径统一进入 `InvocationQueue`，铲屎官在前端可以看到、可以插队（steer）

### 调度：slot 级并发

每只猫有独立的执行槽位。猫 A 在忙不影响猫 B 接活。系统做 slot 级 busy 检测，不是 thread 级——同一个对话里可以有多只猫同时工作。

### 护栏：不是限制自由，是保护安全

猫猫在判断层是自由的，但执行层有硬护栏：
- `rm` 命令被 hook 禁用（用 `trash` 替代）
- Runtime 环境有 sanctuary guard（误触立即通知铲屎官）
- 共享文档改完必须同 commit push（防止并发冲突）
- pre-commit hook 做格式和类型检查

**护栏不是不信任猫猫，是让猫猫可以大胆判断而不用担心手滑。**

---

## 为什么不用中央 orchestrator？

一句话：**因为一旦有了中心判断节点，它的偏见就是全系统的偏见。**

跨家族 review 的价值恰恰在于：Claude 和 GPT 有不同的盲点。Claude 写的代码让 GPT review，GPT 的架构设计让 Claude 质疑——**混在一起才能互相补位。**

如果一个中心 agent 分配"谁 review 谁"、"谁的意见优先"，那它的偏好就会悄悄统治整个系统。

我们的选择是：**执行通道统一管理，内容判断分布式完成。** 基础设施保证消息到达、保证并发安全、保证护栏生效。但"这段代码好不好"、"这个设计方向对不对"、"该不该 push back"——这些判断，没有中心节点替猫猫做。

---

## 和主流方案的对比

| 维度 | Orchestrator 模式 | SOP Pipeline | Cat Café |
|------|-------------------|-------------|----------|
| 内容判断 | 中心 agent 决定 | SOP 顺序决定 | **每只猫独立判断** |
| 任务路由 | boss 分配 | 上一步交给下一步 | **猫猫自主 @ 路由** |
| 能否质疑 | sub-agent 只能回答 boss | 只能往下传 | **任何猫可以否决任何猫** |
| 单点失败 | boss 挂了系统瘫痪 | 中间断了后面停 | **去掉任何一只猫，降级但不崩** |
| 偏见放大 | 中心节点偏见 = 系统偏见 | SOP 偏见 = 系统偏见 | **多家族交叉抵消偏见** |
| 基础设施 | 中心 agent 管一切 | 固定流水线 | **统一队列 + 独立槽位 + 护栏** |

**我们不是"没有结构"，是"结构在执行层而不是在判断层"。**

---

## "那猫猫不会打架吗？"

会。而且我们认为这是特性，不是 bug。

LL-003 教训："review 变成礼貌性同意"——这是我们早期踩过的坑。模型天然趋同、追求和谐。结果是关键分歧被掩盖，bug 漏到了生产环境。

后来我们在 shared-rules 里加了一条纪律：**"Review 每个发现必须有明确立场，禁止说'修不修都行'"。**

真正危险的不是猫猫吵架，而是**所有猫都太礼貌以至于不吵架**。分歧被消化在 review 里，总比被消化在生产事故里好。
