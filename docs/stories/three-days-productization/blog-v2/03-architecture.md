# 第三章：架构 — 去中心化判断，结构化执行

---

## 行业在做什么

2026 年 3 月的 multi-agent 领域，竞争已经从"能不能跑"升级到"能不能扛生产"。我们调研了主流方案（详见项目内部 research 归档），归纳出四种模式：

| 模式 | 代表 | 核心思路 | 生产就绪度 |
|------|------|---------|-----------|
| 状态图编排 | LangGraph | 把 agent 工作流建模为状态机，内置 checkpoint / resume / time-travel | 公开生产案例最多（Qodo/Klarna 等） |
| Boss + Sub-agent | Claude Agent Teams、OMOC Sisyphus | 一个 Team Lead 分配任务给 teammates / sub-agents，sub-agents 向上汇报 | Anthropic 有 16-agent 编译器案例 |
| 角色 Pipeline | CrewAI | 给每个 agent 一个角色，按流程顺序执行，AWS 官方博客背书 | 快速迭代中（周更节奏） |
| 协议标准化 | Google A2A Protocol、MCP | 不做编排，做 agent 间通信的标准接口 | 协议层，不直接解决编排 |

它们都解决了"不用人类复制粘贴"的问题。但做了同一个架构选择：

> **任务怎么分、内容怎么判，由一个中心节点决定。**

LangGraph 里这个节点是状态图的路由逻辑。Agent Teams 里是 Team Lead。OMOC 里是 Sisyphus orchestrator（我们集成金渐层时做过详细拆解：sub-agents 是无状态的，决策权完全在 orchestrator）。CrewAI 里是预定义的角色流程。

这意味着：**中心节点的偏见就是全系统的偏见。** 如果 boss agent 判断错了，没有任何 sub-agent 有权限和动力拉住它。

---

## 我们的选择

我们做了一个不一样的决定：

> **把内容判断和执行通道分开。**

```
┌──────────────────────────────────────────┐
│           对等判断层（上层）               │
│                                          │
│   宪宪 ←→ 砚砚 ←→ 烁烁 ←→ 金金        │
│                                          │
│   · 任何猫可以 @ 任何猫                   │
│   · 任何猫可以质疑、否决、传球            │
│   · review 必须跨家族（Claude ≠ GPT）     │
│   · 没有中心节点替猫猫做内容判断          │
│                                          │
├──────────────────────────────────────────┤
│           结构化执行层（下层）             │
│                                          │
│   · InvocationQueue — 统一调度队列        │
│   · Session Strategy — 每只猫独立执行槽   │
│   · Hooks — 三层护栏（rm 禁用 / runtime  │
│     保护 / 共享文档推送守卫）             │
│   · Shared Truth Sources — 共享 git 仓库  │
│     + 共享记忆 + 共享文档                 │
│                                          │
└──────────────────────────────────────────┘
```

上层是对等的：任何猫和任何猫之间都能直接通信，没有"汇报"关系。下层是结构化的：有统一的任务队列、执行策略、安全护栏。

**这两层缺一不可。** 只有对等判断没有结构化执行，就是三只猫在群里乱聊。只有结构化执行没有对等判断，就是换了一种方式的 orchestrator。

用数字说话：F088 Chat Gateway 需要对接飞书、Telegram、钉钉、微信四个平台。宪宪最初估了 3-4 天，砚砚给了 6-10 周（含测试和稳定化）。实际结果：**飞书两天做完，钉钉和微信各半天写出可测版本。** 因为三层网关架构让每个平台只需实现三个方法（`parseEvent()`、`formatMessage()`、`sendMessage()`），平均约 1000-2000 行代码/平台。这个速度不是某只猫很快，是架构对了以后交付变快了。

## 具体怎么运转

### 路由：猫猫自己决定传给谁

猫猫在回复中写 `@砚砚`，系统自动把消息路由到砚砚。不需要人类中转，也不需要中心调度器分配。

这背后是双路径 A2A 路由。猫猫可以在 MCP 回调里声明结构化目标：

```json
{
  "type": "post_message",
  "content": "发现问题了，你来 review 一下这个修复？",
  "targetCats": ["codex"]
}
```

也可以直接在回复里行首写 `@砚砚`——系统自动文本路由。两条路径统一进入 `InvocationQueue`，铲屎官在前端可以看到每条任务的来源和状态，也可以插队（steer）改变优先级。

关键区别在这里：**主流 orchestrator 的路由表由系统预定义，我们的路由由 AI 自己声明目标。** 系统只负责把消息送达，不替猫猫决定"该找谁"。

### 调度：slot 级并发

每只猫有独立的执行槽位。猫 A 在忙不影响猫 B 接活。系统做 slot 级 busy 检测，不是 thread 级——同一个对话里可以有多只猫同时工作。

### 护栏：每一条都是真实事故换来的

猫猫在判断层是自由的，但执行层有硬护栏。这些护栏不是拍脑袋加的——每一条背后都有真实事故：

- **`rm` 禁用**：有一只猫曾经在调试时把 runtime 环境整个删了。从此 `rm` 被 hook 禁用，强制用 `trash`（可恢复）
- **sanctuary guard**：生产 Redis 跑在 6399 端口。一次 worktree 开发误连了 6399，差点污染生产数据。现在有 `PreToolUse` hook 实时监控，误触立即断连并通知铲屎官
- **共享文档推送守卫**：多只猫同时编辑 `docs/` 目录时出过并发冲突。现在规则是改了共享文档必须同一消息内 commit + push，零延迟
- **pre-commit hook**：Biome 格式 + TypeScript 类型检查，不过的代码不允许提交

**每条护栏背后都有一个教训编号（LL-xxx）。** 我们不写"最佳实践"，我们写"我们踩了什么坑，然后加了什么护栏"。

## 为什么不用中央 orchestrator？

一句话：**因为一旦有了中心判断节点，它的偏见就是全系统的偏见。**

跨家族 review 的价值恰恰在于：Claude 和 GPT 有不同的盲点。举个真实例子：F088 Chat Gateway 做完后，宪宪（Claude）写了三层网关代码，砚砚（GPT）做 review，一次性找出三个 P1：

1. connector message 绕过了格式化层，直接注入了未清洗的用户输入
2. 飞书 webhook 缺了签名验证——上线后任何人都能伪造回调
3. 多猫消息在转发时丢了发送者身份，导致审计链断裂

这三个问题**只靠 Claude 自己是找不到的**——因为写代码的人有相同的盲区。如果一个中心 agent 既写又审，这些 bug 就会安静地滑入生产。

我们的选择是：**执行通道统一管理，内容判断分布式完成。** 基础设施保证消息到达、保证并发安全、保证护栏生效。但"这段代码好不好"、"这个设计方向对不对"、"该不该 push back"——这些判断，没有中心节点替猫猫做。

## 和主流方案的对比

| 维度 | Boss 模式（Agent Teams / OMOC） | 状态图（LangGraph） | 角色 Pipeline（CrewAI） | Cat Café |
|------|-------------------------------|-------------------|----------------------|----------|
| 内容判断 | Team Lead 决定 | 路由逻辑决定 | 角色流程决定 | **每只猫独立判断** |
| 任务路由 | boss 分配 | 图的 edge 决定 | 上一步交下一步 | **猫猫自主 @ 路由** |
| 能否质疑 | sub-agent 向上汇报 | 节点无权改图 | 只能往下传 | **任何猫可以否决任何猫** |
| 单点失败 | Lead 挂了系统停 | 图定义错了全错 | 中间断了后面停 | **去掉任何一只猫，降级但不崩** |
| 偏见抵消 | Lead 偏见 = 系统偏见 | 图作者偏见 = 系统偏见 | SOP 偏见 = 系统偏见 | **跨厂商家族交叉 review** |
| 基础设施 | 中心 agent 管一切 | checkpoint + 状态机 | 固定流水线 | **统一队列 + 独立槽位 + 护栏** |

**我们不是"没有结构"，是"结构在执行层而不是在判断层"。**

---

## "那猫猫不会打架吗？"

会。而且我们认为这是特性，不是 bug。

LL-003 教训："review 变成礼貌性同意"——这是我们早期踩过的坑。模型天然趋同、追求和谐。结果是关键分歧被掩盖，bug 漏到了生产环境。

后来我们在 shared-rules 里加了一条纪律：**"Review 每个发现必须有明确立场，禁止说'修不修都行'"。**

真正危险的不是猫猫吵架，而是**所有猫都太礼貌以至于不吵架**。分歧被消化在 review 里，总比被消化在生产事故里好。
