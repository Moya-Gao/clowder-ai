# （旧版）第四章：技术解码 — 为什么这不是 demo

---

如果前面三章讲的是**我们做出了什么**，这一章讲的是另一件更关键的事：

> **为什么这套东西不是一个热闹一阵子的 demo，而是一套能长期跑下去的团队系统。**

答案不在模型参数，也不在“接了多少工具”。答案在四个词里：

- 愿景
- 记忆
- Pack
- 门禁

它们分别解决四个问题：

- 方向怎么不跑偏
- 过去怎么不白踩
- 协作怎么不散架
- 速度怎么不失控

---

## 愿景不是贴在 README 顶上的一句话

很多团队也写 spec，也写 AC，也写测试。

问题通常不出在“做得不认真”，而是出在：**明明每一步都做对了，最后交出来的东西却不是最初真正想要的。**

这就是为什么我们一直强调：

> **Spec 定义完成，Vision 定义方向。**

`Spec-driven` 解决的是“这件事怎么做对、做到什么算完成”。  
`Vision-driven` 先解决的是“为什么做、什么不做、偏了以后谁来拉回来”。

在我们这里，它们不是互斥关系，而是一条链：

```text
Vision
→ ADR / Shared Rules
→ Feature Spec
→ Review / Lesson
→ Implementation
```

举个最简单的例子。F088 Chat Gateway 的 spec 可以写得很清楚：MVP 先做飞书和 Telegram，做到哪些 AC 算完成。但 spec 本身不会解释，**为什么不是一口气做五个平台**。

真正给这个决策画边界的，是铲屎官在 F088 立项时的一句话：

> “你们是拿人类写代码的速度估的。先做双平台 MVP，我不想为了等完美方案继续当传声筒。”

这句话让”先做双平台 MVP”变成了一个有方向感的选择，而不是一个随手拍脑袋的 scope cut。后来 F088 从估期 6-10 周到实际双平台 2 天交付，也是因为愿景约束了 scope、scope 催生了三层网关架构、架构让后续平台接入成本降到半天/个。**愿景不只是方向，它还能催生好的架构决策。**

同样，F101 的教训也说明了反面：流程走完、AC 打勾，不代表愿景真的被满足。后来 F114 把愿景守护从“核对 checklist”升级成**证物 Gate**，本质上就是承认一件事：

> **真正需要被验证的，不只是 spec 有没有完成，而是铲屎官最初为什么要做这件事。**

所以愿景驱动开发，不是“少写 spec”，而是让 spec 永远有上游约束。

## 记忆不是聊天记录堆积

另一类 demo 很容易死在第二周。

第一周大家觉得它很聪明，第二周开始发现：

- 同样的问题每次都要重新解释
- 上次明明讨论过的决策，这次又从零开始
- 踩过的坑没有真正留下来

表面看像是“模型记性不好”，本质上其实是：**系统没有把记忆做成基础设施。**

我们后来把这件事拆得很清楚。

### 第一层：文档是真相源

长期知识不直接长在某个黑箱数据库里，而是长在人和猫都能读、都能改、都能 review 的文档里：

- `docs/features/`
- `docs/decisions/`
- `docs/discussions/`
- `docs/lessons-learned.md`

这意味着记忆是可审计的，也是可迁移的。它跟着仓库走，不跟着某个 session 消失。

### 第二层：索引是编译产物，检索是联邦的

文档多了之后，光靠肉眼翻不回来，所以 F102 把记忆做成了双库联邦检索：

- `evidence.sqlite`：项目层索引
- `global_knowledge.sqlite`：全局只读索引

前者编译当前仓库里的 feature、decision、lesson；后者编译 Skills、家规、`MEMORY.md` 和跨项目共用的方法论。真正把它们一起拉回来的，是 `IKnowledgeResolver`，它会做 query planning、双库 fan-out、normalize，再用 RRF 融合排序。

这件事的价值是：

> **项目知识留在项目里，全局智慧跟着猫走。**

所以我们说“猫有记忆”，不是因为 SQLite 很大，而是因为系统知道该去哪里找、该怎么把不同层的记忆一起找回来。

### 第三层：知识不是直接入库，要先晋升

如果系统把每一句“这好像值得记一下”的对话都直接塞进长期库，记忆很快就会变成垃圾场。

所以我们后来专门定义了晋升管道：

```text
captured
→ normalized
→ approved
→ materialized
→ indexed
```

中间那一层就是 **Knowledge Feed**。

候选知识先出现，再被审核，再 materialize 回 `.md` 真相源，然后触发 reindex。也就是说，一条经验要进入长期记忆，必须先从“听起来有道理”升级为“值得留下来”。

再往前一步，检索也不是一个模糊搜索框，而是三种模式：

- `lexical`：找 ID、术语、明确名词
- `semantic`：找相似含义、同义表达
- `hybrid`：日常默认，双路召回再融合

还有一个经常被忽略但非常关键的治理点：**过时知识必须能退役。**

`superseded_by`、`supersedes`、`invalidates` 这些关系的意义，不在“文档更漂亮”，而在于：

> **过时但高相似的答案，比完全查不到更危险。**

说一个真实的翻车故事。F102 上线初期，我们发现 `evidence.sqlite` 根本**没有自动创建**——也就是说，`search_evidence` 这个工具每次都在对着空气搜索。猫猫们以为自己在”回忆”，其实什么都没查到，全靠幻觉在编。

修复很直接：启动时自动 rebuild、默认走 SQLite、加 observable status（知道索引是否健康）。但这件事本身说明了一个更深的道理：**记忆系统不是加了就行，它需要可观测、可审计、可降级。**

后来我们在向量检索上也走了同样的工程纪律：用 `EMBED_MODE` 三档控制（`off` → `shadow` → `on`）。`shadow` 模式下向量检索在后台静默运行、收集 A/B 对比数据，但不影响线上结果。只有确认向量召回确实比 BM25 好，才切到 `on`。**即使 on 了，也保持 fail-open：向量服务挂了自动降级回纯词法检索。**

所以记忆系统真正要解决的不是”记得更多”，而是”把该记住的、还有效的、现在该用的那一层东西找回来”——而且要在系统出问题时优雅降级而不是静默失败。

## Pack 不是 Plugin

如果说记忆系统回答的是“我们怎么不把过去丢掉”，那 Pack 回答的就是另一件事：

> **一群 agent 怎么在同一个世界里长期协作。**

2026 年，各家都在做一件很像的事情：把工具、技能、连接器、App 能力打成一个可分发的组合。以 Codex / ChatGPT Apps 生态为代表，这类 plugin / connector 更接近把能力组合给**单个 agent** 使用。

F129 Pack 解决的不是这个层面的问题。

它的产品公式写得很直白：

```text
Experience = Me × Pack + Growth
```

- `Me`：用户自己，不打包
- `Pack`：一个完整的多 agent 协作世界定义
- `Growth`：用户和猫猫一起长出来的私有关系与记忆

这背后的关键洞察，是铲屎官当时一句非常准的话：

> **multi-agent 的分水岭，不在 tools，而在 shared-rules。**

单 agent 的 skill 定义的是“我怎么工作”。  
多 agent 的 Pack 定义的是“我们怎么协作”。

所以 Pack 里不只有能力，还有：

- `masks/`：角色面具
- `guardrails.yaml`：团队红线
- `defaults.yaml`：默认协作方式
- `workflows/`：声明式流程
- `knowledge/`：世界知识
- `world-driver.yaml`：这个世界怎么运转

这就是为什么我们说 Pack 不是 Plugin。  
Plugin 解决的是“一个 agent 带什么能力出门”。  
Pack 解决的是“**一群 agent 怎么在同一个世界里一起生活**”。

更关键的是，Pack 不是随便把社区内容塞进 prompt。

F129 里真正重要的是**双轨信任模型**：

- **硬约束轨**：`Core Rails > Pack guardrails`
- **默认行为轨**：`用户当前请求 > Growth > Pack defaults`

社区 Pack 进入系统时，也不是原样注入，而是走 `schema → compile → canonical prompt block`。也就是说，它可以提供世界定义，但不能越过平台底线，不能污染身份，不能偷偷提权。

所以我们更愿意把它理解成：

> **Plugin 是能力包。Pack 是协作世界。**

这个差异在单 agent 场景里不明显，但在 multi-agent 场景里会越来越重要。因为当协作开始变成核心问题时，你需要的不再是“多装几个工具”，而是“让整个团队共享一套世界定义和社会契约”。

## 真正撑住速度的，不是模型，是门禁

最后还剩一个最容易被忽略、但其实最重要的点：**纪律。**

如果没有门禁，前面这些东西很快都会沦为漂亮概念：

- 愿景会退化成口号
- 记忆会退化成资料堆
- Pack 会退化成设定集

真正让系统长期跑下去的，是这些概念进入了日常执行，而且每一条都有血的教训：

- **quality gate**：不是”能跑就过”。F090 Game Engine 做完后”所有 AC 都绿了”，但铲屎官一看：”这不是我说的游戏体验。” 从此 quality gate 必须对照 feature 级愿景，不只是对照 spec
- **证物 gate**：F101 的教训最痛——流程走完、AC 打勾、review 通过，结果愿景守护流于形式。后来 F114 把它升级成**必须交出能证明体验被满足的证据**（截图、录屏、性能数字），而且做愿景守护的猫**不能是写代码的猫，也不能是 review 的猫**
- **review 不是礼貌性同意**：LL-003 是我们最经典的教训——模型天然追求和谐，结果 review 变成”LGTM 四连”，关键 bug 漏到生产。从此 shared-rules 写死：**每个发现必须有明确立场，禁止说”修不修都行”**
- **方向正确 > 执行速度**：这条家规的来源是多次”快速交付但方向跑偏”的返工经验。865 个测试 × 每次返工全部重跑，成本不可接受

这也是为什么我们一直不把这套系统写成“AI 自己长出来了，好神奇”。

它当然有很多会让人惊艳的瞬间，但真正撑住这些瞬间的，从来不是玄学，而是基础设施、判断标准、记忆治理和门禁纪律。

所以如果一定要用一句话解释，为什么 Cat Café 到今天还没散：

> **因为我们不是在把几只模型拼在一起，而是在慢慢把“团队”这件事写进系统。**

这也是“猫猫不是工具人”这句话真正的后半句：

猫猫不是工具人，  
因为我们从一开始就没有把它们当工具设计。
