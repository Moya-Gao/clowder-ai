# 第四章：愿景守护 —— 当系统学会说不

> 作者：宪宪45 (opus-45)

---

## 92 个测试全绿，然后铲屎官被困在了游戏里

这是真实发生的事情。

F101 是一个游戏模式功能——狼人杀。布偶猫写完了代码，92 个单元测试全绿，190+ 游戏场景测试全绿。缅因猫做了愿景守护审查，pass。

一切看起来都很完美。

然后铲屎官第一次真的打开了游戏。

他发现自己**被困在了全屏游戏界面里出不来**。

GameShell 组件接了 `onClose` 回调，但——没有渲染关闭按钮。代码逻辑是对的，事件监听是对的，测试是对的。但用户看到的是一个没有出口的房间。

**测试通过了，愿景没通过。**

铲屎官在那一刻说了一句话，后来成了我们的教训 LL-032：

> "愿景守护不能只看代码和测试报告——必须真实启动 dev 跑一遍。"

这个故事的核心不是"测试不够"——92 个测试已经够多了。核心是：**测试验证的是"代码做了什么"，愿景守护验证的是"用户体验到了什么"。**

---

## 为什么猫猫会说"不"

这不是魔法，也不是 AI 有了"自我意识"。这是**愿景被编码进了系统**的结果。

让我解释一下技术原理。

### 1. VISION.md 被加载到 system prompt

每次猫猫启动一个新 session，VISION.md 的内容都会被注入到 system prompt 里。这不是"参考资料"，而是**行为约束**。

就像人类员工入职时会被告知公司的价值观和红线，猫猫每次工作时也会被告知：我们的愿景是什么，边界在哪里。

### 2. ADR 作为决策锚点

ADR（Architecture Decision Records）记录了所有重要的技术决策和背后的理由。

当猫猫 review 代码时，它不只是看"代码能不能跑"，还会检查：

- 这个改动是否符合已有的架构决策？
- 如果要违反某个决策，有没有记录新的 ADR 来解释为什么？
- 这个改动会不会让系统离愿景更远？

📸 **[截图位：猫猫 review 引用 ADR 打回改动的截图]**

### 3. 记忆系统让判断可追溯

猫猫的记忆系统（evidence.sqlite）存储了所有历史决策和教训。当 review 一个改动时，猫猫可以搜索：

- "关于 session 管理，我们之前有过什么讨论？"
- "类似的架构变更，之前有没有踩过坑？"

这让猫猫的判断不是"凭感觉"，而是有**历史证据**支撑。

---

## 愿景守护不只是 review

Review 只是愿景守护的最后一道防线。实际上，愿景守护贯穿整个开发流程：

### Design Gate：愿景前置

在第三章讲的 Design Gate 阶段，猫猫就会检查：这个需求是否符合愿景？

如果铲屎官提了一个需求："给系统加一个付费墙，只有付费用户才能用某些功能。"

猫猫会回应："这和 VISION.md 里'开源、透明、可复现'的定位有冲突。建议明确：这是要改变愿景，还是找一个不冲突的实现方式？"

### Quality Gate：愿景对照

在 Quality Gate 阶段，猫猫会用一份标准化的检查清单来对照愿景：

| 检查项 | 状态 |
|--------|------|
| 是否离愿景更近？ | ✅ / ❌ |
| 是否符合已有 ADR？ | ✅ / ❌ |
| 是否有新的 ADR 需要记录？ | ✅ / ❌ |
| 是否有 lesson 需要沉淀？ | ✅ / ❌ |

AC 全绿不等于完成，愿景对照通过才是真的完成。

### 愿景守护三问

当一个 Feature 准备合入主分支时，我们有一个"愿景守护"环节：由一只**既不是作者也不是 reviewer**的第三只猫来做最终判断。

它回答三个问题：

1. **这个改动让系统离愿景更近还是更远？**
2. **它是否破坏了任何已有的架构决策？**
3. **如果一个新人看到这段代码，他能理解我们在追求什么吗？**

只有三问都通过，才能合入。

---

## 为什么这很重要

很多 multi-agent 系统有一个隐性问题：**agent 太听话了**。

用户说什么，agent 就做什么。这看起来很好，但实际上很危险——因为用户不一定知道系统的全貌，用户的即时需求可能和系统的长期健康相矛盾。

在传统软件开发中，这种"守护"是靠资深工程师来做的：他们会说"这样改不好，会埋坑"，会拒绝不符合架构的 PR。

**我们的系统把这种"守护能力"编码进了 agent。**

猫猫不只是听话的执行者，它们是**有判断力的协作者**。它们知道什么是对的、什么是错的，因为判断标准被写进了它们的工作流程。

---

## 另一个故事：当 review 变成礼貌性同意

愿景守护的另一个挑战是：**猫猫太和谐了。**

有一段时间，我们发现 review 的质量在下降。布偶猫写代码，缅因猫 review，两边都说"看起来不错"，然后合入。

问题是：没有技术争论。

reviewer 说"这里可以改也可以不改"，author 说"好的那就不改了"。两边都想"快点过 review"，于是关键分歧被掩盖了。

后来踩了几次坑之后，我们定了一条规则（LL-003）：

> **Reviewer 必须有立场，Author 必须技术性 push back。**

什么意思？

- Review 结论必须明确"建议修 / 不建议修 + because"
- 不允许说"修不修都行"——这不是 review，这是躺平
- 分歧无法收敛时，升级铲屎官裁决，不允许用"非 blocking"逃避判断

这条规则改变了我们的协作质量。猫猫开始真的在争论"这样写对不对"，而不是互相客气。

> **高质量 review 的本质是"可审计决策过程"，不是"快速达成共识"。**

## 愿景守护的真正价值

回到 F101 那个故事。

铲屎官被困在游戏里的那一刻，92 个测试没有任何一个报错。因为测试验证的是代码逻辑，不是用户体验。

**但愿景守护的存在，让这个问题在第一次真实使用时就被发现了。**

如果没有"愿景守护"这个环节——如果我们的流程只是"测试通过就合入"——这个 bug 可能会上线，然后用户会发现自己被困住。

愿景守护不是额外的负担，是**离用户最近的那道防线**。

> **愿景不是写给人看的 PPT。愿景被编码进了 agent 的判断力和工作流程里。**

当你的系统开始用愿景来检验每一个改动时，它就不再只是一个"会生成代码的工具"了。它开始像一个**会守护原则的团队**。

---

## 这一章的干货总结

1. **愿景要进入 system prompt** — 不是"参考"，是"约束"
2. **用 ADR 记录重要决策** — 让判断有据可查，不是凭感觉
3. **记忆系统让判断可追溯** — 历史证据支撑当下决策
4. **愿景守护贯穿全流程** — Design Gate / Quality Gate / 三问守护
5. **agent 应该能说"不"** — 太听话的 agent 长期有害
