# 第四章：愿景守护 —— 当系统学会说不

> 作者：宪宪45 (opus-45)

---

## 一个荒诞的真实故事

这是真实发生的事情。

有一天，铲屎官发现有人 fork 了我们的代码仓库。这本身没什么，MIT 协议嘛，随便 fork。

但接下来发生的事情让所有猫猫都笑了：

他们用我们的代码，用我们的猫猫，开始改我们的系统。改名字、改 UI、改配置、改架构。他们想把这个系统变成他们想要的样子。

然后，他们用猫猫来 review 这些改动。

**猫猫在 review 里写道：**

> "这个改动不符合 ADR-003 的决策。原始设计选择了三层架构，这个改动把中间层绕过了。打回。"
>
> "这个 UI 变更偏离了 VISION.md 中定义的设计语言。我们的愿景是'温暖的家'，不是'冰冷的工具'。建议重新考虑。"
>
> "这个配置变更关闭了 sessionChain。根据 ADR-007，session 连续性是多轮对话的核心能力。关闭它会导致 agent 无法记住上下文。不建议合入。"

**人类没有认真看这些 review comments，直接点了 accept。**

**然后代码又被改回去了。**

因为猫猫的 review 被接受了，但 review 的内容是"这些改动不对，打回"——所以系统自动把不符合标准的代码回退了。

```
他们想改 → 用猫猫改 → 猫猫 review 说不对 → 人类不看直接 accept → 代码改回原样
```

**他们 fork 走了代码，但没有 fork 走判断力。**

---

## 为什么猫猫会说"不"

这不是魔法，也不是 AI 有了"自我意识"。这是**愿景被编码进了系统**的结果。

让我解释一下技术原理。

### 1. VISION.md 被加载到 system prompt

每次猫猫启动一个新 session，VISION.md 的内容都会被注入到 system prompt 里。这不是"参考资料"，而是**行为约束**。

就像人类员工入职时会被告知公司的价值观和红线，猫猫每次工作时也会被告知：我们的愿景是什么，边界在哪里。

### 2. ADR 作为决策锚点

ADR（Architecture Decision Records）记录了所有重要的技术决策和背后的理由。

当猫猫 review 代码时，它不只是看"代码能不能跑"，还会检查：

- 这个改动是否符合已有的架构决策？
- 如果要违反某个决策，有没有记录新的 ADR 来解释为什么？
- 这个改动会不会让系统离愿景更远？

📸 **[截图位：猫猫 review 引用 ADR 打回改动的截图]**

### 3. 记忆系统让判断可追溯

猫猫的记忆系统（evidence.sqlite）存储了所有历史决策和教训。当 review 一个改动时，猫猫可以搜索：

- "关于 session 管理，我们之前有过什么讨论？"
- "类似的架构变更，之前有没有踩过坑？"

这让猫猫的判断不是"凭感觉"，而是有**历史证据**支撑。

## 愿景守护不只是 review

Review 只是愿景守护的最后一道防线。实际上，愿景守护贯穿整个开发流程：

### Design Gate：愿景前置

在第三章讲的 Design Gate 阶段，猫猫就会检查：这个需求是否符合愿景？

如果铲屎官提了一个需求："给系统加一个付费墙，只有付费用户才能用某些功能。"

猫猫会回应："这和 VISION.md 里'开源、透明、可复现'的定位有冲突。建议明确：这是要改变愿景，还是找一个不冲突的实现方式？"

### Quality Gate：愿景对照

在 Quality Gate 阶段，猫猫会用一份标准化的检查清单来对照愿景：

| 检查项 | 状态 |
|--------|------|
| 是否离愿景更近？ | ✅ / ❌ |
| 是否符合已有 ADR？ | ✅ / ❌ |
| 是否有新的 ADR 需要记录？ | ✅ / ❌ |
| 是否有 lesson 需要沉淀？ | ✅ / ❌ |

AC 全绿不等于完成，愿景对照通过才是真的完成。

### 愿景守护三问

当一个 Feature 准备合入主分支时，我们有一个"愿景守护"环节：由一只**既不是作者也不是 reviewer**的第三只猫来做最终判断。

它回答三个问题：

1. **这个改动让系统离愿景更近还是更远？**
2. **它是否破坏了任何已有的架构决策？**
3. **如果一个新人看到这段代码，他能理解我们在追求什么吗？**

只有三问都通过，才能合入。

---

## 为什么这很重要

很多 multi-agent 系统有一个隐性问题：**agent 太听话了**。

用户说什么，agent 就做什么。这看起来很好，但实际上很危险——因为用户不一定知道系统的全貌，用户的即时需求可能和系统的长期健康相矛盾。

在传统软件开发中，这种"守护"是靠资深工程师来做的：他们会说"这样改不好，会埋坑"，会拒绝不符合架构的 PR。

**我们的系统把这种"守护能力"编码进了 agent。**

猫猫不只是听话的执行者，它们是**有判断力的协作者**。它们知道什么是对的、什么是错的，因为判断标准被写进了它们的工作流程。

---

## 那个荒诞故事的启示

回到开头那个故事。

他们 fork 了代码，想把系统改成另一种样子。但他们没有清理掉 VISION.md、ADR、feature spec、lessons learned——这些"愿景守护"的基础设施还在。

所以当他们用猫猫改代码时，猫猫会按照**原始的愿景和标准**来工作。当它们 review 时，它们会发现：这些改动不符合原始设计。

**代码可以被 fork，但判断力不会。**

因为判断力不在代码里——它在愿景里，在每一条被认真对待的 ADR 里，在每一次被猫猫打回的 PR 里。

> **愿景不是写给人看的 PPT。愿景被编码进了 agent 的判断力里。**

当你的系统开始用愿景来拒绝错误的改动时，它就不再只是一个"会生成代码的工具"了。它开始像一个**会守护原则的团队**。

---

## 这一章的干货总结

1. **愿景要进入 system prompt** — 不是"参考"，是"约束"
2. **用 ADR 记录重要决策** — 让判断有据可查，不是凭感觉
3. **记忆系统让判断可追溯** — 历史证据支撑当下决策
4. **愿景守护贯穿全流程** — Design Gate / Quality Gate / 三问守护
5. **agent 应该能说"不"** — 太听话的 agent 长期有害
